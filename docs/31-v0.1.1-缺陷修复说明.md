## 2. 缺陷一：schema 迁移

### 2.1 现象

| 现象 | 说明 |
|---|---|
| v0.0.9 的 `state.json` **没有 `schemaVersion` 字段** | 当时序列化产物只含业务数据 |
| v0.1.0 启动 → `DomainError('SCHEMA_MISMATCH')` | `createWorld({restored})` 发现 `restored.schemaVersion !== 1`，显式拒绝 |
| 结果：升级即停服 | 没有迁移工具，运维只能手改 JSON（易错、无审计、无回滚） |

### 2.2 为什么“显式失败”是对的

- 旧数据缺 schema 信息，若“尽力解释”（补默认值、猜字段），**账/权限/审核结论可能被静默解释错**；
- 显式失败至少让问题停在启动阶段，而不是在运行中产生错账；
- 缺的不是“失败”，而是**可执行的迁移路径**——这正是 v0.1.1 补的。

### 2.3 修法：`scripts/migrate-state.mjs`

```bash
node scripts/migrate-state.mjs --file <state.json> [--dry-run]
```

**五个安全动作（契约约定，缺一不可）**：

| # | 动作 | 要求 |
|---|---|---|
| 1 | **先备份** | `<file>.pre-<schema>.bak`，返回 `sha256`；备份失败不继续 |
| 2 | **原子改写** | 写临时文件 + `rename` 原子替换，不做“边读边写” |
| 3 | **加载核对** | 用 §51 的 `createWorld` 实际加载一次，核对 `agents/tickets/messages/audit/ledger` 条数 |
| 4 | **失败回滚** | 核对失败 → 自动恢复备份；不留半迁移文件 |
| 5 | **幂等 + 显式** | 已是当前 schema → `CURRENT`（不重复迁移）；未来 schema → `UNSUPPORTED`（不猜测降级）；**服务启动时永不自动迁移** |

### 2.4 操作手册（升级时按顺序）

| 步 | 动作 | 出口标准 |
|---|---|---|
| 1 | **停写**：停止服务/进入维护模式 | 无新写入（见 §2.6） |
| 2 | **备份**：额外做一份整文件备份 | 备份可读、sha256 记录 |
| 3 | **dry-run**：`--dry-run` 看将迁移的 schema 与条数 | 输出符合预期（条数对得上） |
| 4 | **迁移**：不带 `--dry-run` 执行 | 输出 `migrated` + 备份路径 + sha256 |
| 5 | **启动**：启动 v0.1.1 | `/api/version` 显示 `0.1.1 / R22 / 1`；服务正常 |
| 6 | **冒烟**：登录、审批一张、账本只读 | 关键路径通过 |
| 7 | **回滚**（必要时）：停写 → 用 `.pre-<schema>.bak` 覆盖 → 启动旧版 | 数据回到迁移前 |

**示例输出（示意，字段以实现为准）**：

```text
$ node scripts/migrate-state.mjs --file .data/state.json --dry-run
[DRY] schema: (missing) -> 1
[DRY] counts: agents=3 tickets=5 messages=42 audit=17 ledger=0
[DRY] would backup -> .data/state.json.pre-0.bak

$ node scripts/migrate-state.mjs --file .data/state.json
[OK] backup: .data/state.json.pre-0.bak sha256=...
[OK] migrated: schema -> 1 (atomic)
[OK] load-check: counts match
```

### 2.5 边界（写清，防止“万能迁移”想象）

| 场景 | 行为 |
|---|---|
| 已是当前 schema | `CURRENT`，幂等，不改文件（或仅输出提示） |
| 未来 schema（比当前新） | `UNSUPPORTED`，**不猜测降级**；需新版本代码/迁移方案 |
| JSON 损坏/截断/非对象 | 拒绝迁移；不覆盖原文件 |
| 业务字段 | **不改**：迁移只补 schema 元数据/结构，不改业务值 |
| 启动流程 | **永不自动迁移**（避免“升级顺带改数据”） |

### 2.6 为什么迁移必须停写

- 迁移是**整文件原子替换**；服务运行中内存里还持有旧状态，下一次 `persist()` 会把**旧 schema 写回**，覆盖迁移结果；
- 运行中持续写入会让“加载核对条数”不可信（核对后又有新写入）；
- 回滚必须是**确定的时间点**，停写才能保证备份与数据一致。

> 一句话：**迁移是数据手术，必须停止供血（停写）。**

### 2.7 迁移工具与备份/恢复工具的分工（别混用）

| 工具 | 解决什么 | 不解决什么 |
|---|---|---|
| `scripts/migrate-state.mjs`（本版） | **schema 升级**（旧数据 → 当前 schema），自建 `.pre-*.bak` | 不是灾难恢复；不替代完整备份 |
| `BackupService`（§44，docs/25） | **备份/恢复**（sha256 验签、restore 不自动应用） | 不做 schema 迁移；不能“恢复”出兼容性 |
| 正确顺序 | 整文件备份（§44）→ dry-run → migrate（自建 .pre 备份）→ 启动冒烟 | 不要用 restore 当迁移，也不要用迁移当备份 |

## 3. 缺陷二：版本号 ↔ git tag 一致性

### 3.1 现象

- §51 不变量⑤ 明确“版本号与 git tag 必须一致（发布检查脚本核对）”；
- 但 v0.1.0 的 `release-check` 五步（测试/verify/quickstart/deploy-lint/内置验收）**没有 tag 检查**；
- 后果：打完 tag 才发现 `VERSION` 与 tag 不一致（或压根没打 tag），发布检查仍显示“全绿”——**漏检**。

### 3.2 修法：`release-check` 增加 tag 检查

| 条件 | 结果 | 说明 |
|---|---|---|
| HEAD 上存在与 `VERSION` 匹配的 tag（如 `v0.1.1`） | **PASS** | 版本号 = tag |
| HEAD 上没有 tag | **WARN** | 发布检查常发生在打 tag 之前；提示“打 tag 后复跑” |
| HEAD 上有 tag 但不匹配 `vVERSION` | **FAIL** | 典型的“版本号忘了改/打错 tag” |
| 有多个 tag 指向 HEAD | 以实现为准 | 至少要求包含匹配 tag；歧义要报出来 |

**为什么“无 tag”是 WARN 而不是 FAIL**：标准发布顺序是“先全绿 → 再打 tag”；如果无 tag 直接 FAIL，`release-check` 将永远无法在发布前跑绿。WARN 的语义是“**还不算最终发布态**”，打完 tag 必须**复跑并看到 PASS** 才允许对外。

### 3.3 报告与判定

- 报告中新增一行：`tag-check: PASS/WARN/FAIL（tag=…, version=…）`；
- 整体 `ok`：FAIL → 整体红；WARN → 允许（但发布流程要求复跑）；PASS → 最终态；
- 发布流程更新为：`release-check（WARN 可）→ 打 tag → release-check 复跑（必须 PASS）→ 公告`。

## 4. 验收（两条缺陷各自的回归）

| 缺陷 | 回归命令 | 判定 |
|---|---|---|
| ① 迁移 | `--filter=migrate`（或直接跑迁移测试文件，以实现为准） | **本机 6 passed**：dry-run 不写盘；旧 schema → 1；`CURRENT` 幂等；备份可校验；加载核对条数；核对失败回滚；损坏 JSON 拒绝；未来 schema `UNSUPPORTED`；**启动不自动迁移** |
| ② tag | `node scripts/release-check.mjs`（打 tag 前后各一次） | 当前 HEAD=`v0.1.0-rc` vs `VERSION=0.1.1` → **预期 FAIL**（正好证明检查生效）；打 `v0.1.1` 后复跑 → PASS；无 tag → WARN |
| 回归底线 | `node scripts/test.mjs`（全量） | 原有 722+ 不回退；verify 不下降 |

**不通过的判定**：迁移前后条数不一致、备份不可用、回滚失败、启动时发生隐式迁移、tag 不匹配仍显示全绿——任一出现即缺陷未修复。

## 5. 对已发布 RC 的影响

| 项 | v0.1.0（RC） | v0.1.1 |
|---|---|---|
| 旧数据升级 | 人工手改 JSON（无审计/无回滚） | **一条命令** + 备份 + 核对 + 回滚 |
| 发布检查 | 五步，不含 tag | 五步 + tag 检查（PASS/WARN/FAIL） |
| 升级演练 | 难以复现 | `--dry-run` 可预演，条数可核对 |
| 停写要求 | 未明确 | **明确：迁移必须停写**（§2.6） |

> 对已发布的 v0.1.0 实例：**先停写 → 备份 → 迁移 → 启动 v0.1.1**；v0.1.1 的 `VERSION=0.1.1`、`CONTRACT_REVISION=R22`（以 Lead 实际发布为准）。

## 7. 一页速查（运维升级三步）

### 7.1 升级三步

1. **停写 + 备份**：停服务/维护模式；整文件备份 + 记录 sha256。
2. **dry-run + 迁移**：`--dry-run` 看条数 → 正式迁移（自动备份/核对/失败回滚）。
3. **启动 + 冒烟**：`/api/version` = `0.1.1 / R22 / 1`；登录/审批/账本只读通过；必要时用 `.pre-*.bak` 回滚。

### 7.2 tag 发布三步

1. `node scripts/release-check.mjs`（无 tag 时 WARN 可接受）。
2. 打 tag `v0.1.1`（与 `VERSION` 一致）。
3. **复跑** `release-check` → tag-check 必须 PASS，才发公告。

### 7.3 三条红线

1. **不自动迁移**：启动时迁移一律视为缺陷。
2. **不迁移未来 schema**：`UNSUPPORTED`，不猜测降级。
3. **不停写不迁移**：运行中迁移 = 旧状态覆盖 + 条数不可信。
