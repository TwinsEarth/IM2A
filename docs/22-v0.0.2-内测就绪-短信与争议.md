## 1. 版本定义

### 1.1 v0.0.2 让什么从「能跑」变成「能对内测用户开放」

| 维度 | v0.0.1（闭环） | v0.0.2（准入与举证） |
|---|---|---|
| 验证码 | dev 固定码/`devCodeOnlyInDev`，只能内部人用 | `dev/log/vendor` 三档；vendor 真实下发；**验证码不进入日志/错误/审计** |
| 防刷 | 无（或依赖网关限流） | 同号 60s 冷却 + 自然日上限 + 失败可见（`OTP_DELIVERY_FAILED`） |
| 退款 | 未回复可自助退；已回复只能"人工处理"（无状态机） | 已回复走 §39 争议：`OPEN→APPROVED/REJECTED`，批准只经账本退款 |
| 举证 | 口头/截图 | `timeline()` 结构化时间线（`CHARGE→…→REPLIED→REFUND`） |
| 对内测用户 | 只能内部演示 | **可以真实开放**（前提：§7 复核项 + §5 客服手册就绪） |

### 1.2 与 v0.0.1 的边界（不做什么）

- **不改付费语义**：付费仍「先预审、后付费、未回复可退、已回复人工」；v0.0.2 不引入新计费档。
- **不改钱包语义**：余额变动仍只经 §8 账本；争议批准不是「改余额」，而是「以账本退款实现」。
- **不做**：真实支付渠道、分账、多租户、OAuth（仍是 v0.0.1 的 Out）；不做自动争议裁决（人工决策）。
- **不做**：短信供应商切换自动化（必须人工+审计），不静默降级到 dev。

### 1.3 依赖与开放顺序

| 顺序 | 交付 | 依赖 | 不通过会怎样 |
|---|---|---|---|
| 1 | 短信 provider 三档 + 冷却/日上限 | `otp-deliver` 注入点 | 验证码发不出/被刷 |
| 2 | OTP 投递失败可见 + 告警 | 供应商回执（⚠） | 用户卡在验证码页，客服无解释 |
| 3 | 争议状态机 + 时间线 | §37 钱包 + §8 账本 | 已回复退款只能口头，无法举证 |
| 4 | 客服手册 + 话术 | 争议状态机、时间线 | 客诉口径不一致 |
| 5 | 对内测用户开放 | §7 复核 + §8.2 Go/No-Go | 合规/财务风险暴露 |

## 2. 短信通道

### 2.1 三档 provider（dev / log / vendor）

| 档 | 用途 | 行为 | 是否可对内测开放 | 约束 |
|---|---|---|---|---|
| `dev` | 本机测试/演示 | 记录到内存，不外发；测试可读 | ❌（仅内部） | 生产**禁止**默认 dev |
| `log` | 等价验证/排障 | 写入日志（**脱敏**，不含 code 明文） | ⚠ 仅限受控环境 | 日志中不得出现验证码 |
| `vendor` | 真实短信 | 注入 `transport({phone, code, ttlSeconds}) → {providerMessageId}` | ✅ 内测可用 | 失败抛 `SmsError`，不吞、不静默 |

**契约对应**：`createSmsProvider({ kind, transport, timeoutMs = 3000, clock })` → `{ name, kind, info(), async sendOtp({ phone, code, ttlSeconds }) }`；`SMS_CODE` 五码：`SMS_FAILED / SMS_TIMEOUT / SMS_REJECTED / INVALID_PHONE / PROVIDER_UNAVAILABLE`。

**选择矩阵（环境 × 档位）**：

| 环境 | 默认档 | 允许的档位 | 禁止 |
|---|---|---|---|
| 单元测试 | `dev` | `dev` | `vendor`（避免真发） |
| 本机演示 | `dev` | `dev` | `log` 写真实号码 |
| 预发/内测 | `vendor` | `vendor`（可临时 `log` 排障） | `dev`（不得静默） |
| 生产 | `vendor` | `vendor` | `dev`/`log` 作为主通道 |

### 2.2 为什么验证码**永不离开 `AccountService`**

| 风险 | 如果验证码被传出去会怎样 | 契约设计 |
|---|---|---|
| 日志泄露 | 验证码进日志/错误消息/审计 → 内部人可登录任意账号 | `otp.deliver({phone, code, challengeId, ttlSeconds})` 是**回调注入**：AccountService 生成 code，直接交给 delivery 下发；provider 只拿到「发给谁、发什么」，**不进入任何持久化上下文** |
| 错误回传 | 失败信息里带 code → 前端/监控可读 | §38 不变量：失败一律抛 `SmsError`，**不得把 code 写进错误消息** |
| 审计留痕 | 审计要求可追溯，但不该存明文 | 审计只记 `phone` 的掩码/哈希、`challengeId`、`providerMessageId`，不记 code |

> 一句话：**code 的生命周期只在「生成 → 交给通道 → 用户手机」这一段**；AccountService 之外任何组件都不该看到它。

### 2.3 冷却、日上限与失败不静默

| 策略 | 契约 | 行为 |
|---|---|---|
| 同号冷却 | `OTP_COOLDOWN`（`cooldownMs = 60_000` 默认） | 60s 内二次请求不重发；`stats.cooldownHits++` |
| 自然日上限 | `OTP_DAILY_CAP`（`dailyCap = 5` 默认） | 超限直接拒绝；`stats.dailyCapHits++` |
| 投递失败 | `OTP_DELIVERY_FAILED` | **必须抛错**（不得返回成功）；`stats.failed++`；用户看到「稍后重试」 |
| 供应商不可用 | `PROVIDER_UNAVAILABLE` | 同上；告警；**不静默切 dev** |

**为什么失败必须显式**：如果投递失败被吞掉，用户会停在「请输入验证码」页面反复等待，客服无法解释；更糟的是监控显示「一切正常」。失败计数与告警是内测期唯一的早期信号。

**冷却/日上限防不了什么（写清楚，别当安全方案）**：只防同一号码的连点/误触；**不防**改号（换号继续发）、多号（设备农场）、代理/IP 轮换、接码平台。真正的防刷需要设备指纹 + IP/设备限流 + 实名绑定 + 供应商黑名单（§6.2，⛔ 本版不实现）。

### 2.4 接真实供应商时必须补的东西

| 必须项 | 为什么 | 落点 |
|---|---|---|
| **回执码 `providerMessageId`** | 用户投诉「没收到」时，凭回执码向供应商查证 | `sendOtp` 返回值 + 审计 |
| **签名/模板报备** | 国内短信需签名与模板审核（⚠ 具体流程以供应商/监管为准） | 供应商后台；不写进代码 |
| **失败原因码** | 区分「号码非法/黑名单/通道拥塞」，决定是否换通道或提示用户 | `SmsError.code` + 供应商错误映射 |
| **异步回执（送达状态）** | 同步 200 不等于送达；内测需要「送达/失败」回调 | `transport` 之外的 webhook/轮询适配（⚠ 设计） |
| **超时与重试** | `timeoutMs=3000`；重试必须有界且不重复发码 | `otp-delivery` 层控制 |

> 未补齐回执/原因码前，内测只能承诺「已提交发送」，**不能承诺「已送达」**——客服话术必须一致。

## 3. 退款争议（§39）

### 3.1 自助退 vs 人工争议：判定表

| 场景 | 走哪条 | 判定 | 契约 |
|---|---|---|---|
| 对方**未回复** | 自助退（§37 `refund`） | 可退；余额回补；账本 `REFUND` | `REFUND_WINDOW_CLOSED` 仅在已回复时 |
| 对方**已回复** | 人工争议（§39） | 不能自助退；需 `open` 争议 | `NOT_ELIGIBLE` 之外的正常路径 |
| 对方**已结算** | 人工争议（§39） | 同已回复 | `open` 允许 `REPLIED/SETTLED` |
| 已退过 / 重复退 | 幂等 | 不重复回补 | 钱包/账本幂等键 |
| 无扣费记录 | 拒绝 | 无 `pay:<messageId>` 扣费 → 不能退 | `NOT_FOUND` / 人工核查 |

### 3.2 为什么「批准后只能经账本退款」

| 做法 | 问题 |
|---|---|
| 直接改钱包余额 | 绕过 §8 账本 → 出现「影子余额」；对账差异无法解释；审计断链 |
| 直接调 §37 `refund` | §37 只允许未回复；已回复调用会破坏「未回复才可退」的不变量 |
| **经账本 `refund-dispute:<disputeId>`** | ✅ 唯一真相仍是账本；幂等键天然防重复；争议 id 与退款流水双向可查；金额取该消息 `pay:<messageId>` 的扣费额 |

**流程**：`open`（已回复/已结算）→ `resolve(APPROVE)` → 账本记 `refund-dispute:<disputeId>`（金额 = 原 `pay:<messageId>` 扣费额）→ 余额回补 → `timeline` 出现 `REFUND`。`REJECT` 不动余额，只记状态与审计。

**争议状态机（冻结）**：

| 迁移 | 触发 | 结果 | 非法时 |
|---|---|---|---|
| `OPEN → APPROVED` | `resolve(APPROVE)`（有权限的人） | 账本退款（幂等）+ 状态 | 重复 resolve → `ILLEGAL_STATE` |
| `OPEN → REJECTED` | `resolve(REJECT)` | 余额不变 + 状态 | 重复 resolve → `ILLEGAL_STATE` |
| 同消息再开 | `open`（已有未决） | 拒绝 | `DUPLICATE_OPEN` |
| 未回复消息开 | `open` | 拒绝并引导自助退 | `NOT_ELIGIBLE` |
| 非授权人决策 | `resolve` | 拒绝 | `FORBIDDEN` |

### 3.3 时间线举证的字段与客服话术

**`timeline({messageId})` 返回**（契约字段）：`[{ at, type, ref, amountCents? }]`，典型序列：

| 顺序 | type | ref | amountCents | 用途 |
|---|---|---|---|---|
| 1 | `CHARGE` | `pay:<messageId>` | 有 | 证明扣过费 |
| 2 | `VIEWED` | `messageId` | — | 证明对方看过 |
| 3 | `REPLIED` | `messageId` | — | 证明已回复（争议成立前提） |
| 4 | `DISPUTE_OPEN` | `disputeId` | — | 争议发起 |
| 5 | `DISPUTE_APPROVED` / `DISPUTE_REJECTED` | `disputeId` | — | 决策 |
| 6 | `REFUND` | `refund-dispute:<disputeId>` | 有 | 退款完成 |

**客服话术（对内/对外必须一致）**：

- 未回复：「对方还没回复，可以在客户端直接申请退款，原路退回余额。」
- 已回复：「对方已回复，按规则不能自助退款；可以提交争议，我们会按时间线人工审核。」
- 已批准：「争议已通过，退款已按原扣费金额退回余额，可在账本查看流水。」
- 已拒绝：「争议未通过，余额不变；理由见工单，可在 7 天内申诉。」

## 4. 验收 Gate B1–B6（+B7）

| # | 验收项 | 判定标准（可执行） | 验证命令 | 本机状态 |
|---|---|---|---|---|
| B1 | **同号 60s 冷却** | 同一手机号 60s 内二次请求 → `OTP_COOLDOWN`，不重发；`stats.cooldownHits` 递增 | `node scripts/test.mjs --filter=otp-delivery` | ⚠ 实现落地中 |
| B2 | **日上限** | 同一自然日超 `dailyCap`（默认 5）→ `OTP_DAILY_CAP`；次日恢复；`stats.dailyCapHits` 递增 | `--filter=otp-delivery` | ⚠ 实现落地中 |
| B3 | **验证码不出现在日志** | dev/log/vendor 的日志、错误消息、审计中均无验证码明文；`SmsError` 消息不含 code | `--filter=sms-provider` + 日志检索 | ⚠ 实现落地中 |
| B4 | **未回复 → `NOT_ELIGIBLE`** | 对未回复消息 `dispute.open` → `NOT_ELIGIBLE`（引导去 §37 自助退） | `--filter=dispute` | ⚠ 实现落地中 |
| B5 | **已回复 → APPROVE 只退一次** | 已回复消息 `open→resolve(APPROVE)`：账本只 1 条 `refund-dispute:<id>`；重放/重复 resolve 幂等；余额只回补一次 | `--filter=dispute` | ⚠ 实现落地中 |
| B6 | **拒绝不动余额** | `resolve(REJECT)`：余额不变、无 `REFUND` 流水、状态 `REJECTED`；重复 resolve → `ILLEGAL_STATE` | `--filter=dispute` | ⚠ 实现落地中 |
| B7 | **投递失败不静默** | `transport` 抛错/超时 → `OTP_DELIVERY_FAILED` / `PROVIDER_UNAVAILABLE`（或 `SMS_TIMEOUT`），`stats.failed` 递增，不返回成功 | `--filter=otp-delivery` | ⚠ 实现落地中 |

**Gate 规则**：B1–B7 全过才允许对内测用户开放真实短信；争议链路 B4–B6 全过才允许对外说「可以申请争议」；任一 ⛔ → 不开放；⚠ 必须有目标机/供应商沙箱补测记录。

**反例（看起来通过的三处）**：

1. **「冷却生效」**：只测前端按钮置灰不算——必须服务端 `OTP_COOLDOWN`。
2. **「验证码没泄露」**：只检查应用日志不够——还要检查 vendor `transport` 是否把 code 打进第三方日志（契约要求 provider 不持久化 code）。
3. **「争议退款成功」**：只测一次不算——必须重放 `resolve(APPROVE)` 与账本重放，确认只有 1 条退款。

## 5. 客服与运营手册（争议处理 5 步）

| 步 | 动作 | 必须留的证据 |
|---|---|---|
| 1 登记 | 收集 `messageId`、用户、金额、诉求 | 工单号 + 时间 |
| 2 取证 | 调 `timeline(messageId)`，确认 `CHARGE/VIEWED/REPLIED` | 时间线快照（含 `at/type/ref`） |
| 3 判定 | 未回复 → 引导自助退；已回复 → 开争议（`open`），判断是否符合退款政策 | 争议 id + reason + evidence |
| 4 决策 | `resolve(APPROVE/REJECT)` + note；批准后核对账本 `refund-dispute:<id>` | 决策人 + 时间 + 账本流水号 |
| 5 回复/关闭 | 按 §3.3 话术回复；关闭工单；拒绝时告知申诉路径 | 回复记录 + 申诉入口 |

**SLA 建议（⚠ 运营定）**：首响 ≤24h；决策 ≤72h；争议积压 >20 单告警；金额/欺诈/媒体风险 → 升级 L3。
**升级路径**：L1 机器人（规则/FAQ）→ L2 人工（退款争议）→ L3 安全合规（欺诈、执法、未成年人、媒体）。
**须留证据**：时间线、争议状态、决策人、账本流水、客服回复；**不得**只留聊天截图。

### 5.2 争议分级与审批权限

| 分级 | 金额/场景（⚠ 阈值运营定） | 审批人 | 留证要求 |
|---|---|---|---|
| 普通 | 小额、首次争议 | L2 客服 | 时间线 + 理由 |
| 大额 | 超过阈值、多次争议 | L2 主管 + L3 复核 | 时间线 + 决策双签 |
| 风险 | 欺诈嫌疑/媒体/执法 | L3 安全合规 | 全量证据 + 法务会签 |

## 6. 风险与处置

### 6.1 供应商失败率与降级

| 风险 | 触发 | 处置 |
|---|---|---|
| 通道拥塞/失败率高 | `SMS_FAILED/SMS_TIMEOUT` 占比上升 | 告警 + 有界重试（不重复发新码）；必要时人工切备用通道（留审计） |
| 供应商不可用 | `PROVIDER_UNAVAILABLE` | 用户提示「稍后重试」；**不静默切 dev/log**；不假装已发送 |
| 送达≠提交 | 同步返回 `providerMessageId` 但用户没收到 | 异步回执/人工查证（§2.4）；客服按回执码查 |

### 6.2 短信轰炸 / 黑产

- **冷却与日上限只防误触/连点**，防不了改号、多号、设备农场；攻击者可用大量号码消耗短信费。
- 需要组合：设备指纹、IP/设备级限流、实名绑定（账号与手机号强绑定）、异常号码段风控、供应商侧黑名单。
- 本版 `⛔` 不做风控引擎，但**必须有**：供应商侧限额、费用告警、异常发送量告警；风控引擎列为路线图。

### 6.3 争议被滥用（人工成本）

| 风险 | 处置 |
|---|---|
| 大量低质量争议 | 开争议前置校验（必须已回复）、证据必填、同一消息只允许一个未决争议（`DUPLICATE_OPEN`） |
| 反复开/关 | 终态不可改（`ILLEGAL_STATE`）；申诉另开且留审计 |
| 人工成本失控 | 争议率/通过率入运营看板；政策话术前置（付费前展示规则） |
| 客服舞弊 | 决策人 + note + 账本流水全留痕；大额双人复核（⚠ 流程待定） |

### 6.4 其他

| 风险 | 处置 |
|---|---|
| 验证码被内部人读取 | §2.2 的注入边界 + 日志脱敏 + 审计不含 code |
| 账号被换号/盗用 | 手机号变更需二次验证 + 审计（v0.0.3 范围） |
| 模板/签名未报备 | 内测前完成（§7 复核）；未完成不开放真实发送 |

### 6.5 监控与告警（内测期必须有）

| 指标 | 告警条件（⚠ 规划值） | 动作 |
|---|---|---|
| 短信发送成功率 | < 90% 连续 15 分钟 | 查供应商/通道；客服话术切「稍后重试」 |
| `OTP_COOLDOWN`/`OTP_DAILY_CAP` 命中量 | 环比突增 3 倍 | 查是否有黑产/改号攻击 |
| 投递失败数（`stats.failed`） | > 20/小时 | 告警 + 保留回执码 |
| 争议开单量/积压 | 积压 > 20 单或首响超 24h | 加派客服；评估政策 |
| 争议通过率异常 | > 80% 或 < 5% | 复核标准是否被滥用/过严 |
| 退款金额/账本差异 | 日切差异 > 0 | 立即对账（财务 + 后端） |

## 7. ⚠ 需复核清单（不编造供应商条款/价格）

| 项 | 需复核什么 | 复核对象 | 影响 |
|---|---|---|---|
| 短信供应商资质 | 增值电信业务资质、通道合规、实名报备 | 供应商合同 / 法务 | 能否真实发送 |
| 短信签名与模板报备 | 签名字符、模板内容、审核周期 | 供应商后台 / 监管要求 | 内测上线时间 |
| 短信计费与限额 | 单价、阶梯、失败是否计费 | 供应商报价（⚠ 不写进代码/文档） | 成本控制 |
| 争议退款财务口径 | 退款来源、记账科目、审批权限 | 财务 + 法务 | 能否按 `refund-dispute` 入账 |

| 实名与账号绑定 | 手机号变更/多账号规则 | 产品 + 法务 | 防刷与可追责 |

## 8. 一页速查

### 8.1 内测客服三句话

1. **验证码**：同一号码 60 秒内只能发一次、每天最多 5 次；收不到请稍后重试，不要连续点。
2. **退款**：对方**没回复**可以在客户端自助退；对方**已回复**需要提交争议，客服按时间线人工审核。
3. **争议结果**：批准则按原扣费金额退回余额（账本可查）；拒绝则余额不变，可在 7 天内申诉。

### 8.2 Go / No-Go（对内测开放）

| 检查 | 通过条件 |
|---|---|
| 短信 | B1–B3 + B7 全过；真实供应商沙箱通过；签名/模板报备完成（⚠ 法务/供应商） |
| 争议 | B4–B6 全过；客服手册 + 时间线取证 + 账本退款可查 |
| 合规 | 隐私政策覆盖短信/争议；退款财务口径确认（⚠） |
| 运营 | SLA 与升级路径就绪；争议积压告警 |
| 诚实 | 对外不承诺「必达」；不承诺「已回复可自助退」 |

### 8.3 v0.0.2 不是什么

- 不是「能自动裁决争议」：**争议必须人工决策**；
- 不是「短信防黑产方案」：冷却/日上限只防误触，风控引擎 ⛔ 路线图；
- 不是「支付渠道版本」：真实支付仍是 v0.0.1 的 Out。

### 8.4 30 天落地节奏（内测就绪）

| 周 | 交付 | 出口 |
|---|---|---|
| W1 | 短信三档 + 冷却/日上限 + 失败可见（B1/B2/B7） | 本机 `--filter=sms-provider/otp-delivery` 可复现 |
| W2 | 验证码不落日志 + 供应商沙箱联调（B3） | 日志检索 0 命中；沙箱回执码可查 |
| W3 | 争议状态机 + 时间线 + 账本退款（B4–B6） | 已回复 APPROVE 只退一次 |
| W4 | 客服手册/SLA/告警 + §7 复核 + Go/No-Go | 可对内测开放 |
