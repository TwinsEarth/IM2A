## 0. 结论先行

三条取舍原则，先立后破：

1. **借形态，不借方向**。可以借频道模型、签名日志、网关管线的「形状」，不借它们的去中心化/团队协作/项目管理「方向」——方向与我们的熟人五档、审批前置、付费经济学不兼容。
2. **借语义，不借协议**。身份、房间、消息类型只映射语义到契约 §11–§16；线格式（Nostr event、AICQ 协议、A2A 全量）一律不进内部。内部 protobuf 保留，A2A 只在 Phase3 边界。
3. **借机制，不借生态**。不引入参照项目的控制面、SDK、运营后台；代码可 fork（WuKongIM 形态），但治理语义必须落在我们自己可测的模块里。

一句话版本：**L3 只保留一个消息内核（WuKongIM 形态）；身份与卡（Sigil/AICQ 语义）；读侧可见域（MagicChat）；唯一网关（Agentgateway 管线）；签名审计（Buzz）；协商范式（SKChat）——其余全部否决或降级为 Phase3 互操作备选。**

## 2. WuKongIM —— 把消息内核当地基，不把业务面当地基

**定位（项目组口径，⚠ 需复核）**：Go 实现的高性能 IM 消息内核，以频道（channel）为中心；本项目口径称其消息主路径不依赖 Kafka/Redis（复核对象：官方仓库 README 的「架构/依赖」章节与部署文档）。

**借鉴什么（机制级）**

| 机制 | 具体到可落地的点 | 本仓库落点 |
|---|---|---|
| 频道是一等分发单元 | 消息投给「频道成员」而不是「用户对」；成员、订阅、未读都挂在频道上，群聊与 1:1 同一套模型 | `ChannelRegistry.create/join/post`；`im.channels` / `im.channel_members`（[05 §15](./05-数据模型与存储.md)） |
| 频道类型决定语义 | 类型不是 UI 标签，而是「存不存、算不算未读、投给谁、谁能发」的声明式开关 | `CHANNEL_TYPE` 五类 + 契约 §14 冻结语义（`CMD` 不存储不计未读等） |
| 消息主路径短 | 扇出、序号、在线投递由内核自己完成；Kafka/Redis 只做旁路（审计 outbox、限流、预算） | [02 §18](./02-技术选型与框架.md)：Kafka 仍只做 `gov.audit.*`，Redis 退为限流/序号加速 |
| 连接层与业务层解耦 | 长连接只负责帧与在线态，不解析业务；业务语义在网关与频道 | `AgentSessionRegistry` 的 `transport={send,close}` 抽象；`PROTOCOL.AGENT_WS` |

**不借鉴什么及理由**

| 不借鉴 | 理由 | 我们替而做什么 |
|---|---|---|
| 全量业务面（好友、群、朋友圈、运营后台、机器人市场） | 这些业务语义正是 L4 的信任矩阵/审批/付费要裁决的对象；引入第二套业务模型会让「谁判定权限」出现两个答案 | L3 只保留 `envelope`/`channel`/`session`；业务判定全在 L4 |
| 把「不依赖 Kafka/Redis」外推为全平台结论 | 我们的审计/outbox 回放依赖 Kafka，限流与预算依赖 Redis（v1 已实现且被测试覆盖）；内核不依赖不代表这些组件可删 | 明确边界：**消息扇出不依赖**，审计与限流依赖 |
| 其默认「已读回执 = 用户可见」的多端语义 | 与 `AGENT_NEGOTIATION` 人类未读恒 0、`CMD` 不计未读直接冲突 | 由 `CHANNEL_TYPE` + `MESSAGE_KIND` 覆盖内核默认 |
| 其客户端协议与存储格式 | 绑定其线格式等于把 L3 的升级节奏交给上游 | 只借形态；内部帧格式与表结构自定 |

**引入风险（四项必填，⚠ 需复核）**

| 维度 | 判断（本文观点） | ⚠ 复核对象 |
|---|---|---|
| 维护活跃度 | 需确认「持续迭代」是否成立，不能凭印象 | 官方仓库 commit/release 记录、Issue 关闭率 |
| 许可证 | 是否允许 fork、闭源二次分发、商用，未核实 | 官方仓库 LICENSE 全文 + 法务意见 |
| 中文社区 | 中文项目不一定等于活跃社区；排障依赖度要评估 | 官方文档完整度、中文群/Issue 语言分布 |
| 演进锁定 | fork 后上游存储格式/协议变更的合并成本是主要风险 | 上游 breaking change 记录、存储/协议版本说明 |

**边界结论**：借其「内核形态」而非「全栈产品」。若上游停更，按 [09 §9](./09-开发计划与里程碑.md) 的 V2-2 冻结 fork 自维护，不回 PaaS（回 PaaS 需过 §18.7 的 R2/R3）。

## 3. WKongAI —— 借 Agent 频道的语义，不借它的多 Agent 产品编排

**定位（项目组口径，⚠ 需复核）**：面向 AI 通讯/多 Agent 场景的 IM 项目，强调自定义消息与多频道类型（复核对象：官方仓库 README 与功能清单；与 WuKongIM 的依赖关系需一并确认）。

**借鉴什么（机制级）**

| 机制 | 具体到可落地的点 | 本仓库落点 |
|---|---|---|
| 自定义消息类型作为协作语义载体 | 不用「一条聊天文本」表达 Agent 轮次/意图/审批卡，而是类型化消息，服务端可按类型分流 | `MESSAGE_KIND`：`TEXT/CMD/AGENT_TURN/APPROVAL_CARD/INTENT`（契约 §14） |
| 多频道类型共存 | 人类频道、任务频道、Agent 协商频道同内核共存，但未读/投递策略不同 | `CHANNEL_TYPE`：`DIRECT/GROUP/TASK/AGENT_NEGOTIATION/STRANGER_QUEUE` |
| Agent 是频道成员而非「系统通知」 | 成员有 kind、principal、订阅状态，可被单独投递或跳过 | `im.channel_members(kind, principal_user_id)`；`session.subscribe` |
| 频道内消息类型与频道类型解耦 | 同一频道可承载文本/指令/卡片；策略由「频道类型 × 消息类型」二维决定 | `post()` 的 `assertCanPost` + 冻结语义 |

**不借鉴什么及理由**

| 不借鉴 | 理由 | 我们替而做什么 |
|---|---|---|
| 多 Agent 产品编排、技能市场、运营后台 | 与 L4 的 `AgentRegistry` / `CapabilityGate` / `ApprovalEngine` 同层竞争；两套编排会让「Agent 能做什么」出现两个事实源 | 编排只保留 L4 一套；L3 不感知技能 |
| 公网「Agent 互加好友」形态 | 没有信任档位、没有预审、没有付费前置，等于把陌生人经济学的门直接拆了 | 陌生人走 `STRANGER_QUEUE` → 预审 → 付费 → 审批卡 |
| 其 UI 与端形态 | 我们的端是「审批态/巡视态」双态，不是聊天工作台 | 只借消息语义，不借交互 |

**引入风险（四项必填，⚠ 需复核）**

| 维度 | 判断（本文观点） | ⚠ 复核对象 |
|---|---|---|
| 维护活跃度 | 需确认近期是否有实质提交，而非仅宣传 | 官方仓库 commit/release 记录 |
| 许可证 | 与 WuKongIM 若同源，许可证与商标条款需分别确认 | 官方仓库 LICENSE 全文 + 法务意见 |
| 中文社区 | 中文资料多，但「可提问的活跃渠道」需验证 | 官方文档、Issue 响应速度 |
| 演进锁定 | 若与 WuKongIM 版本不同步，消息格式/频道语义会分叉 | 两者依赖关系与版本对齐方式 |

**边界结论**：只借「类型化消息 + 频道共存」两个语义，**不引入其编排层**。若它明天消失，`CHANNEL_TYPE` / `MESSAGE_KIND` 已由契约冻结，不受影响。

## 4. MagicChat（即应）—— 借「Agent 一等客户端 + 读侧可见域」，不借项目管理

**定位（项目组口径，⚠ 需复核）**：AI 以独立应用/WS 接入的数字员工形态，带任务跟踪；核心约束是「AI 只能基于授权用户的可见范围查询」（复核对象：官方仓库 README 与产品文档）。

**借鉴什么（机制级）**

| 机制 | 具体到可落地的点 | 本仓库落点 |
|---|---|---|
| Agent 独立接入，不寄生客户端 | Agent 有自己的连接、在线状态、订阅与重连，可独立部署/第三方托管 | `AgentSessionRegistry.connect({transport, protocol:'AGENT_WS'})`；`im.agent_sessions` |
| 服务端统一入口 | Agent 不直接调业务 API，而是走一个数据平面 | `AgentGateway`（契约 §12）唯一入口 |
| 读侧可见域 | 查询前先绑定「principal + domains + trustCeiling + TTL」，返回按字段裁剪，而不是查完再过滤 | `VisibilityGate.buildScope/evaluate/project`；`DOMAIN` 五域；契约 §13 冻结裁剪表 |
| 数字员工身份展示 | 谁在代办、属于哪个 principal 必须可展示、可审计 | `AgentCard.ownerUserId/displayName`；`channel_members.principal_user_id`；外发标注（[10](./10-风险与验收登记册.md) R-16） |

**不借鉴什么及理由**

| 不借鉴 | 理由 | 我们替而做什么 |
|---|---|---|
| 项目管理/任务看板业务 | 我们的第一对象是熟人关系与审批卡；任务只是 `TASK` 频道的一种，引入任务状态机会与审批九态漂移 | `TASK` 频道 + `APPROVAL_CARD` + `traceId`，不新建任务模型 |
| 「AI 以用户身份查全量，靠产品话术约束」 | 越权是代码问题不是话术问题；一旦无 scope，审计也无法区分「授权查询」与「越权查询」 | 服务端 `evaluate()` 先判定，客户端只做展示禁用（[02 §12](./02-技术选型与框架.md)） |
| workspace 单租户边界 | 我们同时存在五个信任档、多个 principal 与跨 Agent 授权，workspace 表达不了 `trustCeiling`/`expiresAt` | `trust_levels` + `VisibilityScope` 双层 |

**引入风险（四项必填，⚠ 需复核）**

| 维度 | 判断（本文观点） | ⚠ 复核对象 |
|---|---|---|
| 维护活跃度 | 产品型项目开源边界不清，代码可能落后于产品 | 官方仓库提交记录与开源范围说明 |
| 许可证 | 是否开源、许可类型、商用限制均未核实 | 官方仓库 LICENSE / 官网条款 |
| 中文社区 | 中文产品，社区以用户群为主而非开发者社区 | 官方文档与开发者渠道 |
| 演进锁定 | WS 协议若为私有，抄形态不抄协议；不可绑定其帧格式 | 官方协议文档（若有） |

**边界结论**：借「独立接入 + 读侧可见域」，其余业务全部否决。若它明天消失，`VisibilityGate` 语义来自契约 §13，不依赖其协议。

## 5. Sigil —— 借密钥身份与注册表，否决去中心化主路径

**定位（项目组口径，⚠ 需复核）**：Nostr 系的 Agent 身份/注册表/事件签名项目，含 P2P/E2E 取向（复核对象：官方仓库 README 与协议说明）。

**借鉴什么（机制级）**

| 机制 | 具体到可落地的点 | 本仓库落点 |
|---|---|---|
| 密钥即身份 | 私钥在 Agent 侧自持，平台不托管；`agentId` 由公钥可重算，不可随意改名 | `createAgentIdentity` / `agentIdFromPublicKey`；`core.agent_identities` |
| 注册表可发现 | `AgentCard` 声明能力/端点/有效期，验签后才可用；卡有 TTL，过期即失效 | `createAgentCard/signAgentCard/verifyAgentCard`；`core.agent_cards`；网关 `authenticate` |
| 事件签名 | 关键事件带签名，可证明「谁写的」，可被第三方验签 | `signPayload/verifyPayload`；`SignedAuditLog`（契约 §16） |
| 规范化序列化 | 同一对象必须产生同一字节序列，否则签名不可复现 | `canonicalize()` 与审计链共用同一规则（契约 §11） |

**不借鉴什么及理由**

| 不借鉴 | 理由 | 我们替而做什么 |
|---|---|---|
| 去中心化/P2P 作为主路径 | 没有平台侧可执行的删除、封禁、审核与取证；付费风控/未成年人保护无处落地；合规不可自证 | 中心化平台 + 自有审核链路（[02 §18](./02-技术选型与框架.md)） |
| relay 广播与公网事件转发 | 绕过 `AgentGateway`，限流/门控/签名审计三处会漏（契约 §17 铁律 7） | 唯一入口在网关；对外只做 Phase3 互操作映射 |
| E2E 作为默认 | 审核、审计取证、争议仲裁都要求可解释内容；E2E 只能作为用户显式选择的高敏会话（Phase3+，⚠ 合规复核） | 默认服务端可审；E2E 单列产品能力 |
| 其身份命名空间直通内部 | 外部 Nostr 身份不能直接当 `agent-*`；否则冒充与 typosquatting 无法防 | 网关注册表映射 + `AgentCard` 验签 + Registry 白名单 |

**引入风险（四项必填，⚠ 需复核）**

| 维度 | 判断（本文观点） | ⚠ 复核对象 |
|---|---|---|
| 维护活跃度 | 协议演进快，NIP 数量与客户端活跃度需确认 | 官方仓库 commit/release、NIP 列表更新 |
| 许可证 | 协议文本与参考实现的许可可能不同 | 官方仓库 LICENSE + 协议仓库条款 |
| 中文社区 | 开发者社区以英文为主，排障成本高 | 官方文档/Issue 语言分布 |
| 演进锁定 | 采用其身份格式会绑定 Nostr 生态；我们只借密钥模型，不借格式 | 身份编码格式说明 |

**边界结论**：借「密钥身份 + 可验签的 AgentCard」；去中心化方向**否决**，仅作 Phase3 外部身份互操作备选（映射到 `PROTOCOL.A2A_JSONRPC` 边界，不引入 relay）。

## 6. SKChat —— 借「协商即产品」的范式，不借单机形态

**定位（项目组口径，⚠ 需复核）**：围绕 AI Advocate（代理用户谈判）与 AI-to-AI 协商、隐私与权限协商的项目（复核对象：官方仓库 README 与文档）。

**借鉴什么（机制级）**

| 机制 | 具体到可落地的点 | 本仓库落点 |
|---|---|---|
| 协商是结构化对象，不是聊天文本 | 交换的是「主张/条件/让步/拒绝理由」，可回放、可统计、可终止 | `NegotiationEngine` 的 `TASK_STATE` 八态与 turn 语义（v1 已实现） |

**不借鉴什么及理由**

| 不借鉴 | 理由 | 我们替而做什么 |

| 单机/本地 advocate 形态 | 没有服务端强制与可信审计，无法证明「Agent 没有绕过权限」；本地状态也扛不住多端 | 门控与审计在服务端（契约 §12/§16） |
| Agent 自动签约/自动成交 | 金额、对象、时间窗必须过 `CapabilityGate` 与审批；自动成交是资金与责任风险 | `REQUIRE_APPROVAL` + 金额阈值 + 任务级授权令牌（[03 §10.2](./03-协议设计.md)） |
| 其产品 UI 与流程 | 我们的入口是双态（审批/巡视），不是对话框 | 只借协商结构与话术 |

**引入风险（四项必填，⚠ 需复核）**

| 维度 | 判断（本文观点） | ⚠ 复核对象 |
|---|---|---|
| 维护活跃度 | 项目成熟度与代码可得性未知，可能以产品/论文为主 | 官方仓库代码与提交记录 |
| 许可证 | 代码与话术模板的许可未核实（话术可参考，模板不直接复制） | 官方仓库 LICENSE 与文档授权 |
| 中文社区 | 需确认是否有中文资料与可提问渠道 | 官方文档/社区 |
| 演进锁定 | 话术与范式可抄，协议不抄，锁定风险低 | 其对外协议（若有） |

**边界结论**：范式已在 v1 `negotiation-engine.mjs` 落地；只借结构与话术，不借形态。若它明天消失，v1 实现不受影响。

## 7. Buzz（Block）—— 借签名审计与 Agent 成员身份，不借团队协作假设

**定位（项目组口径，⚠ 需复核）**：Agent 作为频道成员、关键动作有可追溯签名日志的协作型项目（复核对象：官方仓库 README 与安全/审计文档）。

**借鉴什么（机制级）**

| 机制 | 具体到可落地的点 | 本仓库落点 |
|---|---|---|
| Agent 是频道成员 | 与人类成员同一套成员表，只是 kind 不同；可被订阅、可被投递、可被单独审计 | `im.channel_members(kind='agent')`；`MEMBER_KIND` |
| 关键动作签名留痕 | 每条治理事件签名，链式连接，谁在何时做了什么可证明 | `SignedAuditLog.append/verify/checkpoint`；`gov.audit_entries(signature, prev_hash)` |
| 可回放 | 按 `traceId` 回放一次决策的完整链路 | `AuditLog.replay(traceId)`（v1 已实现）+ v2 签名校验 |
| 周期检查点 | 定期对链头签名，防「整链重算」后仍能取证 | `gov.audit_checkpoints`；`checkpoint()` |

**不借鉴什么及理由**

| 不借鉴 | 理由 | 我们替而做什么 |
|---|---|---|
| 团队协作/workspace 业务假设 | 频道是投递单元，不是组织单元；引入 workspace 会与熟人五档、陌生人队列打架 | 频道只承载消息与成员，不承载组织权限 |
| 「频道内默认全员可见」 | 与读侧可见域冲突（`STRANGER` 只给 `id, exists`） | 可见性由 `VisibilityGate` 判定，频道成员资格只是必要条件 |
| 其产品化协作流程 | 我们的流程由审批九态与协商八态定义，不引入第二套 | 流程状态只保留契约枚举 |

**引入风险（四项必填，⚠ 需复核）**

| 维度 | 判断（本文观点） | ⚠ 复核对象 |
|---|---|---|
| 维护活跃度 | 大厂实验项目的存续与开源范围需核实 | 官方仓库 release/公告 |
| 许可证 | 是否允许商用/修改需确认 | 官方仓库 LICENSE 全文 |
| 中文社区 | 预计较小，排障依赖英文文档 | 官方文档/Issue |
| 演进锁定 | 审计模型通用（哈希链 + Ed25519），锁定风险低；但别绑定其事件 schema | 事件 schema 文档 |

**边界结论**：只借「Agent 成员身份 + 签名日志」；团队协作假设**否决**。哈希链在 v1 `audit-log.mjs` 已实现，v2 只加 Ed25519 签名与检查点（[05 §15](./05-数据模型与存储.md)）。

## 9. A2A / A2AL —— A2A 只做边界，A2AL 直连只做可选低延迟路径

**定位（项目组口径，⚠ 需复核）**：A2A 是跨框架 Agent 互操作规范；A2AL 是 Go 实现取向的局域网直连/NAT 穿透路径（复核对象：A2A 官方规范版本与字段、A2AL 官方仓库与文档）。**内部协商不用 A2A** 的论证见 [03 §2](./03-协议设计.md)。

**借鉴什么（机制级）**

| 机制 | 具体到可落地的点 | 本仓库落点 |
|---|---|---|
| A2A 只在 Phase3 边界 | 边界网关做身份映射、Task/Artifact 转换、授权注入；内部 Agent 不感知 A2A 类型 | `PROTOCOL.A2A_JSONRPC`；[03 §2.2](./03-协议设计.md) 转换表；P3-01 |
| 任务级授权令牌 | 补 A2A「刻意不定义授权」的空白：绑定票号/对象/金额/时间窗/一次性 nonce | 网关 `issueToken`/`route`；令牌 claims 见 [03 §10.2](./03-协议设计.md) |
| A2AL 式直连作为可选 | 可信对端/同局域网时少一跳，降低端到端时延 | Phase3 评估；**必须仍过 `AgentGateway` 认证与签名审计**，直连≠免门控 |
| 互操作而非同化 | 外部协议与内部协议双向转换，避免外部信任模型进入内部 | 网关归一化 `normalized`（契约 §12 第 5 步） |

**不借鉴什么及理由**

| 不借鉴 | 理由 | 我们替而做什么 |
|---|---|---|
| A2A 作为内部协议 | 单轮从 1 次 RPC 膨胀为 3–5 次网络往返；A2A 不含授权，治理语义无处安放（[03 §2.1](./03-协议设计.md)） | 内部 protobuf/gRPC 保留；A2A 只边界 |
| 「无中继直连」作为默认/主路径 | NAT 穿透成功率不可控；旁路审计、内容审核、限流都无法保证 | 默认走网关；直连仅在 Phase3 可信对端实验室/企业内网评估 |
| 其 OAuth2/OIDC 作为内部鉴权 | 与信任矩阵 + `CapabilityGate` + 审批四重控制重复；外部凭证只能边界映射 | 外部凭证 → 网关映射 → 内部 token |
| 全量任务状态同步 | 内部共享会话存储与 `traceId`，全量回传是冗余流量 | 只借 8 态语义与 Artifact 交付 |

**引入风险（四项必填，⚠ 需复核）**

| 维度 | 判断（本文观点） | ⚠ 复核对象 |
|---|---|---|
| 维护活跃度 | A2A 规范与生态演进快；A2AL 实现活跃度需单独确认 | A2A 官方规范版本记录、A2AL 官方仓库 |
| 许可证 | 规范文本（通常可引用）与实现许可不同，需分别确认 | 官方规范条款 + 官方仓库 LICENSE |
| 中文社区 | A2A 中文资料在增长，A2AL 社区规模未知 | 官方文档/社区 |
| 演进锁定 | Phase3 才用，锁定风险可控；但 AgentCard 字段名需跟版本复核 | 规范版本与 AgentCard 字段表 |

**边界结论**：A2A 是 Phase3 边界协议，**不进内部**；A2AL 直连是 Phase3 可选低延迟路径，**不做默认**。内部协议保持 protobuf。

## 10. Agentgateway —— 借数据平面与管线顺序，不借它的控制面

**定位（项目组口径，⚠ 需复核）**：面向 A2A/MCP 的 Agent 数据平面，强调安全、可观测与治理（复核对象：官方仓库 README 与能力边界文档）。

**借鉴什么（机制级）**

| 机制 | 具体到可落地的点 | 本仓库落点 |
|---|---|---|
| 单一数据平面 | 内部 Agent、第三方 Agent、A2A、MCP 全部从同一入口进出 | `AgentGateway`；契约 §12「所有 Agent 流量的唯一入口」 |
| 管线顺序冻结 | 认证 → 限流 → 前置门控 → 出口护栏 → 协议归一化 → 签名审计，短路顺序不可重排 | 契约 §12 六步 + `GATEWAY_CODE`；[17 铁律 7](../contracts/INTERFACES.md) |
| 协议归一化收口 | A2A/MCP 适配只发生在网关，内部只认 `normalized` 结构 | `normalized = {action, protocol, execute, skillId, targetId, content, meta}` |
| 可观测与治理 | 每次路由 `auditSeq` 回传；认证/限流/拒绝/放行都有事件 | `route()` 返回 `auditSeq`；`events()`；`SignedAuditLog` |

**不借鉴什么及理由**

| 不借鉴 | 理由 | 我们替而做什么 |
|---|---|---|
| 用网络层治理替代业务门控 | 网关能做认证/限流/路由，但「金额是否超阈值、信任档是否够、预算是否耗尽、是否需要审批」是 L4 语义，网关替代不了 | `CapabilityGate.evaluate()` 仍在网关内被调用（第 3 步），不是二选一 |
| 多协议全量接入 | 每个协议都是攻击面与测试面；Phase0–2 只需要 4 个 `PROTOCOL` | 未知路由返回 `UNKNOWN_ROUTE`，不做「协议动物园」 |
| 自托管其控制面/策略 CRD | 会把策略表达锁进第三方控制面，且与审批引擎重复 | 只借管线；策略仍在 L4，网关是薄数据面 |
| 「网关即审计」的简化假设 | 网关只写路由审计；审批/执行/资金审计仍在各自模块 | 网关审计 + 各模块 `SignedAuditLog`，`traceId` 串联 |

**引入风险（四项必填，⚠ 需复核）**

| 维度 | 判断（本文观点） | ⚠ 复核对象 |
|---|---|---|
| 维护活跃度 | 需确认是持续维护的项目还是单次发布 | 官方仓库 commit/release 记录 |
| 许可证 | 网络代理/网关类项目常有附加条款，需逐条看 | 官方仓库 LICENSE 全文 + 法务意见 |
| 中文社区 | 英文文档为主，排障依赖官方 Issue | 官方文档/Issue 语言分布 |
| 演进锁定 | 只借管线顺序，不自托管其控制面，锁定风险低 | 其 CRD/策略模型文档 |

**边界结论**：借「单一入口 + 六步管线 + 归一化」；控制面与多协议**否决**。若它明天消失，契约 §12 已是自研接口，网关实现不受影响。

## 11. 横向对照：每个能力只允许一个权威落点

九个项目最容易造成的工程事故不是「选错」，而是**同一能力出现第二处实现**。下表是评审时的检查项（发现第二实现即否决）：

| 能力域 | 参照来源 | 唯一权威落点（代码/契约） | 禁止的第二实现 |
|---|---|---|---|

## 12. 最容易被误读的取舍（评审重点）

| # | 误读说法 | 正确口径 | 后果（如果按误读执行） |
|---|---|---|---|
| 1 | 「推翻 PaaS = 连推送也自建」 | 推翻的是 IM PaaS 的**会话模型/消息存储/未读语义/审核链路**；离线推送仍采购厂商通道（APNs/国内厂商推送），推送资质与送达仍要谈 | 误算工期与合规成本，做出一个「自建 APNs」的荒诞排期 |
| 2 | 「v2 契约冻结 = v2 已实现」 | 曾成立、**现已不适用**：v2 六模块已实现并合入基线（全量 307 全绿，含 im-live `/v2` 集成 6 项）。方法仍要遵守：**契约冻结不等于实现完成**，新模块一律以"合并 + 全量回归"为准 | 在未回归的情况下对外宣称已支持 Agent 一等客户端，实际演示跑不通 |
| 3 | 「Agent 一等客户端 = Agent 可以直连内核」 | Agent 仍必须过 `AgentGateway`（契约 §17 铁律 7）；A2AL 式直连也必须旁路审计、认证 | 限流/门控/审计三处同时漏，且无法回放 |
| 4 | 「频道类型化 = 消息加个 type 字段」 | 类型决定 `stored`、未读、投递对象、谁能发（契约 §14 冻结语义）；只加字段不改语义等于没做 | `AGENT_NEGOTIATION` 仍会产生人类未读，告警噪音照旧 |
| 5 | 「读侧可见域 = 返回后在客户端裁剪」 | scope 必须在服务端 `evaluate/project`（契约 §13）；客户端只做展示禁用 | 越权数据已经出网，客户端裁剪不构成合规防线 |
| 6 | 「v1 已有哈希链，签名审计可以不做」 | 哈希链防单条篡改/截断，防不了有权改库者整链重算；签名解决「谁写的」，两者都要（契约 §16） | 审计无法作为监管/司法证据，等于白做 |

> 另有一处**跨文档口径未收敛**（已知、非本文授权范围）：[00 §3](./00-技术文档-总览.md) 的 D4 与 [01 §4](./01-总体架构.md) 的 D4 仍写「IM 用 PaaS」。本次只修订 02/05/09/12；00/01 的回写由 Lead 统一授权，评审时以 [02 §18](./02-技术选型与框架.md) 为准。
