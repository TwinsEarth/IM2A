# IM2A · 工程基线（v1.0.0-baseline）

> 定位：**面向智能体开发的原生 AI IM 即时通讯系统**。
> 一句话：让每个人都像大老板一样，拥有自己的 Agent 秘书/助理/管家团队，管理日常与杂碎事务，
> 专注于自我提升、家庭生活与工作事业。
>
> 人机混合的含义：**Agent 承担协调/预约/确认的"行政层"，人只处理情感层与最终决策层。**

本文件是 IM2A 的**技术负责人基线**：它不重复愿景，只回答三个问题——
①四条不可妥协的主张各自被哪段代码强制？②基线包含什么、明确不包含什么？③距离"可给熟人圈内测"还差哪几步？

---

## 一、四条不可妥协的主张 → 代码证据

> 判定口径：每条主张都必须能被 `node <file>.test.mjs` 直跑复现，或由 `scripts/verify.mjs` 机械校验。
> 不满足这条的，写成"设计"而不是"已实现"。

### 主张 1：总 Agent → 子 Agent → Skill 三级体系

| 层级 | 职责 | 代码 | 证据 |
|---|---|---|---|
| L0 总管 | 路由、优先级仲裁、跨子 Agent 协调、向人呈报 | `services/orchestrator/src/agent-registry.mjs`、`persona-memory.mjs` | 注册表 12 项单测；总管只持有"协调摘要"、读不到子 Agent 原始记忆（`MEMORY_ISOLATED`） |
| L1 子 Agent | 单一领域闭环（采购/物业/日程/法律/教育/陌生人过滤） | `agent-registry.mjs` 的 `children()`、`capability-gate.mjs` 的 `trustZoneMin` | 每个子 Agent 独立 `trustZoneMin` / 预算 / 自动审批阈值，越权即 `TRUST_TOO_LOW` |
| L2 Skill | 原子能力，声明权限与财务影响 | `services/gateway/src/agent-gateway.mjs`、`tool-policy.mjs`、`confirmation-tier.mjs` | Skill 未授权 → `SKILL_NOT_ALLOWED`；扣费类 Skill 在确认层 → `PLANNER_PREAPPROVAL_REJECTED` |

**关键不变量**：Agent 不得绕过编排层直接调外部能力（`contracts/INTERFACES.md` §20 铁律 7）。

### 主张 2：人类 IM 与 Agent 协商**双通道分离**

| 通道 | 承载 | 代码 | 证据 |
|---|---|---|---|
| 人类 IM | 人与人可见消息、审批卡片 | `services/messaging/src/{envelope,seq,dedupe,channel}.mjs` | 会话内 `seq` 严格递增；`bizId` 去重；频道类型决定未读语义 |
| Agent 协商 | 结构化方案讨论（人不被中间态打扰） | `services/orchestrator/src/negotiation-engine.mjs` + `AGENT_NEGOTIATION` 频道 | 8 态状态机；**该频道对人类未读恒为 0**（有测试）；轮次/Token 硬上限超限转 `INPUT_REQUIRED` |
| 治理/审计 | 门控与审计事件 | `services/audit/src/signed-audit.mjs` | 哈希链 + Ed25519；"换签名者"能被抓住而"改内容"被链抓住（两种攻击两层防御） |

> **v7 的例外必须在这里说清**：底座从"自托管内核"反转为"Phase0–1 腾讯云 IM PaaS + 适配层"（`docs/02 §19`）。
> 分离原则不变，但 PaaS 不提供 `UNREAD_SHAPING`，适配层会**显式报 `CAPABILITY_MISSING`**——
> 补偿方式是"人类未读由业务层自建投影"，不是假装平台支持。

### 主张 3：熟人五档信任矩阵由**代码层** capability 门控强制

| 档位 | 数值 | Agent 可自主 | 需人审批 | 代码断言 |
|---|---|---|---|---|
| 本人 SELF | 0 | 全部 | — | `levelOf <= trustZoneMin` 才放行 |
| 家庭 FAMILY | 1 | 日程协调、家庭采购、物业事务 | 大额支出、对外承诺 | 金额超阈值 → `REQUIRE_APPROVAL` |
| 信任 TRUSTED | 2 | 预约日程、留言转达 | 涉及第三方信息 | 信任不足 → `DENY/TRUST_TOO_LOW` |
| 已知 KNOWN | 3 | 接收留言并摘要 | 所有对外回复 | 读侧可见域只回 `id/displayName/tags` |
| 陌生 STRANGER | 4 | 仅接收结构化来意 | 付费后查看 | 读侧只回 `{id, exists}` |

**这条是产品壁垒**：开源 IM 的关系模型是"好友/成员/角色位"二值或组织权限，表达不了"同一用户对不同目标不同档 + 过期即撤销 + Agent 自己的 trustZoneMin"。外包它 = 外包权限语义与定价权。

### 主张 4：陌生人付费消息**永远发生在 Agent 预审之后**

```
陌生 Agent 来信 → correspondence.open() → SUSPENDED（默认挂起，deliverable=false）
                → 属主 decide(APPROVE)   → 才允许进入会话
                → paid-message: INTENT → AWAITING_PAYMENT → PAID → VIEWED → REPLIED → SETTLED
```

| 环节 | 强制点 | 证据 |
|---|---|---|
| 先预审后付费 | 未 `screen` 的 `pay()` → `NEEDS_SCREENING`；`BLOCK` 后 → `NOT_PAYABLE` | `paid-message` 23 项单测 |
| 人批才投递 | 挂起中的来信 `deliverable` 恒 false；非属主不能批 | `agent-correspondence` 15 项单测 |
| 恰好一次扣费 | 幂等键 `pay:<messageId>`，连点 5 次只 1 条 CHARGE | `ledger` 13 项单测 |
| 驳回不扣费 | `REJECT` → `REFUSED`，账本零条目 | 端到端 e2e |

## 三、基线明确**不包含**什么（防止把"设计"当"已实现"）

1. **生产级 Go/Flutter/PostgreSQL 实现**：本机无 Go/Flutter/Docker/protoc，代码是**语义可执行的参考实现**，端口映射见 `apps/im2agent/PORTING-TO-GO.md`。
2. **硬件与端侧**：耳夹耳机/眼镜、BLE、端侧唤醒均为文档设计；原始音频不出端侧是承诺，不是已验证的实现。
3. **真实资金与实名**：账本是记账不是支付；登录/实名/支付网关在 `apps/im2agent/ROADMAP-v0.6.1+.md` 里，属商业化前置，不在基线内。
4. **跨组织 A2A 互通**：Phase3 规划，边界网关设计已写，未实现。

## 五、从基线到"熟人圈内测"：P0 三件事

| # | 事项 | 为什么是 P0 | 验收 |
|---|---|---|---|
| 1 | 登录 + 实名 | 付费 + 陌生人触达的合规底线；没有实名就没有可追责主体 | 未实名不能收发付费消息；实名只存 hash |
| 2 | 支付通道（代收 + 余额扣减） | 账本没有真实资金流动；"先扣后退"会被退款白嫖 | 连点 10 次只 1 笔 CHARGE；退款仅限未回复态 |
| 3 | 审核链 + 签名审计闭环 | PaaS 后台日志不能当合规证据 | 任一消息可从 messageId 追到"谁审/什么规则/谁批" |

## 六、我作为技术负责人要拍板的三件事

1. **底座是否维持 v7 反转**：Phase0–1 用 PaaS + 适配层（快），Phase2 评估自托管（可控）。若要改回自托管，我需要在 M1 前知道，因为 §31 适配层的能力补偿要跟着改。
2. **陌生人能否被 Agent 主动扩关系**：建议"受限宿主"——Agent 有独立身份与成员资格，但加好友/拉群/发起陌生协商必须人授权或审批。否则会绕过"默认 STRANGER + 预审 + 付费"的经济学。
3. **proto 收口**：v3–v7 共 12 个模块只有契约+实现+测试，没有 `.proto`。要么在 CI 补 `buf`，要么明确"内部服务不对外，proto 只做到 v2"——不能两头悬着。
