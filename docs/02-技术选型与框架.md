## 0. 阅读方式与选型原则

本文每个领域给一张决策表，列含义固定：

| 列 | 含义 |
|---|---|
| 候选 | 2–3 个真实候选，不列凑数项 |
| 结论 | ✅ 采用 / ❌ 否决 / ⏳ 延后 |
| 理由 | 采用或延后的具体工程理由 |
| 否决理由 | 为什么不用；写可验证的短板，不写「生态不好」这类空话 |
| 切换触发条件 | 条件化的反转点。对采用项写「何时迁走」，对否决项写「何时重新评估」 |

两条硬约束：

1. **不写版本号、不写未经实测的性能数字、不给外部链接**。凡属「采购/压测/法务确认后才能定」的参数，一律标 **⚠ 需复核**，并在 §17 汇总。
2. **生产架构与参考实现分开**：生产是 Go + Go-Zero 服务集群；仓库里 `services/**` 的零依赖 Node ESM 模块是**治理与编排层的可运行参考实现**，用来证明判定顺序、状态白名单、幂等键规则可以被单元测试强制。两者映射见 §15，混淆这两者会被本文视为错误引用。

分层对应平台规范的六层：L1 接入（硬件/手机/PC/手表/Web）、L2 端侧（ASR/意图/过滤/BLE 网关）、L3 IM 通信（腾讯云 IM PaaS）、L4 Agent 编排（含 PreToolUse 强制门控）、L5 模型（端侧小模型 ↔ 云端大模型）、L6 数据。选型按「L1/L2 端侧 → L3 通道 → L4 编排与门控 → L5 模型 → L6 数据 → 工程底座」组织。

## 1. 选型总览

| 领域 | 结论 | 一句话理由 | 切换触发（摘要） |
|---|---|---|---|
| API 框架 | Go-Zero | 一套工具链覆盖 API/RPC/网关，goctl 生成契约 | 团队 Go 能力不足或需重度 DDD 分层 |
| 服务间 RPC | gRPC + Protobuf | 强契约、跨语言（Go/Dart/Python）、支持流式 | 对外生态要求纯 REST/JSON |
| 注册发现 | etcd | 强一致 KV + lease，Go-Zero 原生集成 | 全面容器化且由服务网格接管发现 |
| 消息队列 | Kafka | 分区有序 + 回放，审计/outbox 需要 | 多租户海量 topic 或需更低延迟控制面 |
| 关系库 | PostgreSQL | JSONB、RLS、pgvector、唯一索引与分区齐全 | 单库写吞吐触顶或需跨地域多写 |
| 缓存/协调 | Redis | 原子 INCR、TTL、集群成熟 | 只读缓存即可且想省运维 |
| 归档检索 | MongoDB + OpenSearch | 文档归档与全文检索分工 | 检索 QPS 极低时 PG 分区足够 |
| 向量 | pgvector 起步 → Milvus | 与业务库同事务、起步成本低 | 见 §9 量化阈值 |
| IM 通道 | 腾讯云 IM PaaS | 长连接/推送/多端同步采购，关系链与账本自有 | 成本拐点或数据驻留不满足 |
| 工作流 | 自研状态机 | 与契约九态/八态逐字对齐、可测 | 长周期跨系统补偿流程出现 |
| 客户端 | Flutter | 一套 UI 覆盖手机/Web，团队效率高 | 端侧系统级能力不足或手表端受限 |
| 端侧推理 | TFLite Micro + KWS | 低功耗离线守门，隐私边界 | 精度/功耗不达标 |
| 硬件 SoC | 恒玄/高通/Nordic 三档 | 按功耗-算力-生态分档，不锁型号 | BOM/续航/LE Audio 实测不达标 |
| 可观测 | OpenTelemetry 语义 | 全链路 traceId 贯穿人类/协商/审批三流 | 云厂商深度绑定需求 |
| 部署 | 云托管 K8s + 托管 PG/Kafka | Phase0 人力有限，先托管 | 成本/合规要求自建 |

## 2. API 框架（L4 服务出口）

| 候选 | 结论 | 理由 | 否决理由 | 切换触发条件 |
|---|---|---|---|---|
| **Go-Zero** | ✅ 采用 | API/RPC 一体生成，`.api`/`.proto` 双契约；内置熔断、限流、链路追踪；goctl 把「契约先写」变成工程习惯，正好匹配本项目「契约冻结」文化 | — | 团队 Go 经验不足、或需要复杂 DDD 分层与插件生态时迁 Kratos；性能不是切换理由 |
| Gin + Kratos 组合 | ❌ 否决 | — | 两套框架拼接：Gin 管 HTTP、Kratos 管 RPC，错误处理/中间件/配置各有一套，边界靠人守；Phase0 人力不足以维护两套约定 | 若团队已有成熟 Kratos 基建并要求统一 BFF 层，可重评 |
| Java Spring Boot | ❌ 否决 | — | 启动内存与冷启动对长连接网关不友好；与端侧/Go 网关混合栈增加运维面；团队栈已在 Go/Node | 若支付/风控必须接大量 Java 生态 SDK，可让支付侧单独用 Java，不进主栈 |

**落地约定**：所有对外 API 必须有 OpenAPI（`contracts/openapi/orchestrator.openapi.yaml`），内部服务间只能走 gRPC；API 层禁止写业务状态机，只做参数校验、鉴权、协议转换。

## 3. 服务间 RPC（gRPC / Protobuf）

| 候选 | 结论 | 理由 | 否决理由 | 切换触发条件 |
|---|---|---|---|---|
| **gRPC + Protobuf** | ✅ 采用 | 强类型契约、代码生成、双向流适合协商 turn 与长任务进度；错误码可携带 `code` 与业务枚举；跨语言（Go 服务、Dart 客户端、Python Skill） | — | 需向第三方开发者开放 HTTP API 时，只在网关额外暴露 REST，不改内部 RPC |
| REST + JSON 为主 | ❌ 否决 | — | 手写校验与版本兼容易漂移；流式与超时语义弱；契约无法像 proto 一样编译期检查 | 若第三方集成方明确拒绝 gRPC，网关层做 REST 适配即可，不改变内部协议 |
| Dubbo（Java 生态） | ❌ 否决 | — | 与 Go 主栈不一致；注册中心/序列化绑定重 | 若主栈整体迁 Java 再评估 |

**补充**：协商通道必须独立（独立 gRPC service、独立端口、独立配额与超时），与人类 IM 通道物理隔离；`NegotiationEngine` 的 `turn` 语义用 proto 枚举与 `contracts/INTERFACES.md` 的 `INTENT`/`TASK_STATE` 逐字对齐（见 docs/03-协议设计.md）。

## 4. 注册发现（etcd）

| 候选 | 结论 | 理由 | 否决理由 | 切换触发条件 |
|---|---|---|---|---|
| **etcd** | ✅ 采用 | 强一致 KV + lease，服务健康语义清晰；Go-Zero 原生支持；配置中心可复用同一套 | — | 全部服务上 K8s 且由服务网格/mesh 接管发现与配置后，可退化为 K8s Service + ConfigMap |
| Consul | ❌ 否决 | — | 功能重叠但多一套 agent 与 UI；团队无运维经验；强一致保障不如 etcd 直接 | 需要多数据中心原生 WAN gossip 且无 K8s 时可重评 |
| K8s Service/DNS | ⏳ 延后 | Phase0 用 etcd 显式注册，便于本地与多环境一致 | 无健康检查语义细节、无元数据 | 全面容器化并通过压测后可作为 etcd 的补充（不是替代） |

## 5. 消息队列（Kafka / Pulsar / NATS）

| 候选 | 结论 | 理由 | 否决理由 | 切换触发条件 |
|---|---|---|---|---|
| **Kafka** | ✅ 采用 | 分区内有序满足「同聚合根事件顺序」；可回放支撑审计与 outbox 重放；生态与云托管成熟 | — | 需百万级 topic/租户隔离或分层存储成为硬需求时评估 Pulsar |
| Pulsar | ⏳ 延后 | 存算分离与多租户更优雅 | 运维组件更多（BookKeeper），Phase0 人力不足 | 多租户 SaaS 化或 topic 数量爆炸时重评 |
| NATS JetStream | ❌ 否决（数据面） | — | 持久化与回放模型相对弱、跨地域复制方案不成熟（⚠ 需复核）；团队经验少 | 仅用于控制面信号/低延迟通知时可局部引入，不替代审计与计费事件流 |

**Topic 规划**：`im.*`（人类消息元数据事件）、`agent.negotiation.*`（协商）、`gov.audit.*`（审计）、`gov.approval.*`（审批事件）、`pay.ledger.*`（账本条目）。三类流的 topic 前缀不允许混用（见 01 §2.3）。

## 6. 关系库（PostgreSQL）

| 候选 | 结论 | 理由 | 否决理由 | 切换触发条件 |
|---|---|---|---|---|
| **PostgreSQL** | ✅ 采用 | JSONB 存审批 payload/patch；RLS 做记忆按 Agent 隔离；唯一索引实现 exactly-once；声明式分区支持审计/消息按月分区；pgvector 让向量与业务同库同事务 | — | 单库写入接近容量上限、或需要跨地域多写时，评估分库或 TiDB |
| MySQL | ❌ 否决 | — | JSON 能力与索引表达弱；RLS 缺失会让记忆隔离只能靠应用层；向量扩展生态弱；分区/DDL 在线变更体验差 | 团队强 MySQL 且无 RLS 需求时不适用本项目 |
| TiDB | ⏳ 延后 | 水平扩展与 HTAP 诱人 | Phase1 规模不需要分布式事务成本；延迟与运维复杂度增加；⚠ 需压测验证 | 单表/单库写 QPS 与容量触顶（阈值待压测校准，见 §17）时评估 |

## 7. 缓存与协调（Redis）

| 候选 | 结论 | 理由 | 否决理由 | 切换触发条件 |
|---|---|---|---|---|
| **Redis** | ✅ 采用 | `INCR` 做会话序号分配（`seq.mjs` 的 64 分片语义在服务端用 Redis shard 实现）；TTL 做去重与预算缓存；原子脚本做限流 | — | 若一致性要求提高，序号/预算以 PG 为准，Redis 退化为加速层 |
| Memcached | ❌ 否决 | — | 只有 KV、无持久化、无原子计数外的数据结构；去重与限流都要额外造轮子 | 不重评 |
| 纯本地缓存 | ❌ 否决（作为唯一） | — | 多实例下序号与预算必错；本地缓存只允许做只读配置缓存 | 不重评 |

**原则**：Redis 里的一切都可以丢；丢了的后果只能是「变慢/重算」，不能是「账错/权限错」。预算扣减与序号最终以 PG/账本为准。

## 8. 归档与检索（MongoDB + OpenSearch）

| 候选 | 结论 | 理由 | 否决理由 | 切换触发条件 |
|---|---|---|---|---|
| **MongoDB（归档）+ OpenSearch（检索）** | ✅ 采用（Phase2 起） | 归档对象是「会话快照/协商全文/审计详情」，文档模型合适、按时间分片便宜；全文检索与聚合交给 OpenSearch，不影响主库 | — | 若检索 QPS 极低，Phase0–1 用 PG 分区 + `pg_trgm` 即可，暂不引入 |
| 仅 OpenSearch 做主存 | ❌ 否决 | — | 无事务、更新成本高、长期存储贵；不能作为账本/审批的事实源 | 不重评 |
| ClickHouse | ❌ 否决（本场景） | — | 列存适合遥测/指标分析，不适合按会话取全文与单条更新（⚠ 需复核具体查询模式） | 遥测分析量级上来后可独立引入，替代时序库的部分场景 |

**Phase0 决策**：MongoDB 与 OpenSearch 都不部署；归档先用 PG 分区表 + 对象存储，接口留抽象。这是刻意技术债，见 §16。

## 9. 向量检索：pgvector 起步，Milvus 作为迁移终点

| 候选 | 结论 | 理由 | 否决理由 | 切换触发条件 |
|---|---|---|---|---|
| **pgvector** | ✅ Phase0–2 采用 | 向量与 `agent_memories` 同库同事务，删除权/RLS/备份与业务一致；运维零新增组件；参考实现的确定性词频打分可无缝替换为向量召回（接口不变） | — | 触发下列任一量化条件即迁 Milvus |
| Milvus | ⏳ Phase3 候选 | 大规模向量检索、独立扩缩容、多索引类型 | 独立集群 + 对象存储 + 元数据库，Phase0 运维成本不值 | 迁移阈值见下 |
| 云厂商托管向量库 | ⏳ 备选 | 免运维 | 数据驻留与账本/记忆同库事务优势消失，供应商绑定 | 采购评审时与 Milvus 二选一（⚠ 需复核） |

**迁移阈值（同时满足 2 项即启动评估，全部为待压测校准的规划值 ⚠ 需复核）**：

1. 单租户向量行数 > 5000 万，或全库 > 2 亿；
2. 向量检索峰值 QPS > 200，且 pgvector 在该 QPS 下 P99 超过 100 ms（以真实数据实测为准）；
3. 需要按 Agent/用户做「万级隔离组」的强隔离检索，PG 的 HNSW + 过滤组合出现召回不可控；
4. 需要独立于主库扩缩容（例如夜间批量重建索引影响在线业务）。

迁移方式：`memory-store` 的读接口不变，先双写双读比对（影子流量），再切主；向量维度与 embedding 模型必须版本化，⚠ 维度需按所选模型复核。

## 10. IM PaaS 与「关系链/账本必须自有」的边界

| 候选 | 结论 | 理由 | 否决理由 | 切换触发条件 |
|---|---|---|---|---|
| **腾讯云 IM PaaS** | ✅ 采用（Phase0–2） | 长连接、多端同步、离线推送、群组分发是成熟工程；合规资质与国内送达率有保障 | — | 单用户通道成本超过自研 3 年 TCO 的 60%，或数据驻留/私有化不满足 |
| 融云 / 环信 | ⏳ 备选 | 同为国内 IM PaaS，商务与能力接近 | 与腾讯云生态（云主机/对象存储/审核）协同弱一档；⚠ 具体能力/报价需采购复核 | 招标比价时作为第二供应商，保持可迁移抽象 |
| 自研 IM 长连接 | ❌ Phase0 否决 | — | 连接保活、弱网、多端同步、推送合规是长周期工程；Phase0 人力应投在 Agent 治理上 | 用户规模与成本拐点出现后重评；即使自研也只替换 L3 通道，不碰 L4/L6 |

**边界论证（为什么关系链与账本不能托管）**：

- **关系链**：PaaS 的关系模型是「好友/黑名单/群成员」二值关系，无法表达五档 `TRUST_LEVELS`（`SELF/FAMILY/TRUSTED/KNOWN/STRANGER`）、`expiresAt` 过期即撤销、以及「同一用户对不同目标不同档位」。把信任映射进好友列表会导致语义丢失（例如无法表达「仅本次授权」），且 Agent 的 `trustZoneMin` 判定必须在服务端同步完成。因此：**PaaS 只负责人与人之间的消息可达性，关系档位永远在 `trust_levels` 自有表**。
- **账本**：付费消息要求「先预审、后付费、恰好一次、可退款、可对账」。PaaS 的计费是通道侧计量，不是业务账本；一旦托管，`idempotencyKey`、`settle`/`refund` 与渠道对账权都不在自己手里，合规审计也无法自证。因此：**`paid_message_ledger` 必须自有，且只追加**（见 docs/05-数据模型与存储.md §10）。

**可迁移抽象**：`IMChannel` 接口（发送、撤回、已读、推送、群组）与厂商 SDK 解耦，PaaS 切换只影响适配层；审批卡片只依赖 `BIZ_TYPE.APPROVAL_CARD` 业务封装，不依赖厂商消息类型。

## 11. 工作流引擎：自研状态机（Temporal 式延后）

| 候选 | 结论 | 理由 | 否决理由 | 切换触发条件 |
|---|---|---|---|---|
| **自研状态机（PG + 事件溯源 + 扫描任务）** | ✅ Phase0–2 采用 | 契约要求九态审批与八态协商逐字可测；状态机直译成代码最不易漂移；无新增集群 | — | 见下方「迁移触发」 |
| Temporal 式持久化工作流 | ⏳ 延后 | durable execution、内建重试/补偿、精确 timer 是真优势 | 集群 + SDK + 本地开发环境复杂度；Phase0 流程分钟级、状态少、无跨系统补偿，收益不抵成本 | 出现以下任一：跨 ≥3 个外部系统且需补偿；审批生命周期 > 24h；需要精确 durable timer 的 SLA；扫描积压导致审批 P99 超 SLO 20% |
| 简单定时任务 + 内存状态 | ❌ 否决 | — | 重启即丢状态；无法满足 `EXECUTING` 必须终态、超时幂等等不变量 | 不重评 |

**选择自研必须承认的代价**（写进工程预算，不许隐藏）：

1. **没有 durable replay**：进程崩溃后靠扫描 `EXECUTING`/`PENDING` 票恢复，恢复逻辑要自己写、自己测。
2. **超时与升级靠扫描**：`escalateOverdue` 幂等（`escalationLevel`）要落库，扫描频率决定最坏延迟；需要独立监控。
3. **补偿事务靠业务**：外部副作用失败只能 `FAILED` + 人工，不能自动回滚已扣费或已改单。
4. **重试语义自建**：幂等键、去重、超时、退避都要在服务层显式实现（参考实现 `approval-engine.mjs` 已给出状态白名单与事件追加模型，可移植）。

## 12. 客户端：Flutter 三端

| 候选 | 结论 | 理由 | 否决理由 | 切换触发条件 |
|---|---|---|---|---|
| **Flutter** | ✅ 采用 | 一套 UI 覆盖 iOS/Android/Web/桌面骨架；Dart 侧可生成 gRPC 客户端；审批/巡视双态 UI 复用度高 | — | 手表端（watchOS）系统能力受限：手表轻端允许原生/独立实现，只共享模型与 API 层，⚠ 支持边界需复核 |
| React Native | ❌ 否决 | — | BLE/音频/后台常驻插件成熟度与线程模型风险（⚠ 需实测）；与 Flutter 团队栈不符 | 若团队 RN 经验占绝对多数且关键插件验证通过，可重评 |
| iOS/Android 原生双端 | ❌ 否决（Phase0–2） | — | 双倍 UI 人力；本项目竞争点是 Agent 治理而非端侧渲染 | 需要系统级深度集成（如系统级语音助手接入）时，关键模块原生嵌入 + platform channel |

**约束**：客户端的权限判断只做「展示与禁用」，不做「放行」；离线审批缓存只缓存**待审批卡片**与**已批准结果**，不缓存能力令牌（防本地提权）。

## 13. 端侧推理与唤醒栈（L1/L2）

| 候选 | 结论 | 理由 | 否决理由 | 切换触发条件 |
|---|---|---|---|---|
| **TFLite Micro（设备 MCU 唤醒）+ 手机端小模型（ASR/意图/敏感过滤）** | ✅ 采用 | 低功耗离线守门；原始音频不出手机（隐私边界）；唤醒→上传延迟可控 | — | 误唤醒率/漏检率不达标，或手机端算力不足 → 退回「设备仅 VAD + 云端过滤」（须同步改隐私声明） |

**边界**：设备端只做 KWS + VAD + 播报；手机端做 ASR、意图粗分类、敏感前置过滤、BLE 网关、离线审批缓存；云端做规划与协商。模型版本必须可 OTA 回滚（见 docs/04-SDK与端侧设计.md）。

**可直接移植（纯逻辑，语义即规格）**：

- `TRUST_LEVELS`/`TRUST_NAMES` 的档位与默认值、过期判定；
- `CapabilityGate` 判定顺序 1–7、`GATE_CODE` 错误码、审计事件字段；
- `TICKET_STATE`/`TASK_STATE`/`MSG_STATE` 的迁移白名单与错误码（`ILLEGAL_TRANSITION` 等）；
- 账本 `idempotencyKey` 语义与 `duplicate` 返回；付费消息状态机与 `NEEDS_SCREENING` 前置条件；
- `EgressGuard` 默认规则与归一化顺序（零宽字符/全角绕过）。

**必须重写（并发/事务/环境差异）**：

| 差异点 | Node 参考实现 | 生产 Go 实现 |
|---|---|---|
| 并发原子性 | 单线程同步「查重+追加」即原子 | DB 唯一索引 + 事务 + `INSERT ... ON CONFLICT` |
| 事务边界 | 内存操作无事务 | PG 事务 + outbox（业务表与事件同事务） |
| 时钟 | 注入 `clock` 便于测试 | 服务时钟 + 可注入测试时钟；禁止直接 `time.Now()` 散落 |
| 状态存储 | 进程内 `Map`/数组 | PG 表 + Redis 缓存；进程重启不丢状态 |
| 超时/升级 | 调用方显式调用 `escalateOverdue` | 分布式调度器扫描 + 幂等升级（`escalationLevel`） |
| 审计 | `onAudit` 回调 | outbox → Kafka → 审计存储，失败可重放 |
| ID | 调用方传入/简单生成 | 雪花/号段 + 业务前缀（`tkt-`/`neg-`/`msg-`） |
| 对象冻结 | `Object.freeze` 防误改 | 值对象/不可变结构约定 + DB 约束 |
| 错误传播 | 自定义 Error 子类带 `code` | gRPC status + 业务 code 映射表（与契约错误码一一对应） |

## 18. v2 修订：消息内核从 IM PaaS 改为自托管（R4）

> 本节**推翻 §10 的结论**，并冻结为 v2 决策。原文不删除，保留「为什么当初选 PaaS」的证据链；评审以本节为准。
> 三个不变的前置事实：①关系链/账本/审批/协商仍全部自有；②**离线推送仍采购厂商通道**（APNs/国内厂商推送，资质与报价 ⚠ 需复核）——推翻的不是推送，是会话模型；③Kafka 仍只做审计/outbox，Redis 仍只做限流/序号加速，二者不进入消息扇出主路径。

### 18.0 决议摘要

| 项 | v1（原） | v2（新） |
|---|---|---|
| L3 消息内核 | 腾讯云 IM PaaS | WuKongIM 形态自托管（Go 内核 + 频道模型 + 自研业务层） |
| Agent 通道 | 内部 gRPC 协商 + PaaS 人类通道两条 | 同一消息内核内**频道类型隔离**（`CHANNEL_TYPE`），物理通道收敛为一条 |
| 未读语义 | PaaS 会话未读 | 频道类型决定（`AGENT_NEGOTIATION` 人类未读恒 0、`CMD` 不计未读） |
| 内容审核 | 厂商通道审核 | **自有审核链路**（责任不外包），规则版本/命中/复核/申诉全留证 |
| PaaS 角色 | 主路径 | 过渡通道 + 4 周回滚窗口 + 降级兜底 |

### 18.1 决策对比（三选一）

| 候选 | 结论 | 采用/保留理由 | 否决理由 | 切换/反转触发 |
|---|---|---|---|---|
| **腾讯云 IM PaaS**（v1 结论） | ❌ 主路径否决；保留适配器 | 长连接/多端同步/推送成熟，国内送达与合规资质齐全；作为 Phase0 现状与回滚通道 | ①会话模型以「人」为一等公民，Agent 拿不到独立在线/订阅/会话语义；②未读以会话为单位，无法表达 `AGENT_NEGOTIATION` 恒 0 未读与 `CMD` 不计未读；③自定义消息是不透明 payload，服务端无法按 `MESSAGE_KIND` 强制 `stored`/投递/持久化；④审核是通道黑盒，不能作为「平台已尽审核义务」的证据链；⑤回调不可重放，签名审计要做双份账 | 见 §18.7 R1–R3、R5 |
| **自研 Go 长连接网关（从零）** | ❌ 否决（形态上） | 完全自控 | 连接保活/弱网/多端同步/扇出是商品化工程，从零写 ≈ 再养一个 IM 团队；Phase0 人力应投 Agent 治理（v1 结论仍成立） | 若开源内核路线在 W2 许可/安全评审被否，转「自研形态」+8 周（**不回 PaaS**） |
| **WuKongIM 形态自托管**（Go 内核 + 频道模型，业务层自研） | ✅ 采用 | 频道/成员/类型化刚好承载契约 §14 语义；消息主路径不依赖 Kafka/Redis（⚠ 需复核官方文档），架构更短；代码可 fork，演进风险自担 | — | 见 §18.7；成本/可用性/许可三条硬阈值 |

### 18.2 为什么 v1 的 PaaS 结论被推翻（假设失效点）

| # | v1 假设（见 §10） | v2 新增需求（契约 §11–§16） | 是否仍成立 | 后果 |
|---|---|---|---|---|
| 1 | 通道只跑「人可见消息」，Agent 走独立 gRPC | Agent 成为一等客户端（§15）：独立连接/在线/订阅 | 失效 | PaaS 给不了 Agent 干净的 presence 与订阅语义 |
| 2 | 「协商物理隔离」= 不碰 L3 | 频道类型化（§14）：协商是**同一内核里人类未读恒 0 的频道**，不是另一套系统 | 失效 | 两套通道仍会互相污染未读/会话列表/推送配额 |
| 3 | PaaS 自定义消息够用 | 消息类型决定存储/投递/未读（§14 冻结） | 失效 | PaaS 只保证「送达不透明 payload」，语义在客户端，服务端不可强制 |
| 4 | 审核不归通道管 | 内容审核责任不能随通道外包（§18.4） | 失效 | 证据链、规则版本、命中记录必须自有 |
| 5 | 通道成本可接受 | Phase2 50 万 DAU、人均 60 条/日（[01 §5.1](./01-总体架构.md)，⚠ 规划值） | 待验证 | 见 §18.5 TCO 公式与 R1 |
| 6 | `IMChannel` 抽象足够迁移 | 迁移目标从「厂商 A→B」变成「PaaS→自有内核」 | 部分失效 | 抽象面保留，但迁移工作量与验证面更大（§18.6） |

### 18.3 P99 预算重算（审批卡片推送 ≤2s，口径 [01 §5.2](./01-总体架构.md)）

| 环节 | v1 PaaS 预算 | v2 自托管预算 | 说明 |
|---|---|---|---|
| 事件产生 → orchestrator（内网 gRPC） | 120 ms | 120 ms | 不变 |
| `CapabilityGate` 判定 | 15 ms | 15 ms | 不变 |
| `ApprovalTicket` 落库（PG 同步提交） | 80 ms | 80 ms | 不变 |
| outbox → Kafka 投递 | 50 ms | 50 ms | 不变 |
| 审批消费者 → 卡片构造 | 100 ms | 100 ms | 不变 |
| L3 入口（v1 厂商 API 接收 / v2 网关鉴权+路由） | 300 ms | 60 ms | 自托管省掉外部 API |
| 内核处理（v1 厂商内部 / v2 频道扇出） | — | 40 ms | 新增；规划预算 |
| 通道 → 端侧（v1 厂商 / v2 WS 帧，前台） | 700 ms | 350 ms | 规划预算，⚠ 需弱网实测 |
| 端侧渲染可交互 | 150 ms | 150 ms | 不变 |
| 抖动/重试余量 | 485 ms | 1035 ms | 回流 550 ms，覆盖重连/GC/跨城 |
| **合计** | **2000 ms** | **2000 ms** | 同 SLO，不放松 |

**结论**：厂商路径的 1000 ms（300+700）被替换为 450 ms 规划预算（60+40+350），余量从 485 ms 提升到 1035 ms；但这只是**预算分配，不是实测**。v2 起新增两条监控 SLO（均为规划值，⚠ 压测校准）：在线 Agent WS 消息端到端 P99 ≤ 500 ms（同城）；内核连接建立 P99 ≤ 300 ms。后台/锁屏仍只承诺「到达」，不承诺 2s（沿用 [01 §5.2](./01-总体架构.md) 口径）。

### 18.4 合规影响：内容审核不能外包给 PaaS

| 项 | PaaS 模式（v1） | 自托管（v2） | 结论 |
|---|---|---|---|
| 审核责任 | 通道审核结果是黑盒，无法导出完整证据链 | 规则版本/模型版本/命中记录/人工复核/申诉全链路自有 | 自托管更可自证 |
| 证据与取证 | 依赖厂商后台与工单截图 | 可验证签名链（契约 §16）+ 检查点 | 可用于监管/司法举证 |
| 数据驻留 | 受厂商区域与私有化排期约束 | 自有地域/单元化部署 | 更可控 |
| 留存执行 | 依赖厂商留存策略 | 自有 `gov.audit_entries`/`gov.audit_checkpoints` + 对象存储（[05 §15](./05-数据模型与存储.md)） | 法定保留可执行 |
| 成本 | 含在通道费内 | 审核系统 + 人审队列自建（[10](./10-风险与验收登记册.md) R-14） | 需新增人力/预算 ⚠ |

> **红线**：审核结论必须由自有链路产出并可复核。可以采购第三方「审核能力」（模型/词库/人审外包），但**审核责任、规则版本与留证不能随通道外包**。等保三级、生成式 AI 服务备案、未成年人保护的具体适用条款 ⚠ 需法务复核，不在本文下结论。

### 18.5 运维成本（结构，不给报价）

| 项 | PaaS（v1） | 自托管（v2） | 差异与说明 |
|---|---|---|---|
| 长连接节点 | 无 | 连接数由 **Agent 在线率主导**（人类 1 条 + 每用户 3–8 个 Agent 连接），估算模型见 [11 §7.2](./11-AI原生IM架构-v2.md)，单节点连接上限 ⚠ 需压测 | 新增机器与弹性伸缩 |
| 消息存储 | 厂商侧 | 自有 PG/对象存储（与 `messages_meta` 同期） | 存储量按 [01 §5.4](./01-总体架构.md) 估算 |
| 推送 | 厂商推送通道（含在 PaaS） | **仍需采购** APNs/国内厂商推送 | 本项不变，别误算成「全省」 |
| 审核 | 通道审核 | 自有审核系统 + 人审队列 | 新增人力与合规成本 |
| 值守 | 0.25 SRE（对接厂商） | 1.0–1.5 SRE（内核 + 推送 + 审核） | 人力是主要增量 |
| 采购 | 通道费（按 MAU/日消息，⚠ 报价） | 机器 + 带宽 + 推送通道费 | 需 3 年 TCO 比价 |

**TCO 决策公式**：`自托管 3 年 TCO = 机器 + 带宽 + 推送通道费 + 审核系统 + 人力（1.5 FTE × 3 年）`；与 PaaS 3 年报价比较：目标 ≤ 80% 时维持自托管；> 120% 触发 §18.7 R1（数字是阈值，不是报价，⚠ 采购复核）。

### 18.6 迁移步骤（主线与 [11 §6.3](./11-AI原生IM架构-v2.md) 对齐，可回滚）

| 步 | 周 | 动作 | 回滚点 |
|---|---|---|---|
| M0 | W+1 | 冻结契约 R4；v2 六模块单测跑通（不碰 v1 路径） | 不动 v1 路径 |
| M1 | W+1–W+2 | 身份与签名审计接入本地 Demo（**不碰消息路径**） | 关掉 v2 装配层即回 v1 |
| M2 | W+2–W+4 | Agent 外部动作全部改走 `AgentGateway`（v1 Skill 调用收口） | 保留旧调用点开关一个版本 |
| M3 | W+4–W+6 | 新增频道/会话层；协商从独立通道迁入 `AGENT_NEGOTIATION`；`DIRECT` 先双写 | 双写期可只读 v1 |
| M4 | W+7–Phase1 灰度 | 自托管内核替换 PaaS（生产 Go 网关）；PaaS 保留为人类消息回退通道 | 一个版本内可切回 PaaS（窗口 ≥4 周） |
| M5 | Phase2 末 | 下线 PaaS 适配器（需连续 8 周无回滚且成本达标） | 不可逆，需 Gate |

**迁移铁律**：双写期间只允许内核写审计、只允许 PaaS 写未读，避免两套未读打架；切换以「用户」为单位而非「消息」为单位，否则未读一致性无法保证。审批卡片 P99 ≤2s 的口径与 [11 §7.5](./11-AI原生IM架构-v2.md) 一致：内核 hop 不增加端到端预算，省下的厂商路径预算回流到抖动余量（§18.3）。

### 18.7 反转触发条件（可观测，评审只谈阈值）

| 编号 | 条件（均为可观测指标） | 动作 |
|---|---|---|
| R1 成本 | 自托管 3 年 TCO > PaaS 3 年报价 × 120%（报价 ⚠ 采购复核） | 回 PaaS；内核只保留 Agent 频道 |
| R2 可用性 | 连续 2 个自然月：消息可用性 < 99.9%，或在线 P99 > 1s，或推送到达 P99 > 3s（=2s 预算 × 150%） | 回 PaaS 或双活 |
| R3 运维 | 单季 P0/P1 事故 > 2 次且 MTTR > 30 min；或内核 SRE > 2 FTE 仍不达标 | 回 PaaS |
| R4 合规 | 自建审核无法通过等保/监管检查，或人审成本 > 预算 150% | 审核能力改采购（责任仍自有），内核保留 |
| R5 规模 | DAU < 5 万且峰值连接 < 2 万，连续 2 个季度 | 回 PaaS（规模不经济） |
| R6 许可/安全 | 开源内核许可或供应链安全评审不通过（复核对象：官方仓库 LICENSE、依赖清单、安全公告） | 转自研形态（+8 周），**不回 PaaS** |
| R7 上游停滞 | 上游连续 6 个月无 release / 无安全响应（⚠ 官方仓库 release 记录） | 冻结 fork 自维护；或按 R1 回 PaaS |

> 反转不是失败：**账本/关系链/审计永不自外迁**（v1 D4 的不变量保留）。PaaS 回滚只回退「通道与会话模型」，不回退治理数据。

## 19. v7 修订：Phase0–1 底座回到 IM PaaS + 适配层（R10）

> 一句话：**§18 的「自托管内核」结论被 Phase 决策覆盖**，但**不删除**——保留为决策审计记录（技术理由未被证伪，改变的是优先级）。**评审以本节为准**。
> 三个不变：①关系链/信任/账本/审批/审计仍全部自有；②离线推送仍采购厂商通道；③Kafka 仍只做审计/outbox，Redis 仍只做限流/序号加速。
> 完整的三条路线、反转代价与逐条补偿见 [17](./17-三条路线与分层决策.md)；契约侧机制见 §31（适配层）与 §32（陌生 Agent 审批挂起）。

### 19.0 决议（覆盖 §18）

| 项 | §18（v2，R4） | §19（v7，R10，当前） |
|---|---|---|
| L3 消息底座 | WuKongIM 形态自托管内核 | **Phase0–1：腾讯云 IM PaaS + 适配层**；Phase2 评估自研/WKongAI |
| 切换方式 | 迁移步骤 M0–M5（PaaS→内核） | **部署选择**：业务只面向统一 `MessageEvent`，换底座=换适配器（§31） |
| PaaS 角色 | 过渡通道 + 4 周回滚窗口 | **Phase0–1 主底座**；自托管降为 Phase2 备选 |
| 未读/自定义/审核 | 由内核原生保证 | **应用层补偿**（§19.2），PaaS 只做传输 |
| 文档状态 | 保留为审计记录 | 当前口径；§18 中与本表冲突处由本节覆盖 |

### 19.1 反转理由（为什么接受相反结论）

| # | 理由 | 说明 |
|---|---|---|
| 1 | **用户决策：Phase0–1 优先上线速度与合规资质** | Phase0–1 的目标是验证审批态频次与治理闭环，不是验证「我们能不能运维 IM 内核」 |
| 2 | PaaS 的长连接/多端同步/推送/资质成熟 | 这些正是 v1 §10 选 PaaS 的理由；⚠ 报价、配额、私有化能力需复核 |
| 3 | 自托管需要 1.0–1.5 SRE + 数月级工程（§18.5 规划值，⚠ 需复核） | Phase0 团队 6 人，人力应投在隐私/审批/付费这些差异点上 |
| 4 | §18 的技术理由仍然成立 | 未读整形/自定义消息/审核链/回调可重放——只是**在 Phase0–1 用补偿换时间**，不是被证伪 |
| 5 | 反转是「底座可替换」不是「治理回退」 | v2–v6 的身份/频道/可见域/会话/信封/邮箱/委托全部保留（§31 让它们与底座解耦） |

### 19.2 补偿措施（§31 适配层 + 应用层补偿）

| §18 的自托管理由 | PaaS 不提供什么 | 我们怎么办 | 类型 |
|---|---|---|---|
| 频道类型化 / 未读整形 | 未读以会话为单位，无频道类型 | 自有未读投影为准，读侧按类型整形；缺 `UNREAD_SHAPING` → 协商频道只在巡视态可见、不产生未读 | 补偿 + 降级 |
| 自定义消息语义 | 自定义消息是不透明 payload | `MESSAGE_KIND` 放信封 payload，收发走 §31 `normalizeEvent`；`CMD` 应用层不落 `messages_meta`；敏感正文不进 PaaS 字段 | 补偿 + 不做 |
| Agent 成员/独立在线 | 会话模型以人为一等公民 | `AgentSessionRegistry` 与自有路由保留，PaaS 只承载人类可见消息 | 补偿 |
| 审核链自证 | 通道审核是黑盒 | 自有审核链（规则/模型版本/命中/人审/申诉）+ §16 签名审计；**不把 PaaS 后台当证据** | 自研保留 |
| 回调可重放 | 平台回调不可验证/重放 | 每个归一化事件写签名审计 + 日对账；**不承诺平台回调抗篡改** | 补偿 + 不做 |
| 流式回复 | 部分 PaaS 不提供真流式 | 先最终态送达；需要时用分片/SSE；Phase2 自托管再补 | 降级 |
| 审批卡片回调 | 回调能力因平台而异 | 回调只作输入源 → 自有 `ticketId` + `principalUserId`；缺 `CARD_CALLBACK` → 只读通知 | 补偿 + 降级 |

**适配层机制（§31）**：`ADAPTER_CAPABILITY` 六项能力（`UNREAD_SHAPING/CUSTOM_MESSAGE/AGENT_MEMBERSHIP/AUDIT_CHAIN/STREAMING/CARD_CALLBACK`）由适配器**显式声明**；缺能力必须 `CAPABILITY_MISSING`，**不允许假装支持**。`ADAPTER_CODE`：`ADAPTER_UNKNOWN/ADAPTER_EXISTS/CAPABILITY_MISSING/EVENT_INVALID/PLATFORM_ERROR`。

### 19.3 保持不变的铁律

1. **关系链/信任矩阵、账本、审批、审计永不自外迁**（v1 D4 不变量保留）。
2. 离线推送仍采购厂商通道（推翻的不是推送）。
3. Kafka 只做审计/outbox，Redis 只做限流/序号加速，均不进消息主路径。
4. v2–v6 的全部治理模块与契约语义保留；§31 只改变「底座怎么接」，不改变「谁能做什么」。
5. 平台最多 L2（卡片+回调输入），不做治理闭环（[16 §2.4](./16-三层技术栈与平台接入边界.md)）。

### 19.5 代价与明确不做（诚实）

- **代价**：未读/自定义/审核需应用层补偿（多一块代码与一致性校验）；审计证据强度下降（平台回调不可验证）；P99 余量从自托管的 1035ms 缩回 485ms；Phase2 迁移工作量被推迟但未消失（适配器、双轨测试、灰度仍要做）；Phase0–1 双轨维护。
- **明确不做**：不把 PaaS 审核/后台当证据；不把正文/敏感内容放进 PaaS 自定义字段（只放引用/密文）；不承诺平台回调抗篡改；不用平台组织角色映射 `TRUST_LEVELS`。
- **再反转一句话**：当补偿后的体验损失（V1–V4 任一持续超窗）或成本/规模/合规越过阈值（V5–V8），必须把自托管从 Phase2 **提前**，不能等到 Phase2 末。
