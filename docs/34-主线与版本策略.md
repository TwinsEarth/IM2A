## 1. 主线声明（main）

`main` 上现在只有一条实现线：

- **代码**：`apps/im2agent`（7 形态原型：demo/lan/prod/llm/client/admin/acceptance）
- **契约**：`contracts/INTERFACES.md` §1–§52，修订 R1–R24
- **服务层**：`services/*`（orchestrator / payment / messaging / identity / gateway / audit / account / moderation / observability / resilience / persistence / acceptance）
- **测试**：732 项（`node scripts/test.mjs`），一致性验收 134 项（`node scripts/verify.mjs`）
- **发布**：`scripts/release-check.mjs` 6 步门禁；`reports/RELEASE-REPORT.md` 归档
- **版本坐标**：`0.1.3 / R24 / schema 2`，25 个版本 tag（`v0.0.1-demo` … `v0.1.3-fix`）

判定主线的唯一标准：**`GET /api/version` 返回的三元组与 `package.json`、git tag 三者一致**（release-check 会核对）。

## 2. 旧副本封存（legacy/im2a）

原 `main`（commit `e2338a1`，58 文件）是另一条独立实现（`apps/im2a` + v0.2.0 TaskLedger），与主线**历史无关**（无共同祖先）。为避免两条线在同一目录互相覆盖（`package.json`/`scripts/test.mjs`/`services/messaging/*` 同名但语义不同），已按 A 方案合并：

- 合并提交 `fb3db15`：文件树取主线，原 `main` 作为父提交保留；
- 旧副本**完整封存**为：
  - 分支：`origin/legacy/im2a`
  - tag：`legacy-im2a-2026-10-21`

### 2.1 取回旧副本（只读查证）

```bash
# 整棵旧树
git show legacy/im2a:apps/im2a/server.mjs
git ls-tree -r --name-only legacy/im2a | head -20

# 或从 tag
git show legacy-im2a-2026-10-21:README.md

# 需要本地运行旧实现（隔离目录，避免污染主线）
git worktree add ../im2a-legacy legacy/im2a
```

### 2.2 为什么"隐藏"而不是"删除"或"并列"

| 方案 | 问题 |
|---|---|
| 删除旧文件 | 丢掉历史实现与对比价值；不可追溯 |
| 两套并列在 `main` | 同名文件冲突（`package.json`、`scripts/test.mjs`、`services/messaging/*`），CI 与测试入口互相打架 |
| **封存为分支 + tag（采用）** | 主线树干净；历史可随时取回；不产生第二条活跃维护线 |

## 3. 开发与迭代规则（0.1.x）

| 规则 | 判定 |
|---|---|
| 什么算缺陷（可进 0.1.x） | 在**已声明能力内**出错、可复现、修复不需要新依赖/新渠道 |
| 什么算缺口（进 0.2.0） | 从未声明、或需要新依赖/新渠道/新能力（真实短信、实名、机审、支付、Redis、PG…） |
| 版本号 | `0.1.x`；加能力才 `0.2.0`；**不允许只改文档/版本号就发版**（连续两个此类版本 → 停止 0.1.x） |
| 数据 schema | 破坏性变更必须升 `schemaVersion`，并提供 `scripts/migrate-state.mjs` 迁移路径（先备份→原子改写→加载核对→失败回滚） |
| 发布流程 | 分支 → CI 绿 → `release-check` 全绿 → 打 tag → 归档 `RELEASE-REPORT.md` → 推送 |
| 禁止 | 强推 `main`；把 mock 能力写成"已接入"；跳过 CI 直接打 tag |

> 以上判据来自 [docs/32 §5](./32-v0.1.2-缺陷修复与0.1.x停止条件.md)，本文不重复论证。

## 4. 升级 / 迭代的推荐流程

```
1) 从 main 切分支：   git switch -c fix/xxx main
2) 先写复现测试（红灯）→ 修 → 测试转绿
3) 本地门禁：         node scripts/test.mjs && node scripts/verify.mjs
4) 发布检查：         node scripts/release-check.mjs
5) 提交 + 打 tag：    git commit … ; git tag -a v0.1.N-fix -m …
6) 推送 main + tag；归档 reports/RELEASE-REPORT.md
7) 若涉及 schema：   先备份旧数据 → migrate-state 副本 → 启动冒烟 → 对账
```

**回滚**：v0.1.x 的回滚 = 切回上一个 tag（`git switch --detach v0.1.(N-1)-fix`），数据侧用备份 + `restore`（不自动应用，人工确认）。

## 5. 0.2.0 启动条件（硬门槛）

以下**至少满足一条**，否则 0.2.x 不启动（继续 0.1.x 修缺陷或冻结）：

| 资源 | 验收标准 |
|---|---|
| 真实短信供应商 | `G-PROVIDERS` 从 SKIP 变 PASS；OTP 真实到达 |
| 真实实名服务 | 未实名仍拦截；实名只存 hash+尾号；核验流水号入库 |
| 真实机审服务 | 熔断 → `HUMAN_PENDING`；人审可降级；误杀申诉闭环 |
| 真实支付渠道 | 回调验签（渠道证书/非对称）+ 入账幂等 + 日切对账 |
| Linux + 域名 + 证书 | `node scripts/accept.mjs --target https://域名 --require-real-providers` 预检 7/7 |
| 内测名单（20 人） | 协议/隐私/客服话术就绪；备份与恢复演练至少一次 |
