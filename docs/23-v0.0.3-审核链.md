## 1. 版本定义

### 1.1 从「能收钱」到「敢收钱」

| 维度 | v0.0.1/v0.0.2（能收钱） | v0.0.3（敢收钱） |
|---|---|---|
| 付费消息 | 预审（规则层 `EgressGuard`）+ 付费 + 退款窗口 | **审核链前置**：机审 → 人审 → 申诉；结论进审计 |
| 内容风险 | 规则命中即拦；拿不准没有人审队列 | `FLAG` 进人工队列，可申诉改判 |
| 扣费时机 | 付费即扣（在规则通过后） | **审核通过（`canDeliver`）之后才扣费**；被拒/待审不扣费 |
| 举证 | 有审计但无审核版本 | 每条结论绑 `caseId/messageId/ruleVersion/modelVersion/actor/decision` |
| 对内测开放 | 只能“熟人圈 + 规则拦” | 可对**陌生人付费消息**开放（灰度），因为拿不准的有人审兜底 |

### 1.2 三套状态机 / 两个 `VERDICT` 的边界（最容易混，评审必看）

| 名字 | 归属 | 值 | 用途 | 禁止 |
|---|---|---|---|---|
| `TICKET_STATE` | §4 审批引擎 | 九态（`PENDING…COMPLETED`） | **动作审批**（人决定“做不做这件事”） | **禁止**拿来当审核状态；审核不产生审批单 |
| `MODERATION_STATE` | §40 审核链 | `RECEIVED/MACHINE_PASSED/HUMAN_PENDING/APPROVED/REJECTED/APPEALED/APPEAL_GRANTED/APPEAL_UPHELD` | **内容审核**（这条内容能不能发） | 不复用 ticket 状态；不把审核结论写成审批单 |
| `VERDICT`（§7） | `EgressGuard` | `PASS/REVIEW/BLOCK` | 同步前置规则（外发前阻塞） | 不把 `REVIEW` 传给 §40 |
| `VERDICT`（§40） | 审核链机审 | `PASS/FLAG/BLOCK` | 机审结论（决定自动/人审/拒） | 不把 `FLAG` 当成 §7 的 `REVIEW` |
| 争议状态（§39） | 退款争议 | `OPEN/APPROVED/REJECTED` | 钱退不退 | 不和审核状态混用 |

> 一句话：**§7 是“发不发得出去”，§40 是“该不该发”，§4 是“要不要做这个动作”。** 三者串联但状态机各自独立；把审核塞进审批单（或反之）会让「谁在什么阶段拒了什么」无法回放。

### 1.3 依赖与调用顺序（谁先谁后）

```
付费消息提交
  → §40 submit（RECEIVED）
  → 机审 machine(...)
      PASS → APPROVED（记录 rule/model 版本）
      FLAG → HUMAN_PENDING（人审队列）
      BLOCK→ REJECTED（可申诉）
      抛错/不可用 → HUMAN_PENDING（fail-closed）
  → canDeliver(caseId)  ← 唯一闸门
      ok → §37 钱包 charge → §14/§15 投递
      !ok → 不扣费、不投递（等待人审/被拒/申诉）
```

## 2. 审核链

### 2.1 机审三态 → 流转（冻结）

| 机审 `verdict` | 流转 | 是否扣费/投递 | 说明 |
|---|---|---|---|
| `PASS` | `RECEIVED → MACHINE_PASSED → APPROVED` | ✅ 可扣费/投递 | 自动通过也**必须**记录 `ruleVersion/modelVersion/hits` |
| `FLAG` | `RECEIVED → HUMAN_PENDING` | ❌ 等待人审 | 拿不准交人；**不得先扣费** |
| `BLOCK` | `RECEIVED → REJECTED` | ❌ 拒 | 可申诉（窗口内） |
| 机审抛错/不可用 | `RECEIVED → HUMAN_PENDING` | ❌ 等待人审 | **fail-closed**；`MACHINE_UNAVAILABLE` 用于标记“机审不可用”的事实 |

**契约对应**：`machine({ messageId, content, senderUserId })` 返回 `{ verdict, ruleVersion, modelVersion, hits[] }`；`MODERATION_CODE` 八码：`NOT_FOUND / ILLEGAL_STATE / ALREADY_DECIDED / FORBIDDEN / SELF_REVIEW_FORBIDDEN / MACHINE_UNAVAILABLE / APPEAL_WINDOW_CLOSED / CONTENT_REQUIRED`。

### 2.2 fail-closed vs fail-open（反例写清楚）

**反例：fail-open 会造成什么**——机审供应商超时，代码为了“别卡用户”默认 `PASS`：

| 后果 | 具体表现 |
|---|---|
| 内容风险直接放行 | 诈骗/转账话术在机审宕机窗口被放行并扣费投递 |
| 无法申诉/无法追溯 | 已投递的消息没有机审结论，事后无法解释“为什么通过” |
| 资金与内容双风险 | 用户付费后收到违规内容 → 退款 + 客诉 + 监管风险 |
| 供应商故障变成业务故障 | 供应商抖动期间平台“看起来正常”，实则闸门失效 |

**我们的选择**：机审不可用/抛错 → `HUMAN_PENDING`（人审兜底），**绝不自动放行**；宁可慢、不可漏。人审超时按 [08 §2.1](./08-运营客服运维与合规.md) 的「超时自动 BLOCK（宁严勿松）」处理。

### 2.3 人审队列与 SLA（引用 [08 §2.1](./08-运营客服运维与合规.md)）

| 环节 | SLA（既有口径） | 超时兜底 | 本版要求 |
|---|---|---|---|
| 人审初审 | 工作时段 ≤30 分钟 / 夜间 ≤2 小时 | 超时自动 `BLOCK` | 队列可见、按提交时间排序、超时告警 |
| 人审复审（申诉） | 首响 ≤24h / 结论 ≤72h | 超时按“用户胜诉”并记录 | 申诉窗口 `appealWindowMs = 7 天`（契约默认） |
| 审核员操作 | — | — | 每次 `review/resolveAppeal` 写审计（含 note） |

> 内测 20 人也要有人审上限：**队列积压 > 20 单或初审超时率 > 5% 即告警**（⚠ 运营校准）；宁可灰度缩量，不让人审变成 SLA 黑洞。

### 2.4 申诉与改判

| 规则 | 契约 | 说明 |
|---|---|---|
| 谁可申诉 | 仅 `senderUserId` 本人 | 别人不能代申诉 |
| 可申诉状态 | 仅 `REJECTED` / `APPEAL_UPHELD` | `APPROVED` 无需申诉 |
| 窗口 | `appealWindowMs = 7 天`（默认） | 超窗 → `APPEAL_WINDOW_CLOSED` |
| 申诉动作 | `appeal → APPEALED` | 记 reason 与时间 |
| 改判 | `resolveAppeal(GRANT)` → `APPEAL_GRANTED`（可投递） | `GRANT` 后 `canDeliver` 才 ok |
| 维持 | `resolveAppeal(UPHOLD)` → `APPEAL_UPHELD` | 可再次申诉在窗口内 |
| 复审人 | **不得与原审核人相同** → `SELF_REVIEW_FORBIDDEN` | 防“自己推翻自己” |
| 重复决策 | → `ALREADY_DECIDED` / `ILLEGAL_STATE` | 终态不可改 |

## 3. 为什么扣费在审核通过之后

### 3.1 `canDeliver` 是唯一判定

| 场景 | `canDeliver` | 是否扣费 | 是否投递 |
|---|---|---|---|
| `APPROVED`（PASS 或人审通过） | `{ok:true}` | ✅（随后由钱包执行） | ✅ |
| `APPEAL_GRANTED` | `{ok:true}` | ✅ | ✅ |
| `HUMAN_PENDING` | `{ok:false}` | ❌ | ❌ |
| `REJECTED` / `APPEAL_UPHELD` | `{ok:false}` | ❌ | ❌ |
| `RECEIVED/MACHINE_PASSED/APPEALED` | `{ok:false}` | ❌ | ❌ |

> `canDeliver` 是**唯一**放行判定：投递层与钱包层都必须调它；任何“审核模块内部通过、业务层没调”的实现都视为未接入。

### 3.2 先收钱再退 vs 审核后收钱

| 方案 | 客诉 | 账务 | 结论 |
|---|---|---|---|
| 先扣费 → 审核 → 拒了退款 | 用户被扣钱后收到“被拒”，退款走 §37/§39，账务噪音大 | 每笔拒绝都产生 CHARGE+REFUND 两条流水 | ❌ 不采用 |
| **审核 → 通过才扣费** | 用户只会看到“审核中/未通过”，没有资金动作 | 拒绝零流水；争议只发生在“已通过后” | ✅ 采用（本版） |

**与既有模块的关系**：§9 付费消息状态机不改语义；本版只把「审核通过」插在「扣费」之前。`§39` 的退款争议仍只处理“已投递/已回复”的情况；审核拒绝不进入退款争议链路。

## 4. 审计留痕

### 4.1 每条结论必须绑的字段（契约不变量⑨）

| 字段 | 来源 | 用途 |
|---|---|---|
| `caseId` | `submit` 生成 | 审核案卷主键 |
| `messageId` | 付费消息 | 与扣费/投递/争议对齐 |
| `ruleVersion` | 机审返回 | 规则可回放（规则改了能解释当时结论） |
| `modelVersion` | 机审返回 | 模型可回放 |
| `hits[]` | 机审返回 | 命中项（可审计，不暴露给用户全文） |
| `actor` | 人审/复审操作人（机审为 `machine`） | 追责 |
| `decision` | `APPROVE/REJECT/GRANT/UPHOLD` + `note` | 结论与理由 |
| `at` | clock 注入 | 时间线 |

### 4.2 审核日志 vs 签名审计

| 层 | 存什么 | 给谁看 | 与 §16 的关系 |
|---|---|---|---|
| 业务审核日志 | case 全字段、命中、note、队列操作 | 审核员/运营后台 | 可查询、可导出 |
| **签名审计（§16）** | 每次迁移的摘要事件（`caseId/messageId/版本/actor/decision` + `contentHash`） | 合规/争议/执法 | **证据链**：不可篡改、可验签 |

> 内容正文**不进签名链**（体积与隐私），只进 `contentHash`/引用；链上能证明“谁在何时根据哪个规则版本做了什么决定”，正文按 [08 §9](./08-运营客服运维与合规.md) 的留存期单独保管。

### 4.3 一次 case 的完整回放

`submit`（RECEIVED）→ 机审（verdict + 版本）→ 人审（HUMAN_PENDING → APPROVED/REJECTED）→ 申诉（APPEALED）→ 改判（APPEAL_GRANTED/UPHELD）→ `canDeliver` → 扣费/投递。每一步都有 `at/actor/decision`，可按 `caseId` 或 `messageId` 回放。

## 5. 验收 Gate C1–C6

| # | 验收项 | 判定标准（可执行） | 验证命令 | 本机状态 |
|---|---|---|---|---|
| C1 | **PASS 自动放行** | 机审 `PASS` → `APPROVED`；`canDeliver` ok；记录 rule/model 版本 | `node scripts/test.mjs --filter=moderation` | ⚠ 实现落地中 |
| C2 | **FLAG 转人审且不扣费** | `FLAG` → `HUMAN_PENDING`；`canDeliver` false；钱包无 CHARGE | `--filter=moderation` + 钱包断言 | ⚠ 实现落地中 |
| C3 | **BLOCK 自动拒且不扣费** | `BLOCK` → `REJECTED`；`canDeliver` false；无 CHARGE | `--filter=moderation` | ⚠ 实现落地中 |
| C4 | **机审抛错 → HUMAN_PENDING** | `machine` 抛错/不可用 → `HUMAN_PENDING`（fail-closed），**绝不 APPROVED** | `--filter=moderation` | ⚠ 实现落地中 |
| C5 | **申诉 GRANT 后可投递** | `REJECTED` → `appeal` → `APPEALED` → `resolveAppeal(GRANT)` → `APPEAL_GRANTED`；`canDeliver` ok | `--filter=moderation` | ⚠ 实现落地中 |
| C6 | **原审核人不得复审自己的案子** | `resolveAppeal` 的 `actorUserId` 等于原审核人 → `SELF_REVIEW_FORBIDDEN` | `--filter=moderation` | ⚠ 实现落地中 |

**Gate 规则**：C1–C6 全过才允许对陌生人付费消息开放；任一 ⛔ → 不开放；⚠ 必须有目标机/供应商沙箱补测记录。

**反例（看起来通过的三处）**：

1. **「FLAG 转人审」**：只测状态不算——必须断言**钱包没有扣费**（C2 的账务侧）。
2. **「机审抛错」**：只测抛错不算——必须断言状态是 `HUMAN_PENDING` 而非 `APPROVED`（C4）。
3. **「申诉改判」**：只测 GRANT 不算——必须测**原审核人复审被拒**（C6）与超窗 `APPEAL_WINDOW_CLOSED`。

## 6. 运营手册

### 6.1 人审 5 步

| 步 | 动作 | 必须留的证据 |
|---|---|---|
| 1 接单 | 从队列取 `HUMAN_PENDING`，按提交时间（FIFO） | 接单时间/审核员 |
| 2 取证 | 看内容 + 机审 `verdict/hits/ruleVersion/modelVersion` | 命中项快照 |
| 3 判定 | 按 [08 §2](./08-运营客服运维与合规.md) 标准判 `APPROVE/REJECT` | 理由 note |
| 4 回填 | `review({caseId, actorUserId, decision, note})`；写审计 | 决策 + 时间 |
| 5 通知/移交 | 通过 → 进入扣费/投递；拒绝 → 告知可申诉；重大违规 → 移交 L4 | 通知记录/移交单 |

### 6.2 误杀申诉处理

- 申诉只对发送者开放，窗口 7 天；复审人不得是原审核人（`SELF_REVIEW_FORBIDDEN`）。
- 误杀判定：复审 `GRANT` 即计入**误杀率**（[08 §2.3](./08-运营客服运维与合规.md) 目标 ≤0.5% 机审误杀）；每周抽样复盘规则。
- 申诉期间不扣费、不投递；`GRANT` 后才进入扣费/投递。

### 6.3 灰度策略

| 阶段 | 范围 | 目的 |
|---|---|---|
| G0 | 仅陌生人付费消息（20 人内测） | 高风险场景先审；熟人消息不打扰 |
| G1 | 陌生人来意 + 协商摘要 | 观察人审吞吐 |
| G2 | 全量付费消息 | 指标达标后放开 |

**指标**：机审误杀率、人审超时率、申诉推翻率、C2/C3 的“未扣费”比例（应 100%）。

### 6.4 审核员权限与轮班

| 项 | 规则 |
|---|---|
| 最小权限 | 审核员只能看案卷、做 `review/resolveAppeal`，不能改账本/用户数据 |
| 双人复核 | L3/L4 处罚与大额争议必须双人复核（操作留痕） |
| 抽查 | 每周抽查已审 case ≥10%（⚠ 运营定），错误回训 |
| 轮班 | 工作时段/夜间两档覆盖 [08 §2.1](./08-运营客服运维与合规.md) SLA；交接班有队列快照 |
| 离岗 | 账号停用 + 权限回收 + 审计 |

## 7. 风险

### 7.1 误杀率与体验

- 目标引用 [08 §2.3](./08-运营客服运维与合规.md)：机审误杀 ≤0.5%、人审误判 ≤2%、漏放 ≤0.1%（重大违规 0）。
- 处置：`FLAG` 不直接拒（给人审机会）；申诉 GRANT 计入误杀；规则/模型版本可回滚。

### 7.2 人审吞吐（内测 20 人也要有上限）

- 风险：内测小样本也会出现集中提交 → 队列积压 → 付费体验崩塌。
- 处置：队列积压 >20 单告警；初审超时率 >5% 缩量灰度；超时自动 `BLOCK`（宁严勿松，[08 §2.1](./08-运营客服运维与合规.md)）。

### 7.3 审核员滥用

- 风险：随意 `APPROVE`、打击报复、私下收费放行。
- 处置：双人复核 + 抽查 + 全员审计 + 权限最小化；`SELF_REVIEW_FORBIDDEN` 只是底线，不是全部。

### 7.4 机审供应商锁定

- 风险：机审以供应商 SDK/私有协议接入 → 换供应商=重写。
- 处置：`machine` 是**注入接口**（返回 `verdict/ruleVersion/modelVersion/hits`），业务不感知供应商；规则/模型版本必须由我方统一编号；换供应商需重跑基线集并保留旧版本可回放。

### 7.5 其他

| 风险 | 处置 |
|---|---|
| 审核延迟卡付费 | 状态可见（“审核中”）；SLA 告警；不扣费 |
| 内容泄露 | 审核员最小权限；内容访问审计；不把正文写进签名链 |
| 审核规则变化不可解释 | `ruleVersion` 随结论落库；规则变更需版本号 |
| 供应商故障 | fail-closed → HUMAN_PENDING；不静默放行 |

## 9. 一页速查

### 9.1 审核链一张图（文字版）

`submit → 机审(PASS/FLAG/BLOCK/异常) → APPROVED / HUMAN_PENDING / REJECTED → 人审(APPROVE/REJECT) → 申诉(APPEALED) → GRANT/UPHOLD → canDeliver → 扣费 → 投递`

### 9.2 评审检查清单（6 条）

- [ ] 三套状态机是否真的分开：`MODERATION_STATE` 没有被塞进 `TICKET_STATE`。
- [ ] 两个 `VERDICT` 是否分开：`REVIEW`（§7）与 `FLAG`（§40）没有互相传值。
- [ ] 所有付费入口是否都调 `canDeliver`（不是只在审核模块里调）。
- [ ] 机审抛错是否 `HUMAN_PENDING`（fail-closed），没有默认 `PASS`。
- [ ] C2/C3/C4 是否都断言了「不扣费」。
- [ ] 申诉复审人是否校验了 `SELF_REVIEW_FORBIDDEN`；超窗是否 `APPEAL_WINDOW_CLOSED`。

### 9.3 内测客服三句话

1. **审核中**：付费消息会先审核；通过才扣费，未通过不扣钱。
2. **被拒**：可以在 7 天内申诉；我们会换人复审，不会由原审核人自己改。
3. **审核时长**：工作时段一般 30 分钟内；夜间可能到 2 小时，超时会按规则处理。

### 9.4 v0.0.3 不是什么

- 不是「自动裁决」：`FLAG` 必须人审，模型不能代替人做最终内容判决。
- 不是「替代审批引擎」：§4 的动作审批仍在，审核只管“内容能不能发”。
- 不是「替代 EgressGuard」：§7 仍是同步前置规则，§40 是审核链；两者串联，不互相替代。
