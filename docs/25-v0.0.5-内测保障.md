## 1. 版本定义

### 1.1 不加功能，只加保障

| 维度 | v0.0.4（能运营） | v0.0.5（有保障） |
|---|---|---|
| 外部依赖故障 | 能看到失败率/告警，但请求可能卡超时 | **熔断快速失败 + 显式降级**，不雪崩、不假装成功 |
| 数据损坏/误删 | 有账本与审计，但没有可演练的备份 | **每日备份 + sha256 验签 + 恢复演练** |
| 用户沟通 | 客服各自发挥 | **统一三句话 + 分级升级路径** |
| 协议/隐私 | 有隐私政策草案 | **内测协议要点补齐**（计费/审核/实名/数据权利） |

**明确不做**：不新增付费功能、不改审核状态机、不改钱包语义；不接真实支付渠道；不做多地域容灾（⛔ Phase2）；不做自动恢复线上（见 §4.3）。

### 1.2 依赖与开关

| 依赖 | 契约模块 | 失败时的默认姿势 |
|---|---|---|
| 短信通道 | §38 `sms-provider` + §43 `ProviderGuard` | 快速失败 + 备用通道/人工协助（限白名单） |
| 实名核验 | §36 `account.realName` + §43 | 拒绝新用户开付费（`REALNAME_REQUIRED` 语义不变） |
| 机审 | §40 `moderation.machine` + §43 | **fail-closed → `HUMAN_PENDING`** |
| 数据文件 | §44 `BackupService` | 停写 → 验签 → 演练恢复 → 对账 |

## 2. 外部依赖降级矩阵

> 原则：**降级不是“假装成功”**，而是“明确告诉用户现在不行 + 给出替代路径 + 留下证据”。任何降级都必须标 `usedFallback:true` 与 `causeCode`（§43 不变量③）。

| 依赖 | 不可用时表现 | 降级动作 | 用户提示 | 告警 | 是否阻断付费 |
|---|---|---|---|---|---|
| **短信通道** | 新用户注册/登录收不到 OTP；`sendOtp` 抛 `SMS_FAILED/SMS_TIMEOUT/PROVIDER_UNAVAILABLE` | ①备用通道（第二供应商，人工切换+审计）；②人工协助（仅白名单内测用户，双人确认+审计）；③已登录用户**不受影响**（session 有效） | “验证码发送失败，请稍后重试或联系客服” | 短信失败率 >10% WARN；熔断 `OPEN` >10min 升级 P1 | **否**（只影响新登录；已登录用户的付费不阻断） |
| **实名核验** | 新用户 `verifyRealName` 失败/超时；`REALNAME_REJECTED` 或服务不可用 | 禁止“先开后补”；可走人工核验（双人复核+审计）作为替代通道；**未核验通过一律 `REALNAME_REQUIRED`** | “实名认证服务暂不可用，请稍后再试” | 实名失败率/熔断 OPEN WARN | **是**（未实名新用户不能开付费） |
| **机审** | `machine` 抛错/超时/不可用 | **fail-closed → `HUMAN_PENDING`**（转人审），绝不放行；人审队列承压 | “审核中，请稍候” | 机审失败率 >10% WARN；人审积压 >20 WARN | **是**（审核通过前不扣费） |
| **三方都挂** | 登录/实名/审核均不可用 | **只读模式**：已登录可看历史/审批状态，不能发付费消息、不能新注册 | “系统维护中，暂时只能查看” | CRITICAL（P0/P1，视影响面） | **是**（全部暂停） |

### 2.1 为什么这些“阻断”是正确的

- **短信挂但不阻断老用户**：付费能力依赖的是 session 与实名状态，不依赖“再收一次验证码”；把老用户一起停掉是过度降级。
- **实名挂必须阻断新付费**：没有实名就没有可追责主体（[21 §4](./21-v0.0.1-产品版范围与验收.md)）；“先开后补”会让付费争议立不住，也违反合规底线。
- **机审挂必须转人审而不是放行**：fail-open 会让违规内容在故障窗口被扣费投递（[23 §2.2](./23-v0.0.3-审核链.md) 的反例），且无法事后举证。
- **三方都挂只读**：保留“看”的能力（用户能确认自己的钱与状态），关闭“写”的能力（避免新增不可对账的状态）。

### 2.2 降级决策树（值班按顺序判断）

1. **这个依赖是否在付费主链上？** 是 → 继续；否 → 可局部降级（如短信走备用）。
2. **有没有“明确声明”的 fallback？** 有 → `ProviderGuard` 走 fallback 并标 `usedFallback`；没有 → `NO_FALLBACK`，直接按矩阵阻断。
3. **降级后的数据还能对账吗？** 能 → 降级继续；不能（例如“先开后补”）→ **宁可阻断**。
4. **是否会影响已登录/已付费用户？** 会 → 优先只读而不是全停；不会 → 按依赖矩阵阻断新动作。

> 顺序不能反：先看“钱/对账”，再看“体验”。**不能对账的降级一律不做。**

## 3. 熔断语义与值班

### 3.1 `CLOSED / OPEN / HALF_OPEN` 怎么读

| 状态 | 含义 | 行为 | 值班动作 |
|---|---|---|---|
| `CLOSED` | 正常 | 请求打主方；连续失败累计 | 无需动作；看失败率 |
| `OPEN` | 熔断 | `execute` 直接抛 `GuardError(CIRCUIT_OPEN)`，**不调用主方**（快速失败，避免雪崩） | 切换备用/降级；`OPEN` 超 **10 分钟**必须人工介入 |
| `HALF_OPEN` | 半开探测 | **只允许一次探测**；成功 → `CLOSED`，失败 → 重新 `OPEN` 并重置冷却 | 盯探测结果；连续失败 → 保持降级 |

**契约参数**：`failureThreshold = 3`、`cooldownMs = 30_000`；`ProviderGuard.execute(args)` 返回 `{ value, provider:'primary'|'fallback', usedFallback, causeCode }`；`stats()` 提供 `state/failures/successes/openedAt/lastError`。

### 3.2 `usedFallback` 为什么必须标记

| 不标记会怎样 | 具体后果 |
|---|---|
| 用户不知道走了备用通道 | 备用通道更慢/更贵/更不可靠，用户按主通道预期投诉 |
| 指标失真 | 备用成功率被算进主通道，无法判断主方是否恢复 |
| 审计断链 | 事后无法回答“这次为什么慢了/贵了/失败了” |
| 静默降级 | 主方已挂但无人处理，直到备用也挂 |

`causeCode` 必须带**两个原因码**（主方失败 + 备用失败）当两者都失败时，返回 `FALLBACK_FAILED`；未声明 fallback → `NO_FALLBACK`；配置错误 → `INVALID_CONFIG`。**任何情况都不得静默返回空值。**

### 3.3 必须人工介入的情形

| 信号 | 阈值（建议 ⚠） | 动作 |
|---|---|---|
| `OPEN` 持续 | >10 分钟 | 值班切换备用/降级，通知依赖 owner |
| 半开连续失败 | ≥3 个冷却周期 | 判定主方未恢复，保持降级并升级 |
| 主备都失败 | 任一请求 | `FALLBACK_FAILED` → 进入只读/阻断（按 §2 矩阵） |
| 降级频率 | 1 小时内 >5 次 | 判定“抖动”，按故障处理 |

### 3.4 与 docs/24 告警的联动

- 熔断迁移与降级写**签名审计**（§43 不变量⑤），同时 `inc()` 计入 §41 指标（如 `OTP_FAILED`）。
- 五条**默认**告警规则不改；在 §41 的**自定义 rules** 里增加一条 `provider_guard_open > 10min`（WARN/P1），不覆盖默认规则。告警动作仍由值班按本手册执行（不自动停服）。

### 3.5 熔断与重试的边界（别把熔断做成雪崩）

| 规则 | 说明 |
|---|---|
| 重试必须有界 | 依赖层重试 ≤2 次、指数退避；重试耗尽才计一次失败，避免“重试放大失败数” |
| 只重试幂等请求 | 发短信/机审可重试；扣费/退款不得因超时盲目重试（靠幂等键，不靠重试） |
| 熔断优先于重试 | `OPEN` 状态直接快速失败，**不再重试**（否则熔断形同虚设） |
| 半开只探测一次 | 防止恢复瞬间被流量打垮（§43 不变量②） |
| 降级也不能无限重试 | fallback 失败 → `FALLBACK_FAILED`，立即按矩阵阻断并告警 |

## 4. 备份与恢复演练

### 4.1 备份策略（内测 `jsonfile`）

| 项 | 建议 | 说明 |
|---|---|---|
| 频率 | **每日全量** + 关键操作前手动 `create({label})` | 内测数据量小；手动备份用于“改配置/灰度前” |
| 保留 | `keep = 5`（契约默认） | `rotate()` 只留最近 5 份，**不删最新** |
| 校验 | 每份带 `sha256`；恢复前 `verify` | 篡改/损坏 → `HASH_MISMATCH` |
| 存放 | 与数据目录分离 + 对象存储/另一台机器 | 防同盘损坏（⚠ 运维落地） |
| 边界 | **仅文件级**（jsonfile/快照） | **PostgreSQL 备份走数据库自身机制**（`pg_dump`/WAL/PITR），不在本模块范围 |

### 4.2 恢复 5 步（演练也必须按这 5 步）

| 步 | 动作 | 出口标准 |
|---|---|---|
| 1 **停写** | 进入只读/维护模式（禁止新扣费/新审核/新注册） | 写入口关闭，有审计 |
| 2 **取备份** | 选最近一份 `verify` 通过的备份 | `verify({file}) → {ok:true}` |
| 3 **验签** | `restore({file})` 会先 verify；失败抛 `HASH_MISMATCH` | 失败即停止，不“尽力恢复” |
| 4 **演练恢复** | 恢复到**独立目录/临时实例**，先看数据完整性 | 演练环境可读、审计链可验 |
| 5 **对账** | 账本/钱包/审计与备份时点比对；差异进“待查池” | 差异有清单、有 owner、不改账 |

> **为什么 `restore` 不自动应用**：恢复=**状态切换**，不是“读文件”。自动应用会：①覆盖停写前的合法新数据；②造成与账本/审计的双写或断链；③让“谁在何时决定回滚”无记录。契约因此规定 `restore` **只返回数据**，切换由人工决定并写审计。

### 4.3 RPO / RTO 建议值（⚠ 需复核）

| 指标 | 建议值（内测） | 依据/说明 |
|---|---|---|
| RPO | **≤24h**（每日全量）；关键操作前手动备份 → ≤1h | 内测数据量小；真实用户资金相关应更严（⚠ 财务/法务） |
| RTO | **≤2h**（从停写到恢复可读） | 20 人内测；依赖人工演练熟练度 |
| 演练频率 | **每两周 1 次**（含一次“篡改备份”负例） | 不演练=没有备份 |

### 4.4 PostgreSQL 迁移后的边界变化

- `backup.mjs` 只覆盖文件级；迁移 PG 后：**备份能力来自数据库**（全量 + WAL/PITR），本模块不再是主备份路径。
- 迁移当天必须做一次 **PG 恢复演练**；RPO/RTO 重新评估；审计/账本的不变性验证从“文件 hash”换成“数据库约束 + 审计链验证”。
- 迁移前：`backup.mjs` 仍是唯一可演练的备份（内测阶段）。

### 4.5 备份内容清单与排除项

| 类别 | 是否进备份 | 说明 |
|---|---|---|
| `jsonfile` 业务数据（账户/钱包/审核/争议） | ✅ | `BackupService.create` 的对象 |
| 审计链快照 | ✅（随 store 或独立导出） | 恢复后必须能验链 |
| 账本快照 | ✅ | 对账基准 |
| 配置（非敏感） | ✅ | 便于恢复后对齐规则/版本 |
| **密钥/凭证/`.env`** | ❌ | 走 KMS/密钥管理，**不得进备份文件** |
| 真实证件明文 | ❌ | 本来就不存（§36） |

**检查表**：备份文件是否含 PII/凭证（否）→ `sha256` 是否记录 → 是否异地/分离存放 → 最近一次 `verify` 时间 → 最近一次恢复演练时间。

| 降级告知 | 服务不可用/只读时通过站内/短信/客服告知；不承诺“必达/必审完” | 与 §2 用户提示一致 |

### 5.1 协议不得包含的“过度承诺”

| 不要写 | 原因 | 改写为 |

## 6. 验收 Gate E1–E6

| # | 验收项 | 判定标准（可执行） | 验证命令 | 本机状态 |
|---|---|---|---|---|
| E1 | **短信挂不阻断老用户** | 模拟短信 provider `OPEN`/失败：已登录 session 仍可查看/付费；新 OTP 请求明确失败（`SMS_FAILED`/`OTP_DELIVERY_FAILED`），不静默 | `--filter=provider-guard` + `--filter=otp-delivery` | ⚠ 集成中（provider-guard 18 passed） |
| E2 | **实名挂不放开付费** | 实名服务失败时 `canUsePaidMessaging` 仍 `{ok:false,code:'REALNAME_REQUIRED'}`；无临时白名单绕过付费 | `--filter=account` + `--filter=provider-guard` | ⚠ 集成中（provider-guard 18 passed） |
| E3 | **机审挂转人审** | `machine` 抛错 → `HUMAN_PENDING`（fail-closed）；`canDeliver=false`；不扣费；积压告警可触发 | `--filter=moderation` + `--filter=provider-guard` | ⚠ 集成中（provider-guard 18 passed） |
| E4 | **备份可 verify 且篡改被发现** | `create → verify ok`；修改文件任一字节 → `verify({ok:false,code:'HASH_MISMATCH'})`；`restore` 抛 `HASH_MISMATCH` | `--filter=backup` | ✅ 已代码化（backup 11 passed） |
| E5 | **恢复后对账一致** | 恢复到独立目录后，账本/钱包/审计与备份时点一致；`restore` **不自动应用**（线上状态不变） | `--filter=backup` + 对账脚本 | ⚠ 模块层 11 passed；对账演练待执行 |
| E6 | **降级事件有审计与告警** | 熔断迁移/降级写审计（含 `usedFallback/causeCode`）；`provider_guard_open>10min` 触发自定义告警 | `--filter=provider-guard` + `--filter=metrics` | ⚠ 集成中（告警联动待接） |

**Gate 规则**：E1–E6 全过才允许把“内测保障”写进对内承诺；任一 ⛔ → 不对外承诺“高可用/可恢复”；⚠ 必须有目标机补测记录。

**反例（看起来通过的三处）**：

1. **「降级成功」**：只测返回了 fallback 结果不算——必须断言 `usedFallback:true` 与 `causeCode`，且指标/审计可见。
2. **「备份可用」**：只测 `create` 成功不算——必须测**篡改检测**与“恢复演练到独立环境”。
3. **「只读模式」**：只测读接口可用不算——必须测**写接口全部拒绝**（扣费/审核/注册/退款）。

### 6.1 演练方式与证据（每 Gate 怎么验）

| Gate | 演练方式 | 要留的证据 | 责任人（⚠ 排班） |
|---|---|---|---|
| E1 | 把短信 provider 置为失败/OPEN，用已登录账号发起付费 | 请求结果 + 审计 + 客服提示截图 | 后端 + 客服 |
| E2 | 实名 provider 失败，走新用户付费入口 | `REALNAME_REQUIRED` 返回 + 审计 | 后端 + 安全 |
| E3 | `machine` 抛错，提交付费消息 | `HUMAN_PENDING` + 无 CHARGE + 积压告警 | 后端 + 内容安全 |
| E4 | 创建备份后篡改 1 字节再 verify/restore | `HASH_MISMATCH` 输出 | SRE |
| E5 | 恢复到临时目录并与账本对账 | 对账清单（差异/原因/owner） | SRE + 财务 |
| E6 | 触发一次真实降级（或注入故障） | 审计条目 + 告警记录 | SRE + 值班 |

## 7. 应急联系与升级路径

### 7.1 分级（沿用 [08 §6.2](./08-运营客服运维与合规.md)）

| 级别 | 场景（本版） | 响应 | 恢复目标 | 通报 |
|---|---|---|---|---|
| P0 | 对账差异≠0、数据损坏、资金错误 | 5 分钟 | ≤30 分钟止损 | 全员 + 法务 |
| P1 | 机审/短信/实名熔断 `OPEN` >10min、只读模式、大面积失败 | 15 分钟 | ≤1 小时 | 值班 + 产品 |
| P2 | 单依赖降级但主流程可用（如短信走备用） | 30 分钟 | ≤4 小时 | 值班 |
| P3 | 单个用户问题 | 4 小时 | ≤3 工作日 | 工单 |

### 7.2 升级路径

值班 → TL（15 分钟无响应）→ 技术负责人 → CTO；资金/隐私/大面积不可用 → 立即 P0 并通知法务。依赖 owner：短信/实名/机审各指定 1 名对接人（⚠ 运营排班）。

### 7.3 对外话术三句（统一口径）

1. **依赖波动**：“检测到短信/审核服务波动，我们正在处理；已登录用户的查看与已通过审核的消息不受影响。”
2. **功能暂不可用**：“验证码/实名认证暂时不可用，请稍后重试或联系客服；已登录用户不受影响。”
3. **只读保护**：“为保护数据安全，系统暂时进入只读模式；恢复后第一时间通知，期间不会产生新的扣费。”

> 话术红线：**不承诺“马上恢复”的具体时间**；不解释未确认的根因；不对外说“数据丢了”（先确认再通报）。

### 7.4 事故通报模板（首报/进展/恢复/复盘）

| 阶段 | 内容（模板） | 时限建议 |
|---|---|---|
| 首报 | “我们发现 XX 依赖波动，影响 XX 功能；已启动应急；当前状态：只读/降级/正常” | 发现后 15 分钟内 |
| 进展 | “已切换备用/已缩小影响面；正在处理；预计下一次更新 XX 分钟” | 每 30 分钟 |
| 恢复 | “服务已恢复；影响范围 XX；数据无丢失/已对账；后续复盘” | 恢复后 1 小时内 |
| 复盘 | 时间线/根因/为何未提前发现/修复/新增告警或演练 | 3 个工作日内 |

## 9. 一页速查

### 9.1 值班前 3 分钟检查单

- [ ] 短信/实名/机审三个 `ProviderGuard.stats().state` 是否都 `CLOSED`；有无 `OPEN` 超 10 分钟。
- [ ] §24 告警列表：有无 `WARN/CRITICAL` 未闭环；对账差异是否 ≠0。
- [ ] 最近一份备份是否 `verify ok`；上次恢复演练日期（是否超两周）。
- [ ] 当前是否只读/灰度缩量；写入口是否已按预案关闭。
- [ ] 客服话术版本是否为最新（三句话）；升级联系人是否在线。

### 9.2 三条降级铁律（背下来）

1. 机审挂 → **转人审**（fail-closed），不放行。
2. 实名挂 → **不放开付费**（`REALNAME_REQUIRED` 不变），不先开后补。
3. 降级必须 **`usedFallback:true + causeCode`**，不静默返回空值。

### 9.3 三个依赖哪个挂了最该立刻对外沟通

**机审**：它直接决定“付费消息发不发得出去”，已付费/已扣费用户的**核心动作**被卡住，且用户不知道要等多久；短信/实名影响的是“新用户能不能进来”，沟通优先级可以稍后。机审挂必须第一时间对**已提交付费消息的用户**发“审核中”告知，并给客服统一话术。

### 9.4 v0.0.5 不是什么

- 不是「高可用架构」：没有多地域容灾/自动故障转移（⛔ Phase2）；
- 不是「自动恢复」：`restore` 不自动应用，恢复是人工决策；
- 不是「真实支付保障」：支付渠道仍是 Out；体验额度不是真实资金。

### 9.5 30 天落地节奏

| 周 | 交付 | 出口 |
|---|---|---|
| W1 | `ProviderGuard` + 熔断（E1/E2 的依赖侧） | OPEN 不调用主方；usedFallback/causeCode 可断言 |
| W2 | 降级矩阵接线（E1–E3）+ 只读模式 | 三依赖各演练一次 |
| W3 | `BackupService`（E4/E5） | 篡改可发现；恢复演练到独立目录 |
| W4 | 告警联动（E6）+ 协议要点 + 值班手册 | E1–E6 全过、话术定稿 |
