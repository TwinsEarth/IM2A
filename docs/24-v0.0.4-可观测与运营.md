# 24 · v0.0.4 可观测与运营（IM2A）

> 版本 v0.0.4（R15 对齐）· 对应契约 `contracts/INTERFACES.md` v1.0（变更记录 **R15**，§41–§42）· 作者：架构组
> 定位：用户指令「按清单开始 v0.0.4 的开发」。**v0.0.4 让内测从「能跑」变成「能运营」**：付费漏斗、审核时效、机审失败率、退款率可看，越线告警；一条 `messageId` 能串起审核→扣费→投递→回复→退款。
> 与 [23](./23-v0.0.3-审核链.md) 的边界：**23 是闸门，24 是仪表盘与刹车**——审核链负责“该不该发”，可观测负责“发得顺不顺、哪里在漏、什么时候该停”。
> 与 [21 §3](./21-v0.0.1-产品版范围与验收.md)（A1–A8）、[22 §4](./22-v0.0.2-内测就绪-短信与争议.md)（B1–B7）、[23 §5](./23-v0.0.3-审核链.md)（C1–C6）的关系：前三个 Gate 管“功能与准入”，本文的 D1–D6 管“**可观测与可运营**”；[08 §6](./08-运营客服运维与合规.md) 的 SLO/告警分级沿用，不重复。
> 状态口径：**✅ 本机实测通过**（命令可复现）· **⚠ 实现中/需目标机** · **⛔ 未实现/明确不做**。SLO 数值为建议值，标注 ⚠ 需复核；不编造法规条款。

## 1. 版本定义

### 1.1 「能跑」→「能运营」

| 维度 | v0.0.3（能跑） | v0.0.4（能运营） |
|---|---|---|
| 审核 | 有闸门、有队列、有申诉 | 能看到**审核时效/积压/失败率/误杀**，越线告警 |
| 付费 | 审核通过才扣费 | 能看到**六段漏斗**：哪一段在掉、掉多少 |
| 资金 | 有账本幂等 | 能看到**退款率/争议率/对账差异**，差异≠0 立即 CRITICAL |
| 举证 | 有签名审计 | 一条 `messageId` 串起全链；**缺环显式** |
| 运营 | 出问题靠猜 | 日/周看板 + Go/No-Go + 复盘模板 |

### 1.2 与 v0.0.3 的边界（别把仪表盘当闸门）

- 可观测**不改变任何业务状态**：`trace` 只读（契约不变量④），指标 `inc/observe` 不触发扣费/审核/投递。
- 告警**不自动执行业务动作**：告警是“叫人”，停机/切灰度由值班按 Runbook 人工执行（避免误告警自动停服）。
- 审核链的 `canDeliver` 仍是唯一放行判定；可观测只统计它的结果，不做第二次判定。

### 1.3 依赖关系

| 依赖 | 说明 |
|---|---|
| §41 `Metrics` | 计数器/直方图/漏斗/告警纯函数；被业务模块调用（`inc/observe`） |
| §42 `AuditTrace` | 读 moderation/ledger/dispute/audit 四源；只读 |
| A/B/C Gate 的埋点 | A1–A8、B1–B7、C1–C6 的关键动作要能被计数，否则漏斗是空的 |

## 2. 付费漏斗：六段与产品解释

**漏斗固定顺序（契约冻结）**：`PAID_SENT → MODERATION_PASS|HUMAN_PENDING → CHARGE → VIEWED → REPLIED → SETTLED`。分母为 0 时转化率返回 0（不得 NaN）。

| 段 | 从 → 到 | 转化率含义 | 掉下去说明什么 | 先修哪个 |
|---|---|---|---|---|
| 1 | `PAID_SENT → 审核通过` | 提交的付费消息有多少被审核放行 | 规则太严/误杀高/人审积压导致超时拒 | **先修规则阈值与人审 SLA**（本版最优先） |
| 2 | `审核通过 → CHARGE` | 放行后有多少真正扣费 | 余额不足、`canDeliver` 调用顺序错、幂等键冲突 | 查钱包/扣费调用链 |
| 3 | `CHARGE → VIEWED` | 扣费后有多少被对方看到 | 通道延迟/推送失败/卡片不吸引 | 查投递与通知 |
| 4 | `VIEWED → REPLIED` | 看了有多少回复 | 来意质量差、价格/价值不匹配、骚扰感 | 查预审话术与内容质量 |
| 5 | `REPLIED → SETTLED` | 回复后有多少结算成功 | 结算失败/争议/账务异常 | 查账本与争议链路 |
| 6 | `SETTLED`（终态） | 完成率 | — | 复盘整体漏斗 |

**读法（防止误判）**：

- 内测样本小：用**滚动 7 天**看转化率，单日只看计数与告警，不用单日比率下结论。
- 分母为 0 的段显示 0（不是“100%”），避免“新功能看起来完美”。
- 段与段之间不是严格同批用户：`PAID_SENT` 与 `SETTLED` 可能跨天，复盘时按 `messageId` 关联更准（见 §5 追溯）。

### 2.1 漏斗与三段 Gate 的关系（埋点别漏）

| 漏斗段 | 依赖的 Gate/动作 | 没埋点的后果 |
|---|---|---|
| `PAID_SENT` | A1 准入（未实名不能发付费消息） | 第一段恒 0，误判“没有需求” |
| 审核 | C1–C6 审核链 | 审核通过率无从判断，规则没法调 |
| `CHARGE` | A4/A5 钱包 + `canDeliver` | 扣费失败被当成“用户不想买” |
| `VIEWED` / `REPLIED` | 投递与回复链路 | 掉段无法区分“没送达”与“不想回” |
| `SETTLED` | §8/§37 结算 | 终态统计失真，复盘结论反了 |

## 3. 关键指标表（与 §41 默认规则逐条对齐）

| 指标 | 口径（分子 / 分母） | 目标（建议，⚠ 需复核） | 告警阈值（§41 默认） | 级别 |
|---|---|---|---|---|
| **机审失败率** | 机审异常/不可用次数 ÷ 提交审核次数 | <2%（内测） | **>10%** | **WARN** |
| **人审积压** | `HUMAN_PENDING` 队列长度（或最老等待时长） | 积压 <10 单 | **>20** | **WARN** |
| **人审时效 P95** | 人审 `submit → review` 的 P95（`observe` 直方图） | 工作时段 ≤30min（⚠ 引用 [08 §2.1](./08-运营客服运维与合规.md)） | 超 SLA 即告警（⚠ 运营定） | WARN |
| **退款率** | `REFUND` 笔数 ÷ `CHARGE` 笔数（滚动 7 天） | <10% | **>30%** | **CRITICAL** |
| **争议率** | `DISPUTE_OPEN` ÷ `CHARGE`（滚动 7 天） | <5% | 建议 >10%（⚠ 需实测校准） | WARN |
| **短信失败率** | `OTP_FAILED` ÷ (`OTP_SENT` + `OTP_FAILED`) | <5% | **>10%** | **WARN** |
| **对账差异** | 账本 vs 渠道/钱包日切差异笔数 | =0 | **≠0** | **CRITICAL** |
| 审核结果分布 | `MODERATION_PASS/FLAG/BLOCK/APPROVE/REJECT` 计数 | FLAG 占比可解释 | 建议 FLAG >20%（⚠ 需实测） | INFO/WARN |
| 漏斗转化（六段） | 见 §2 | 按阶段设基线（⚠ 校准） | 单段周环比跌 >20%（⚠） | WARN |

> **口径铁律**：指标与财务报表必须同口径——「退款率」= 账本 `REFUND` 笔数 ÷ `CHARGE` 笔数，不是“客服觉得退得多”；「对账差异」以财务日切为准（[08 §6.4](./08-运营客服运维与合规.md)）。

## 4. 告警与值班

### 4.0 告警规则生命周期（防“规则腐烂”）

| 阶段 | 动作 | 留痕 |
|---|---|---|
| 新增 | 定义指标口径 + 阈值 + owner + 处置动作 | 变更记录 |
| 调阈值 | 说明原因（误报/漏报/业务变化）并评估影响 | 审计 |
| 静默 | 限时 + 原因 + 替代监控 | 静默清单（到期复查） |
| 删除 | 说明替代指标；不得无替代直接删 | 审计 |

> 每季度复核五条默认阈值（⚠ 运营 + SRE）；阈值长期不动 = 要么业务没变，要么没人看。

### 4.1 五条默认规则（§41 `DEFAULT_ALERT_RULES`）

| # | 规则 | 阈值 | 级别 | 处置动作 | 升级路径 |
|---|---|---|---|---|---|
| 1 | 机审失败率 | >10% | WARN | 查供应商/超时；必要时全量转人审；通知内容安全 | 值班 → 内容安全（15min 无响应） |
| 2 | 人审积压 | >20 | WARN | 加派审核员/缩灰度；检查超时自动 BLOCK 是否生效 | 值班 → 运营主管 |
| 3 | 退款率 | >30% | **CRITICAL** | 暂停陌生人付费灰度；查争议/内容质量；对账确认 | 值班 → 产品 + 财务 + 安全（P0/P1 口径） |
| 4 | 短信失败率 | >10% | WARN | 查供应商/通道；客服话术切“稍后重试”；必要时切备用通道（留审计） | 值班 → 供应商对接人 |
| 5 | 对账差异 | ≠0 | **CRITICAL** | 立即挂账、停止相关扣费/退款自动动作；财务介入；保留现场 | 值班 → 财务 + CTO（P0） |

> 级别映射：CRITICAL 对应 [08 §6.2](./08-运营客服运维与合规.md) 的 P0/P1（资金/合规/主链），WARN 对应 P2；INFO 只进看板不进电话。

### 4.2 避免「告警疲劳」的三条原则

1. **阈值可执行**：每条告警必须对应一个动作与 owner；没有动作的指标只进看板，不告警。
2. **聚合窗口**：必须“连续 N 分钟/滚动窗口超阈值”才触发（如机审失败率连续 10 分钟），避免毛刺；CRITICAL 可缩短窗口但需双人确认。
3. **可静默但不可隐藏**：维护期/供应商已知故障可静默告警，但必须记录原因、到期时间与替代监控；**不得**为了安静直接删规则。

### 4.3 值班交接

| 项 | 规则 |
|---|---|
| 交接内容 | 未闭环告警、灰度状态、争议积压、对账差异 |
| 交接证据 | 告警 id + 处置记录 + 后续 owner |
| 静默清单 | 谁静默、为什么、何时到期 |
| 升级兜底 | 15 分钟无响应 → TL；资金/隐私 → 立即 P0 |

## 5. 审计追溯：`trace(messageId)`

### 5.1 四个来源与顺序（契约冻结）

| source | 提供什么 | 典型 type |
|---|---|---|
| `moderation` | 审核案件与结论 | `SUBMIT / MACHINE_PASS/FLAG/BLOCK / REVIEW_APPROVE/REJECT / APPEAL / APPEAL_GRANT/UPHOLD` |
| `ledger` | 扣费/退款流水 | `CHARGE / REFUND` |
| `dispute` | 争议状态 | `DISPUTE_OPEN / DISPUTE_APPROVE / DISPUTE_REJECT` |
| `audit` | 签名审计事件（兜底/证据） | 治理动作摘要 |

**排序**：`steps` 按 `at` 升序；同刻按固定优先级 `moderation < ledger < reply < dispute`（reply 归入投递/回复侧，不单独作为 source）。

### 5.2 时间线示例（完整链）

| at | source | type | actor | amountCents | ref |
|---|---|---|---|---|---|
| T0 | moderation | SUBMIT | 发送者 | — | `caseId=c-1` |
| T1 | moderation | MACHINE_PASS | machine | — | `ruleVersion=r-3 / modelVersion=m-2` |
| T2 | ledger | CHARGE | wallet | 500 | `pay:<messageId>` |
| T3 | audit | DELIVER | gateway | — | `messageId` |
| T4 | audit | VIEWED | 接收者 | — | `messageId` |
| T5 | audit | REPLIED | 接收者 | — | `messageId` |
| T6 | dispute | DISPUTE_OPEN | 发送者 | — | `disputeId=d-1` |
| T7 | dispute | DISPUTE_APPROVE | 客服 L2 | — | `refund-dispute:d-1` |
| T8 | ledger | REFUND | wallet | 500 | `refund-dispute:d-1` |

### 5.3 `complete=false` 时怎么办（缺环显式）

| 缺环 | 可能原因 | 复盘动作 | 客服话术 |
|---|---|---|---|
| 有 `CHARGE` 无审核记录 | 旧路径先扣费/审核未接线（最危险） | 立即查调用顺序；暂停该入口；补审计 | “我们正在核查这笔扣费的审核记录，X 小时内答复” |
| 有审核无 `CHARGE` | 审核通过但扣费失败/用户放弃 | 查钱包/幂等；确认是否需要重试 | “审核已通过，扣费未完成，可重新发起” |
| 有 `CHARGE` 无 `VIEWED` | 投递失败/对方未打开 | 查通道；必要时补发/退款 | “消息可能未送达，我们正在核查” |
| 有 `REFUND` 无争议/无 `CHARGE` | 数据异常/手工退款 | 财务 + 审计介入；**不得直接改账** | “退款记录异常，我们正在核对” |

> **为什么“缺环显式”比“看起来完整”更有价值**：完整的时间线会让复盘停止思考；显式的缺口会强制问“为什么缺”，从而发现接线错误、旧路径、数据丢失。**宁可报表难看，不可报表骗人。**

### 5.4 追溯的只读约束

`trace` 与 `byAccount` 只读：不触发审核/扣费/退款/状态迁移（契约不变量④）。调用前后业务状态与账本必须一致；测试要断言这一点（D5）。

### 5.5 trace 与签名审计的关系（别把视图当证据）

| 层 | 作用 | 是否可篡改 | 用途 |
|---|---|---|---|
| `trace` | 把四源拼成可读时间线 | 视图，依赖源数据 | 客服/复盘/看板 |
| 签名审计（§16） | 不可篡改证据链 | 不可（哈希 + 签名） | 合规/争议/执法 |

> `trace` 缺环时，最终以签名审计与账本为准；`trace` 不替代证据链，也不得回写。客服可读 `trace`，但对外举证必须用签名审计。

## 6. 内测运营看板

### 6.1 日看（5 分钟）

| 指标 | 看什么 | 越线动作 |
|---|---|---|
| 付费漏斗六段计数 | 是否有段为 0/异常 | 查埋点与调用链 |
| 机审失败率 | 供应商/超时 | WARN 处置（§4.1） |
| 人审积压/时效 | 队列与 P95 | 加派/缩灰度 |
| 退款/争议 | 比率与原因分布 | CRITICAL → 停灰度 |
| 对账差异 | 是否 ≠0 | **立即 P0** |

### 6.2 周看（30 分钟）

- 漏斗周环比、误杀率（申诉 GRANT 占比）、人审误判率、短信失败率、告警数量与误报率。
- 复盘本周所有 CRITICAL/WARN：是否都有 owner 与闭环。
- 更新基线：阈值是否仍合理（避免“阈值永远不动”）。

### 6.3 Go / No-Go（是否继续对陌生人付费开放）

| 条件 | 通过标准 |
|---|---|
| 漏斗 | 审核通过率与 CHARGE 转化有合理基线，无“断崖段” |
| 审核 | 人审积压 <20；时效达标；无 fail-open 事件 |
| 资金 | 对账差异 =0；退款率 <30%（建议 <10%） |
| 争议 | 争议率可解释；SLA 达标 |
| 可观测 | D1–D6 全过；trace 缺环能解释 |

### 6.4 复盘模板（三类）

| 模板 | 字段 |
|---|---|
| **事故** | 时间线、影响面、根因、为何未提前告警、修复、预防（含新增指标/告警） |
| **退款** | `messageId`、时间线、退款原因、是否误杀/内容问题、规则/话术改进 |
| **误杀** | `caseId`、机审版本、命中的规则、复审结论、误杀率影响、规则回滚记录 |

### 6.5 看板字段与来源（防“数字对不上”）

| 看板字段 | 来源 | 刷新 |
|---|---|---|
| 漏斗六段 | §41 `snapshot().funnel` | 实时/分钟 |
| 退款率 / 争议率 | 账本 + 争议事件 | 小时 |
| 审核时效 P95 | `moderation` 的 `observe` 直方图 | 小时 |
| 短信失败率 | `OTP_SENT` / `OTP_FAILED` 计数 | 分钟 |
| 对账差异 | 财务日切（T+1，[08 §6.4](./08-运营客服运维与合规.md)） | 日 |
| 告警列表 | `evaluateAlerts` 输出 | 实时 |

> 看板只展示“有来源”的数字；同一指标不允许两个口径（例如“退款率”不能一处按笔数、一处按金额）。

## 7. 验收 Gate D1–D6

| # | 验收项 | 判定标准（可执行） | 验证命令 | 本机状态 |
|---|---|---|---|---|
| D1 | **漏斗六段转化正确** | 计数器推导六段转化率；分母为 0 → 0（**不得 NaN/Infinity**）；段顺序固定 | `node scripts/test.mjs --filter=metrics` | ⚠ 实现落地中 |
| D2 | **五条默认告警逐条触发** | 构造超阈值快照 → 五个规则各返回对应 `id/severity/value/threshold`；未超不告警 | `--filter=metrics` | ⚠ 实现落地中 |
| D3 | **完整追溯** | `trace(messageId)` 返回四源 steps、按 `at` 升序、同刻 `moderation<ledger<reply<dispute`；完整链 `complete=true` | `--filter=trace` | ⚠ 实现落地中 |
| D4 | **缺环显式** | 构造“有 CHARGE 无审核” → `complete=false` 且 `missing` 明确列出缺失环节（不隐藏） | `--filter=trace` | ⚠ 实现落地中 |
| D5 | **追溯只读** | 调用 `trace/byAccount` 前后：业务状态、账本、争议状态不变（无状态迁移） | `--filter=trace` | ⚠ 实现落地中 |
| D6 | **告警纯函数确定性** | `evaluateAlerts` 同输入同输出；不读环境/不发网络；自定义 rules 可覆盖默认 | `--filter=metrics` | ⚠ 实现落地中 |

**Gate 规则**：D1–D6 全过才允许把看板作为“运营决策依据”；任一 ⛔ → 只能看、不能据此停灰度；⚠ 必须有目标机补测记录。

**反例（看起来通过的三处）**：

1. **「漏斗有数」**：只测计数不算——必须测**分母为 0 的段返回 0**（否则新阶段显示 100% 假象）。
2. **「追溯完整」**：只测正常链不算——必须测**缺环**（D4）与**只读**（D5）。
3. **「告警触发」**：只测阈值超了不算——必须测**未超不告警**与**severity 正确**（避免全量告警刷屏）。

## 9. 一页速查

### 9.1 内测运营每天看哪三个数

1. **审核通过率**（`PAID_SENT → 审核通过`）——掉说明规则/人审有问题，最该先修。
2. **退款率**（`REFUND/CHARGE`，滚动 7 天）——>30% 立即 CRITICAL、停灰度。
3. **对账差异**（账本 vs 财务）——≠0 立即 P0，先挂账再排查。

### 9.2 五条告警（速记）

| 告警 | 阈值 | 级别 |
|---|---|---|
| 机审失败率 | >10% | WARN |
| 人审积压 | >20 | WARN |
| 退款率 | >30% | CRITICAL |
| 短信失败率 | >10% | WARN |
| 对账差异 | ≠0 | CRITICAL |

### 9.3 评审检查清单（6 条）

- [ ] 漏斗六段是否固定顺序、分母为 0 返回 0（无 NaN）。
- [ ] 五条默认规则是否与 §41 逐条一致（值/级别）。
- [ ] `trace` 是否四源齐、按时间排序、同刻优先级正确。
- [ ] `complete=false` 时是否显式列 `missing`，没有“补一条假记录”。
- [ ] `trace/byAccount` 是否只读（调用前后状态不变）。
- [ ] 每个告警是否有 owner/动作/升级路径；有没有“无动作告警”。

### 9.4 v0.0.4 不是什么

- 不是「自动降级/自动停服」：告警只叫人，动作由值班按 Runbook 执行。
- 不是「业务状态机」：可观测只读统计，不改变审核/扣费/投递状态。
- 不是「数据仓库/长期 BI」：内测看板只覆盖当前闭环，长期分析另立项。

### 9.5 30 天落地节奏

| 周 | 交付 | 出口 |
|---|---|---|
| W1 | `Metrics` 计数/直方图/漏斗（D1） | 分母 0 → 0；六段可看 |
| W2 | 五条默认告警（D2/D6） | 五条逐条触发、未超不告警 |
| W3 | `AuditTrace` 四源（D3） | 完整链可跑、顺序正确 |
| W4 | 缺环/只读（D4/D5）+ 看板/复盘模板 | D1–D6 全过 |
