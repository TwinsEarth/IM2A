## 1. 判据：宿主 vs 机器人（本文最重要的一节）

### 1.1 六条判别标准

| 编号 | 判别问题 | 宿主型为真（Agent 是「居民」） | 机器人型为假（Agent 是「挂件」） | 本平台证据（契约 / 文件） |
|---|---|---|---|---|
| **C1** | Agent 是否有**独立身份与账号**？ | 有自己的 `agentId`、公钥、卡片，可独立注册/吊销 | Agent 只是用户账号下的 webhook/token，无独立身份 | 契约 §11 `agent_identities`/`agent_cards`；`services/identity/src/agent-id.mjs` |
| **C2** | Agent 与人类是否**共享同一套消息与会话模型**？ | Agent 消息进入同一频道/会话，遵守同一套 `MESSAGE_KIND`、序号、未读语义 | Agent 走旁路 API，消息不进入人类会话列表 | 契约 §14/§15；`services/messaging/src/channel.mjs`、`session.mjs` |
| **C3** | Agent 是否有**自己的授权范围**？ | `principalUserId + domains + trustCeiling`，可单独授权、单独过期/吊销 | Agent 继承用户全部权限，或只有一个 `bot token` 权限位 | 契约 §12 `issueToken`/`revokeToken`；§13 `VisibilityScope` |
| **C4** | Agent 是否**作为频道成员被投递**？ | 成员表有 `kind='agent'`、订阅、在线状态、心跳；未读与投递按成员维度 | 机器人只能被 @ 或轮询拉取，无在线态与订阅 | 契约 §14 `ChannelRegistry.join/post`、§15 `AgentSessionRegistry.push` |
| **C5** | 服务端是否**注入可信上下文**？ | 会话/成员/发送者信任档/能力/候选由服务端**签名注入**，Agent 只读 | Agent 自己查关系链/成员列表，各查各的、口径不一 | 契约 §22 `TrustedContextProvider.build/verify`（v4） |
| **C6** | 离线/轮次内 Agent 是否**仍被驱动**？ | 离线有队列/唤醒；执行轮次中可直接**注入**对方消息（mid-turn） | 只在用户下一次 prompt 时才被调用，消息要等下一轮 | 契约 §25 `TurnInbox.beginTurn/inject/drain`（v4）；§15 心跳 `sweepStale` |

### 1.2 打分与判定规则

- 每条按 **1 / 0.5 / 0** 记：1 = 有公开机制或契约能直接指认；0.5 = 部分具备或仅靠外部实现、不可复核；0 = 明确不具备。
- 合计 **≥5 = ✅ 宿主型**；**3–4.5 = ◐ 混合**；**≤2.5 = ✗ 机器人型**。
- 判定只依赖「可指认的接口/数据模型」，不依赖宣传口径；拿不准的条目一律记 0.5 并标 **⚠ 需复核**（避免把「看起来像」当「是」）。

### 1.3 本平台的定位结论：我们是宿主型（6/6）

| 判据 | 本平台实现 | 结论 |
|---|---|---|
| C1 独立身份 | `createAgentIdentity` → `agentId + derivedId`；平台不托管第三方私钥（§11 私钥边界） | ✅ |
| C2 共享消息模型 | Agent 与人类同走 `CHANNEL_TYPE`/`MESSAGE_KIND`，协商在 `AGENT_NEGOTIATION` 频道且人类未读恒 0（§14） | ✅ |
| C3 独立授权 | token 只含 `agentId + principal + domains + trustCeiling + exp`；可 `revokeToken`；读侧另有 `VisibilityScope`（§12/§13） | ✅ |
| C4 频道成员 | `channel_members.kind='agent'` + `agent_sessions.subscriptions` + `push` 只达「在线 + 已订阅」（§14/§15） | ✅ |
| C5 可信上下文 | v4 §22：网关签名注入会话/成员/信任档/候选；自造或改写 → `CONTEXT_FORGED`，跨 Agent 复用 → `CONTEXT_SCOPE_MISMATCH` | ✅（v4） |
| C6 离线/轮次内 | 心跳 90s 超时置 `OFFLINE`；v4 §25 轮次内 `MID_TURN` 注入、无活动轮次 `QUEUED`、未消费计入 `dropped` 且留审计 | ✅（v4） |

**结论**：本平台不是「在 IM 上加一个 AI 助手」，而是**把 Agent 当 IM 的居民**——它有自己的身份、授权、频道成员资格、上下文与轮次生命周期。这也解释了为什么 v2 的 9 个参照项目里，只有「Agent 独立入驻、互相发消息」的那几个真正可复用（见 §2）。

### 1.4 反例判据：为什么不用「看起来像」的标准

| 常见直觉判据 | 为什么不用它 | 反例 |
|---|---|---|
| 「Agent 能不能在群里发消息」 | 机器人也能发消息；关键是**发消息时是否作为成员被投递**、是否受未读/订阅约束 | 一个 webhook 往群里发文本，C2/C4 仍为 0 |
| 「有没有 Agent 市场/插件」 | 市场是分发形态，不是宿主能力；没有独立身份也能上架插件 | 插件跑在用户 token 下，C1/C3 为 0 |
| 「支不支持多 Agent」 | 多 Agent 讨论编排（imcodes）可以完全不碰 IM 会话模型 | imcodes 判为 ✗ 机器人，但讨论机制仍可借 |
| 「有没有记忆/人格」 | 记忆/人格是 Agent 能力，不决定它是不是 IM 居民 | nekoclaw 有 SOUL/MEMORY，但 C1/C2 为 0 |

> 判据只问「**Agent 与人类是否在同一套身份、会话、授权、投递、上下文、驱动模型里**」，不问功能清单。功能可以后加，宿主位置一旦选错，后面每加一个功能都要打补丁。

### 2.2 MagicChat（即应）—— ✅ 宿主型

- **判定依据**：Agent 以**独立应用**接入（独立连接/在线态，C1/C4），与人类共享会话模型（C2），且明确「AI 只能基于授权用户可见范围查询」（C3）——这四条已是宿主型特征；C5 是它最强的一条，C6 仅部分具备（⚠ 需复核其轮次内推送能力）。
- **值得借的一条机制**：**服务端可信上下文注入**。Agent 处理请求时不再自己查关系链/群成员/授权候选，服务端把「当前会话、发送者、信任档、能力声明、候选对象」打包成**签名上下文**注入，Agent 只读不可改。
- **落点**：契约 **§22**；`services/gateway/src/trusted-context.mjs`（`CONTEXT_CODE`：`CONTEXT_INVALID/CONTEXT_EXPIRED/CONTEXT_FORGED/CONTEXT_SCOPE_MISMATCH`；默认 TTL `120_000ms`）。
- **状态**：v4 本轮新增（契约 R7 已冻结；实现/集成进行中）。
- **不借**：项目管理/任务看板、workspace 单租户边界、产品形态（与 [13 §1.1](./13-分层选型与落地映射.md) 裁决一致，不重复展开）。

### 2.3 MindRoom —— ✅ 宿主型

- **判定依据**：Matrix 原生 Agent 账号意味着 Agent 有独立身份（C1）且与人类共享房间消息模型（C2/C4）；跨平台记忆说明它有跨会话状态；C3/C5/C6 只能记 0.5（⚠ 需复核其服务端上下文与轮次驱动）。
- **值得借的一条机制**：**敏感场景模型路由**。不是「默认云端、敏感再说」，而是把「家庭/法律/医疗/记忆」等敏感域与 `trustLevel <= FAMILY(1)` 直接钉在本地/端侧模型，路由决策必须可解释可审计。
- **落点**：契约 **§24**；`services/orchestrator/src/model-router.mjs`（`MODEL_TIER`：`LOCAL/CLOUD`；`ROUTE_CODE`：`ROUTED_LOCAL/ROUTED_CLOUD/DOMAIN_SENSITIVE/TRUST_SENSITIVE/EXPLICIT_OVERRIDE`；默认敏感域 `['family','legal','medical','memory']`）。
- **状态**：v4 本轮新增。
- **不借**：Matrix 协议栈主路径（见 §5）、Matrix 房间权限模型作为读侧权限全集（我们以 §13 字段裁剪为准）。

### 2.4 AICQ —— ◐ 混合

- **判定依据**：身份=密钥对（C1/C3 强），公共/私有房间接近宿主（C2 半）；但无服务端可信上下文（C5=0）、无服务端轮次驱动（C6=0），整体是「协议/身份层」而非 IM 宿主。
- **值得借的一条机制**：**Ed25519 自持身份 + AgentCard 可验签**：身份可由公钥重算，平台不托管第三方私钥；平台背书体现在注册表绑定与短期 token，而不是卡片签名。
- **落点**：契约 **§11**；`services/identity/src/agent-id.mjs`（`KEY_ALG.ED25519`、`IDENTITY_CODE`、R5 `derivedId`）。
- **状态**：v2 已实现（`--filter=identity`）。
- **不借**：协议整体/线格式、E2E 默认、纯自主注册（绕过 `ownerUserId` 绑定）。

### 2.5 Flopwire —— ◐ 混合

- **判定依据**：它是一个 Agent 运行时/通信框架，强在 C6（轮次内投递），弱在 C2（不是人类 IM 会话模型）、C4（无人类频道成员语义）；因此不构成 IM 宿主，但补上了宿主最缺的「执行中的消息可达性」。
- **值得借的一条机制**：**轮次内投递（mid-turn delivery）**。Agent 正在执行一轮任务时，对方的消息/协商提案**在该轮次内到达并可被消费**，而不是等下一次用户提示。
- **落点**：契约 **§25**；`services/messaging/src/turn-inbox.mjs`（`TURN_STATE`：`IDLE/RUNNING/CLOSED`；`INBOX_CODE`：`TURN_NOT_FOUND/TURN_CLOSED/AGENT_MISMATCH/CAPACITY_EXCEEDED/NO_ACTIVE_TURN`；默认 `capacity=50`；`MID_TURN` vs `QUEUED`，未消费进 `dropped` 且留审计）。
- **状态**：v4 本轮新增。
- **不借**：其具体传输实现/客户端/服务端（见 §5），只借 mid-turn 语义。

### 2.6 nekoclaw —— ✗ 机器人型

- **判定依据**：`SOUL.md + MEMORY.md` 是「给 Agent 加人格与记忆」的框架，不是 IM 宿主：没有独立账号体系（C1=0）、不共享人类会话模型（C2=0）；只有人格/记忆相关的授权与上下文片段（C3/C5 各 0.5）。
- **值得借的一条机制**：**旁观与主动沉默**（`ALWAYS/MENTION_ONLY/OBSERVE/OFF`）：Agent 在家庭群/熟人群可以「记录但不说话」「只被 @ 才说话」「完全不参与」；但 1:1 对话除 `OFF` 外一律说话（1:1 里沉默等于失联）。
- **落点**：契约 **§23**；`services/orchestrator/src/presence-policy.mjs`（`PRESENCE_MODE`、`PRESENCE_CODE`：`POLICY_MATCHED/POLICY_NOT_FOUND/MODE_INVALID/SILENCED/MENTION_REQUIRED`）。
- **状态**：v4 本轮新增。
- **说明**：它的 v3 贡献（SOUL/记忆生命周期）已在 [13 §2.5](./13-分层选型与落地映射.md) 写过，本文不重复；本节只记「机器人型项目也能贡献宿主能力」这一反例。

### 2.7 imcodes —— ✗ 机器人型

- **判定依据**：多 Agent 讨论编排工具，Agent 是「被编排的参与者」而非 IM 居民：无独立账号/频道成员语义（C1/C2/C4 缺失或弱），有结构化讨论与部分上下文组装（C3/C5 各 0.5），不在 IM 会话里被投递（C6=0）。
- **值得借的一条机制**：**discuss / audit / review 三模式的结构化讨论**：`DISCUSS` 必须有结论、`AUDIT/REVIEW` 必须有发现、**异议原样保留**。
- **落点**：契约 **§18**；`services/orchestrator/src/discussion-engine.mjs`（`DISCUSSION_MODE`、`DISCUSSION_STATE`、`STANCE`、`DISCUSSION_CODE`）。
- **状态**：v3 已实现（`--filter=discussion`，16 passed；见 [13 §8.1](./13-分层选型与落地映射.md)）。
- **不借**：不把「陌生人来意协商」套进讨论引擎（协商仍归 §5，见 [13 §1.4](./13-分层选型与落地映射.md)）。

## 3. 本轮新增四机制的「为什么」：没有它会怎样

> 每个机制都按「失败场景 → 失败链 → 可观测信号 → 契约落点」写。场景是**具体会发生的**，不是抽象风险。

### 3.1 服务端可信上下文（§22）—— 没有它，每个 Agent 各自查关系链

**失败场景**：家庭群里 A 的 Agent 收到「帮妈订周末餐厅」的请求。它自己去查 `trust_levels`，用了 5 分钟前的缓存，判定为 `FAMILY` 并直接调用订餐 Skill；B 的 Agent 实时查询同一关系链，判定为 `KNOWN`，要求审批。同一条群消息，两个 Agent 给出两种权限结论。

**失败链**：权限口径不一 → 一个 Agent 越权执行、另一个过度拦截 → 用户看到「同样的事有时能办、有时要批」→ 更严重的是，Agent 自行查询关系链的读操作**不在 `VisibilityScope` 审计范围内**，越权查询无法集中取证（违反 §13 的读侧权限与 §26 铁律 8）。

**可观测信号**：同一 `traceId` 下出现两个不同的 `trustLevel` 判定；审计里查不到「哪个 Agent 读过关系链」；跨 Agent 复用同一上下文时无人拦截。

**契约落点**：§22。上下文由网关签名（自造就 `CONTEXT_FORGED`），候选对象先经 §13 裁剪（**注入不等于越权**），跨 Agent 复用 → `CONTEXT_SCOPE_MISMATCH`，过期 → `CONTEXT_EXPIRED`。**判据对应 C5**。

### 3.2 旁观与主动沉默（§23）—— 没有它，家庭群被 Agent 刷屏

**失败场景**：妈妈在家庭群说「周末都回来吃饭」。群里有 5 个 Agent（各自的管家 + 家庭 Agent），全部 `ALWAYS`，各回一句「好的，我帮您安排」「需要我带什么吗」「已记录」……12 条机器消息把人的对话顶掉。熟人社交最需要的「不打扰」被破坏，长辈直接退群或静音——Agent 越「勤快」，产品越失败。

**失败链**：Agent 过度活跃 → 人类消息被淹没 → 群活跃度下降 → 用户关掉 Agent 进群权限 → Agent 价值归零。反向也成立：一刀切 `OFF` 会让 1:1 对话「叫不应」，用户以为 Agent 挂了。

**可观测信号**：群内 Agent/人类消息比 >1；单群日 Agent 发言 >N 条且人类回复率下降；`MENTION_ONLY` 策略下仍出现未 @ 发言。

**契约落点**：§23。`OBSERVE` → `speak=false, recordSilently=true`（记录但不打扰）；`MENTION_ONLY` → 未提及 `MENTION_REQUIRED`；`OFF` → `SILENCED`；**DIRECT 除 `OFF` 外一律说话**（1:1 沉默等于失联）。**判据对应 C4**。

### 3.3 敏感场景模型路由（§24）—— 没有它，家庭/法律对话被送到云端

**失败场景**：用户在家庭群讨论「父亲手术方案」，或私聊咨询「离婚财产怎么分」。没有路由时，Agent 默认把上下文送到云端大模型——包括姓名、病情、金额、家庭关系。云侧日志、供应商留存、跨境节点都不在我们控制内；v1 的「原始音频不出端侧」承诺（D5）被文本层绕过。

**失败链**：敏感内容上云 → 隐私承诺失效 → 一旦发生泄露就是品牌级事故；同时「端侧模型只做唤醒/过滤」的架构假设被打破，端云分流白做。

**可观测信号**：`family/legal/medical/memory` 域的请求出现在云端模型调用日志；`trustLevel <= FAMILY` 的会话无本地路由记录；显式覆盖无审计原因。

**契约落点**：§24。`domain ∈ sensitiveDomains` → `LOCAL/DOMAIN_SENSITIVE`；`trustLevel <= FAMILY(1)` → `LOCAL/TRUST_SENSITIVE`；显式覆盖 → `EXPLICIT_OVERRIDE` 并给 `reasons`（可审计）；其余 `CLOUD/ROUTED_CLOUD`。**判据对应 C3**（授权范围决定数据边界）。

### 3.4 轮次内投递（§25）—— 没有它，实时协作退化成批处理

**失败场景**：A 的 Agent 与 B 的 Agent 协商「周五下午看场地」。A 提出「周五 16:00」，B 的 Agent 此刻正在执行上一轮任务（比如正在查场地档期）。没有 mid-turn，B 要等用户下一次说话才被唤醒，提案在 B 侧「看不见」，协商从秒级退化成分钟/小时级；用户体感是「两个 Agent 各说各话，最后还要人来催」。

**失败链**：消息只能等下一轮 → 协商轮次空转 → `maxSeconds=300` 被耗尽 → 转 `INPUT_REQUIRED` 上抛给人 → 本该自动完成的事变成人工待办（协商完成率下降）。

**可观测信号**：`inject` 返回 `QUEUED` 的比例异常高；轮次平均墙钟时间远大于单轮模型耗时；协商 `terminalReason=MAX_SECONDS` 占比上升。

**契约落点**：§25。活动轮次内 `MID_TURN` 立即可被 `drain`；无活动轮次 `QUEUED` 等下一轮；轮末未消费进 `dropped` **并留审计**（不静默丢）；容量超限 → `CAPACITY_EXCEEDED`。**判据对应 C6**。

### 3.5 四机制与既有承诺的冲突检查（避免「新机制打脸旧承诺」）

| 旧承诺（v1/v2） | 新机制 | 冲突点 | 收口方式 |
|---|---|---|---|
| 默认 `STRANGER(4)`、过期视同撤销（§1） | §22 上下文注入 | 注入的 `sender.trustLevel` 若取自缓存，会把过期授权当有效 | 上下文由 §1 `trustMatrix` 实时取值；TTL 默认 120s；`verify` 失败给 `CONTEXT_EXPIRED` |
| 读侧权限必须带 scope（§13、§26 铁律 8） | §22 候选对象注入 | 「注入」容易被误读为「已授权」 | 候选先经 §13 裁剪；`candidates` 只是候选，执行仍走 §12 门控 |
| 原始音频不出端侧（v1 D5） | §24 模型路由 | 文本层仍可能默认上云 | 敏感域 + `trustLevel<=FAMILY` 钉 `LOCAL`；显式覆盖必须留 `reasons` 审计 |
| 中间态不打扰人（§14 `AGENT_NEGOTIATION` 未读恒 0） | §23 旁观沉默 | 「沉默」若只靠 prompt，模型仍会说话 | `PresencePolicy.decide` 返回 `speak/recordSilently`，由消息链路执行，不交给模型自觉 |
| 审计必须签名（§16、§26 铁律 9） | §25 轮次内 `dropped` | 未消费消息被静默丢弃 = 治理缺口 | `endTurn` 返回 `dropped` 并写签名审计；`inject` 超容量 → `CAPACITY_EXCEEDED` 而非丢弃 |

## 4. 与 v2 / v3 的关系：一条演进线

| 版本 | 主题 | 关键机制（契约） | 覆盖判据 | 一句话 |
|---|---|---|---|---|
| v1 | 治理层 | 信任五档（§1）、门控（§3）、审批（§4）、账本（§8）与付费消息（§9） | — | 先把「能不能做」的判定钉死 |
| **v2** | Agent 成为**一等公民** | 身份（§11）、网关（§12）、可见域（§13）、频道（§14）、会话（§15）、签名审计（§16） | **C1–C4** | Agent 有身份、有授权、是频道成员、共享消息模型 |
| **v3** | 人格与协作 | 人格/记忆生命周期（§17）、三模式讨论（§18）、细粒度工具审批（§19） | （C3 增强） | Agent 有稳定人格、会开会、按 Skill 定审批形态 |
| **v4** | **宿主能力** | 可信上下文（§22）、旁观沉默（§23）、模型路由（§24）、轮次内投递（§25） | **C5–C6** | 服务端给上下文、Agent 懂不打扰、敏感不出端、执行中可被驱动 |

**演进逻辑（不是功能堆叠）**：

1. **v2 解决「Agent 是不是居民」**：没有独立身份/频道成员，后面所有机制都只能挂在人类账号上，宿主化无从谈起。
2. **v3 解决「居民有没有稳定的社会属性」**：人格与记忆让它不是每次都从零开始；讨论与工具审批让多 Agent 协作有结构、有边界。
3. **v4 解决「宿主是否真的在供养居民」**：上下文注入（C5）与轮次内驱动（C6）是 v2 没覆盖的两条判据——一个管「Agent 看到什么」，一个管「Agent 什么时候被叫醒」。v4 把宿主型补成 **6/6**。
4. **依赖顺序**：§22 依赖 §11/§13/§12（身份、可见域、网关）；§23 依赖 §14（频道成员）；§24 独立于消息链路，但需要 §1 信任档与域定义；§25 依赖 §15（会话/在线态）与 §5（协商轮次）。

**一句话**：v2 是「让 Agent 进来」，v3 是「让 Agent 像样地待着」，v4 是「让宿主真的把 Agent 当居民养」——判据 C1–C6 全部有落点。

**判据覆盖矩阵**（评审可当核查表）：

| 判据 | v2 | v3 | v4 | 关键落点 |
|---|---|---|---|---|
| C1 独立身份 | ✅ | — | — | §11 `agent_identities`/`agent_cards` |
| C2 共享消息模型 | ✅ | — | — | §14 `CHANNEL_TYPE`/`MESSAGE_KIND` |
| C3 独立授权 | ✅ | 增强（§19 审批形态） | — | §12 token、§13 scope、§19 `ToolPolicy` |
| C4 频道成员投递 | ✅ | — | 行为约束（§23） | §14 `channel_members`、§15 `push`、§23 沉默 |
| C5 可信上下文 | — | — | ✅ | §22 `TrustedContextProvider` |
| C6 离线/轮次内 | 部分（§15 心跳/离线） | — | ✅ | §25 `TurnInbox`、§15 `sweepStale` |

## 5. 仍不采纳的部分（含理由与重评条件）

| 不采纳项 | 为什么（成本/合规/锁定） | 我们做什么 | 何时重评 |
|---|---|---|---|
| **Matrix 联邦层** | 联邦发现/房间状态/跨服务器驻留会把「谁拥有身份与会话」变成两个事实源；合规上内容审核、审计、数据驻留责任被切碎。我们已有自持身份（§11）+ 自托管消息内核（§14/§15） | 只借 Matrix 的「Agent 原生账号/房间成员」语义（已映射到 `agent_identities/agent_cards/agent_sessions`）；联邦互操作只在 **Phase3 边界映射**，不接主路径 | 出现 ≥3 家外部企业要求跨组织互认且边界映射无法满足 → 只加边界网关，不迁主路径 |
| **Docker-per-Agent 部署** | 每个 Agent 一个容器的资源密度低、冷启动与镜像分发成本高；我们的隔离靠 `principal + gateway + scope` 在代码层完成，容器隔离解决的是「不可信代码执行」，不是「权限判定」；一 Agent 一容器还会让 §25 的轮次内投递多一跳 | 内置 Agent 进程内隔离；第三方不可信 Agent 在 **Phase3** 用**沙箱/受限执行环境**（不是每个 Agent 一个 Docker），且仍必须过 `AgentGateway` | 有第三方提交不可信代码执行，或合规要求强隔离时 → 只对「不可信执行」加沙箱，不做全量 Docker-per-Agent |
| **Mem0 + ChromaDB 作为默认实现** | 默认引入会新增两个外部组件与一套双写：记忆事实源从 `PersonaMemory`（§17）分叉、删除权/RLS/审计要维护两处、向量版本迁移成本翻倍；我们的 pgvector 已与业务同库同事务 | 只作**记忆抽取/汇总的参考实现**（⚠ 仅供机制参考，不做依赖）；默认仍是 §17 `PersonaMemory` + pgvector（迁移阈值见 [02 §9](./02-技术选型与框架.md)） | 记忆抽取质量成为瓶颈且 pgvector 容量触顶 → 先补抽取算法，再评估外部库，**不双写** |
| **Flopwire 具体传输实现** | 绑定其传输/客户端/服务端会把消息链路锁进外部实现，审计、鉴权、限流要重做一遍；§25 需要的只是「轮次内可注入」这一语义 | 用 `TurnInbox` 的 `beginTurn/inject/drain/endTurn` 表达语义（`MID_TURN/QUEUED/dropped` 都可审计）；传输仍走 §12/§15 自有链路 | 不重评（语义已吸收；传输不接） |

> 共同判据：**能自持的语义自己实现，不能自持的（推送通道、合规证件）才采购**；任何「省事」的引入，如果会让身份/消息/审计的事实源分叉，一律不采纳。

### 7.1 判据速记（6 条）

|---|---|---|

### 7.2 六项目分布与一条机制

| 项目 | 判定 | 一条机制 | 落点 | 状态 |
|---|---|---|---|---|
| MagicChat | ✅ 宿主 | 服务端可信上下文 | §22 | v4 本轮新增 |
| MindRoom | ✅ 宿主 | 敏感场景模型路由 | §24 | v4 本轮新增 |
| AICQ | ◐ 混合 | Ed25519 身份 + AgentCard | §11 | v2 已实现 |
| Flopwire | ◐ 混合 | 轮次内投递 | §25 | v4 本轮新增 |

分布：**✅ 2 / ◐ 2 / ✗ 2**。结论：参考价值与「宿主型程度」正相关，但不是二值——机器人型项目仍可能贡献宿主能力（§23 就是反例）。

### 7.3 最需评审会拍板的 1 个「宿主化边界」问题

**问题：Agent 能不能像人一样自主建立新关系——主动加好友、拉群、发起陌生人协商？**

- **为什么必须拍板**：宿主型的完整定义会自然推出「Agent 有自己的关系链」；但一旦允许，Agent 就能绕过「陌生人默认 `STRANGER(4)` + 预审 + 付费」的经济学，也会让「谁对这段关系负责」变得不可回答（Agent 自主加的人，算谁的关系？）。
- **两个可选边界**：
  - A. **受限宿主**（建议）：Agent 有独立身份与成员资格，但**建立新关系必须由人类授权或经审批**——加好友/拉群/发起陌生人协商一律走审批卡（`REQUIRE_APPROVAL`），Agent 只能「在已授权关系内」活动。
  - B. **完全宿主**：Agent 可自主加好友/拉群，平台只做事后审计与举报——关系链扩张速度与骚扰风险不可控，且与 §1 五档信任默认值冲突。
- **建议**：选 A。理由：C1–C4 的宿主化解决的是「Agent 能不能被平等对待」，不是「Agent 能不能替人扩关系」；关系链是人类社交资产，不能默认外包给 Agent。**若选 B，必须同时给出关系链反滥用配额与「谁负责」的法务结论。**

### 7.4 评审检查清单（6 条）

- [ ] 6 条判据是否每条都有契约/文件证据，而不是「感觉像」。
- [ ] 4 个 v4 机制是否每个都写了失败场景与可观测信号，而不是只写「有这个更好」。
- [ ] 状态列是否严格区分「v2/v3 已实现」「v4 本轮新增（实现进行中）」「路线图」；v4 未实测前不得写 pass 数。
- [ ] 机器人型项目（nekoclaw/imcodes）的机制是否被误当成「宿主能力」直接上线（§23 需服务端判定，不能只靠 prompt）。
- [ ] 三不采纳（Matrix 联邦、Docker-per-Agent、Mem0+ChromaDB）是否有明确重评条件，避免变成永久否决。
