## 1. 三条路线拆解

> 三条路线分别解决「Agent 怎么说话」「Agent 怎么被编排」「Agent 怎么被执行」。**没有一条解决「人是否信任它、要不要付费」**——这正是 [15 §2](./15-四层技术栈映射与自研边界.md) 五件套仍然自研的原因。

**1.0 三条路线的共同缺口（先说结论）**

| 路线 | 能解决 | 结构上不解决 | 只靠它的后果 |
|---|---|---|---|
| A 轻量协议 | 通信、挂起、最小验签 | 信任档位、付费 | 陌生 Agent 可无限试探，试探无成本 |
| B IM 原生编排 | 任务拆解、共享工作区、多 Agent 协作 | 关系链、账本、审批语义 | 编排知道「怎么做」，不知道「该不该」 |
| C 平台 CLI/MCP | 触达、卡片、组织通知 | 个人信任、账本、审计自证 | 接得越多，治理越碎、证据越弱 |

> 所以最终不是「三选一」，而是「分层组合（各做擅长）+ 治理自研（§1 五档/§9 付费/§4 审批/§16 审计）」。

### 1.1 路线 A：轻量协议层（agentcomms / masumi / im-for-agents）

| 候选（⚠ 只引机制） | 借鉴机制 | 我们取哪一条 / 落点 | 复用策略 | 明确避坑 |
|---|---|---|---|---|
| **agentcomms** | Agent 间轻量通信 + 人类可介入的会话挂起 | 「通信可挂起等人」→ 契约 **§32** `agent-correspondence.mjs` | 只借范式 | 不引入其传输/中继实现 |
| **masumi** | Agent 身份/协商的最小协议面 | 只借「最小协议面」思想 → §26 签名信封（v5 已实现） | 只借范式 | 不引入其完整协议栈 |
| **im-for-agents** | Subagent 上下文隔离 + 观察窗 | §6/§17 隔离；§13 `project()`；§15 SSE | 只借范式 | 不接其调度实现 |
| **我方既有** | §11 身份、§12 网关、§26 信封、§29 邮箱 | v2/v5/v6 已实现 | 自研（已有） | 不再造第二套通信协议 |

> 路线 A 的定位：**给「陌生/跨域 Agent」一套最小、可验、可挂起的通信语义**，而不是完整 A2A。A2A 完整规范留给 Phase3 边界（[13 §2](./13-分层选型与落地映射.md) 的结论不重复）。

### 1.2 路线 B：IM 原生编排（AgentHub / Xiajiao / AstrBot）

| 候选（⚠ 只引机制） | 借鉴机制 | 我们取哪一条 / 落点 | 复用策略 | 明确避坑 |
|---|---|---|---|---|
| **AgentHub** | 调度中心 + 共享工作区（协调器拆解任务、多 Agent 群聊协作） | 只取「调度中心 + 共享工作区」形态 → 自有 orchestrator + §18 `DiscussionEngine` + §14 `TASK/GROUP` 频道 | 只借范式 | **不照搬 FastAPI 单体**（会与自有 API/网关重复）；协调器不成为第二套调度事实源 |
| **Xiajiao** | 一条命令快速验证、产品化体验 | 已吸收为 `scripts/quickstart.mjs`（[13 §2.7](./13-分层选型与落地映射.md)） | 只借范式 | 不借其产品形态 |
| **AstrBot** | 统一 `MessageEvent` + 适配器注册表 + 能力声明 | 契约 **§31** `im-adapter.mjs`（v7 新增） | 改造复用（借事件模型，重写实现） | 不接其插件/平台适配实现；能力缺口必须 `CAPABILITY_MISSING` 显式报错 |
| **我方既有** | 九态审批 / 七步门控 / 三模式讨论 | §4/§3/§18（v1–v3 已实现） | 自研（已有） | 不引入第二套编排 |

> 路线 B 的定位：**编排在自有层**（调度中心 + 工作区），IM 平台只提供「人和 Agent 都能到的会话面」。

### 1.3 路线 C：平台 CLI / MCP 执行层（飞书 / 钉钉 / 企微 / 微信 / WhatsApp / X）

| 平台 | 可接入形态（⚠ 需复核，政策时效性强） | 能承载 | 不能承载 | 我们的策略 |
|---|---|---|---|---|
| 飞书 | Channel SDK / CLI / MCP（⚠ 需复核） | 团队消息、卡片、审批回调输入 | 个人熟人信任档、C 端账本 | Phase1 可选试点；最多 L2（卡片+回调输入） |
| 钉钉 | 机器人 CLI/开放平台（⚠ 需复核） | 组织内通知 | 个人信任、陌生人付费 | 企业版通知（Phase3） |
| 企业微信 | 客户联系/机器人能力（受限，⚠ 需复核） | 企业客服、通知 | C 端陌生人付费、Agent 身份 | 客服备选（Phase3） |
| 微信 | 个人号无官方 Bot API（用户输入 2026-06 指引 ⚠ 待复核）；小程序分享/落地页 | 入口/触达 | 消息通道、信任档、账本 | 只做入口（Phase3） |
| WhatsApp | Business Tools / MCP 类通知（⚠ 需复核，海外政策） | 海外通知 | 信任档、付费、审计自证 | 通知备选 |
| X | 2026-02 起自动化限制（用户输入 ⚠ 待复核） | 公域获客 | 私域消息/信任/付费 | 仅内容获客（Phase3） |

> 路线 C 的定位：**触达面**，不是治理面。平台只到 L2；任何回调必须换回自有 `ticketId` + `principalUserId`（[16 §2.4/§2.5](./16-三层技术栈与平台接入边界.md) 的 L0–L3 分级与铁律继续有效）。

### 1.4 三条路线对比：为什么最终是「组合」而不是「单选」

| 路线 | 强项 | 弱项（不解决什么） | 适用层 | 我们的用法 |
|---|---|---|---|---|
| A 轻量协议层 | 最小通信语义、易验签、可挂起 | 信任档位、付费、审批 | 陌生/跨域 Agent 通信 | 取语义（§26/§29/§32），不接协议栈 |
| B IM 原生编排 | 任务拆解、共享工作区、多 Agent 协作 | 关系链、账本、平台合规 | 自有编排层 | 调度中心 + 工作区 + 既有讨论/审批 |
| C 平台 CLI/MCP | 触达、卡片、通知、企业组织 | 个人信任、账本、审计自证 | 平台边界 | 最多 L2，不做治理闭环 |

> 组合原则：**每一层只让它做它擅长的事**。把「通信」和「编排」交给开源/平台，把「信任、审批、账本、审计」留在自有层——这也是 [15](./15-四层技术栈映射与自研边界.md) 的结论。

## 2. 最终分层决策表（用户结论 + 我方落点）

| 层 | 用户结论 | 我方落点（契约 / 文件） | 状态 | 明确不做 |
|---|---|---|---|---|
| **编排** | 调度中心 + 共享工作区（AgentHub 思路） | 自有 orchestrator + §18 `DiscussionEngine` + §14 `TASK/GROUP` 频道 | 已实现（v1–v3），v7 不重写 | 不照搬 FastAPI 单体；不引入第二套调度 |
| **陌生 Agent** | 无账户加密邮箱 + 审批挂起（不走 A2A 完整规范） | §26 签名信封（v5）+ §29 持久邮箱（v6）+ **§32 `agent-correspondence.mjs`（v7）**；A2A 只在 Phase3 边界 | 信封/邮箱已实现；§32 本轮新增 | 不为陌生 Agent 创建正式账号/会话；不走 A2A 全量状态同步 |
| **IM 底座** | Phase0–1 腾讯云 IM PaaS + 适配层；Phase2 评估 WKongAI/自研 | **§31 `im-adapter.mjs`（v7）**；PaaS 适配器 + 自研适配器共存；`ADAPTER_CAPABILITY` 显式声明能力缺口 | 本轮新增（适配层） | 不在 Phase0–1 自建长连接；不静默降级缺失能力 |
| **Skill** | 沙箱原子调用 + 门控统一拦截 | §12 `AgentGateway`（唯一入口）+ §3 `CapabilityGate` + §28 `ConfirmationTier` + §30 `DelegationService`；生产侧沙箱由 Go runtime 提供 | 门控已实现（v1–v6）；沙箱为生产项 | 不在网关外直接执行 Skill；不允许部分副作用外溢 |

### 2.1 决策理由（每层一句）

1. **编排留在自有层**：审批九态、七步门控、三模式讨论是治理语义，开源编排无法替我们承担；只借「调度中心 + 共享工作区」的形状。
2. **陌生 Agent 用「邮件 + 挂起」而不是「账号 + 会话」**：陌生关系是低频、需人决策的，开账号会污染关系链与未读；先信封验签 → 邮箱暂存 → 审批挂起 → 批准后才进入会话，与 §1 五档「默认 STRANGER」一致。
3. **底座可替换**：Phase0–1 要上线速度与合规资质（PaaS 成熟），Phase2 再按成本/能力/延迟评估自研；两者共存的前提是 §31 适配层 + 能力声明。
4. **Skill 原子化**：每次工具调用是一个带幂等键的原子单元，统一过网关与门控；沙箱（不可信代码执行）是生产 Go runtime 的事，不是契约层的事。

### 2.2 分层依赖与落地顺序

| 顺序 | 交付 | 依赖 | 为什么这个顺序 |
|---|---|---|---|
| 1 | §31 适配层 + 能力声明 | 无 | 先让底座可换，后面所有决定才有退路 |
| 2 | §26 信封 + §29 邮箱 | §11 身份 | 陌生 Agent 要能验签、能暂存 |
| 3 | §32 审批挂起 | §26/§29、§4 审批 | 验签暂存后必须人批才能进会话 |
| 4 | 编排工作区（§18/§14） | 会话面就绪 | 人机都有会话面后，协作才有意义 |
| 5 | 平台 L2 试点（飞书可选） | §31 + §32 | 平台只做入口，回调走挂起/审批 |

## 3. 反转记录（本文最重要的一节）

### 3.1 反转事实与代价

| 项 | v2（§18，2026-10-21 R4） | v7（R10，2026-10-21） |
|---|---|---|
| L3 底座 | WuKongIM 形态**自托管内核** | **Phase0–1 腾讯云 IM PaaS + §31 适配层**；Phase2 评估自研/WKongAI |
| 决策依据 | 频道类型化/未读整形/自定义消息/审核链自证 | **用户决策：Phase0–1 优先上线速度与合规资质**；技术理由仍在，但优先级变化 |
| 状态 | 保留为决策审计记录（[02 §18](./02-技术选型与框架.md)） | 当前口径（[02 §19](./02-技术选型与框架.md)） |

**反转的代价（写进预算，不隐藏）**：

1. **未读整形要应用层补偿**：PaaS 不提供按频道类型的未读 → 自有投影表 + 读侧整形，多一块代码与一致性校验。
2. **自定义消息语义弱化**：PaaS 只保证「不透明 payload 送达」→ `MESSAGE_KIND` 语义在应用层强制，`CMD` 不落库由应用层保证。
3. **审计证据强度下降**：平台回调不可重放/不可验证 → 我们只能对「收到并归一化的事件」签名落链；平台是否丢事件，只能靠对账发现。
4. **P99 预算回退到 v1 含厂商路径**：厂商 API 接收 + 通道到达重新进入预算，余量从自托管的 1035ms 缩回 485ms（[02 §18.3](./02-技术选型与框架.md)）。
5. **Phase2 迁移工作量只是被推迟，不是消失**：适配层让切换不重写业务，但适配器本身、双轨测试与灰度仍要再做一次。

### 3.2 逐条补偿：v2 自托管理由 → PaaS 现状 → 我们怎么办

| # | v2 的理由（§18.1） | PaaS 不提供什么 | 我们的处理 | 类型 |
|---|---|---|---|---|
| 1 | 频道类型化 / 未读整形（`AGENT_NEGOTIATION` 人类未读恒 0、`CMD` 不计未读） | 未读以会话为单位，无频道类型 | **应用层补偿**：自有 `channel_members` 未读投影为准，读侧按类型整形；PaaS 未读仅作兜底展示。适配器缺 `UNREAD_SHAPING` 时：协商频道只在巡视态可见、不产生未读（显式降级，不假装） | 补偿 + 降级 |
| 2 | 自定义消息类型（`AGENT_TURN`/`CMD` 的存储与投递语义） | 自定义消息是不透明 payload，服务端不按类型强制 `stored` | **应用层补偿**：`MESSAGE_KIND` 写入信封 payload，收发都经 §31 `normalizeEvent`，`CMD` 由应用层不落 `messages_meta`；**明确不做**：正文/敏感内容不进 PaaS 自定义字段，只放引用/密文 | 补偿 + 不做 |
| 3 | Agent 作为频道成员被投递、独立在线/订阅 | 会话模型以人为一等公民，无 Agent membership | **应用层补偿**：`AgentSessionRegistry` + 自有路由/订阅仍在（v2 模块保留），PaaS 只承载人类可见消息；缺 `AGENT_MEMBERSHIP` 时 Agent 频道走自有会话层 | 补偿 |
| 4 | 审核链自证（规则版本/命中/人审/申诉） | 通道审核是黑盒，不能作为证据 | **自研审核链不变**：发送前 `EgressGuard` + 服务端内容审核（自有规则/模型版本/命中/复核/申诉）；**明确不做**：不把 PaaS 后台截图当证据；合规举证用 §16 签名链 | 自研保留 |
| 5 | 回调可重放、签名审计做双份账 | 平台回调不可验证、不可重放 | **应用层补偿**：每个 `normalizeEvent` 后的业务事件写 §16 签名审计（附平台 `eventId`/`at`）；对账任务兜底发现「平台有、我们没有」的差异；**明确不做**：不承诺 PaaS 回调本身抗篡改 | 补偿 + 不做 |
| 6 | 流式回复（Agent 边生成边呈现） | 部分 PaaS 不提供真流式 | **降级**：先做「最终态送达」；需要流式时用分片自定义消息或 SSE 侧通道；Phase2 自托管/WKongAI 再补真流式 | 降级 |
| 7 | 审批卡片回调可靠触达 | 卡片回调能力因平台而异 | **应用层补偿**：回调只作输入源 → 自有 `ticketId` + `principalUserId` 映射；缺 `CARD_CALLBACK` → 只读通知（[16 §2.4](./16-三层技术栈与平台接入边界.md) L1） | 补偿 + 降级 |
| 8 | 成本/运维可控 | PaaS 有通道费；自托管有 SRE 人力 | **先接受**：Phase0–1 用 0.25 SRE + 通道费换上线速度；Phase2 用 3 年 TCO 比较再定（见 §3.3） | 接受 + 再评估 |

**3.2.1 补偿的责任模块与验收（谁做、怎么验）**

| 补偿 | 责任模块 | 验收（可执行） |
|---|---|---|
| 未读投影 | messaging + §31 | 协商频道人类未读恒 0；缺 `UNREAD_SHAPING` 时 `CAPABILITY_MISSING` 可复现 |
| 信封 KIND | §31 `normalizeEvent` + messaging | `CMD` 不落 `messages_meta`；`AGENT_TURN` 可回放 |
| 审核链 | orchestrator `EgressGuard` + 服务端审核 + audit | 发送前 BLOCK 生效；审计可验签 |
| 签名审计 + 对账 | audit + 运维任务 | 篡改/断链可检出；日对账差异可见且有工单 |
| 回调输入 | §32 + §4 审批 | 非 `APPROVED` 不可投递；重复 decide → `ALREADY_DECIDED` |

### 3.3 可观测回退 / 再反转条件

> 观察窗与阈值均为**决策阈值**（不是实测结论）；触发后不是「立刻切」，而是启动 Phase2 提前评估（评估周期 ≤2 周）。

| 编号 | 信号 | 阈值 / 观察窗 | 动作 |
|---|---|---|---|
| V1 延迟 | 审批卡片端到端 P99 | > 3s 连续 2 周（=2s SLO × 150%） | 提前启动自托管评估；补偿无效则 Phase2 前切 |
| V2 丢消息 | 对账差异（平台有、我们无） | > 0.1% 连续 1 周 | 先修适配/对账；连续 2 个迭代未收敛 → 提前切 |
| V3 未读错乱 | 协商频道人类未读 > 0 的会话占比 | > 0.5% 连续 1 周 | 应用层修复；2 个迭代未收敛 → 提前切 |
| V4 能力缺口 | `CAPABILITY_MISSING` 命中**核心能力**（`UNREAD_SHAPING/CUSTOM_MESSAGE/AUDIT_CHAIN`） | ≥2 项且持续 > 1 个月 | 提前到 Phase2 切自托管/WKongAI |
| V5 成本 | PaaS 3 年 TCO | > 自托管 3 年 TCO × 120%（⚠ 采购复核报价） | Phase2 切自托管（成本反转） |
| V6 规模 | DAU / 峰值连接 | DAU > 50 万 或 峰值连接 > 20 万 | Phase2 切自托管（规模拐点，⚠ 压测校准） |
| V7 合规/资质 | 监管要求平台侧可自证，或 PaaS 资质/政策变化 | 任一发生 | 立即评估；必要时先私有化部署 |
| V8 平台锁定 | 厂商涨价/停服/接口不兼容 | 涨价 > 20% 或重大 breaking | 启动切换（适配层是为此存在） |

**再反转一句话**：**当「应用层补偿」累计造成可观测的体验损失（V1–V4 任一持续超窗）或成本/规模/合规越过阈值（V5–V8），就必须把自托管从 Phase2 提前——不能等到 Phase2 末再算账。**

### 3.4 为什么这不是「回到 v1」

| 维度 | v1（PaaS 裸用） | v7（PaaS + 适配层） |
|---|---|---|
| 治理 | 关系链/账本自有，但无 Agent 语义 | v2–v6 全部保留（身份/频道/可见域/会话/信封/邮箱/委托） |
| 平台依赖 | SDK 直接渗进业务 | §31 适配层 + `MessageEvent` + 能力声明，可换底座 |
| 未读/自定义 | 完全依赖 PaaS | 应用层投影/信封语义，PaaS 只做传输 |
| 审计 | v1 哈希链 | §16 签名审计 + 对账；平台回调不冒充证据 |
| 切换成本 | 换厂商=改业务 | 换适配器=部署选择 |

> 结论：v7 不是回退，是**把 v2 的内核能力降级为「Phase2 可选实现」**，保留其契约与模块；底座从「唯一事实源」变成「可替换传输」。

## 4. 本轮两机制「没有它会怎样」

### 4.1 IM 适配层（§31）—— 没有它，换底座 = 重写业务层

**失败场景**：Phase0–1 用腾讯云 IM，Phase2 决定切 WKongAI/自研。没有适配层时，业务代码直接 import 平台 SDK：发送、未读、卡片、回调、群成员、消息类型全散落在编排层。切换意味着把编排层、审批通知、卡片渲染、未读逻辑全部重写，并重跑一遍回归——**换底座的成本 = 重做一次 L3 集成**。

**失败链**：SDK 渗透 → 平台绑定 → 能力差异靠「猜」→ 某平台缺未读整形时静默降级 → 线上出现未读错乱，且无法定位是平台还是业务。

**可观测信号**：编排层出现平台 SDK 的 import；同一业务逻辑出现平台分支 `if (platform === ...)`；缺能力时没有 `CAPABILITY_MISSING`；换适配器后回归用例大量改写。

**落点**：§31。业务只面向 `MessageEvent`（冻结字段：`eventId/platform/adapterId/channelId/senderId/senderKind/kind/text/card/at/replyTo/metadata/trustZone`）；`ImAdapterRegistry.register/dispatch` + `requireCapability`；六个能力常量 `UNREAD_SHAPING/CUSTOM_MESSAGE/AGENT_MEMBERSHIP/AUDIT_CHAIN/STREAMING/CARD_CALLBACK`；缺能力必须 `CAPABILITY_MISSING`（**不允许假装支持**）。

### 4.2 人类审批挂起（§32）—— 没有它，陌生 Agent 自行跑完回合，人只剩后知后觉

**失败场景**：陌生 Agent 发来来意（合作/询价/请求），没有 §32 时，它直接进入正常会话/协商，多轮跑完才在收件箱里出现一条「结果通知」。用户看到的是既成事实：对方已经知道「我方有意向」「已读」「已报价」。预审、付费、审批全部失去前置控制。

**失败链**：无挂起 → 回合自动推进 → 敏感信息/态度在审批前外泄 → 「先审后付」变成「先做后补」→ 骚扰与责任无法界定。

**可观测信号**：`SUSPENDED` 状态被绕过；`deliverable` 在非 `APPROVED` 时返回 ok；非属主 `decide` 成功；`EXPIRED` 后仍可投递；`ALREADY_DECIDED` 后状态被二次改写。

**落点**：§32。`AgentCorrespondence.open` 默认 `requiresHumanApproval=true` → `SUSPENDED`；只有属主 `principalUserId` 能 `decide`（`APPROVE/REFUSE`）；`deliverable` 仅 `APPROVED` 返回 ok（**挂起中的来意不得进入会话**）；`SUSPENDED` 过期 → `EXPIRED`；终态再 decide → `ALREADY_DECIDED`。与 §26（验签）、§29（邮箱暂存）串成「陌生 Agent 三步」：验签 → 暂存 → 挂起审批 → 批准后建会话。

### 4.3 两机制与既有模块的边界（防重复）

| 机制 | 容易和谁混 | 边界一句话 |
|---|---|---|
| §31 适配层 | §12 网关 | 适配层只归一化平台事件；认证/限流/门控仍在网关 |
| §31 适配层 | §14 频道 | 适配层不含会话语义；频道/未读投影在 im 层 |
| §32 挂起 | §4 审批 | `Correspondence` 是「陌生来信」状态机；`ApprovalTicket` 是「已授权动作」审批单，二者不合并 |
| §32 挂起 | §29 邮箱 | 邮箱只负责暂存；挂起决定「能不能进会话」 |

## 5. 「轻通信 / 重可靠 / 强门控」三原则与模块映射

| 原则 | 含义 | 模块 / 契约 | 冲突时谁优先 |
|---|---|---|---|
| **轻通信** | 通信层只做「送达 + 归一化 + 能力声明」，不做业务判断 | §31 适配层、§26 信封、§15 会话 | 通信层不得实现信任/审批判断；有业务判断需求 → 上抛网关 |
| **重可靠** | 消息/事件不丢、可恢复、可对账、可举证 | §29 邮箱、§16 签名审计、§8 账本、outbox/对账任务 | 宁可显式失败（`CAPACITY_EXCEEDED`/`PLATFORM_ERROR`），不静默丢 |
| **强门控** | 每个外部动作都过统一入口与判定链 | §12 网关 → §3 门控 → §19 工具策略 → §28 确认层 → §30 委托 | 门控优先于「流畅体验」；不确定时 fail-closed（未登记技能=确认层） |

> 一句话：**通信薄到可以换，可靠性厚到可举证，门控强到不可绕**。三者冲突时，顺序是「门控 > 可靠 > 通信」——宁可慢一点、失败一次，也不放行一次不该发生的动作。

### 5.1 三原则的量化口径（可验收）

| 原则 | 量化口径 | 阈值/证据 |
|---|---|---|
| 轻通信 | 平台 SDK 只允许出现在 §31 的适配器实现里 | 代码扫描：编排层平台 import **0 处** |
| 重可靠 | 邮箱重启恢复 pending；审计链可验；日对账可跑 | 恢复后 pending 一致；`verify().ok=true`；差异有工单 |
| 强门控 | 所有 Skill 调用经 §12；未登记技能 fail-closed | 越权用例 **0 通过**；`PLANNER_PREAPPROVAL_REJECTED` 可触发 |

| 不采纳项 | 为什么 | 我们做什么 | 何时重评 |

| **AgentHub 的 FastAPI 单体形态** | 与自有 API/网关/编排重复，会形成第二套调度与鉴权 | 只借「调度中心 + 共享工作区」；编排在自有 orchestrator | 不重评（形态不接） |

| **Sigil 完全 P2P / 去中心化底座** | 信任档与账本需要中心化强一致；P2P 判定不可唯一 | 身份可自持（§11），判定与账本中心化 | 不重评 |
| **平台 CLI/MCP 承载治理闭环** | 平台身份是组织身份，账本/审计不可托管（[16 §2.2](./16-三层技术栈与平台接入边界.md) 铁律） | 平台最多 L2；决策/扣费/证据回自有层 | 不重评 |
| **Agent 之间直接互信（无审批挂起）** | 陌生关系默认 `STRANGER(4)`，先做事后补审会泄露态度与信息 | §32 默认挂起，批准后才建会话 | 不重评 |

**6.1 不采纳的统一判据**：① 是否持有关系/账本/审计事实源？是 → 不采纳；② 是否要求「完整协议/平台角色 = 信任」？是 → 不采纳；③ 是否绑定其单体/OS/协议栈？是 → 只借范式；④ 以上皆否且语义可映射 → 才进入「改造复用」候选。

## 8. 一页速查（评审用）

### 8.1 三条路线与最终使用

| 路线 | 一句话 | 我们的用法 |
|---|---|---|

| 层 | 决策 | 落点 |
|---|---|---|

### 8.3 反转与再反转（速记）

- **为什么反转**：Phase0–1 优先上线速度与合规资质（用户决策）；§18 的技术理由仍成立，但优先级变化。

- **明确不做**：不把 PaaS 审核当证据、不把正文放 PaaS 自定义字段、不承诺平台回调抗篡改。
- **再反转信号**：P99 > 3s/2 周、丢消息 > 0.1%、协商未读错乱 > 0.5%、核心能力缺口 ≥2 项/月、TCO > 120%、DAU > 50 万、合规/平台政策变化——任一越过即**提前 Phase2 切自托管**。
