## 0. 文档定位

这套文档回答一个问题：**如何把「Agent 自主性 + IM 实时性 + 熟人信任约束 + 陌生人付费经济 + 可穿戴隐私合规」收敛进同一个系统。**

核心立场只有一句：

> **把「Agent 想做什么」和「系统允许它做什么」分成两层。模型负责提出意图，权限门控与状态机负责执行边界。**

凡是涉及信任档位、付费扣费、硬件音频出端的动作，一律不依赖模型"自觉遵守"，而由代码层状态机强制执行。这不只是架构洁癖——它决定了平台能不能过审、账能不能对平、隐私承诺能不能兑现。

**本仓库同时是这份文档的可执行证据**：`services/` 下的零依赖 Node 实现与契约逐字对应，`tests/e2e.test.mjs` 与 12 项治理自检把这些判定变成可运行的断言。生产栈是 Go + Flutter + IM PaaS（见 [02](./02-技术选型与框架.md) §15 映射表），但治理语义在这里已被钉死，移植时不会走样。

## 1. 一页读懂

**产品**：每个人有自己的总管 Agent（管家/秘书/助理）+ 领域子 Agent 团队（工作邮件、采购比价、物业水电煤、日程、法律、教育亲子、陌生人过滤）+ 24 小时在线的随身硬件入口（耳夹式耳机首发），客户端分「审批态 / 巡视态」两态。

**用户价值**：把行政层、杂碎事务交给 Agent 团队，人只处理情感层与最终决策——"像大老板一样"。

**社交机制**：

| 场景 | 机制 |
|---|---|
| 熟人 | 五档信任矩阵（本人/家庭/信任/已知/陌生），每档对应不同的 Agent 自主权与需审批项 |
| 陌生人 | 双方 Agent 先结构化协商来意 → 目标侧 Agent 按预设规则预审 → 通过后才进入**付费环节** → 生成审批卡片等人决策 |
| 付费 | 两档：发送即扣费（过滤批量垃圾）/ 看到且回复才扣费（高价值触点）；铁律是**付费发生在预审之后，绝不替代预审** |
| Agent↔Agent | 独立 gRPC 协商通道，多轮方案讨论，终止时只产出一张审批卡片，全程不打扰人 |

**商业与社会目标**：让 Agent 承担重复劳动，把人的时间还给自我提升、家庭与事业；付费消息不是收入噱头，而是**改变规模化骚扰经济学的过滤器**——一笔小额支付对真有事的人可忽略，对批量自动化骚扰是致命成本。

## 2. 系统全景

```
┌──────────────────────────────────────────────────────────────────────┐
│ L1 接入层    耳夹式耳机 / AI 眼镜（BLE） · 手机 · PC · 手表 · Web      │
├──────────────────────────────────────────────────────────────────────┤
│ L2 端侧层    手机 App：唤醒后 ASR · 意图粗分类 · 敏感前置过滤         │
│              BLE 网关 · 离线审批缓存                                  │
├──────────────────────────────────────────────────────────────────────┤
│ L3 IM 通信层 腾讯云 IM PaaS（Phase0–1）：长连接 · 多端同步 · 离线推送  │
├──────────────────────────────────────────────────────────────────────┤
│ L4 Agent 编排层（自研核心）                                           │
│   AgentRegistry   SkillRuntime   CapabilityGate（门控）               │
│   ApprovalEngine  NegotiationEngine  记忆分层   EgressGuard（出口护栏）│
│   ⚠ 治理不是并列的一层，而是本层内部的强制门控子层（见 §3 D2）        │
├──────────────────────────────────────────────────────────────────────┤
│ L5 模型层    端侧小模型（唤醒/意图/过滤，守门人）↔ 云端大模型（规划/   │
│              协商/专业推理，大脑）                                     │
├──────────────────────────────────────────────────────────────────────┤
│ L6 数据层    PostgreSQL（关系链/信任/账本）· pgvector（记忆）          │
│              对象存储+OpenSearch（归档检索）· Kafka · 时序库 · 不可变审计 │
└──────────────────────────────────────────────────────────────────────┘
```

**三条流量必须物理分离**（混在一起的后果见 [01](./01-总体架构.md) §2）：

| 流量 | 通道 | 为什么不能合并 |
|---|---|---|
| 人类 IM 消息 | IM PaaS 长连接 | 需要离线到达、多端同步、未读语义 |
| Agent ↔ Agent 协商 | 自研 gRPC（Phase3 边界接 A2A） | 高频多轮结构化，会污染未读/推送配额；中间态不该出现在会话列表；需细粒度审计与轮次硬上限 |
| 审批与审计事件 | 内部 Kafka | 可解释性与合规追溯的基础，不能与业务消息混流 |

## 3. 五个关键设计决策

每个决策的完整论证（含被否方案、代价、**反转触发条件**）见 [01](./01-总体架构.md) §4。

| # | 决策 | 一句话理由 | 代码落点 |
|---|---|---|---|
| **D1** | 人类 IM 与 Agent 协商**物理分离** | PaaS 的会话模型以「人」为一等公民，Agent 轮次拿不到干净的可控性；轮次/Token 硬预算必须在服务端同步短路 | [`negotiation-engine.mjs`](../services/orchestrator/src/negotiation-engine.mjs) |
| **D2** | 权限门控在**代码层**（L4 PreToolUse 位置），不靠提示词 | 提示词不可测、可被注入绕过、无统一错误码，审计粒度只能到模型输出；模型越强越需要确定性的拒绝路径 | [`capability-gate.mjs`](../services/orchestrator/src/capability-gate.mjs) |
| **D3** | 审批状态机**自研**，Phase0–2 不引入工作流引擎 | 审批生命周期是分钟级、状态少、无跨系统补偿；Temporal 式引入整套集群运维与 SDK 版本成本，契约还要求状态名可测 | [`approval-engine.mjs`](../services/orchestrator/src/approval-engine.mjs) |
| **D4** | IM 用 PaaS，但**关系链与账本必须自有** | PaaS 关系链是"好友/群"二元模型，表达不了五档 `TRUST_LEVELS`、子 Agent `trustZoneMin`、授权过期即撤销；PaaS 计费模型承载不了「先预审后付费 + 幂等恰好一次 + 按 messageId 退款」 | [`paid-message.mjs`](../services/payment/src/paid-message.mjs) · [`ledger.mjs`](../services/payment/src/ledger.mjs) |
| **D5** | 端侧过滤优先，**默认原始音频不出端侧** | 卧室/车内对话上云是不可接受的产品风险；代价是端侧模型精度受限、误唤醒需 OTA 修 | 见 [04](./04-SDK与端侧设计.md) §3 隐私时序 |

> D2 是整套架构与"普通 Agent 框架"最重要的差别：**治理一旦成为并列层，调用方就有理由绕开它**；放在编排层内部、位于每一次工具调用之前，才是"代码强制"。

## 4. 状态机：全套技术的脊柱

三张状态机是契约的核心，**迁移白名单之外一律抛错**，且每个终态都不可复活。这是"付费不重复、审批不越权、协商不无限"的工程保证。

### 4.1 审批单（9 态，人机混合里"人"的唯一落点）

```
PENDING ──► REVIEWING ──► APPROVED ──┐
   │            │                    ├──► EXECUTING ──► COMPLETED
   │            ├──────► MODIFIED ────┘                     │
   ├──────────────────► REJECTED                    └────► FAILED
   └──────────────────► EXPIRED（超时；30min→手表，2h→短信）
```
不变量：事件溯源只追加；决策人必须是单据属主（否则 `FORBIDDEN`）；终态再决策 → `ILLEGAL_TRANSITION`。

### 4.2 Agent 协商（8 态，独立 gRPC 通道）

```
SUBMITTED ──PROPOSE──► WORKING ──ACCEPT──► COMPLETED（产出 AGREEMENT artifact）
                          │  ▲
                    COUNTER└──┘  （round++；超过 maxRounds=5 或 maxTokens=4000
                          │        → INPUT_REQUIRED + terminalReason，不抛异常，上抛人）
                          ├──REQUEST_INFO──► INPUT_REQUIRED
                          └──REQUEST_AUTH──► AUTH_REQUIRED
任意非终态 ──REJECT──► REJECTED        FAILED / CANCELED（外部调度介入）
```
不变量：中间轮次**不产生用户可见通知**；终止时才注入一张审批卡片。

### 4.3 陌生人付费消息（9 态）

```
INTENT ──screen PASS──► AWAITING_PAYMENT ──pay──► PAID ──view──► VIEWED
  │                          │                     │               │
  └─screen BLOCK─► REFUSED   └─refuse/expire─► REFUSED/EXPIRED      ├─refund─► REFUNDED
                                                                   └─reply──► REPLIED ──settle──► SETTLED
```
不变量（全部有测试）：未 `screen` 的 `pay()` → `NEEDS_SCREENING`；`REFUSED` 后 `pay()` → `NOT_PAYABLE`；重复 `pay()` 返回 `charged:false` 且账本只有一条 `CHARGE`（幂等键 `pay:<messageId>`）；`payerUserId` 必须等于发送方，否则 `PAYER_MISMATCH`。

## 7. 评审会需要拍板的 5 件事

1. **审批卡片的通道归属**：走 IM PaaS 自定义系统消息会削弱"三条流量分离"的纯度（PaaS 未读/推送配额被治理流量占用）；备选是独立推送服务。要在 Phase1 前定，否则后期拆成本高。（源自 [01](./01-总体架构.md) §8）
2. **陌生人"先协商后付费"的资损敞口**：协商完成后若用户不付款，Agent 已消耗算力与轮次。是否对"协商发起"预扣/预授权？这是合规（预付费）与体验的裁量点。
3. **原始音频是否允许上云**：D5 默认不出端侧，但识别质量与多语种/噪声场景需实测；若必须上传，隐私声明、等保与硬件指示灯规格都要重做。
4. **首发硬件形态**：文档结论是耳夹式耳机（佩戴门槛低、接电话/听留言/语音审批是最高频场景），眼镜作为第二形态。需与供应链确认首版 ODM 排期。（[06](./06-产品形态与硬件.md)）
5. **付费默认档与信任矩阵默认值**：新用户默认"看到且回复才扣费"还是"发送即扣费"、默认信任档位与自动审批阈值的出厂值——直接决定第一批用户的骚扰量与体验基线。（[07](./07-客户端与UI交互.md) · [09](./09-开发计划与里程碑.md)）
