## 1. 版本定位（为什么仍属 0.1.x）

对照 [32 §5.1](./32-v0.1.2-缺陷修复与0.1.x停止条件.md) 的「缺陷 vs 缺口」判据：

| 判据 | 缺陷一（备份 schema 闸门） | 缺陷二（版本探针限流） | 证据补强 |
|---|---|---|---|
| 是否已声明能力 | ✅ 备份/恢复已声明（§44 `restore`） | ✅ 健康/版本已声明（§51 `/api/version`） | — |
| 是否可复现 | ✅ 造 schema=1 备份 → 200 摘要但加载失败 | ✅ `RATE_LIMIT_PER_MIN=1` 探针 3 次 → 429 | ✅ 手工探测 |
| 修复代价 | 只收紧校验，不加依赖/能力 | 只加豁免名单，不改限流语义 | 不改代码 |
| 结论 | **缺陷 → 0.1.x** | **缺陷 → 0.1.x** | **非缺陷 → 文档证据** |

> 两个缺陷都在“已声明能力内出错、且不需要新依赖”，所以按 32 §5 走 0.1.x；证据补强只是把“已验证”写清楚，不占版本能力。

## 2. 缺陷一：恢复备份的 schema 闸门

### 2.1 现象（“校验通过 ≠ 能用”）

| 步骤 | 修复前 |
|---|---|
| `POST /api/ops/backup` 创建备份 | 200，备份带 sha256 |
| 用**旧 schema**（如 `schemaVersion:1`）的备份调 `POST /api/ops/backup/restore` | **200 + `summary`**（agents/tickets/messages/audit 条数）——看起来“恢复成功” |
| 真正把数据交给 `createWorld` 加载 | `SCHEMA_MISMATCH`（schema 1 ≠ 2） |
| 结果 | 用户拿到一份“校验通过但加载即失败”的备份；**故障在最后一步才暴露** |

根因：`restore` 只做了 **sha256 验签**，没有校验 **备份数据的 `schemaVersion`**；而“验签通过”只证明文件没被篡改，不证明数据能被当前代码加载。

### 2.2 修法（恢复端点先拦 schema）

```
POST /api/ops/backup/restore
  → backup.restore({file})            // 验签（sha256）不变
  → 读 restored.data.schemaVersion
  → 与当前 VERSION_SCHEMA 比较
      一致 → 200 { ok:true, applied:false, summary }（不自动应用）
      不一致 → 409 { error:'SCHEMA_MISMATCH', restored:false,
                     backupSchema, currentSchema,
                     needsMigration:true,
                     hint:'先对备份文件执行 node scripts/migrate-state.mjs --file <backup.json> 再恢复' }
```

**判定字段（逐字）**：`error='SCHEMA_MISMATCH'`、`restored=false`、`backupSchema`、`currentSchema`、`needsMigration=true`。

> 关键变化：不再返回 200 摘要。**要么明确“可恢复”，要么明确“需要先迁移”**，没有第三种“看起来成功”。

### 2.3 为什么不能自动迁移备份

| 理由 | 说明 |
|---|---|
| 备份是**时点事实** | 它的价值在于“当时是什么”；自动改写会让“备份内容”与“备份时刻”不再对应 |
| 可审计性 | 备份文件/哈希是审计证据；自动迁移会改变哈希，破坏“这份备份没被动过”的证明 |
| 失败不可逆 | 自动迁移失败可能同时损坏备份与线上状态；人工迁移可 dry-run、可回滚 |
| 职责分离 | 迁移是显式人工动作（§51），恢复只做“校验 + 返回数据”，`restore` 本来就不自动应用 |

### 2.4 验收（㉑ ①）

| 断言 | 期望 |
|---|---|
| 造 `schemaVersion:1` 的合法签名备份 → restore | **409**（不是 200） |
| `error` | `SCHEMA_MISMATCH` |
| `restored` | `false` |
| `needsMigration` | `true` |
| `backupSchema` | `1` |
| 线上状态 | **未被修改**（restore 不自动应用） |

## 3. 缺陷二：版本探针豁免限流

### 3.1 现象

- `RATE_LIMIT_PER_MIN=1`（内测小额度/防刷）时，监控/预检/负载均衡的**健康与版本探针**会每秒/每几秒请求 `/api/version`；
- 探针很快耗尽额度 → 后续正常请求（包括运维自己的）**429**；
- 更糟：预检（§45）和监控会因 429 判定“目标不可用”，把**正常运维**打成故障。

### 3.2 修法

| 路径 | 修复前 | 修复后 |
|---|---|---|
| `/api/version` | 参与限流 | **豁免**（不消耗额度） |
| `/api/health` | 豁免 | 豁免（不变） |
| 其他 `/api/*` | 限流 | **限流不变**（不得借机扩大豁免面） |

实现：限流判断条件排除 `/api/health` 与 `/api/version`（`pathname !== ...`），其余逻辑不变。

### 3.3 边界（豁免 ≠ 无保护）

- 探针仍受**连接数/超时/反代层**保护；豁免只是“不计入按客户端 key 的额度”；
- **不得**把豁免扩大到业务接口（如 `/api/state`、`/api/wallet`）；否则等于关掉限流；
- 反代后仍需 `TRUST_PROXY=1` 才能正确识别客户端（与限流口径一致）。

### 3.4 验收（㉑ ②）

| 断言 | 期望 |
|---|---|
| `RATE_LIMIT_PER_MIN=1` 时 `/api/version` 连打 3 次 | **均 200** |
| 同一实例 `/api/state` 连续请求 | 第 2 次 **429**（限流仍生效） |

### 4.3 证据类型与建议

| 项 | 状态 |

## 7. ⚠ 需复核：备份迁移顺序

| 方案 | 做法 | 评价 |
|---|---|---|
| **A（建议）** | **先迁移备份文件的副本** → 校验/恢复 → 人工应用 | 保留原备份不动（时点事实+审计）；迁移可 dry-run；恢复仍不自动应用 |
| B | 恢复后再迁移线上数据 | 线上会被半应用/覆盖；原备份被绕过；回滚点不清 |
| C | 自动迁移备份 | **禁止**：改变哈希/破坏审计（§2.3） |

**建议 A 的理由**：备份文件是证据，**只读它、改副本**；迁移工具对副本执行后生成新哈希，原备份仍可证明“当时是什么”。迁移后的副本再走 `restore`（验签+schema 校验）→ 人工确认应用。⚠ 迁移副本的保留期与销毁策略需法务/运维复核。

## 8. 一页速查

### 8.1 备份恢复三步

1. **确认 schema**：`GET /api/version` 看 `schemaVersion`；备份摘要里看 `backupSchema`（恢复端点返回）。
2. **恢复**：`POST /api/ops/backup/restore` → 200（可恢复，不自动应用）或 409（需迁移）。
3. **应用**：人工确认后切换；保留原备份与报告。

### 8.2 不兼容时怎么办

1. 409 `SCHEMA_MISMATCH` + `needsMigration:true`；
2. **复制**备份文件（不动原件）→ `node scripts/migrate-state.mjs --file <副本> --dry-run` 核对；
3. 正式迁移副本 → 再 `restore` → 按 §8.1 应用；
4. 备份是**未来 schema**（> 当前）→ `UNSUPPORTED`，升级代码/等新版本，不降级。

### 8.3 三条红线

1. **验签通过 ≠ 能用**：恢复前必须校验 schema。
2. **不自动迁移备份**：时点事实不可改写。
3. **豁免只给健康/版本**：业务接口必须继续限流。
