> 版本 v0.0.9（R20 对齐）· 对应契约 `contracts/INTERFACES.md` v1.0（变更记录 **R20**，§49–§50）· 作者：架构组

## 2. 支付链路

### 2.1 四步链路（每步的失败码与用户文案）

| # | 步骤 | 动作 | 失败码 | 用户可见文案 |
|---|---|---|---|---|
| 1 | **下单（INTENT）** | `createIntent({userId, amountCents, channel})` → 冻结 order，返回 `payUrl` | `CHANNEL_UNSUPPORTED`（未实现渠道，不静默降级）、`ORDER_EXISTS` | “已创建支付订单，请在渠道完成支付” / “该支付方式暂不可用” |
| 2 | **渠道回调（PENDING/PAID）** | `handleCallback({channel, headers, body})` | `SIGNATURE_INVALID`、`TIMESTAMP_EXPIRED`、`ORDER_NOT_FOUND`、`AMOUNT_MISMATCH`、`ILLEGAL_STATE`、`CALLBACK_REPLAYED` | “支付处理中，请稍候” / “支付成功，余额已到账” / “支付校验异常，请联系客服” |
| 3 | **入账（DEPOSIT）** | 回调 `PAID` 后写账本 `DEPOSIT`（幂等） | 账本写入失败 → 不改状态、告警；重复回调 → `duplicate:true` | “余额已到账” |
| 4 | **对账** | 日切 `Reconciler.run({date})` → 逐笔差异 | `MISMATCH`、`NOT_FOUND`、`INVALID_ARGUMENT` | 对用户不直接可见；客服/财务按差异处理 |

### 2.2 状态机（冻结）

```
INTENT ──渠道回调(PENDING)──> PENDING ──渠道回调(PAID)──> PAID ──refund()──> REFUNDED
   │                              │
   └──回调(FAILED)──> FAILED      └──回调(FAILED)──> FAILED
```

| 状态 | 含义 | 是否有账本 |
|---|---|---|
| `INTENT` | 已创建订单，未支付 | ❌ |
| `PENDING` | 渠道处理中 | ❌ |
| `PAID` | 渠道确认收款 | ✅ `DEPOSIT`（仅一次） |
| `FAILED` | 渠道失败/关闭 | ❌ |
| `REFUNDED` | 已退款 | ✅ 追加 `REFUND` |

> 状态迁移由回调驱动；**非法迁移 → `ILLEGAL_STATE`**（例如 `REFUNDED` 再回调 `PAID`）。

### 2.3 失败码与用户提示的对应（不暴露内部细节）

| 失败码 | 对用户 | 对客服/后台 |
|---|---|---|
| `SIGNATURE_INVALID` | “支付校验异常，请联系客服” | 记录请求指纹/渠道/时间；**不入账** |
| `TIMESTAMP_EXPIRED` | “支付信息已过期，请重新支付” | 检查渠道时钟/重试 |
| `AMOUNT_MISMATCH` | “支付金额校验异常，请联系客服” | 订单/回调金额对比；**不改状态** |
| `CHANNEL_UNSUPPORTED` | “该支付方式暂不可用” | 渠道未实现/未配置 |
| `ORDER_NOT_FOUND` | “订单不存在或已失效” | 核对 orderId/渠道单号 |
| `CALLBACK_REPLAYED` | （一般无感，幂等处理） | 重放记录；若无法幂等映射则告警 |

### 2.4 时序（文字版）

1. 用户选金额/渠道 → 后端 `createIntent` → 返回 `payUrl`（`INTENT`，不写账本）；
2. 用户在渠道完成支付 → 渠道异步回调 → 后端 `handleCallback`：
   - 验签（原始 body）→ 时间窗 → 订单存在 → 金额一致 → `providerTxnId` 幂等；
   - 写账本 `DEPOSIT`（一次）→ 订单置 `PAID`；
3. 前端轮询/SSE 看到 `PAID` → 展示“余额已到账”；
4. 退款：`refund(orderId)`（仅 `PAID`）→ 渠道退款 + 账本 `REFUND` → `REFUNDED`；
5. 日切：`Reconciler.run({date})` → 逐笔对账 → 差异挂单。

## 3. 回调安全

### 3.1 为什么必须验**原始 body**（不是解析后的 JSON）

| 做法 | 问题 |
|---|---|
| 先 `JSON.parse` 再 `JSON.stringify` 验签 | 键顺序、空格、Unicode 转义、数字格式都可能变化 → 签名必然不一致（正常回调被拒） |
| 用解析后的对象“按字段重算签名” | 不同解析器对重复键/大整数/转义处理不同 → **签名歧义**，攻击者可构造“解析后一样、原始字节不同”的 body 绕过 |
| **验原始字节（推荐）** | 渠道签的是**它发出的原始字节**；我们保留 raw body，用 `secret` 做 HMAC-SHA256，再解析副本 |

契约口径：`x-signature: sha256=<hex>`，对**原始 body 字节**做 HMAC-SHA256；比较用**恒定时间**比较；secret 不落日志；验签通过前**不解析、不入账、不改状态**。

### 3.2 时间窗 + `providerTxnId` 幂等 + 金额强校验

| 防线 | 规则 | 失败码 |
|---|---|---|
| 时间窗 | 渠道时间戳与本机时间差 > `timestampWindowMs`（默认 5 分钟） | `TIMESTAMP_EXPIRED` |
| 幂等 | 同一 `providerTxnId` 重复回调 → 只入账一次，返回 `duplicate:true` | （正常幂等，不报错） |
| 金额 | 回调金额（整数分）必须与订单 `amountCents` 完全一致 | `AMOUNT_MISMATCH` |
| 订单 | 订单必须存在且状态允许该回调 | `ORDER_NOT_FOUND` / `ILLEGAL_STATE` |

### 3.3 验签失败为什么**绝不能入账**

- 伪造回调 = 凭空给账户加钱（`missingInProvider` 的源头），是**直接资金损失**；
- 一旦入账再“冲正”，需要额外账本条目、客服解释与风控调查；**在入口拒绝的成本最低**；
- 验签失败时：**不改订单状态、不写账本、不返回成功**；记录告警与请求指纹（用于溯源），但响应不泄露内部细节。

### 3.4 重放攻击的三种形态

| 形态 | 攻击方式 | 防线 | 结果 |
|---|---|---|---|
| **原样重放** | 把同一回调 body 再发一次 | `providerTxnId` 幂等 | 第二次 `duplicate:true`，不重复入账 |
| **旧时间戳重放** | 用过去截获的回调（签名仍有效）重发 | 时间窗（5 分钟） | `TIMESTAMP_EXPIRED` |
| **篡改重放** | 改订单号/金额/接收方后重发 | HMAC 验签（签名对不上） | `SIGNATURE_INVALID` |
| （补充）跨渠道重放 | 把 A 渠道回调发给 B 渠道 | 渠道与 order.channel 校验 | `ILLEGAL_STATE` / `CHANNEL_UNSUPPORTED` |

> 三种形态对应三种不同失败码——**不能用一个“验签失败”糊弄全部**，否则排查时无法区分“伪造”与“过期”。

### 3.5 回调验签落地检查表

| 检查项 | 要求 | 反例 |
|---|---|---|
| 原始 body 保留 | 在路由层以 `Buffer/raw` 读取，验签后再解析 | 框架自动 `JSON.parse` 后再拼回去 |
| 签名头 | `x-signature: sha256=<hex>`，恒定时间比较 | 用 `===` 比较（时序侧信道） |
| secret | 来自 KMS/env，可轮换；不落日志 | 硬编码/提交仓库 |
| 时间戳 | 5 分钟窗口；本机时钟校准 | 忽略时间戳，只验签 |
| 幂等 | `providerTxnId` 唯一约束/去重表 | 只按 orderId 去重（不同渠道单号会撞） |
| 金额 | 整数分强校验；渠道金额单位转换只发生在 provider | 元/分混用，或先入账后校验 |
| 渠道 | 回调渠道必须等于订单渠道 | 任意渠道回调都可入账 |
| 日志 | 记录 orderId/渠道/结果；不记录 secret/完整 body | 把 body（含 PII）整段打日志 |

## 4. 对账

### 4.1 日切口径（订单/金额，不按笔数）

| 口径项 | 规则 |
|---|---|
| 对账对象 | 同一自然日（以渠道结算/订单完成时间为准）的 `PAID` 订单 vs 账本 `DEPOSIT` |
| 主键 | `orderId`（与 `pay:<messageId>` 类幂等键关联，具体以实现为准） |
| 金额 | **整数分**；逐笔比较 `providerAmountCents` vs `ledgerAmountCents` |
| 不按笔数 | “渠道 100 笔、账本 99 笔”只说明有差，**说不清差哪笔**；必须逐笔 |

### 4.2 结果分类

| 分类 | 含义 | 危险度 |
|---|---|---|
| `matched` | 订单与入账一一对应、金额一致 | 无 |
| `mismatched` | 同一订单金额不一致（多/少入账） | 高（需调账/查 bug） |
| `missingInLedger` | 渠道收款但账本无 `DEPOSIT`（用户已付钱、余额没到） | 高（客诉；可补） |
| `missingInProvider` | 账本有 `DEPOSIT` 但渠道无对应收款（**无源入账**） | **最高**（资金凭空多出，可能被套现） |

### 4.3 处置流程与升级

| 步 | 动作 | 责任 |
|---|---|---|
| 1 | 日切后跑 `run({date})`，归档 `report({date})` | 财务/运维 |
| 2 | 差异逐笔挂工单（订单号/金额/原因） | 财务 |
| 3 | `missingInLedger`：凭渠道对账单核实 → **补记 `DEPOSIT`（带原因与审批，不改历史）** | 财务 + 后端 |
| 4 | `missingInProvider`：**立即暂停相关入账/提现**，查回调来源（伪造/重复/内部 bug），按 P0 处理 | 安全 + 财务 |
| 5 | `mismatched`：查订单/回调/账本三段；以账本为真相，**追加调账条目**，不直接改余额 | 财务 + 后端 |
| 6 | 关闭工单并更新规则/告警；连续差异升级供应商 | 财务 + 采购 |

**升级规则**：出现 `missingInProvider` 或单日差异金额超过阈值（⚠ 阈值财务定）→ P0；同一渠道连续 3 日差异 → 暂停该渠道入账并升级。

### 4.4 只读、空日与报告

- **对账只读**：`run/report` 不修改订单/账本状态（契约不变量④）；修正走独立调账流程。
- **空数据日**：`checked:0, ok:true`（不是错误）；避免“没有交易=对账失败”。
- **报告**：`report({date})` 产出可归档 Markdown（含日期/checked/matched/差异逐笔）；归档保留期 ⚠ 财务/法务定。

### 4.5 对账报告样例（示意）

```markdown
# 对账报告 2026-10-21
- checked: 128 · matched: 126 · ok: false
- mismatched:
  - order-1001: provider=5000 ledger=4800 reason=AMOUNT_MISMATCH
- missingInLedger: order-1002
- missingInProvider: order-1003   ← 最高危险：无源入账，升级 P0
```

> 报告只列事实与原因分类，**不写“已修正”**；修正由调账流程单独记录。

## 5. 接真实渠道的切换清单

### 5.1 只换 provider（接口不变）

`createIntent / handleCallback / refund` 的调用方不变；新增渠道只需实现 provider 的：
①`createPayUrl(order)`；②`verifyCallback(headers, rawBody)`；③`parseCallback(rawBody)`（金额/单号/状态）；④`refund(order, amount)`；⑤渠道配置（证书/密钥/商户号）。

### 5.2 微信支付 v3 / 支付宝 的差异（⚠ 全部需复核官方文档）

| 项 | 微信支付 v3 | 支付宝 | 我们的 provider 责任 |
|---|---|---|---|
| 验签材料 | 商户私钥 + 平台证书/公钥；回调签名头（`Wechatpay-*` 系列） | 应用私钥 + 支付宝公钥；`sign` 参数（RSA2/SHA256withRSA） | provider 内完成，业务不感知 |
| 回调体 | JSON，`resource` 为加密数据（AES-256-GCM，需解密） | 表单/JSON 参数（`notify`），需按规则验签 | provider 解密/验签后**统一成内部回调结构** |
| 金额 | 整数分 | 字符串“元”（需转分） | provider 统一成 `amountCents`（整数分） |
| 退款 | 退款单号、部分退款规则 | 退款请求号、部分退款规则 | provider 映射到内部 `refund(orderId, amount)` |
| 幂等键 | 商户订单号/`providerTxnId` | 商户订单号/`trade_no` | provider 统一成内部 `providerTxnId` |

> **唯一替换点**：`channel-adapter.mjs` 的渠道实现；**不允许**在 `handleCallback` 业务分支里写 `if (channel === 'wechat')`。

### 5.3 真实渠道沙箱联调顺序

| 步 | 动作 | 出口 |
|---|---|---|
| 1 | 用沙箱商户号跑通「下单→支付→回调」 | order `PAID`、账本 1 条 `DEPOSIT` |
| 2 | 校验验签（含错误签名/过期/篡改） | 三种失败码可复现 |
| 3 | 校验退款（全额/部分、重复退款） | `REFUNDED`、账本 `REFUND` 幂等 |
| 4 | 拉渠道对账单跑日切对账 | 差异逐笔可解释 |
| 5 | 与 mock 语义对照 | 同一套 E1–E6 通过 |

## 6. 验收 Gate E1–E6（docs/29 的 E，非 25 的 E）

> 命名提醒：[25 §6](./25-v0.0.5-内测保障.md) 也有一组 E1–E6（健康保障 Gate）。引用时必须写「docs/29 E1」或「docs/25 E1」，**禁止混用**。

| # | 验收项 | 判定标准（可执行） | 验证命令 | 本机状态 |
|---|---|---|---|---|
| E1 | **INTENT 不产生账本** | `createIntent` → 订单 `INTENT`；账本无 `DEPOSIT`；重复 `orderId` → `ORDER_EXISTS` | `--filter=payment-channel` | ⚠ 实现落地中 |
| E2 | **正常回调入账** | mock 签名回调 → `PAID`；账本恰好 1 条 `DEPOSIT`，金额一致 | `--filter=payment-channel` | ⚠ 实现落地中 |
| E3 | **验签失败不入账** | 错误签名 → `SIGNATURE_INVALID`；订单状态不变；账本无流水 | `--filter=payment-channel` | ⚠ 实现落地中 |
| E4 | **重放/过期** | 同 `providerTxnId` 再回调 → `duplicate:true` 且仍 1 条 `DEPOSIT`；超时间窗 → `TIMESTAMP_EXPIRED` | `--filter=payment-channel` | ⚠ 实现落地中 |
| E5 | **金额不一致拒入账** | 回调金额 ≠ 订单金额 → `AMOUNT_MISMATCH`；不入账、状态不变 | `--filter=payment-channel` | ⚠ 实现落地中 |
| E6 | **对账逐笔与只读** | 构造 mismatched/missingInLedger → 逐笔列出且 `ok=false`；空日 `checked:0, ok:true`；对账前后状态不变 | `--filter=reconcile` | ⚠ 实现落地中 |

**Gate 规则**：E1–E6 全过才允许接真实渠道沙箱；mock 全过不等于真实渠道可用（真实渠道还要过 §5 的验签/解密/对账差异）。

**反例（看起来通过的三处）**：

1. **「回调成功」**：只测返回 ok 不算——必须断言账本**恰好一条** `DEPOSIT`。
2. **「重放防护」**：只测同单号重复不算——必须测**过期时间戳**与**篡改 body**。
3. **「对账通过」**：只测 `ok=true` 不算——必须构造差异，验证**逐笔列出**与只读。

## 7. 风险与合规

| 风险 | 说明 | 处置 |
|---|---|---|
| **二清边界** | 代收/分账/资金池可能触发二清；本版只做单商户代收（mock） | 不接分账；真实渠道前法务复核（§8） |
| **退款与发票** | 渠道退款 ≠ 已开发票冲红；发票需财务流程 | 退款只动账本；发票另走财务系统（⚠ 税务） |
| **对账差异的资金归属** | `missingInProvider` 可能是套现/伪造；`missingInLedger` 是用户应得 | 差异挂账不直接改余额；P0 升级 |
| **拒付/chargeback** | 本版**未做**：真实渠道的拒付/争议会反向扣款 | ⛔ 未实现；真实渠道上线前补（见 §8） |
| **渠道不可用** | 见 [25 §2](./25-v0.0.5-内测保障.md) 降级矩阵：不阻塞内测体验额度 | 渠道降级/备用，不静默成功 |
| **密钥泄露** | HMAC secret / 商户私钥泄露 = 可伪造回调 | KMS/密钥管理；轮换；日志不留 secret |

## 9. 一页速查（运营/财务每天看什么）

### 9.1 财务每天三件事

1. **对账 `ok`**：`missingInProvider` / `mismatched` 是否为空；不为空 → 挂工单，**不改余额**。
2. **金额口径**：只按「订单/入账金额」核对，不按笔数；差异逐笔。
3. **差异升级**：`missingInProvider` → P0（可能套现）；连续 3 日差异 → 暂停该渠道入账。

### 9.2 运营/客服常见问题

| 用户说 | 看什么 | 回复 |
|---|---|---|
| “我付了钱没到账” | 订单状态 + `missingInLedger` | “已记录，财务核实后补入账” |
| “重复扣款” | `providerTxnId` 去重记录 | “只入账一次，重复回调已幂等处理” |
| “退款没到” | `REFUND` 流水 + 渠道退款单 | “退款已提交，到账时间以渠道为准” |

### 9.3 三条红线

1. **验签失败绝不入账**（伪造回调 = 凭空加钱）。
2. **对账只读**：差异只能挂账/补记，不能直接改余额。
3. **唯一替换点是 provider**：业务代码不得出现渠道分支。

### 9.4 v0.0.9 不是什么

- 不是「真实支付已上线」：mock 先行；真实渠道需资质 + 沙箱 + §5 清单。
- 不是「分账/二清/发票系统」；不是「chargeback 处理」；不是「自动调账」。

### 9.5 30 天落地节奏

| 周 | 交付 | 出口 |
|---|---|---|
| W1 | mock provider + 意图/回调/入账（E1–E3） | 验签失败不入账 |
| W2 | 幂等/时间窗/金额校验（E4/E5） | 重放只入账一次 |
| W3 | 对账 `run/report`（E6） | 差异逐笔、只读、空日 ok |
| W4 | 真实渠道沙箱评估 + §8 复核 | 是否具备接渠道条件（不承诺开通） |
