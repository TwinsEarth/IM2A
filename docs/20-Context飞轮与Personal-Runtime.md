## 1. 一句话判据 + 四项工程命题

### 1.1 判据：把「Personal Agent」拆成 Context + Agent

| 传统说法 | 问题 | 我们的拆法 |
|---|---|---|
| 「我的 Personal Agent」 | 暗示 Agent 本身是资产，但它随时可换模型/换框架/换机器 | **Agent = 可替换的执行体**（模型、运行时、框架都可租） |
| 「它记得我」 | 记忆散落在会话历史/供应商云/端侧缓存，迁移即丢 | **Context = 用户资产**：`PERSONAL/TASK/WORKING` 三层显式管理（§33），可 snapshot/restore、可审计 |
| 「它懂我」 | 懂不懂取决于样本，而样本是协商/审批记录 | **飞轮输入 = 协商与审批记录**（§18/§4/§16），越用越厚、越厚越难搬走 |

**为什么「Context 租不到」**：模型 API 谁都能买；但「这个人的关系档位、边界、历史决策、被谁授权过什么」不在任何供应商的通用模型里，只能由我们自己累积并保证主权（§33 的 `snapshot` 不包含 `WORKING` 与凭证，见 §3）。

### 1.2 四项工程命题：我们的答案、落点、状态

| # | 命题 | 我们的答案 | 落点（契约/文件） | 状态 |
|---|---|---|---|---|
| P1 | **状态如何跨任务延续** | `PERSONAL`（年/画像/边界）+ `TASK`（天/检查点/等待条件）进可迁移包；`WORKING`（单次执行）永不迁移 | **§33** `services/orchestrator/src/person-runtime.mjs`（`STATE_LAYER`、`RUNTIME_TASK_STATE`、`snapshot/restore`） | **✅ 已代码化**（`--filter=person-runtime`，12 passed） |
| P2 | **权限如何管理** | 授权是 scope 化的、单次消耗、带签名回执；委托必须衰减；读侧另有可见域 | **§35** `scoped-grant.mjs`（`GRANT_SCOPE`/`GRANT_CODE`）+ 既有 §30 委托 + §13 可见域 | **✅ 全链已代码化**（§35 `--filter=scoped-grant` 11 passed；§30 已代码化） |
| P3 | **后台任务如何启动** | 任务状态显式管理：`WAITING`（外部事件/审批/日程）→ `resume`；持久邮箱兜底离线投递 | **§33** `wait/resume` + `RUNTIME_TASK_STATE`；**§29** 邮箱 | **✅ §33 已代码化**（12 passed）/ 邮箱已代码化 |
| P4 | **跨服务身份如何传递** | 密钥即身份（§11）→ 签名信封（§26）→ scoped 授权 + 回执（§35）；不靠「内部网络即可信」 | §11/§26/§35；生产侧 mTLS | **✅ 已代码化**（§11/§26/§35 均有测试） |

> 四项命题的共同点：**都不依赖「模型记住」**。状态在 Runtime、权限在授权对象、后台任务在状态机、身份在密钥与回执——模型只是执行体。

### 1.3 四项命题的验收口径（评审可直接抽查）

| 命题 | 验收问题 | 通过标准 | 证据（测试名） |
|---|---|---|---|

### 2.1 云端 Runtime：取「显式 Task State」，不取「厂商云 VM」

| 候选机制（⚠ 需复核） | 我们取什么 | 为什么 |
|---|---|---|
| Meta Muse Secure VM 的「安全执行环境」 | 只取「执行环境可替换、状态外置」的思想 | Context 若在 VM 内，迁移=搬迁；我们把状态放 §33 的显式三层 |
| OpenAI dots 的「云电脑」形态 | 只取「任务可等待外部事件」的交互范式 | 云电脑是产品形态；我们要的是**任务状态机**（`WAITING` + `resume`） |
| 腾讯云「执行与等待交替」 | 取「等待不是挂起进程，而是状态 + 条件」 | 进程会丢，状态可恢复；与 §33 `wait/resume` 一致 |

**不采纳厂商云 VM 的理由**：VM 提供的是「执行」，不是「主权」；把 `PERSONAL` 状态放进厂商 VM，等于把 Context 租出去——与本文判据直接冲突。

**状态**：§33 已代码化（`--filter=person-runtime`，12 passed）；端侧方案为 ⚠ 设计、无硬件不实现。

### 2.2 端侧上下文层：感知常在线、编排按需唤醒、能力 MCP 暴露

| 端侧候选（⚠ 需复核） | 借什么 | 我们的设计 | 明确不采纳 |
|---|---|---|---|
| 高通 Liquid Context | 「上下文随场景分层、端侧先筛」的思路 | 端侧只做唤醒/VAD/意图粗分类/敏感前置过滤（[04](./04-SDK与端侧设计.md)） | 绑定芯片 SDK |
| Tandem 前缀复用 | 「复用已有前缀降低端侧推理成本」 | 端侧缓存系统前缀，云端 planner 按需唤醒 | 绑定其推理栈 |
| StepX Neo（NDP120 + MCP 原子能力） | 「端侧能力以 MCP 暴露、原子调用」 | 端侧能力（KWS/VAD/播报）以原子能力暴露，不跑完整 Agent Loop | 绑芯片/OS（[15 §5](./15-四层技术栈映射与自研边界.md) 已否决） |

**设计口径**（⚠ 设计，无硬件不实现）：感知层常在线（低功耗守门）；编排层按需唤醒（云端 planner）；端侧能力以 MCP 原子调用暴露，**端侧不持有长期 token、不判断业务权限**。原始音频不出端侧、物理指示灯与静音开关不变。

**端侧上下文的三条硬约束**（设计评审用）：

1. 端侧只缓存投影，不是 Context 事实源（事实源在 §33 服务端）。
2. 端侧能力以原子 MCP 调用暴露，单次调用可审计；不跑完整 Agent Loop。
3. 不与任何芯片厂商 SDK 绑定：能力接口按 MCP 描述，换芯片只换适配层。

### 2.3 授权协议：取「scope 化 + 签名回执」，不接 PAP/PACT 完整栈

| 协议候选（⚠ 需复核） | 借什么 | 我们落点 | 与既有模块的关系 |
|---|---|---|---|
| PAP：身份与授权分离 | 「身份可验证 ≠ 已授权」 | §11 身份自签卡片；平台只签短期 token（§12） | 与 §12 的 token 边界一致 |
| PACT 三步（发现→OAuth 同意→短期委托 token） | 「发现 → 人类同意 → 短期 scope」三步骨架 | **§35** `ScopedGrant.grant`（scopes/ttl/priceCents）→ `consume`（单次）→ `verifyReceipt` | §35 负责「单条消息的 scope 与回执」；§30 负责「Agent 之间的委托衰减」；§31 负责「平台事件入链」 |

**三者的分工（防重复）**：

| 机制 | 管什么 | 不管什么 |
|---|---|---|
| §35 `ScopedGrant` | 一条消息的「看摘要/看原文/回复」scope 与单次回执 | 不负责 Agent 层级委托，不负责平台接入 |
| §30 `DelegationService` | Agent 之间的再授权：scope 子集/时限不超父/跳数受限/级联撤销 | 不负责单条消息的消费与回执 |
| §31 `ImAdapter` | 平台事件归一化 + 能力声明 | 不负责授权判定（判定在 §35/§30/§13） |

**PACT 三步 ↔ 我们的三步（映射不是照搬）**：

| PACT 步骤 | 我们对应 | 差异 |
|---|---|---|
| 发现（发现对方能力/端点） | §11 `agent_cards` + §12 网关注册表 | 我们要求卡片自签 + 平台 token 双证 |
| OAuth 同意（人类授权） | §32 审批挂起（陌生来信）+ §4 审批单（动作） | 我们把「同意」拆成「关系级同意（挂起）」与「动作级审批」 |
| 短期委托 token | §35 `grant`（scope + 5min 默认 TTL）+ §30 委托（链式） | 我们加**单次消耗 + 签名回执**，不做长期 refresh token |

### 2.4 Context 飞轮：确认锁定 + 三层 + 指标，不接单一记忆框架全家桶

| 候选（⚠ 需复核） | 借什么 | 落点 | 策略 |
|---|---|---|---|
| MyContext：确认锁定 | Agent 只能 propose，人确认才 `LOCKED`；冲突上抛 | **§34** `context-lock.mjs`（`LOCK_STATE`、`CONTEXT_LOCK_CODE`） | 改造复用（自研实现） |
| HMO 三层 | 「稳定层/任务层/工作层」的分层思想 | **§33** `STATE_LAYER`（PERSONAL/TASK/WORKING） | 只借范式（我们加「是否可迁移」判据） |
| 「文件即记忆」渐进披露 | 记忆以可读单位渐进披露、可引用 | §17 `PersonaMemory`（SOUL/记忆分离、晋升/衰减/遗忘）+ §34 锁定关键结论 | 只借范式（文件是视图，不是事实源） |
| Mem0 / Zep / Letta | 记忆抽取/检索/会话记忆的工程经验 | 参考实现（⚠ 不引入默认栈，[15 §5](./15-四层技术栈映射与自研边界.md) 已写） | 只作参考 |

**飞轮指标（✅ 其中一部分已由现有模块产出）**：

| 指标 | 来源 | 用途 | 状态 |
|---|---|---|---|
| `personalKeys` / `tasksTotal/tasksCompleted/tasksWaiting` | §33 `metrics()` | 看「跨任务延续」是否真的发生 | ⚠ 设计（随 §33 落地） |
| `pending/locked/conflicts` | §34 `stats()` | 看「确认锁定」是否被使用、冲突是否被上抛 | ⚠ 设计（随 §34 落地） |
| 审批通过率/驳回率/修改率 | §4 审批事件 | 飞轮输入质量（决定边界收紧/放宽） | ✅ 已代码化（审批引擎） |
| 协商完成率/超限率 | §5 `TASK_STATE` | 协商轨迹是否健康 | ✅ 已代码化（协商引擎） |

> 飞轮不是「多存点记忆」，而是**把人的确认与决策转成下一次更少的确认**：审批记录→边界收敛→Agent 自主率上升→审批记录更多。指标只用于判断「这个环有没有转起来」，不是 KPI 粉饰。

**飞轮闭环（文字版，六步）**：

1. 记录：协商轮次（§5）与审批决策（§4）进签名审计（§16）。
2. 抽取：从记录中提取候选结论/偏好（Agent 只能 `propose`，§34）。
3. 确认：属主确认 → `LOCKED`（`confirm` 只有 owner 能调，非 owner `FORBIDDEN`）。
4. 消费：`LOCKED` 的结论进入 `PERSONAL` 层（§33），下次执行直接复用。
5. 收敛：审批通过率/修改率驱动边界收紧或放宽（§19 工具策略）。
6. 再记录：新的决策产生新的记录——环闭合；任何一步都不允许模型自称「已确认」。

**状态**：§34 已代码化（`--filter=context-lock`，14 passed）；飞轮指标中的审批/协商类来自已代码化模块，§33/§34 的指标随两模块落地。

## 3. 三个结构性差异（与云厂商路径明确区分）

| # | 差异 | 云厂商路径（一般做法） | 我们（契约依据） | 为什么重要 |
|---|---|---|---|---|
| 1 | **Context 主权可迁移** | Context 在厂商云里，导出=妥协；换平台=重来 | §33 `snapshot()` 只含 `PERSONAL/TASK`，**不含 `WORKING`、不含凭证**；带 `hash`，`restore` 校验 `version`/`hash`，损坏即拒绝（`BUNDLE_INVALID`/`VERSION_MISMATCH`）；`secret:*` 写入 → `SECRET_IN_LAYER` | 用户能带着 Context 走，才是「Personal」；不能迁移就只是「租了个 Agent」 |
| 2 | **飞轮输入源是协商与审批记录** | 通用平台的输入是聊天/点击，不产生「决策边界」 | 协商（§5 8 态）+ 审批（§4 九态）+ 签名审计（§16）→ 边界收紧/放宽（§19 工具策略）+ 锁定（§34） | 这些记录**别的平台不会产生**：它们没有五档信任、预审、付费、审批的完整链路 |
| 3 | **付费 = 可验证意图信号，只解锁 scope** | 付费=买通道/买曝光，容易变成「花钱绕过过滤」 | §35：`priceCents` 只是记录，**不参与授权判定**；scope 白名单 `VIEW_SUMMARY/VIEW_ORIGINAL/REPLY`，每个 scope 单次消耗；回执绑定 `messageId+scope+action+at`，可验签 | 付费买的是「已被预审过的有效触点」的**查看权**，不是通行证；否则 v1 的「付费不能绕过预审」被推翻 |

> 一句话：云厂商卖「执行 + 存储」，我们卖「**主权 + 边界 + 证据**」。三者都不是模型能力，而是治理能力。

## 4. 两个风险的处置

### 4.1 端侧 Context 碎片化 → 跨设备同步/归并协议（设计要求）

**风险**：手机/耳机/眼镜/手表各自缓存 Context 片段，换设备或断网后出现「同一用户不同记忆」；若绑定某家芯片 SDK，换芯片即迁移灾难。

**处置（⚠ 设计，⛔ 实现路线图）**：

| 设计要点 | 内容 |
|---|---|
| 单一事实源 | Context 的权威副本在服务端（§33 `PERSONAL/TASK`）；端侧只是缓存/投影 |
| 归并协议 | 端侧提交带 `version + deviceId + 逻辑时钟` 的增量；服务端按 §34 `propose` 入 PENDING，冲突上抛人（`CONFLICT`），不自动合并 |
| 跨设备身份 | 设备身份用独立密钥（§11），不与用户密钥混用；设备丢失可单独吊销 |
| 明确禁止 | 绑定单一芯片 SDK；端侧持有长期 token；端侧决定权限 |

### 4.2 协商 Context 污染（传话游戏）→ Sentinel 式协商轨迹审查器

**风险**：多轮协商中每一方 Agent 都会「转述」对方立场；几轮之后，提案可能已经偏离用户预设边界（例如「可以接受 200 元内」被传成「300 元左右」）。我们已有 `maxRounds=5/maxTokens=4000/maxSeconds=300`、`EgressGuard`、`VisibilityGate`，但**没有「每轮提案是否仍在你预设边界内」的漂移检测**。

**已有 vs 缺什么（诚实拆分）**：

| 能力 | 状态 | 依据 |
|---|---|---|
| 轮次/Token/墙钟硬上限 | ✅ 已代码化 | §5 `NegotiationEngine`（超限转 `INPUT_REQUIRED`） |
| 外发内容出口护栏 | ✅ 已代码化 | §7 `EgressGuard`（`BLOCK` 必拦） |
| 读侧可见域 | ✅ 已代码化 | §13 `VisibilityGate` |
| 每轮提案的**边界漂移检测** | ⛔ 路线图 | 计划：从 `PERSONAL` 规则抽取「边界向量」（金额/对象/时间窗/承诺级别），每轮提案与上轮、与边界做 diff；越界 → `INPUT_REQUIRED` 上抛 + 审计；不回写 Context |

> 漂移检测器的定位是**审查器**，不是「另一个模型裁判」：它只做结构化比较（金额/对象/时间/承诺），命中即上抛人；模型不能替人决定「这算不算越界」。

### 4.3 两个风险的量化信号（验收用）

| 风险 | 可观测信号 | 阈值（⚠ 规划值，需运营校准） | 动作 |
|---|---|---|---|
| 端侧碎片化 | 同一用户跨设备 `snapshot.hash` 不一致次数；同步冲突计数 | 周冲突 > 5 次或出现「记忆回退」投诉 | 触发归并协议评审，禁止端侧单写 |
| 协商漂移 | 每轮提案与 `PERSONAL` 边界的 diff 命中数；越界提案占比 | 单会话越界 ≥1 次即上抛；越界率 > 5% 周 | `INPUT_REQUIRED` 上抛 + 审计留痕；连续超阈值 → 收紧 `maxRounds` |

## 7. 一页速查（评审用）

### 7.1 判据与四项命题

| 判据 | 四项命题 → 答案 |
|---|---|
| 模型可以租，Context 租不到 | P1 状态延续 → §33 三层；P2 权限 → §35+§30+§13；P3 后台任务 → §33 `WAITING`+§29；P4 身份传递 → §11+§26+§35 |

### 7.2 四层取/不取

| 层 | 取 | 不取 |
|---|---|---|
| 云端 Runtime | 显式 Task State + Person-scoped Runtime（§33） | 厂商云 VM（Context 会被托管） |
| 端侧上下文 | 感知常在线/编排按需唤醒/端侧能力 MCP | 绑定芯片厂商 SDK |
| 授权协议 | scope 化 + 签名回执（§35） | PAP/PACT 完整协议栈 |
| Context 飞轮 | 确认锁定（§34）+ 三层（§33）+ 指标 | 单一记忆框架全家桶 |

### 7.3 三个结构性差异（评审必看）

1. **Context 主权可迁移**：`snapshot` 不含 `WORKING`、不含凭证；`hash`/`version` 校验，损坏拒绝。
2. **飞轮输入 = 协商与审批记录**：别的平台不产生这类「决策边界」数据。
3. **付费 = 可验证意图信号**：`priceCents` 只记录，scope 白名单 + 单次回执，**付费不扩权**。

### 7.4 两个风险

| 风险 | 现有 | 缺什么 | 处置 |
|---|---|---|---|
| 端侧 Context 碎片化 | 端侧只做守门（设计） | 跨设备归并与逻辑时钟 | 归并协议（⛔ 路线图），禁止绑芯片 SDK |
| 协商 Context 污染 | 轮次/Token 上限、EgressGuard、可见域（✅） | 每轮提案的边界漂移检测 | Sentinel 式审查器（⛔ 路线图），越界上抛人 |

### 7.5 最需拍板的 Context 主权问题

**`PERSONAL` 层可迁移包能否由 Agent 主动申请导出？**

- **建议：不能**。导出必须由用户本人在可信端确认，并生成与 §35 同款签名回执；Agent 只能 `propose`（§34），不能 `confirm`。
- 开放给 Agent 申请导出 = 把 Context 主权交回给可被注入的执行体；一旦模型/框架被换或被盗用，用户无法知道是谁导出了什么。
- 若要支持「换机/换平台」，走「用户确认 + 一次性导出回执 + 导入后本地销毁旧包」流程；第三方 Agent 永远拿不到 `PERSONAL` 全量。

- [ ] 是否把「契约冻结」写成「已实现」；✅/⚠/⛔ 是否每条都有依据。
- [ ] §33 的 `WORKING` 是否真的不进 snapshot；`secret:*` 是否真的被拒绝入层。
- [ ] §34 的 `LOCKED` 是否不可被子 Agent 覆写；冲突是否上抛而不是自动合并。
