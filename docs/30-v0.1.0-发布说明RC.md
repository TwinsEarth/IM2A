## 2. 版本三元组

### 2.1 三元组定义（§51）

| 字段 | 值 | 含义 |
|---|---|---|
| `version` | **`0.1.0`** | 产品/代码版本（与 tag 一致） |
| `contractRevision` | **`R21`** | 契约修订号（§1–§52；R1–R21 可追溯） |
| `schemaVersion` | **`1`** | 持久化数据 schema 版本（`jsonfile`/快照；PG 迁移后另定） |

### 2.2 端点字段

| 端点 | 字段 | 用途 |
|---|---|---|
| `GET /api/version`（公开） | `{version, contractRevision, schemaVersion, capabilities, node}`（与 `buildInfo` 一致） | 任何实例可自报身份；运维/客服排查第一步 |
| `GET /api/health` | `{ok, version, schemaVersion, ...}` | 健康检查同时暴露版本三元组 |
| 发布报告 | 三元组 + 每条命令/耗时/结果 | 归档与回溯 |

> 实现说明：`buildInfo` 的 `capabilities` 字段当前返回**能力数量**（声明清单本体是 `CAPABILITIES` 数组）；`/api/version` 直接透出 `buildInfo`。对外说“有多少项能力”可以，说“这些能力已验证”不行——验证看 §3 的 Gate 列。

### 2.3 为什么 schema 不匹配必须显式失败

| 场景 | 静默迁移/猜测的后果 | 我们的做法 |
|---|---|---|
| 新代码读旧数据 | 字段缺失被默认值填充 → **账/权限/审核结论被解释错**，且无告警 | `SCHEMA_MISMATCH` 显式失败；迁移由人执行 |
| 旧代码读新数据 | 新字段被忽略 → 数据丢失/幂等失效 | 同上；禁止“尽力恢复” |
| 备份恢复 | 用错版本备份覆盖线上 → 不可逆 | restore 前校验 `schemaVersion`；不匹配即拒绝 |
| 灰度/回滚 | 回滚到旧代码后 schema 已升级 → 启动即失败（显式，比带病运行好） | 回滚前确认 schema 兼容；不兼容走迁移回退方案 |

> 一句话：**“能启动”不等于“读得懂”。** 宁可启动失败并告警，也不要静默把旧数据解释成新语义。

## 4. 发布检查（§52）

### 4.1 `release-check.mjs` 五步

| 步 | 检查 | 失败含义 | 证据 |
|---|---|---|---|
| 1 | **全量测试** `node scripts/test.mjs` | 有测试失败/导入失败 | 命令 + 耗时 + 结果 |
| 2 | **一致性** `node scripts/verify.mjs` | 文档/契约/代码不一致 | 同上 |
| 3 | **自检** `node scripts/quickstart.mjs --check` | 本机起服务/自检失败 | 同上 |
| 4 | **部署产物 lint** `node scripts/deploy-lint.mjs` | systemd/Caddy/Docker 配置缺失/危险 | 同上 |
| 5 | **内置实例验收**（内存存储 + 随机端口跑默认 Gate） | 健康/鉴权/审计/指标/备份等 Gate FAIL | 同上 |

**判定（冻结）**：①任一步非零退出 → 整体失败（`exit 1`）；②报告必须含**命令、耗时、结果、版本三元组**；③只读——不修改代码/数据，内置实例用内存存储与随机端口；④失败报告**仍落盘**（归档失败现场）。

### 4.2 发布流程

```
release-check 全绿
  → 归档报告（reports/RELEASE-REPORT.md）
  → 打 tag（v0.1.0，与 VERSION 一致）
  → 发布说明/CHANGELOG 更新
  → 内测用户公告（含已知缺口）
```

**红灯处理**：不修完不打 tag；不允许“先打 tag 后补测”。

### 4.3 报告样例（归档核对）

```markdown
# RELEASE-REPORT v0.1.0
- version: 0.1.0 · contract: R21 · schema: 1
- 1 全量测试: PASS (…ms)
- 2 verify: PASS (…ms)
- 3 quickstart: PASS (…ms)
- 4 deploy-lint: PASS (…ms)
- 5 内置验收: PASS (pass 8 / fail 0 / skip 1)
- 结论: GREEN（允许打 tag）
```

> 失败时同样落盘，`结论: RED`，并把失败命令与退出码写进报告——**失败现场比成功截图更有价值**。

## 5. 升级与回滚

### 5.1 升级/回滚五步（引用 [25 §4](./25-v0.0.5-内测保障.md)）

| 步 | 动作 | 出口标准 |
|---|---|---|
| 1 **备份** | 升级前 `BackupService.create`，`verify` 通过 | `sha256` 校验 ok |
| 2 **校验** | 确认目标版本三元组与 schema 兼容性 | `schemaVersion` 匹配或已有迁移方案 |
| 3 **升级** | 停写 → 替换版本 → 启动 | 服务起、`/api/version` 正确 |
| 4 **冒烟** | `/healthz`、`/api/version`、登录、审批一张、账本只读 | 关键路径通过 |
| 5 **回滚**（如需） | 停写 → 回退版本 → 恢复备份（`restore` 不自动应用，人工决定） → 对账 | 数据与备份时点一致，差异进清单 |

### 5.2 schema 变更要求

- 任何 schema 变更必须：**新 schemaVersion + 迁移脚本 + 迁移审计**；不允许 `createWorld({restored})` 自动猜；
- 升级前先备份；迁移在停写窗口执行；迁移后跑 `release-check`/冒烟；
- 回滚到旧代码前确认 schema 兼容；不兼容 → 只能用“备份恢复 + 数据回退”，并记录数据丢失窗口（⚠ 财务/业务确认）。

### 5.3 不可回滚/高代价项

| 项 | 为什么 |
|---|---|
| 账本/审计 | 只追加；不能“回滚掉”已发生的入账（只能冲正条目） |
| 真实资金 | 渠道侧退款/对账是外部事实，回滚系统不改变渠道记录 |
| 已通知用户 | 对外话术/公告不可“撤回”，只能更正 |

### 5.4 发布后 24h 观察

| 观察项 | 阈值（⚠ 运营定） | 动作 |
|---|---|---|
| 5xx / 崩溃 | 突发上升 | 回滚或热修 |
| 登录/实名失败率 | 明显高于基线 | 查依赖/降级 |
| 付费漏斗审核段 | 异常下跌 | 查审核/人审积压 |
| 对账差异 | 出现非空 | 财务介入（不在线上改） |
| 告警量 | 是否告警疲劳 | 调阈值/静默需留痕 |

> 合计 **17 条**。**对外公告必须带“已知缺口”章节**；不许把 ⚠/⛔ 写成“已完成”。

### 6.1 缺口对 Gate 的影响（哪些 Gate 因此无法自动）

| 缺口 | 受影响的 Gate | 只能人工/暂缓 |
|---|---|---|

| Linux/证书未实测 | 预检 `TLS_INSECURE`、G5 双机 SSE | 公网内测前必须补 |
| 真实短信未接 | B1/B2/B3/B7（真实到达） | 只能 dev/log 验证逻辑 |
| 真实实名未接 | A2（真实核验） | 只能 mock 核验 |
| 真实机审未接 | C2/C4/C5（真实审核） | 只能 mock/fail-closed 验证 |
| 真实支付未接 | E1–E6（docs/29） | 只能 mock 渠道 |
| Redis/双机未验 | G1/G5（真实网络） | 单节点内测 |
| PG 未接 | 备份/恢复（PG 机制） | jsonfile + 备份 |

## 7. 对内测开放的 Go/No-Go

### 7.1 必须满足（缺一不可）

| # | 条件 | 证据 |
|---|---|---|
| 1 | **真实环境预检 7/7 绿**（可达/鉴权三态/Node/持久/真实依赖/时钟/TLS） | `scripts/accept.mjs --target ... --require-real-providers` 的预检输出 |
| 2 | **`release-check.mjs` 全绿** | RELEASE-REPORT.md |
| 3 | **33 条业务 Gate 人工签核**（docs/26 §3：2 自动 + 31 人工） | 签字表 + 证据目录 |
| 4 | **真实短信/实名/机审已接且可降级**（机审 fail-closed 到人审） | 供应商回执 + 降级演练记录 |
| 5 | **备份 verify 通过 + 恢复演练至少一次** | 备份 sha256 + 演练对账清单 |
| 6 | **协议/隐私政策就绪**（计费/退款/审核/实名/数据权利） | 法务确认版本 |
| 7 | **值班/客服话术就绪**（退款争议/降级/只读） | [25 §7](./25-v0.0.5-内测保障.md) 话术 |

### 7.2 允许带缺口上线（写明）

- **Flutter 未编译** → 只开放 Web/PWA 地址；
- **真实支付渠道未接** → 只承诺“体验额度”，不承诺充值/提现；
- **Redis/双机未接** → 单节点部署，公告“单节点维护窗口”；
- **PG 未接** → jsonfile + 备份，公告“内测数据可能清理”；
- **硬件/A2A/多租户/分账发票** → 不在本版承诺；
- **proto 未编译** → 不对外提供 SDK。

### 7.3 明确不允许（红线）

- 预检未绿 / release-check 未绿 / 人工签未齐 → **不得对外内测**；
- 真实短信/实名/机审任一未接 → **只能内部演示，不得对真实用户开放付费**；
- 无备份/未演练恢复 → 不得升级/上线；
- 把体验额度当真实资金宣传 → 一律禁止。

### 7.4 对内测公告模板（必须含）

1. 版本：`v0.1.0 RC`（不是生产版）；地址：`/app/`；
2. 能做什么：登录/实名、审批、账本、退款（未回复自助/已回复争议）；
3. 不能做什么：真实充值/提现、原生 App 推送、Flutter 客户端、多节点高可用；
4. 已知缺口：引用本文 §6（至少列 1/3/4/5/6/7 条）；
5. 支持渠道：客服/工单/SLA（⚠ 运营定）。
