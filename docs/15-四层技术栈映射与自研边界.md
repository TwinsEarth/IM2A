> 版本 v5.0（R8 对齐）· 对应契约 `contracts/INTERFACES.md` v1.0（变更记录 **R8**，§26–§28）· 作者：架构组

> 与 [13](./13-分层选型与落地映射.md)、[14](./14-宿主型IM判据与机制落点.md) 的分工：13 按能力层裁决选型，14 按「宿主/机器人」判据重排；15 只做**四层栈位 + 复用边界**，不重复前两篇的逐项目细节（引用其小节号即可）。

## 0. 一页结论（TL;DR）

| 项 | 结论 |
|---|---|
| 总判断 | **开源解决「连接与执行」，我们解决「信任与治理」**。四层里开源能帮到的部分集中在①③④的形态与机制，②的「付费协议」只能借签名/任务语义，账本必须自研 |
| 四层复用结论 | ①**只借范式**（第三人称转达，§27）；②**改造复用**（信封/TOFU/A2A Task 语义，§26 + 既有 §5/§11/§12）；③**只借范式**（确认层 §28；渠道适配器本机不实现）；④**只借范式**（架构映射，无硬件） |
| 为什么没有「直接复用」 | 本仓库零第三方依赖、本机无网络、无硬件；四层里没有任何一层可以直接拷贝代码进来——**最接近的是「改造复用」**（借机制、重写实现），这是刻意的供应链/许可/演进锁定策略，不是能力不足 |
| 必须自研的 5 条 | 熟人五档信任矩阵、陌生人付费消息状态机、审批工作流引擎、跨 Agent 记忆隔离、签名审计链（§2） |
| 本轮三机制 | §26 签名信封 + 重放保护 + TOFU；§27 第三人称转达（禁止冒充人类）；§28 确认层不可被 planner 预批准 |
| 状态快照（2026-10-21） | 契约 R8 已冻结（§26–§28）；v5 三模块与单测已落地、`--filter` 本机复现通过：signed-envelope **10**、relay-summary **12**、confirmation-tier **10**；`verify.mjs` 写作快照 **43/43**。**全量与集成以 Lead 最终回归为准，本文不写全量 pass 数** |
| 最需评审会强调的自研壁垒 | **熟人五档信任矩阵**（§2.1）：开源 IM 的关系模型是「好友/成员」二值，无法表达 `0–4` 档 + 过期即撤销 + 每目标不同档；一旦把它外包给渠道/框架，权限语义就不在我们手里 |

## 1. 四层拆解表

| 层 | 该层解决什么 | 候选项目（⚠ 只引机制） | 我们取哪一条机制 | 复用策略 |
|---|---|---|---|---|
| **① AI 原生 IM 交互范式** | AI 在人际会话里以什么身份出现、怎么说话 | Pisces、Convia | **第三人称转达**：AI 作为合法第三方节点注入摘要，绝不冒充任何一方（§27） | **只借范式**（自研 `relay-summary.mjs`） |
| **② Agent 间通信与付费协议** | Agent 怎么互发消息、怎么表达任务、怎么收费 | dsh-meeting、a2a-dm、Beacon | **签名信封 + TOFU + 重放保护**（§26）；A2A Task 语义只放边界；付费仍走 §9 状态机 + §3 门控 | **改造复用**（借信封/任务语义，重写实现）；**付费自研** |
| **③ IM 渠道网关抽象** | 多渠道接入、连接资源占用、Token 预算、确认层 | MalikClaw、ZLAgent | **确认层**：`PLANNER` 可自动执行、`CONFIRMATION` 必须人确认，planner 自称已批准一律无效（§28）；渠道抽象只作架构参考 | **只借范式**（渠道适配器本机不实现） |
| **④ 端侧与可穿戴 Agent 运行时** | 低内存 ReAct、端侧 MCP、多节点协作、通道裁剪 | openvela | 只做**架构映射**：端侧守门、原始音频不出端侧、物理指示灯与静音开关不变 | **只借范式**（无硬件，不引 OS） |

> 策略口径：**直接复用**（拷贝/依赖其代码或服务）＝ 0 项；**改造复用**＝ 1 项（②的信封/任务语义）；**只借范式**＝ 3 项（①③④）；**自研**＝ 治理五件套（§2）。这不是保守，是四层栈位的必然结果：开源项目优化的是「连接/执行」，而我们的产品价值在「谁可以做什么」的判定权。

### 1.0 四层栈位与职责边界

| 栈位（自下而上） | 该层对谁负责 | 我们对应模块/契约 | 不允许越界的事 |
|---|---|---|---|
| ④ 端侧运行时 | 设备的采集/唤醒/播放 | [04](./04-SDK与端侧设计.md)、[06](./06-产品形态与硬件.md)；端侧不持契约模块 | 不判断业务权限、不持长期 token |
| ③ 渠道网关 | 外部 IM 渠道的接入与转换 | 生产 Go 网关（[02 §15](./02-技术选型与框架.md) 映射）；**本机不实现** | 不做业务判定、不持有账本 |
| ② 消息内核与 Agent 通信 | 消息可达、任务语义、签名 | 契约 §12/§14/§15/§26 | 不决定「能不能做」（§3 门控） |
| ① 交互范式 | 人类会话里 AI 怎么出现 | 契约 §27 `relay-summary` | 不冒充人、不替人承诺 |

**复用策略四档定义（全文统一）**

| 策略 | 定义 | 本项目适用 | 理由 |
|---|---|---|---|
| 直接复用 | 拷贝代码，或直接依赖其运行时/服务 | **0 项** | 零依赖、无网络、无硬件；供应链/许可/演进锁定 |

### 1.1 第①层：AI 原生 IM 交互范式（Pisces / Convia）→ 只借范式

| 项 | 内容 |
|---|---|
| 该层的问题 | AI 进入人际会话时，通常只有两种坏选择：把自己变成"一个人"说话（冒充，破坏信任），或者干脆不进入人类会话（价值断在 Agent 之间） |
| 候选机制 | Pisces/Convia 的「AI 是会话中的第三方节点」范式（⚠ 实现细节需复核：官方仓库 README/文档） |
| 我们取的机制 | **第三人称转达**（§27）：`RELAY_KIND.THIRD_PERSON_RELAY`；产出恒带 `attribution:'AGENT_SUMMARY'`、`notFromHuman:true`；`from` 必须是参与方 Agent；`provenance` 可追溯到是哪几个 Agent 协商出的结论 |
| 落点 | `services/orchestrator/src/relay-summary.mjs`；契约 §27；`RELAY_CODE` 五个错误码 |
| 复用策略 | **只借范式**：不接 Pisces 的 Firestore/Ably 后端（§5），自研 builder 与渲染 |
| 状态 | **v5 本轮新增**（模块与单测已落地；集成以 Lead 最终回归为准） |
| 为什么不是"直接复用" | 其数据后端与前端形态绑定自有产品；我们的会话模型是 §14 `CHANNEL_TYPE` + §16 签名审计，接不进来 |

### 1.2 第②层：Agent 间通信与付费协议（dsh-meeting / a2a-dm / Beacon）→ 改造复用（付费自研）

| 子项 | 借什么 | 落点 | 结论 |
|---|---|---|---|
| **Beacon** | Ed25519 **签名信封**（`sign`/`verify`）、**TOFU 密钥学习**（首次学习，冲突 `TOFU_CONFLICT`）、**重放保护**（nonce，`REPLAY_DETECTED`）、时间窗（`CLOCK_SKEW`） | 契约 **§26**；`services/identity/src/signed-envelope.mjs`；`ENVELOPE_CODE` 六码 | 改造复用：信封锁定「谁发的」；**验签通过 ≠ 有权发**，授权仍在 §12 网关、付费仍在 §9 |
| **a2a-dm** | ① A2A **Task 语义**（任务生命周期只放 Phase3 边界）；② **per-friend 记忆隔离**（我们已有 §6/§17 的 `MEMORY_ISOLATED`，不新造）；③ **四种接驳模式**只借「按场景选择接驳方式」的范式（具体命名/边界 ⚠ 需复核） | 契约 §5（协商 8 态）、§6/§17（隔离）、§12（归一化 `PROTOCOL`） | 只借范式：不引入其守护进程实现（§5） |
| **dsh-meeting** | A2A 协商 + 本机 MCP 受限能力 → 只借「受限能力清单」的思想；**其「无鉴权局域网」前提明确否掉**（见下；该前提的描述 ⚠ 需复核官方文档） | 契约 §3（能力门控）、§12（唯一入口） | 部分借思想；**否掉无鉴权前提** |
| **付费协议** | 中心化账本（我们已有 §8 账本 exactly-once、§9 付费消息状态机） | 契约 §8/§9 | **自研**：不引 crypto payments（§5） |

**为什么明确否掉 dsh-meeting 的「无鉴权局域网」前提**：

1. 局域网的「物理可达」不等于「有权发」——同一 Wi-Fi 下的任何设备都能冒充 Agent 投递协商/付费意图；
2. 我们的陌生人经济建立在「预审 → 付费 → 审批」上，**任何未鉴权的注入都能把门控变成摆设**；
3. 无鉴权 = 无可信审计主体，签名审计链无法回答「是谁发的」；
4. 安全边界必须是 **§12 唯一入口 + §26 签名信封 + §11 身份**，不能是「同一个局域网」。

> 一句话：dsh-meeting 的便利性来自「信任 LAN」，我们的场景恰恰假设**没有 LAN 可信任**。

## 2. 「不可复用、必须自研」清单（用户最看重的结论）

> 判据：不是「开源没有现成代码」就叫自研，而是**开源的结构性假设与我们的产品假设冲突**——即使有代码，接进来也会把治理权让渡出去。下面每一条都写「为什么开源没有」与「为什么是壁垒」。

### 2.1 熟人五档信任矩阵（§1）

| 项 | 内容 |
|---|---|
| 为什么开源没有 | 通用 IM/框架的关系模型是「好友/成员/权限位」二值或平台自定义角色；没有「同一用户对不同目标不同档位 + 档位过期即撤销 + Agent 的 `trustZoneMin`」这套语义。Matrix/Telegram/WhatsApp 的房间角色是**组织权限**，不是**社会关系信任** |
| 开源接了会怎样 | 把 `TRUST_LEVELS(0–4)` 映射成「角色」会丢失过期与逐目标差异；上游一次权限模型变更就重开一次越权面；判定散落在渠道层，`STRANGER` 默认值不再可证明 |
| 为什么是壁垒 | 它是产品的**社会契约**：档位决定 Agent 自主权、决定陌生人能否触达、决定付费与审批粒度。这份数据不在任何开源项目里，且越用越厚（关系+历史+例外），迁移成本极高 |
| 落点 | 契约 §1 `trustMatrix`；`services/orchestrator/src/trust-zone.mjs`；表 `core.trust_levels` |

### 2.2 陌生人付费消息状态机（§9 + §8）

| 项 | 内容 |
|---|---|
| 为什么开源没有 | 开源 IM 不解决「inbound attention 的定价」；加密支付项目解决的是**转账**，不是「预审 → 付费 → 查看 → 回复 → 结算」的业务状态机；更没有人把「付费不能替代过滤」写成状态前置条件 |
| 开源接了会怎样 | 用 crypto/第三方支付替换会失去 `idempotencyKey` 恰好一次、按 `messageId` 退款、渠道对账与合规自证；链上支付不可退款、不可冻结，与诈骗风控冲突 |
| 为什么是壁垒 | 它改变的是**骚扰经济学**：让批量自动化骚扰承担真实成本，同时保护「真有事的人」的低摩擦。状态机 + 账本 + 风控规则库是运营资产，不是代码资产 |
| 落点 | 契约 §8/§9；`services/payment/src/{ledger,paid-message}.mjs`；表 `pay.*` |

### 2.3 审批工作流引擎（§4）

| 项 | 内容 |
|---|---|
| 为什么开源没有 | 通用工作流（Temporal 类）提供 durable execution，但不提供「九态审批 + 白名单迁移 + 超时升级幂等 + 与门控/账本/审计绑定」的领域语义；开源审批工具多是表单流，不接 Agent 执行 |
| 开源接了会怎样 | 状态名与迁移一旦被外部引擎定义，契约就无法逐字可测；事件溯源、升级幂等、补偿边界都要重新适配，等于把治理语义外包 |
| 为什么是壁垒 | 审批是「人机分工」的产品表达：什么该人决定、什么可自动、升级给谁。它沉淀为流程模板与组织习惯，外部引擎无法复用 |
| 落点 | 契约 §4；`services/orchestrator/src/approval-engine.mjs`；表 `gov.approval_*` |

### 2.4 跨 Agent 记忆隔离（§6 / §17）

| 项 | 内容 |
|---|---|
| 为什么开源没有 | 开源记忆库（Mem0 类，默认隔离模型 ⚠ 需复核）优化「抽取/检索/召回」，默认假设「一个用户一个库」；不处理「butler 只能读摘要、不能读子 Agent 原始记忆」「`MEMORY` 域永不返回原文」「用户删除权 + tombstone + 审计可证」 |
| 开源接了会怎样 | 记忆库成为第二事实源：删除权要跨库执行、审计无法解释「谁在何时读过哪条记忆」、`MEMORY_ISOLATED` 只能靠应用层自觉 |
| 为什么是壁垒 | 隐私承诺（家庭/健康/财务记忆）靠隔离语义兑现；隔离规则与审计证据链是合规资产，不能靠外部库的默认配置 |
| 落点 | 契约 §6/§17；`memory-store.mjs`、`persona-memory.mjs`；`core`/`mem` 表与 RLS |

### 2.5 签名审计链（§16）

| 项 | 内容 |
|---|---|
| 为什么开源没有 | 有通用审计日志/区块链，但没有「业务事件（审批/付费/协商/网关路由）× 哈希链 × Ed25519 × checkpoint × WORM 归档」的组合；开源审计库通常只保证「日志不丢」，不保证「谁写的、可举证」 |
| 开源接了会怎样 | 用第三方日志服务 = 审计数据驻留与密钥在他处；用通用链 = 事件语义与业务脱节，无法按 `traceId`/`ticketId` 回放 |
| 为什么是壁垒 | 它是**合规与争议解决的证据链**：监管/司法可验证、内部可回放；每多一条业务流接入，壁垒加厚 |
| 落点 | 契约 §16；`services/audit/src/{audit-log,signed-audit}.mjs`；`gov.audit_entries/audit_checkpoints` |

> **结论**：开源给的是「连接（消息能不能到）与执行（工具能不能调）」；我们自研的是「谁可以做什么、凭什么、出了事怎么证明」——这五件套没有任何一个开源项目可以整包提供，而它们恰好是产品的定价权与合规权。

### 2.6 自研壁垒的检验方法（评审可复用）

**三问检验**：①开源是否有**结构等价**的实现（不是"有类似代码"）？②接进来后，判定权/数据/密钥是否仍在自己手里？③换掉它是否需要重写产品语义？

| 自研项 | 切换成本 | 合规权重 | 数据厚度 | 强度（排序用） |
|---|---|---|---|---|
| 熟人五档信任矩阵 | 极高（全产品依赖） | 高 | 高（关系 + 历史 + 例外） | ★★★ |
| 陌生人付费消息状态机 | 高（账本/风控/对账） | 高 | 中（交易记录） | ★★★ |
| 审批工作流引擎 | 高（用户习惯） | 中 | 高（流程模板） | ★★☆ |
| 跨 Agent 记忆隔离 | 高（删除权/RLS） | 极高 | 高（记忆数据） | ★★★ |
| 签名审计链 | 中（接口稳定） | 极高 | 中（事件链） | ★★★ |

> 表里强度只用于**排序评审优先级与预算**，不是精确评分；任何一项一旦被外部实现接管，对应强度直接降为 ★（判定权丢了）。

## 3. 本轮三机制「没有它会怎样」

### 3.1 签名信封（§26）—— 没有它，陌生人 Agent 可伪造/重放来意

**失败场景**：攻击者伪造 `from: agent-victim` 的陌生人来意信封，投递给目标用户的 Agent。没有签名/防重放时，目标侧预审看到「对方 Agent 发来合作意向」，按规则放行到付费环节；用户付费查看后对方说「我没发过」。同一封信封被重放 1000 次，付费与骚扰计数全部失真。

**失败链**：不可验证来源 → 预审结论不可信 → 付费门控建立在沙上 → 争议无法举证（审计里只有"某 Agent 发过"，没有"确实是它发的"）→ 陌生人经济学的信任基础崩塌。

**可观测信号**：`SIGNATURE_INVALID`/`TOFU_CONFLICT` 占比异常；同一 `nonce` 重复出现（`REPLAY_DETECTED`）；`CLOCK_SKEW` 集中出现（时钟漂移或伪造）。

**落点**：§26。判定顺序冻结：结构 → 签名 → 时间窗（默认 `windowMs=300_000`）→ `expectedTo` → nonce 重放 → 已知公钥验签；未知公钥 `KEY_UNKNOWN`，须先 `learnKey`。**验签通过 ≠ 有权发**，授权仍走 §12，付费仍走 §9。

### 3.2 第三人称转达（§27）—— 没有它，Agent 只能冒充人说话，或干脆不进人类会话

**失败场景**：A 的日程 Agent 与 B 的日程 Agent 谈好「周五 16:00 看场地」。没有第三人称转达，只剩两条坏路：① Agent 以 A 的口吻在会话里说「我周五 16:00 有空」——B 以为是 A 本人确认，实际 A 根本没看过；② 结果只留在 Agent 之间，人类会话里什么都没有，用户仍要自己约。前者是信任事故（「AI 代聊被识破」），后者是价值断点。

**失败链**：冒充 → 人际信任被机器伪造 → 一旦识破，用户关闭 Agent 代发（[10 R-16](./10-风险与验收登记册.md)）；不进入会话 → Agent 协商成果无法转化为人类共识。

**可观测信号**：`IMPERSONATION_BLOCKED` 命中；摘要 `attribution !== 'AGENT_SUMMARY'` 或 `notFromHuman !== true`；`provenance` 缺失；`SUMMARY_TOO_LONG`。

**落点**：§27。`RelaySummaryBuilder.build` 产出带 `kind/attribution/notFromHuman/provenance/text/hash` 的冻结对象；`assertNotImpersonation` 在 `from ∈ humanUserIds` 时抛 `IMPERSONATION_BLOCKED`；摘要走 §14 会话与 §16 签名审计。

### 3.3 确认层（§28）—— 没有它，规划器可以「预批准」扣费

**失败场景**：Agent 规划「订花 → 付款 → 通知对方」。规划器为了"流畅"，在计划里标注「已获用户批准」，直接跳过审批调用扣费工具；或新接入的 Skill 未被登记，默认按 `PLANNER` 放行。用户没点过任何确认，账上已经扣款。

**失败链**：规划器自批 → 审批引擎被绕过 → 扣费/对外承诺发生 → 事后只能退款+道歉；更严重的是审计无法区分「用户批准」与「模型自称批准」。

**可观测信号**：`PLANNER_PREAPPROVAL_REJECTED` 出现（有人/模型尝试预批准确认层）；未登记 Skill 被 `AUTO` 放行（应为 `CONFIRMATION`）；`humanApproved=true` 但无对应审批单号。

**落点**：§28。未登记技能默认 `CONFIRMATION`（fail-closed）；`CONFIRMATION` 必须 `humanApproved=true`；`plannerClaimsApproved=true` 而无人批 → `REQUIRE_APPROVAL + PLANNER_PREAPPROVAL_REJECTED`，**越权主张进审计**。扣费/审批/对外承诺必须落在确认层。

### 3.4 三机制与既有模块的分工（防重复建设）

| 新机制 | 容易和谁混 | 边界一句话 | 错误码 |
|---|---|---|---|
| §26 签名信封 | §11 身份 / §12 网关 | 信封证明「谁发的」；网关判「能不能发」；身份提供公钥 | 独立 `ENVELOPE_CODE`，不复用身份码 |
| §27 第三人称转达 | §14 频道消息 / §16 审计 | 转达是「摘要作为第三方节点进入会话」，不是普通消息 | 独立 `RELAY_CODE` |
| §28 确认层 | §3 门控 / §19 工具策略 | 门控判权限；工具策略判审批形态；确认层判「是否必须人批」 | 独立 `TIER_CODE` |

> 三个机制都不新增「执行权」：执行仍由 §12 网关与 §4 审批引擎完成；它们的共同作用是**让「谁在什么时候能做什么」可验证**。

|---|---|---|---|---|
| v1 | 治理层 | §1–§10 | 信任五档、门控、审批、账本、信封/序号/去重 | 先把「能不能做」钉死 |
| v2 | Agent 一等公民 | §11–§16 | 身份/网关/可见域/频道/会话/签名审计 | Agent 有身份、有授权、是频道成员 |

|---|---|---|---|

| C6 | 离线/轮次内驱动 | v4 | §25 |

## 5. 明确不采纳的部分

| 不采纳项 | 为什么 | 我们做什么 | 何时重评 |
|---|---|---|---|
| **Pisces 的 Firestore/Ably 后端**（⚠ 需复核其实际后端） | 会话/消息事实源会被第三方托管；实时层（Ably）与 §14 消息内核重复；数据驻留与删除权不可控 | 只借「第三人称转达」范式（§27），后端用自有消息内核 + PG | 不重评（后端不自外迁） |

| **Beacon 的 P2P mesh 与 crypto payments**（形态 ⚠ 需复核官方文档） | 付费必须走中心化账本（§8/§9）：可退款、可冻结、可对账、可自证；P2P mesh 与合规审核/数据驻留冲突 | 只借签名信封 + TOFU + 重放保护（§26）；支付保持中心化 | Phase3 若出现「机器间微支付」实验场景，只做独立试点，不进主账本 |
| **MalikClaw 的具体渠道实现**（接口口径 ⚠ 需复核） | 本机无网络、零依赖；渠道适配属于生产 Go 网关（[02 §15](./02-技术选型与框架.md)）；直接引其实现会把连接层锁进外部 | 只作 Channel 抽象与低占用的架构参考；生产侧自研适配器 | 生产化阶段（Phase1）按渠道需求实现 |
| **openvela 的具体 OS**（能力/许可 ⚠ 需复核） | 无硬件、无网络；OS 选型反向锁定 SoC/驱动/OTA，属 Phase2 硬件评审 | 只做端侧架构映射；端侧承诺（音频不出端、物理灯/静音）不变 | 硬件立项后评估（[06](./06-产品形态与硬件.md)） |

> 共同判据：**事实源（身份/消息/账本/审计）永不自外迁；连接层的实现可以换，判定权不能换。**

**不采纳的统一决策树**：① 它是否持有事实源（身份/消息/账本/审计）？是 → 不采纳；② 它是否要求我们接受「网络位置 = 信任」或「验签 = 授权」？是 → 不采纳；③ 它的实现是否绑定其控制面/OS/后端？是 → 只借范式；④ 以上皆否且语义可映射 → 才进入「改造复用」候选。

### 7.1 四层复用策略（一句话版）

| 层 | 候选 | 取哪条机制 | 策略 | 状态 |
|---|---|---|---|---|

| ③ IM 渠道网关 | MalikClaw / ZLAgent | 确认层不可被 planner 预批准 §28 | **只借范式** | v5 本轮新增 |
| ④ 端侧/可穿戴 | openvela | 架构映射（不出音频、物理灯/静音） | **只借范式** | 路线图（Phase2+） |

### 7.2 五条自研壁垒（按重要性排序）

1. 熟人五档信任矩阵（社会契约 + 权限语义，外包即失权）
2. 陌生人付费消息状态机（改变骚扰经济学，账本即资产）
3. 审批工作流引擎（人机分工的产品表达）
4. 跨 Agent 记忆隔离（隐私承诺与删除权）
5. 签名审计链（合规与争议解决的证据链）

### 7.3 三机制与失败场景（速记）

| 机制 | 没有它会怎样 | 关键错误码 |
|---|---|---|
| §26 签名信封 | 伪造/重放来意 → 预审与付费建在沙上 | `SIGNATURE_INVALID`、`REPLAY_DETECTED`、`TOFU_CONFLICT`、`CLOCK_SKEW` |
| §27 第三人称转达 | 冒充人说话或成果进不了人类会话 | `IMPERSONATION_BLOCKED`、`SUMMARY_TOO_LONG` |
| §28 确认层 | 规划器预批准扣费，审批形同虚设 | `PLANNER_PREAPPROVAL_REJECTED`、`CONFIRMATION_REQUIRED` |

### 7.4 评审检查清单（6 条）

- [ ] 四层是否每层都写了「取哪条机制 + 复用策略 + 落点」，没有「看情况」。
- [ ] 「不可复用」五条是否都是**结构冲突**，而不是「暂时没人力」。
- [ ] 三机制是否都有「没有它会怎样」的具体失败场景与可观测错误码。
- [ ] 是否没有把「验签通过」当「已授权」（§26 边界），也没有把「确认层」当「权限门控」（§28 与 §3/§19 分工）。
- [ ] 是否没有引用 star/版本/许可结论；外部项目是否都有 ⚠ 复核对象。
- [ ] 状态是否区分「已实现」与「契约 R8 已冻结、实现进行中」；未实测不写 pass 数。

### 7.5 评审 60 秒版

- 开源给**连接与执行**；我们做**信任与治理**（五件套自研）。
- 四层策略：①只借范式（§27）；②改造复用 + 付费自研（§26）；③只借范式（§28，渠道适配器本机不实现）；④只借范式（无硬件，端侧承诺不变）。
- 三机制：信封防伪造/重放；转达防冒充；确认层防「规划器预批准」。
- 三句红线：**「验签通过 = 已授权」**（错，授权在 §12）；**「planner 自称已批准」**（错，§28 记 `PLANNER_PREAPPROVAL_REJECTED`）；**「局域网即可信」**（错，dsh-meeting 前提已否）。
