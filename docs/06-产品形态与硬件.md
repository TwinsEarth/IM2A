## 0. 一句话结论

首发形态是**耳夹式开放式耳机**（不是眼镜、不是指环）；
「24 小时在线」不是单次续航 24 小时，而是**单次佩戴 ≥12h + 充电盒 3 次补电覆盖 48h + 待机时云端 Agent 常驻**；
硬件不做整机自研，基于成熟 BLE SoC + ODM 打样，零售价控制在**千元以内**并绑定 **6 个月 Agent 订阅**；
隐私承诺由**物理指示灯 + 机械静音开关 + 端侧过滤后才上云**三件硬件事实兑现，而不是由隐私政策兑现。

## 1. 软硬件形态总览矩阵

| 形态 | 阶段 | 在系统里的角色 | 承载的契约对象 | 决策带宽 | 结论 |
|---|---|---|---|---|---|
| 耳夹式耳机 | Phase1 首发 | 语音审批端 + 全天在场 | `APPROVAL_CARD`、`STRANGER_INTENT` 摘要 | 二值/三值 + 语音 | **做**（唯一首发硬件） |
| AI 眼镜 | Phase2 第二形态 | 提示端（不承载审批正文） | `AGENT_DIGEST`、通知 | 单值提示 | 做，但砍掉屏幕审批 |
| 指环 | Phase3 远期 | 微交互（震动 + 单击） | 无（只映射到手机/手表动作） | 单值 | 延后，不做独立 SKU |
| 夹子（BLE 桥） | Phase3 远期 | 存量耳机升级件 | 无 | 继承耳机 | 观察，不做首发 |
| 手机 App | Phase0 起 | **主决策端**（审批态 + 巡视态） | `TICKET_STATE` 全生命周期 | 全带宽 | 最高优先级 |
| PC / Web | Phase1 起 | 巡视态深钻、批量审批 | 执行轨迹、`TASK_STATE` | 大屏多列 | 做（只读优先） |
| 手表 | Phase1 起 | **决策端**（三屏） | `APPROVAL_CARD` 摘要 + 三动作 | 二值 | 做，严格限幅 |

设计原则：**决策带宽决定形态归属**。凡是「看一眼、点一下」的动作放可穿戴；
凡是「看依据、做取舍、改参数」的动作只放手机/PC；凡是「连续读」的动作一律不给可穿戴。

## 2. 形态逐项论证

### 2.1 耳夹式耳机（首发）

| 维度 | 判断 |
|---|---|
| 为什么这个阶段选它 | ① 全天佩戴率是所有可穿戴里最高的（不需要换鞋/摘镜/换手）；② 开放式不入耳，能听见环境声，会议/通勤/带娃场景可用；③ 麦克风离嘴近，语音审批摘要与确认的识别率高于手表与眼镜；④ BOM 与 ODM 成熟度最高，6 个月内可量产；⑤ 与「管家在你耳边汇报」的心智天然吻合 |
| 佩戴与社会接受度 | 单耳 ≈ 5–6g，耳夹结构可连续佩戴 4–6h 无明显压痛（⚠需实测）；旁人观感等同普通运动耳机，不构成「被偷拍」联想；比眼镜低一个量级的社交摩擦 |
| 功耗与续航现实 | 单耳电池 45 mAh（≈171 mWh），常开唤醒词是最大功耗项（占 ~48%）；单次佩戴 12–14h，配充电盒 3 次补电覆盖 48h；**不支持**单次 24h 连续通话式使用（见 §3） |
| 交互范式 | 唤醒词 → 播报审批摘要（≤15 秒）→ 语音「通过/驳回」→ 播报结果；触摸单击=确认、长按 1.5s=取消、双击=「稍后」；**资金类/第三方类审批强制上屏二次确认**（见 07 §7） |
| 否决理由（若不做） | 若首批只做 App，会丢掉「人不在手机旁」这一核心使用时刻，产品退化为又一个审批后台 |

### 2.2 AI 眼镜（第二形态）

| 维度 | 判断 |
|---|---|
| 为什么这个阶段选它 | Phase2 用户已接受「耳边有个管家」，眼镜补的是**抬头场景**（开车、做饭、带娃、会议中不便看手机）；同时是品牌差异点与媒体话题点 |
| 佩戴与社会接受度 | 摄像头是所有形态里社会接受度最低的部件。**产品决策：首发眼镜不带摄像头**，只保留骨传导/定向扬声器 + 麦克风 + 单色提示灯 |
| 功耗与续航现实 | 眼镜腿电池 2×80–120 mAh，若带彩色显示 + 常亮提示，续航会掉到 4–6h，破坏「全天在场」承诺；因此只做**低功耗单色提示 + 语音**，显示交由手机 |
| 交互范式 | 眼镜只说「有一张高优先级审批卡，已转手机/手表」，不朗读金额与对象细节（公共场所偷听风险） |
| 否决理由 | ① 不做眼镜屏上审批正文：旁人可读、字太小、误触成本高；② 不做摄像头：隐私故事讲不圆，且与本产品「端侧过滤、原始音频不出端」的硬承诺冲突；③ 不做首发：处方镜片渠道、验光配镜、退换货复杂度是耳机的 3 倍以上 |

### 2.3 指环 / 夹子（远期）

| 形态 | 定位 | 佩戴与社会接受度 | 功耗与续航现实 | 交互范式 | 否决理由（当前阶段） | 重启条件 |
|---|---|---|---|---|---|---|
| 指环 | 玄关式微交互：震动提示 + 单击确认 | 接受度最高（无麦无摄像头，最不像监视器），但尺寸决定电池极小 | 10–25 mAh，常开 BLE + 震动下续航 2–4 天（⚠ 需复核）；撑不起语音与常开唤醒 | 单值（震一下 + 单击）；无屏无语音 | 交互带宽太低，无法承载「审批摘要」；手指姿态下天线与 BLE 稳定性差；不能独立承担决策 | Phase3 出现「只想确认、不想说话」的高频场景（如会议中），且手机端已承接 90% 决策 |
| 夹子 | 给存量 TWS 耳机的 BLE 桥接件 | 夹在领口/耳机柄，观感像工牌别针，可接受 | 自身 50–80 mAh（⚠ 需复核），靠耳机盒补电；功耗主要在 BLE 中继 | 继承耳机（只做通道，不做交互） | 属于「兼容件」而非形态；易丢失、充电触点可靠性差、售后成本高于售价 | 存量用户 ≥50 万后作为配件评估，永不作为独立 SKU |

### 2.4 手机 / PC / 手表（客户端矩阵）

| 端 | 主场景 | 必做能力 | 明确不做 |
|---|---|---|---|
| 手机（iOS/Android） | 审批态默认入口 | 审批卡片三动作、批量、陌生人来意卡片、五档权限设置、巡视态钻取 | 不做长文阅读器（依据展开限 3 层） |
| PC / Web | 巡视态 | 多 Agent 泳道、执行轨迹回放、审计导出、批量审批 | 不做默认通知端（避免与手机抢注意力） |
| 手表（Wear OS/watchOS） | 决策端 | 三屏：审批卡片（是/否/稍后）、未读摘要、紧急联系人 | 不做列表滚动浏览、不做金额修改、不做自由文本 |

### 2.5 形态组合的日均触达预算（多设备如何不互相骚扰）

| 通道 | 每日上限 | 允许触发的内容 | 超限后的降级 |
|---|---|---|---|
| 耳机语音播报 | 8 次（其中高优先级 ≤3） | `priority` 为 `urgent` / `high` 的审批摘要 | 静音后只保留震动 + 手表卡片 |
| 手表震动 | 12 次 | 所有 `urgent`、`high`，以及 `normal` 的第一张 | 折叠为「未读摘要」一屏 |
| 手机通知 | 20 次 | 全部待办（含 `low`） | 合并为每日 3 次聚合提醒（早/午/晚） |
| 眼镜提示灯 | 不限（视觉弱提示） | 只提示「有事」，不含内容 | — |
| PC | 0 次（默认静默） | 仅在巡视态页面内更新 | — |

**规则**：同一 `ticketId` 只允许在一个通道上「响」一次，跨通道升级由 `ApprovalEngine.escalateOverdue()` 的
`channels: ['watch','sms']` 逐级驱动，客户端不得自行广播。每日触达超限是**产品指标事故**（见 08 §5 体验指标），
而不是「用户没看见」的运营问题。

## 3. 「24 小时在线」的工程定义

### 3.1 定义（三句话）

1. **硬件层**：单次佩戴 12–14h；充电盒提供 3 次补电，合计覆盖 ≥48h 不插墙；摘下放盒即补电，无需记得关机。
2. **待机层**：耳机在盒内/低电时只维持 **BLE 广播 + 本地唤醒词**（KWS），不上传音频；用户唤醒或云端需要触达时，通过 BLE 唤醒手机侧的轻量连接。
3. **云端层**：Agent 常驻在云（`butler` + L1 子 Agent），**在线的是 Agent 不是耳机**。耳机离线时，审批卡照常生成、按 `escalation.channels`（`watch` → `sms`）升级；耳机只负责「最后一米」的播报与确认。

> 因此对用户的承诺口径是：**「管家 24 小时在线；耳机需要每天回盒一次」**，绝不承诺「单次续航 24 小时」。
> 契约对应：`ApprovalEngine` 的 `escalation = { afterMs: [30*60e3, 2*3600e3], channels: ['watch','sms'] }` 就是「耳机不在场」时的兜底链路。

### 3.2 电量预算表（单耳，结构性估算 ⚠ 需复核）

| 功耗项 | 组成 | 典型功率 (mW) | 占空比 | 折算平均 (mW) | 占比 |
|---|---|---|---|---|---|
| 本地唤醒词 KWS | DSP/NPU 常开，TFLite Micro 小模型 | 6.0 | 100% | 6.0 | 48.0% |
| BLE 维持 | 广播 + 连接间隔 300ms 保活 | 1.8 | 100% | 1.8 | 14.4% |
| VAD 预筛 | 与 KWS 共享前端，语音活动时才升频 | 1.2 | 100% | 1.2 | 9.6% |
| SoC / PMIC 基础 | 深睡漏电 + 电源转换损耗 | 0.8 | 100% | 0.8 | 6.4% |
| 上云传输 | BLE 上行到手机（音频不出端，只传事件/文本特征） | 45 | 2.2% | 1.0 | 8.0% |
| 播报 | 定向扬声器 + 功放 | 30 | 1.7% | 0.5 | 4.0% |
| 余量/温漂/老化 | 预留 | — | — | 1.2 | 9.6% |
| **合计** | | | | **12.5 mW** | **100%** |

推算：171 mWh ÷ 12.5 mW ≈ **13.7h** 单次佩戴（3 次语音审批/天、无音乐播放）；充电盒 500 mAh（1900 mWh）可补电 3 次以上 → **≥48h** 覆盖。
**验收口径**：量产样机在 25℃、每天 3 次审批 + 10 分钟语音、其余待机的脚本下，单次佩戴 ≥12h、盒内总覆盖 ≥44h，连续 3 台样机均达标。

### 3.3 实测与验收（不可用实验室单点数据交付）

| 测试项 | 方法 | 通过阈值 | 责任角色 |
|---|---|---|---|
| 单次续航 | 脚本化 KWS 常开 + 每日 3 次审批 + 10min 播报 | ≥12h（3 台均值，最差 ≥11h） | 硬件测试 |
| 盒内覆盖 | 单耳循环：佩戴 4h → 回盒 1h × 4 轮 | ≥44h 累计佩戴 | 硬件测试 |
| 唤醒率 | 安静/通勤/风噪 3 场景，各 100 次唤醒 | 安静 ≥95%，通勤 ≥88% | 端侧算法 |
| 误唤醒 | 8h 日常录音回放 | ≤1 次/8h（目标 ≤0.5 次/8h） | 端侧算法 |
| 端到端时延 | 唤醒→首字播报 | p50 ≤800ms，p95 ≤1.5s | 客户端 + 云 |

## 4. 隐私硬件规格（不可妥协项）

### 4.1 硬规格表

| 编号 | 规格 | 工程实现 | 验收方法 | 为什么不可妥协 |
|---|---|---|---|---|
| P-01 | 麦克风启用时**硬件指示灯**长亮 | 指示灯与 MIC 供电同一路 PMOS，**软件无法单独关闭**；固件无法改写成「录音不亮灯」 | 拆机 + 逻辑分析仪抓 GPIO；对固件做「强制关灯」注入测试，灯仍亮 | 一旦软件能关灯，隐私承诺变成一句政策 |
| P-02 | **物理静音开关**（机械断电） | 滑钮直接切断 MIC 偏置与指示灯回路，非软件 mute | 开关关闭时示波器测 MIC 无偏置；上传侧 0 字节 | 用户需要「拔掉」的确定性，而不是一个红点图标 |
| P-03 | **端侧过滤后才上云** | KWS/VAD 在端侧判定语音活动，只有命中审批/唤醒后，上云的是**ASR 文本片段 + 事件元数据** | 抓包审计：上行载荷不得含 PCM/AMR 原始音频 | 原始音频不出端是本文最硬的一条 |
| P-04 | **原始音频不出端** | 端侧保留 ≤2s 环形缓冲，仅用于本地唤醒判定，命中后清空；云端只收文本 | 固件代码审计 + 存储介质取证（断电后无残留） | 「听了一整天」和「听懂一句话」是两件事 |
| P-05 | **可审计的传输事件** | 每次上云写设备侧 tamper-evident 日志（滚动哈希），云端回执 receipt，用户可在 App 查看「什么时间、传了什么、多大、给谁」 | 抽查 100 条事件与云端日志比对一致率 100% | 让「我们没传音频」可被验证，而不只是被声明 |
| P-06 | 离线可用 | 断网时耳机仍可唤醒、播报本地缓存的审批摘要、语音确认落本地队列 | 断网 30min 场景回归 | 隐私与可用性不能互相牺牲 |
| P-07 | 出厂默认关闭摄像头类能力 | 眼镜形态（Phase2）默认无摄像头；如有，需物理遮挡片 + 指示灯 | BOM 与固件双重确认 | 从源头消除最敏感的攻击面 |

### 4.2 承诺 → 工程 → 验证 的映射（对外可用口径）

| 对外承诺 | 工程手段 | 用户可自证的方式 |
|---|---|---|
| 「没有在听」 | P-02 机械断电 | 拨到静音，指示灯灭，MIC 无偏置 |
| 「在听你说话时你看得见」 | P-01 硬件指示灯 | 录音时灯必亮，拆机也关不掉 |
| 「录音不上云」 | P-03 / P-04 端侧过滤 + 环形缓冲 | App 内「传输事件」页可逐条核对 |
| 「你可以查」 | P-05 设备日志 + 云回执 | 导出传输事件，与云端对账 |
| 「删了就删了」 | 记忆层 `purge({userId})` 级联 + 设备端缓冲清零 | 删除后 24h 内全链路检索不到（见 08 §7 留存周期） |

### 4.3 我们**拒绝**做的「伪隐私」设计（写进评审否决项）

- ❌ 软件 mute 图标（系统被攻破即失效）→ 必须机械断电。
- ❌ 「行业领先的加密」但无传输事件日志（无法自证）。
- ❌ 指示灯呼吸/可配置亮度（等于可关）。
- ❌ 把「端侧处理」只做成 marketing 词，实际仍上传压缩音频。
- ❌ 用「用户已同意隐私政策」兜底任何麦克风常开行为。

## 5. 硬件路线：不自研整机

### 5.1 SoC 与 ODM 策略

| 决策 | 内容 | 理由 | 触发切换条件 |
|---|---|---|---|
| 不自研整机 | 结构、声学、天线、认证全部由 ODM 交付，我方定义规格与验收 | 自研整机需 18–24 个月与 8–12 人硬件团队，Phase1 无法承受 | 出货 >50 万台且 ODM 无法满足成本/迭代节奏时，评估自建产线 |
| SoC 选型 | 成熟 BLE Audio SoC（带小 NPU 跑 KWS），片内 RAM ≥256KB，支持 LE Audio/LC3 | 不开新芯片流片，风险与周期最低；LC3 与 04 文档的 BLE 帧设计对齐 | 若 KWS 模型压不进片内 RAM，先降模型复杂度，不换 SoC |
| 双供应商 | SoC 与电池各备 1 家二供 | 断供是硬件最常见的死法 | 任一主供 L/T >16 周 |
| 认证 | SRRC（无线电）+ 3C（如适用）+ 出口地认证 | 无 SRRC 不得在国内销售 | 认证不过 → 延迟上市而非降规 |

### 5.2 BOM 结构与成本区间（单耳 + 盒，结构性估算 ⚠ 需复核）

| 成本项 | 关键规格约束 | 区间 (¥) | 备注 |
|---|---|---|---|
| BLE SoC + 小 NPU | 支持 KWS、LE Audio | 28–45 | 量大可降 |
| MEMS 麦克风 ×2/耳 | 双麦降噪 + 波束 | 6–10 | 语音审批主路径 |
| 扬声器 + 功放 | 开放式定向 | 12–20 | 音量需满足户外播报 |
| 电池 | 45 mAh ×2 + 盒 500 mAh | 15–24 | 含保护板 |

## 8. 与其他契约/文档的接口（防漂移）

1. 耳机语音产生的每一条审批，都必须落到 `ApprovalEngine.create()` 生成的 `tkt-*` 对象，状态只能是
   `TICKET_STATE` 中的九个值；客户端不得自造 `DONE`/`CANCELED` 之类的「顺口状态」。
2. 语音确认只允许产生 `action: 'APPROVE' | 'REJECT'`；`MODIFY` 必须走屏幕（见 07 §7）。
3. 陌生人付费消息在耳机上只播报「有一条预审通过的来意，是否查看」，**不得**在语音里完成付费决策
   （付费动作必须上屏，因为涉及金额与 `MSG_STATE` 的单向流转）。
4. 硬件侧离线队列中的审批，重连后按 `createdAt` 升序补投，过期者由 `ApprovalEngine` 判定 `EXPIRED`，
   客户端**不得**自行改状态。
