**裁决分布说明**：3 个 ✅ 都是「该层的语义基座可直接用」——nekoclaw 提供人格/记忆生命周期语义、imcodes 提供三模式讨论语义、AICQ 提供密钥身份与签名语义；3 个 ◐ 都是「机制可用、外壳不可用」——MagicChat/AICQ 的一部分已被 v2 吸收，MindRoom 的协议栈与 Xiajiao 的产品形态不借。**没有整行 ⛔**的理由见 §5.1：裁决的对象是「能力层」而不是「项目整体」，整行否决会让该层出现真空。

### 1.1 第 1 行：接入模型 = MagicChat —— ◐

- **借什么（机制级）**：① Agent 作为独立应用通过 WS 接入，而不是平台进程内函数；② 读侧「授权用户 + 范围 + 时效」的可见域；③ 数字员工要有可展示、可审计的 principal 归属。
- **落点**：`services/messaging/src/session.mjs`（独立连接/在线/订阅）、`services/gateway/src/visibility.mjs`（`buildScope/evaluate/project`）、`services/gateway/src/agent-gateway.mjs`（唯一入口）。
- **v2 已覆盖**：是。证据见 §2.1。
- **不借**：项目管理/任务看板（会引入第二套任务状态机）、workspace 单租户边界（表达不了五档信任与 `trustCeiling`）、其产品形态。
- **裁决理由**：该层真正可复用的机制已在 v2 落地；剩余部分是业务不是接入模型，故 ◐ 而非 ✅。

### 1.2 第 2 行：账号与记忆 = MindRoom —— ◐

- **借什么（机制级）**：① Agent 是「账号/成员」而不是 API key：有身份、可加入房间、有在线态；② **跨平台持久记忆**：记忆可导出/导入，换平台不丢；③ **细粒度工具审批**：审批粒度到「每个 Agent × 每个 Skill 一条策略」，而不是全局金额阈值。
- **落点**：账号 → 契约 §11 `agent_identities` / `agent_cards` + §15 `agent_sessions`（v2 已实现）；跨平台记忆 → §17 `exportPortable/importPortable`；细粒度审批 → §19 `ToolPolicy`。
- **v2 缺口**：v2 只有 `CapabilityGate`（权限）与 `ApprovalEngine`（审批单），没有「按 Skill 的审批形态」这一层；记忆也没有可携带导出包。
- **裁决理由**：账号部分采纳（已覆盖），记忆与审批部分是新机制、已在 v3 补；Matrix 协议栈作为主路径不采纳（§5），故 ◐。

### 1.3 第 3 行：隔离与人格记忆分层 = nekoclaw —— ✅

- **借什么（机制级）**：① 人格（SOUL：价值观/规则/边界/语气）与记忆分开存、分开授权；② 记忆分层不是 TTL 过期，而是**生命周期**（晋升/衰减/遗忘）；③ 遗忘是软删除（tombstone 留证，`recall` 不再返回内容）。
- **落点**：`services/orchestrator/src/persona-memory.mjs`；契约 §17；表 `mem.*`（与 v1 `mem.agent_memories` 同库）。
- **不借**：`SOUL.md` 的**文件格式**（借语义不借格式，见本文 §5）。
- **裁决理由**：该层要解决的是「人格稳定 + 记忆会衰老」的语义问题，与文件格式无关；语义已逐条冻结为 `MEMORY_STAGE` 与三条晋升/衰减规则，故 ✅。

### 1.4 第 4 行：陌生人协商模式化审计 = imcodes —— ✅

- **借什么（机制级）**：① 讨论/审计/评审是三种**模式**，不是同一种聊天；② 结构化产出：`DISCUSS` 必须有结论、`AUDIT/REVIEW` 必须有发现；③ **异议不可被"综合"掉**——`dissent` 原样进纪要。
- **落点**：`services/orchestrator/src/discussion-engine.mjs`；契约 §18；会议纪要 `minutes()`。
- **关键分工（防混用）**：陌生人来意「是否成交」仍走契约 §5 `NegotiationEngine`（两方、8 态、达成一致）；imcodes 的价值是把它之后的**评审/审计**变成有模式、有立场、有异议记录的会议，落契约 §18。**同一个 case 不允许同时开协商状态机与讨论状态机**。
- **裁决理由**：三模式解决的是 v2 的「多 Agent 形成结论」缺口，语义冻结完整，故 ✅。

### 1.5 第 5 行：快速产品验证 = Xiajiao —— ◐

- **借什么（机制级）**：一条命令完成「起服务 → 跑自检 → 打印入口」，把「能不能跑起来」变成 10 秒内可回答的问题；失败返回非零退出码，可直接进 CI。
- **落点**：`scripts/quickstart.mjs`（`--check` 模式只跑自检；默认模式起服务并保持运行）。
- **不借**：Xiajiao 的产品/业务形态（与熟人 Agent 治理不是同一命题）。
- **裁决理由**：只借「验证方法」不借「产品形态」，故 ◐。

### 1.6 第 6 行：身份与消息签名 = AICQ —— ✅

- **借什么（机制级）**：① Ed25519 自持密钥，身份可由公钥重算；② 公共/私有房间的可见性语义；③ 消息与关键事件可签名、可验签。
- **落点**：`services/identity/src/agent-id.mjs`、`services/audit/src/signed-audit.mjs`、`core.agent_identities`、`gov.audit_entries`；契约 §11/§16。
- **v2 已覆盖**：是（v2 实现，v3 只做 R5 `derivedId` 澄清）。
- **不借**：协议整体/线格式、E2E 默认、纯自主注册（绕过平台 `ownerUserId` 绑定）。
- **裁决理由**：身份与签名的语义正是我们 v2 的实现依据，故 ✅；协议层不借不影响该层裁决。

> 反转条件是**可观测阈值**（评审时只谈阈值，不谈感受）；带「⚠」的是规划值，需压测/评审校准，不是实测结论。

|---|---|---|---|---|
| 接入模型 | MagicChat 式独立应用 WS / 平台内嵌 Agent（进程内函数）/ 第三方 A2A 边界 | `AgentSessionRegistry`（独立连接/在线/订阅）+ `AgentGateway` 唯一入口；A2A 只做 Phase3 边界 | 第三方 Agent 平均接入改造 > 1 人日/家，或在线保持率 < 99.5%（连续 2 周，⚠ 规划值）→ 提供官方 SDK/托管 runtime，但**不改为进程内嵌** | `session.test.mjs`、`agent-gateway.test.mjs` |

**跨层约束**（矩阵之外的硬规则）：

1. 接入模型的选择不得绕过 `AgentGateway`（契约 §20 铁律 7）；独立接入 ≠ 免门控。
2. 账号与身份分离：`agentId` 是平台可读名，`derivedId` 是自证值；对外互操作用 `derivedId`，内部运维用 `agentId`（R5）。
3. 记忆只在 `PersonaMemory` 一个写入口；`MemoryStore` 只保留 v1 读兼容或转为项目记忆，不得出现两套生命周期。
4. 讨论与协商分属两个引擎；同一条 case 不允许同时开两套状态机（见 §7.3 分歧 1）。
5. 产品验证以「一条命令可复现」为底限；任何「已实现」若不能 `node <file>.test.mjs` 直跑，就必须降级为「设计」。

**3.2 阈值来源与复核责任**：矩阵里的 99.5% 在线保持率、1 人日/家接入成本、20% 轮次超限率、15% 结论驳回率均为**规划值**（⚠ 需压测/运营校准），不是实测结论；向量阈值 5000 万 / P99 100ms 沿用 [02 §9](./02-技术选型与框架.md) 的既有口径。复核责任：接入模型与记忆阈值 → 架构 + SRE；讨论/审批阈值 → 算法 + 产品；身份互认 → 安全 + 法务。阈值一旦实测校准，只改本表与 [02](./02-技术选型与框架.md) 对应条目，不改契约。

## 4. 术语对齐表（外部概念 → 我们的契约名）

> 团队最容易各说各话的地方。**左列是外部说法，右列是本仓库唯一权威名**；评审/工单/代码注释只允许用右列。

| 外部概念 | 我们的契约名/接口 | 落点 | 易错点 |
|---|---|---|---|
| SOUL / 人格文件 | `setSoul` / `soul`（`values/rules/boundaries/voice`） | §17 `PersonaMemory` | 不是文件；是结构化对象，写入必须留审计，非法 `values` → `SOUL_INVALID` |
| MEMORY.md / 记忆 | `remember` / `recall` + `MEMORY_STAGE` | §17 | 层级是 `WORKING/EPISODIC/SEMANTIC/ARCHIVED`，不是 v1 的 `MEMORY_LAYER`（`working/episodic/semantic`） |

| 跨平台记忆 | `exportPortable` / `importPortable` | §17 | 包版本 `agentim-persona/1`；冲突进 `conflicts`，不静默覆盖 |

| 消息/审计签名 | `signPayload` / `verifyPayload`；`SignedAuditLog` | §11/§16 | 审计链 = 哈希链（防篡改）+ Ed25519（防整链重算），两者都要 |
| 陌生人来意协商 vs 讨论 | `NegotiationEngine`（§5，两方，达成一致） vs `DiscussionEngine`（§18，≥2 方，形成结论） | 两个模块 | 同一个 case 只能有一个状态机在跑 |

**4.1 术语使用三条铁律**：

1. **代码/文档/工单只允许契约名**；外部说法（SOUL/MEMORY.md/discuss/Matrix 账号）只出现在本对照表左列，不得进入实现或接口。
2. **同一概念不得有别名**：`MEMORY_STAGE`（v3，含 `ARCHIVED`）与 `MEMORY_LAYER`（v1，不含 `ARCHIVED`）必须分开说；把两者统称"记忆层"会导致晋升/衰减被 TTL 绕过。
3. **大小写敏感**：`AUTO/APPROVE/DENY`、`DISCUSS/AUDIT/REVIEW`、`WORKING/EPISODIC/SEMANTIC/ARCHIVED` 一律大写；proto 侧的大小写映射由 SDK 收敛（见 `contracts/README.md` 的映射说明），业务代码不得自行转换。

## 5. 明确不采纳的部分（子项级否决）

> 说明：**没有任何整行 ⛔**。因为 6 行里每一行的「最小可用机制」都能映射到已有契约；⛔ 只作用于上述子项。这是刻意的裁决口径：不因为项目整体形态不适用，就丢掉它解决某个具体问题的机制。

**5.1 为什么没有整行 ⛔（裁决方法论）**

- 裁决的对象是**能力层**，不是项目整体：一行被 ⛔ 会让该层没有落点（例如把「接入模型」整行否决，就等于退回「Agent 是进程内函数」，与 v2 §15 的一等客户端冲突）。
- ⛔ 只对**具体机制**生效：Matrix 协议栈、SOUL.md 格式、Xiajiao 产品形态各自有明确替代（自持身份+消息内核、`setSoul` 结构化对象、quickstart 方法），因此不必整行否决。
- 若某层出现「所有候选机制都不可用且无自研替代」的情况，才允许整行 ⛔，并必须在同一行写明「替代路线 + 重评条件」。当前 6 行不满足该条件。

### 7.3 评审会必须拍板的 2 个选型分歧（本文作者观点）

**分歧 1：讨论引擎与协商引擎的边界——两套状态机如何共存？**
- 现状：§5 `NegotiationEngine`（两方、8 态）与 §18 `DiscussionEngine`（≥2 方、6 态）都能「多 Agent 交互」。
- 风险：若同一条 case 先开协商、再开讨论，会出现两套状态机对同一事实各自推进，审计无法判断哪个是权威。
- 建议拍板：**协商只用于「是否成交/是否放行」，讨论只用于「形成结论/发现/评审」；讨论的输入只能是协商的终止态或审批单，不允许反向驱动协商**；同一条 `traceId` 只允许一个活动状态机，违反即 `ILLEGAL_STATE`。

**分歧 2：记忆事实源——v1 `MemoryStore` 与 v3 `PersonaMemory` 是否合并？**
- 现状：v1 `MemoryStore` 用固定 TTL（1h/7d/90d）分层；v3 `PersonaMemory` 用 24h/30d/90d 的晋升/衰减规则 + 可选的 per-record `ttlMs` 软过期 + SOUL + tombstone。
- 风险：两套生命周期并存 → 同一条记忆在 `MemoryStore` 里过期、在 `PersonaMemory` 里还在（或反之）；`recall` 结果取决于走了哪个入口。
- 建议拍板：**`PersonaMemory` 成为唯一写入/晋升/衰减入口；`MemoryStore` 降级为只读兼容层（或直接下线）**；在替换完成前，两个入口都不得对同一 `agentId+userId` 双写。这条若不拍板，v3 的「遗忘可审计」会被 v1 的 TTL 悄悄绕过。
