## 1. 本版缺陷总览

| # | 缺陷 | 现象 | 根因 | 修法 |
|---|---|---|---|---|
| ① | **重启丢账户/会话** | 重启后原 token 调 `/api/wallet` → **401**；需重新注册/登录 | 产品域（AccountService）从未被 `serialize()`；`createWorld` 恢复时没有 `accounts` 可导入 | `AccountService.exportState/importState`；`serialize` 写入 `accounts`；schema 升 2 |
| ② | **重启余额归零** | 账本条目持久化了，但钱包/对账读到的 `ledger` 是空的 → 余额 0 | 恢复时只把 `ledger` 原样塞回快照，**没有回放进程内 `Ledger`**；钱包投影基于空账本 | `createWorld` 恢复时**逐条回放**账本（保留原时间戳），再交给钱包投影 |
| ③ | **下单不落盘** | 重启后 `GET /api/pay/orders` 为空，已下单未支付的订单丢失 | `/api/pay/intent` 创建订单后**没有调用 `persist()`** | 下单成功后显式 `persist()`；订单是资金链起点 |

## 2. 缺陷细节

### 2.1 重启丢账户/会话

- **根因**：`AccountService` 的状态（账户、手机号索引、会话）只在内存；`domain.serialize()` 只序列化审批/审计/账本等，不包含产品域。
- **修法**：`AccountService` 增加 `exportState()` / `importState(state)`：
  - `exportState` → `{ accounts, phoneIndex, sessions }`；
  - `importState` 校验形状后重建 Map（账户冻结、会话冻结）；
  - **OTP challenge 不导出**（短命且含验证码明文，设计上不持久化，见 §3）。
- **schema**：`serialize()` 产物含 `schemaVersion=2` 与 `accounts`；`createWorld` 恢复时导入。

### 2.2 重启余额归零（账本回放）

| 项 | 说明 |
|---|---|
| 根因 | 持久化的是“数据快照”，恢复时 `Ledger` 被重新 `new`，**没有把历史条目 post 回去**；钱包/对账读空账本 |
| 修法 | 恢复时**逐条回放**持久化条目：`ledger.post({ idempotencyKey, type, userId, amountCents, ref })`；保留原 `at` 时间戳（注入 clock 从条目取时间） |
| 异常历史条目 | 回放失败的坏条目**跳过且保留原始投影**，不阻断启动，**绝不静默改写已入账事实** |
| 验收 | 重启后 `balance.availableCents` 仍为 5000（测试 ⑳） |

> 回放不是“重新记账”：它恢复的是**同一批已入账事实**；幂等键保证不会重复入账。

### 2.3 下单不落盘

- **根因**：`/api/pay/intent` 只 `createIntent` + 返回，未 `persist()`；重启后订单消失（资金链断点）。
- **修法**：创建订单成功后调用 `persist()`；`PaymentIntentService` 增加 `exportState/importState`（`orders` + `txnToOrder` 防重放索引），恢复后**重复回调不会二次入账**。

### 2.4 验收（回归证据）

| 验收项 | 命令 | 判定 |
|---|---|---|
| 重启持久化（测试 ⑳） | `node tests/im2agent.test.mjs` | 起→停→起：会话 `200`、余额 `5000`、订单 `1`；**19 passed** |
| schema 迁移 | `--filter=migrate` | **6 passed**（缺失 schema→当前、幂等、dry-run 不写盘、未知/损坏拒绝、迁移后可加载） |
| 全量不回退 | `node scripts/test.mjs` | 原有测试数不回退（以最新报告为准） |

### 2.5 恢复顺序与幂等（避免“回放了但没导入”）

| 顺序 | 动作 | 失败处理 |
|---|---|---|
| 1 | 校验 `schemaVersion`（不匹配 → `SCHEMA_MISMATCH`） | 启动失败，不进入半恢复 |
| 2 | **回放账本**（逐条 post，保留 `at`；坏条目跳过并保留投影） | 单条失败不阻断；计数进报告 |
| 3 | **导入账户/会话**（`AccountService.importState`） | 形状错误 → 启动失败（显式） |
| 4 | **导入支付订单/txn 索引**（`PaymentIntentService.importState`） | 同上；导入后重复回调不会二次入账 |
| 5 | 交给钱包/对账投影（基于已回放账本） | 余额 = 回放结果，不是“重新计算” |

> 顺序不能反：先回放账本再投影，否则钱包又会读到空账本；导入失败必须显式失败，不“尽量恢复”。

## 3. 仍未持久化（诚实清单，4 项）

> 契约明确：`schemaVersion=2` 持久化账户/手机号索引/会话 + 支付订单与 txn 索引 + 账本。**审核案与争议仍只在内存**（重启丢失），属已知缺口，不得对外声称「完整持久化」。

| # | 项 | 现状 | 影响 | 临时缓解 |
|---|---|---|---|---|
| 1 | **审核案（moderation）** | 内存态 | 重启后 `HUMAN_PENDING/APPROVED` 案卷与 `caseId` 丢失；已投递消息不受影响 | 重启前不依赖在途案卷；发布/重启公告避开审核高峰；重启后重新提交 |
| 2 | **争议（disputes）** | 内存态 | 重启后未决争议丢失；`timeline` 可能缺 `DISPUTE_*` 步 | 重启前清空/关闭未决争议；客服记录 `disputeId`；重启后按账本/审计重建工单 |
| 3 | **OTP challenge** | **设计上不持久化** | 重启后未完成登录需重新发码 | 短 TTL（分钟级）；重发即可；不属于缺陷 |
| 4 | **SSE / 广播总线** | 不持久化（预期） | 重启后事件不补发、在线连接断开重连 | 客户端重连 + 手动刷新；总线本就不是队列（§48） |

> 前两项是**待补的持久化缺口**（进 0.2.0 或后续 0.1.x 缺陷；若重启丢争议造成用户损失，按缺陷处理）；后两项是**预期行为**，不修。

### 3.1 判断“该不该持久化”的四条标准

| 标准 | 该持久化 | 不该持久化 |
|---|---|---|
| 生命期 | 跨重启仍需要（账户/订单/账本） | 分钟级（OTP challenge） |
| 是否含明文敏感信息 | 不含或已 hash（实名 hash） | 含验证码/密钥明文 |
| 可否从真相重建 | 不必（本身是真相） | 可由账本/审计重建（投影/缓存） |
| 是否外部事实 | 是（订单/渠道回调） | 否（SSE 在线状态） |

> 用这四条复核“仍未持久化”清单：审核案/争议属于“跨重启仍需要”，所以是**缺口**；OTP/SSE 属于“短命/可重建”，不持久化是**设计**。

## 4. 数据 schema 1→2 迁移

### 4.1 变更范围

| 数据 | schema 1（v0.1.1） | schema 2（v0.1.2） |
|---|---|---|
| `accounts`（账户/手机号索引/会话） | ❌ 不落盘 | ✅ |
| `payments`（订单 + txn 索引） | ❌ 不落盘 | ✅ |
| `ledger` | ✅ 落盘，但恢复时不回放 | ✅ 落盘 + 恢复回放 |
| 其余（审批/审计/消息等） | ✅ | ✅ 不变 |

### 4.2 `migrate-state.mjs` 的支持范围（R23）

| 输入 schema | 行为 |
|---|---|
| 缺失（v0.0.9 及更早） | ✅ 迁移到 2 |
| 更旧整数（如 1） | ✅ 迁移到 2（`isOlder`） |
| 已是 2 | `CURRENT` 幂等，不改写 |
| 未来/未知（>2、非整数） | `UNSUPPORTED`，不猜测降级、文件不动 |

**五安全动作不变**：先备份（`.pre-<schema>.bak` + sha256）→ tmp+rename 原子改写 → `createWorld` 加载核对条数 → 失败自动回滚 → 幂等。**启动时永不自动迁移**。

### 4.3 运维步骤（升级 v0.1.1 → v0.1.2）

1. **停写**：停服务/维护模式；
2. **备份**：整文件备份 + `.pre-*.bak` 由迁移工具生成；
3. **dry-run**：`node scripts/migrate-state.mjs --file <state.json> --dry-run`，确认 `schema: 1 -> 2` 与条数；
4. **迁移**：正式执行，记录备份 sha256；
5. **启动 + 冒烟**：`/api/version` 显示 `0.1.2 / R23 / 2`；登录 → 余额 → 订单 → 审批；
6. **回滚**（必要时）：停写 → 用 `.pre-*.bak` 覆盖 → 启动 v0.1.1。

### 4.4 测试覆盖与缺口（⚠ 建议补）

- 现测覆盖：缺失 schema → 2、幂等、dry-run、未知/损坏拒绝、迁移后可加载（6 项）。
- **未单列“schema 1→2”用例**：代码 `isOlder` 支持，但测试里没有显式 `schemaVersion:1` 样本；**建议补一条**，避免回归时漏掉。

|---|---|
| 文件 / 备份路径 / sha256 | … |

## 5. 0.1.x 停止条件

### 5.1 缺陷 vs 缺口的判据

| 判据 | 缺陷（走 0.1.x） | 缺口（进 0.2.0/路线图） |
|---|---|---|
| 能力是否已声明 | 已声明能力内出错（如“能持久化”却丢数据） | 从未声明（如 Flutter 未编译、多租户） |
| 是否可复现 | 有测试/现象/根因 | 无复现路径，只是“还没做” |
| 修复代价 | 不新增依赖/能力，语义不变 | 需要新依赖/新渠道/新功能 |
| 用户影响 | 数据/资金/安全/主流程受损 | 体验缺失但不误导 |

> 一句话：**“说了能做却没做到”是缺陷；“还没说要做”是缺口。**

### 5.2 停止条件（满足任一条，则不再开 0.1.x）

1. **没有可复现的真实缺陷**：不得为凑版本号发 0.1.x（没有缺陷就不发版）；
2. **修复需要新增能力/依赖**：例如接真实短信/实名/机审/支付、做多节点/多租户——进 0.2.0，不塞进补丁；
3. **出现数据/资金/安全类回归**，或需要破坏性 schema/契约变更：停止 0.1.x，升 0.2.0 并走完整发布流程；
4. **0.1.x 连续两个版本只改文档/注释/版本号**：视为“无事可修”，冻结 0.1.x 线。

### 5.3 发版纪律

- 每个 0.1.x 必须有：**可复现缺陷 + 根因 + 修复 + 回归测试**；三者缺一不发；
- 发布说明必须写“本版修了什么/没修什么”；不得把缺口写成缺陷修复；
- 版本号必须与 tag 一致（§51⑤，`release-check` 已查）。

### 5.4 判定流程（每次想开 0.1.x 时走一遍）

1. 有可复现缺陷吗？**没有 → 不发版**（文档/注释类改动走 commit，不占版本号）。
2. 缺陷在已声明能力内、且修它不需要新依赖/新能力吗？**是 → 0.1.x**；**否 → 0.2.0**。
3. 修复涉及 schema/契约破坏性变更或数据/资金/安全回归吗？**是 → 停止 0.1.x，升 0.2.0**。
4. 连续两个 0.1.x 只改文档/版本号吗？**是 → 冻结 0.1.x 线**。

## 9. 一页速查

### 9.1 升级三步（v0.1.1 → v0.1.2）

1. **停写 + 备份**（整文件 + 记录 sha256）；
2. **dry-run → 迁移**：`node scripts/migrate-state.mjs --file <state.json> --dry-run`，确认 `1 -> 2` 与条数后正式执行；
3. **启动 + 冒烟**：`/api/version` = `0.1.2 / R23 / 2`；登录/余额/订单/审批通过。

### 9.2 回滚三步

1. 停写；
2. 用迁移生成的 `.pre-*.bak` 覆盖当前文件；
3. 启动 v0.1.1，确认 `/api/version` 回到 `0.1.1 / R22 / 1`。

### 9.3 v0.1.2 不是什么

- 不是“完整持久化”：审核案/争议/OTP/总线仍不持久化（§3）；
- 不是 0.2.0：真实短信/实名/机审/支付仍未接；
- 不是“0.1.x 会一直发”：满足 §5 停止条件即冻结。
