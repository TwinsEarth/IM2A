# 28 · v0.0.8 横向扩展与多节点（IM2A）

> 版本 v0.0.8（R19 对齐）· 对应契约 `contracts/INTERFACES.md` v1.0（变更记录 **R19**，§48）· 作者：架构组
> 定位：用户指令「按清单开始 v0.0.8 的开发」。v0.0.8 = 清单 P1「WS 横向扩展」的**最小可验证实现**：**零依赖 TCP 广播总线**（`memory`/`tcp` 同构），任一节点的事件扇出到所有节点的在线客户端；生产映射到 **Redis Pub/Sub**。
> 与 [27](./27-v0.0.7-客户端交付说明.md) 的边界：**27 是客户端（能打开、能点），28 是后端扇出（点了以后别的节点也能收到）**；与 `channel.mjs`（§14 频道订阅语义）和 `apps/im2agent/server.mjs` 的 `/api/events`（SSE）配合，但**总线不是消息存储**。
> 状态口径：**✅ 本机实测通过** · **⚠ 实现中/需多机** · **⛔ 未实现/明确不做**。不编造 QPS/延迟数字——容量一律「待压测」。

## 0. 一页结论（TL;DR）

| 项 | 结论 |
|---|---|
| 版本一句话 | **v0.0.8 = 让「事件」跨节点**：任一节点 publish，所有节点上的 SSE 客户端都能收到；本机用 TCP 总线验证，生产换 Redis Pub/Sub 只改一处 |
| 解决什么 | 单节点 SSE 的墙：A 节点 `/api/events` 只收到 A 的事件；B 节点产生的 `decide`/`preview` 到不了 A 的客户端 |
| 不解决什么 | **不持久化、不保证全局顺序、不做共识、不做离线补发**——它是广播总线，不是 Kafka/消息队列（见 §3.2） |
| 投递语义 | 每节点最多一次（按事件 `id` 去重）、同源保序、无订阅者直接丢弃、单条 JSON ≤64KB、超限丢弃计数、`close` 后 `publish` 不抛 |
| 接口同构 | `memory` 与 `tcp` 同一接口（`start/close/publish/subscribe/stats`）；**替换 Redis 的唯一位置**是 `services/messaging/src/broadcast.mjs` 的工厂实现（业务与 SSE 桥接不改） |
| 拓扑 | 单节点 `memory`；多节点 `tcp`：`nodeId + listenPort + peers`（节点间私有网络，不走反代、不对公网） |
| 故障边界 | 节点掉线/重连记录 `PEER_FAILED`，**本地 publish 永不阻塞业务**；分区期间事件丢失（无持久化）；**本版不做脑裂共识** |
| 验收 | **G1–G6**：两节点互收 / 每节点最多一次 / 同源保序 / close 后 publish 不抛 / SSE 跨节点收到 `decide` / 64KB 超限丢弃且计数 |
| 本机状态（写作快照） | 契约 R19 已冻结（§48）；`services/messaging/src/broadcast.mjs` 与 `tests/broadcast.test.mjs` 已落地，`--filter=broadcast` **4 passed**，覆盖 G1–G6 的模块级语义（memory/tcp 互收、同源保序、回环去重、close 不抛、超限丢弃、跨节点 SSE）；**双进程/双机部署复验仍待执行**（发布前条件 ⚠） |
| 多节点第一个真实故障最可能是什么 | **节点间 TCP 端口没放通/peers 配错**（安全组、监听地址、nodeId 为 null）：表现为**单节点一切正常、另一节点永远收不到事件**，而 `publish` 也不报错（只在 `stats` 里看到 `PEER_FAILED`） |

## 1. 版本定义

### 1.1 单节点 SSE 的墙（为什么需要总线）

当前 `apps/im2agent/server.mjs` 的 SSE 是**进程内**实现：

| 位置 | 现状 | 后果 |
|---|---|---|
| `holder.sseClients = new Set()` | 只保存**本进程**的连接 | 别的节点的客户端不在这个 Set 里 |
| `holder.broadcast(payload)` | 遍历本进程 Set 写 SSE | 只服务本节点 |
| `GET /api/events` | 本节点订阅 | 跨节点事件收不到 |
| 审批决定 `decide` / 预览 `preview` | 本节点广播 | 双节点部署时，一半用户“看不到变化” |

> v0.0.8 把「本进程广播」换成「总线 publish + 总线 subscribe → 本地 SSE」，**SSE 端点、事件格式、客户端行为都不变**。

### 1.2 与 v0.0.7 的边界

| 维度 | v0.0.7（客户端） | v0.0.8（后端扇出） |
|---|---|---|
| 目标 | Web/PWA 能打开、能点、角色门控 | 事件跨节点到达在线客户端 |
| 改动面 | `apps/im2agent/public/app/*` | `services/messaging/src/broadcast.mjs` + server 桥接 |
| 不涉及 | 后端多节点 | 客户端三态/离线/角色 |
| 数据一致性 | 单节点读写 | **仍不做分布式一致性**；账本/审计仍是单主真源 |

### 1.3 交付物与集成点

| 项 | 内容 |
|---|---|
| 新增模块 | `services/messaging/src/broadcast.mjs`：`createBroadcastBus({kind, nodeId, listenPort, peers, clock})` |
| 集成点 | server 启动时创建总线 → `subscribe(topic, payload => 写本地 sseClients)`；业务广播改为 `publish(topic,payload,{id})` |
| 兼容 | 单节点（`memory`）行为与现在一致；`kind` 由配置决定 |
| 不做 | 不替换账本/审计/消息存储；不把总线当 MQ |

### 1.4 本版改动面（文件级）

| 文件 | 改动 | 说明 |
|---|---|---|
| `services/messaging/src/broadcast.mjs` | **新增** | `memory/tcp` 同构实现、去重/保序/丢弃/64KB |
| `apps/im2agent/server.mjs` | **改桥接** | `holder.broadcast` 改为 `bus.publish`；`bus.subscribe → sseClients` |
| 配置（env） | **新增** | `BUS_KIND/BUS_NODE_ID/BUS_PORT/BUS_PEERS`（名称以实现为准） |
| `tests/broadcast.test.mjs` | **新增** | memory/tcp/SSE 跨节点/边界测试 |
| 客户端（Web/PWA） | **不改** | 仍连 `/api/events` |

## 2. 为什么先总线不是先 Redis

### 2.1 三个理由

1. **零依赖可验证**：本机无 Redis/无网络代理，TCP 总线可在两个本地进程间跑通「跨节点」语义，验收不依赖外部服务。
2. **接口同构**：`memory` / `tcp` / 未来 `redis` 共用 `publish/subscribe/stats`；业务代码只面向接口，换实现不改调用方。
3. **先把语义钉死**：去重、同源保序、丢弃、64KB、close 语义先在总线层用测试钉住；换 Redis 时只需验证「同一套语义」而非重新设计。

### 2.2 接口同构与「唯一替换位置」

| 层 | 文件 | 换 Redis 时改什么 |
|---|---|---|
| 业务调用方 | `apps/im2agent/server.mjs`（`holder.broadcast` 调用点） | **不改**（只调 `publish/subscribe`） |
| 桥接层 | server 内 `bus.subscribe → sseClients.write` | **不改** |
| 实现层 | **`services/messaging/src/broadcast.mjs`** | **只改这里**：新增/切换 `kind`（如 `redis`），把 `publish/subscribe` 映射到 Redis `PUBLISH/SUBSCRIBE` |
| 契约 | §48 `BUS_KIND/BUS_CODE/createBroadcastBus` | 若新增 `kind`，按加法扩展枚举（不破坏 `memory/tcp`） |

> 「唯一位置」是刻意的：**换基础设施不改业务**。如果发现有第二处需要改，说明抽象漏了。

### 2.3 三种实现的语义对照

| 维度 | `memory`（单节点） | `tcp`（本版多节点） | Redis Pub/Sub（生产，未接） |
|---|---|---|---|
| 依赖 | 零依赖 | 零依赖（`node:net`） | 外部 Redis 集群 |
| 跨进程 | ❌ | ✅ | ✅ |
| 跨机器 | ❌ | ✅（内网） | ✅（受网络/集群限制） |
| 投递保证 | 每节点最多一次 | 每节点最多一次 | 每节点最多一次（订阅连接） |
| 持久化 | ❌ | ❌ | ❌（Pub/Sub 本身不持久） |
| TLS/鉴权 | — | ❌（内网假设） | ✅（TLS/ACL） |
| 适用 | 本机/单实例 | 内测多节点验证 | 生产多节点 |

## 3. 投递语义

### 3.1 保证 / 不保证

| 性质 | 保证？ | 说明 |
|---|---|---|
| 每个事件**每节点最多投递一次** | ✅ | 按事件 `id` 去重；跨节点回环（A→B→A）不得重复触发本地订阅 |
| 同一 origin 的事件在订阅端**保序** | ✅ | 单条 TCP 连接/单线程发布，按 origin 顺序到达 |
| 无订阅者时丢弃 | ✅ | 与 SSE 语义一致；**不排队、不补发** |
| 持久化 / 离线补发 | ❌ | 总线不写盘；节点离线期间事件丢失 |
| 全局顺序 | ❌ | 不同 origin 之间没有全局先后；只有同源保序 |
| 消息确认 / 重试 / 死信 | ❌ | 这是广播，不是队列；需要可靠投递走 §8/§16/outbox |
| 跨节点精确一次 | ❌ | 只保证「每节点最多一次」，不保证全网恰好一次 |

### 3.2 与「消息队列」的区别（别把总线当 Kafka）

| 维度 | 本总线（§48） | Kafka / MQ |
|---|---|---|
| 目的 | 在线客户端通知（SSE 扇出） | 可靠事件流/回放/解耦 |
| 持久化 | 无 | 有（保留期/分区） |
| 订阅者离线 | 事件丢弃 | 可从未读位点补 |
| 顺序 | 仅同源 | 分区内有序、可回放 |
| 失败语义 | 丢弃 + `stats` 计数 | 重试/死信/对账 |
| 用途 | `preview`/`decide` 等 UI 通知 | 账本/审计/outbox 等治理事件 |

> **红线**：账本、审计、审批事件**不得**只经总线传递；它们必须走 §8/§16 的持久化链路，总线只做通知（丢一条通知不应导致账不平）。

### 3.3 去重 / 保序 / 64KB / 丢弃

| 机制 | 规则 | 可观测 |
|---|---|---|
| 去重 | 事件必须带 `id`；每个节点维护「已见 id」集合（有界/TTL） | 重复事件计数进 `stats` |
| 保序 | 同一 origin 内按发布顺序；跨 origin 不排序 | 乱序只可能出现在跨 origin，不应影响 UI 决策 |
| 64KB | `topic + payload + id + origin` 的 JSON > 64KB → 不投递 | `stats.dropped` 递增；**不得截断后发送** |
| 无订阅者 | 直接丢弃 | `stats.dropped` 递增 |
| `close` 后 publish | 返回 `{ok:false, code:'BUS_CLOSED'}`，**不抛** | 业务主流程不受影响（不因总线关闭导致审批失败） |

### 3.4 事件信封与 topic 规范

| 字段 | 必填 | 说明 |
|---|---|---|
| `topic` | ✅ | 如 `sse.decide` / `sse.preview`；**只放通知类**，不放账本/审计事件 |
| `payload` | ✅ | JSON 对象（≤64KB；不含 PII 明文） |
| `id` | ✅ | 全局唯一（`nodeId + 序号/随机`），用于每节点去重 |
| `origin` | ✅ | 发布节点 `nodeId`；用于回环识别与同源保序 |

**topic 命名建议**：`sse.<eventType>`（与 `/api/events` 的事件 `type` 对齐）；禁止把 `ledger.*`/`audit.*` 放进总线（它们走 §8/§16）。

## 4. 拓扑与配置

### 4.1 单节点（默认，`memory`）

| 配置 | 值 |
|---|---|
| `kind` | `'memory'` |
| `nodeId` | 可空（单节点无关） |
| `listenPort` | 0（不监听） |
| 行为 | 进程内扇出，等价当前 SSE；用于本机/单实例 |

### 4.2 多节点（`tcp`）

| 配置 | 说明 |
|---|---|
| `nodeId` | **必填且唯一**；用于回环识别与去重 origin |
| `listenPort` | 本节点总线监听端口（私有网络） |
| `peers` | 其他节点 `host:port` 列表；启动后建立连接 |
| 重连 | 断开后指数退避重连；`PEER_FAILED` 记录但**不阻塞本地发布** |
| 启动顺序 | 允许乱序启动；先启动的节点等 peer 重连，不因此失败 |

### 4.3 端口、反代与防火墙

| 项 | 规则 |
|---|---|
| 总线端口 | **只在内网/安全组内开放**；不对公网、不加反代、不走 80/443 |
| 反代 | 反代只服务 HTTP/SSE；**不要把总线端口挂到反代**（会引入超时/缓冲问题） |
| 安全组 | 仅允许「节点 IP 之间」的端口互访；单节点部署不开该端口 |
| TLS | v0.0.8 的 TCP 总线**不做 TLS**（内网假设）；生产 Redis 用 TLS/密码（见 §7） |
| 时钟 | 总线不依赖全局时钟；去重 TTL 用本机 `clock`，节点时钟漂移会影响 TTL，但不影响正确性 |

### 4.4 双节点配置样例（示意，变量名以实现为准）

```bash
# 节点 A
BUS_KIND=tcp BUS_NODE_ID=node-a BUS_PORT=7901 BUS_PEERS=10.0.0.12:7901 \
  PORT=8081 node apps/im2agent/server.mjs

# 节点 B
BUS_KIND=tcp BUS_NODE_ID=node-b BUS_PORT=7901 BUS_PEERS=10.0.0.11:7901 \
  PORT=8082 node apps/im2agent/server.mjs
```

> 两个节点的 `nodeId` 必须不同；`peers` 填对方总线地址；总线端口只在内网安全组放通。

## 5. 容量与故障

### 5.1 扇出复杂度与慢消费者

- 单事件成本 ≈ **O(节点数 × 该事件订阅者数)**；节点数与在线客户端数增长时，写入成本线性叠加（**具体 QPS/延迟待压测**，本文不编数字）。
- **慢消费者**：SSE 写阻塞不该拖垮总线；本地桥接对每个客户端有界缓冲，超限断开并计数（避免一个慢客户端拖慢全节点）。
- 总线层对 peer 发送同样需要**有界队列**：队列满 → 丢弃并 `stats.dropped++`，不允许无限内存增长。

### 5.2 节点掉线/重连

| 场景 | 行为 |
|---|---|
| peer 连不上 | `PEER_FAILED`；本地 publish/subscribe 正常运行 |
| peer 断开 | 从活动 peer 移除；指数退避重连 |
| 重连成功 | 正常收新事件；**不补发断线期间事件**（无持久化） |
| 本节点关闭 | `close()` 后 publish 返回 `BUS_CLOSED`；不抛 |

### 5.3 脑裂边界（本版不做共识，写清）

- 网络分区时，两侧各自继续本地服务；**跨区事件不会到达对方**；
- 本版**不做 leader 选举/共识/冲突合并**；不承诺分区期间「全局一致」；
- 可接受的原因：总线只承载 UI 通知（`preview/decide`），**账本/审计/审批状态**仍由单主数据源决定；
- 若未来需要「分区期间不丢事件」，引入 Redis/Kafka 或持久化方案（§7），不在本版范围。

### 5.4 扩容顺序与回滚

| 步 | 动作 | 出口 |
|---|---|---|
| 1 | 先起两节点（`memory` 改 `tcp`），只验证总线互收/SSE | G1/G5 通过 |
| 2 | 把**一小部分**流量切到第二节点（负载均衡/固定用户） | 跨节点事件到达；无重复 |
| 3 | 观察 `stats` 与告警（peer 失败/丢弃） | 无 PEER_FAILED 持续 |
| 4 | 再扩节点 | 同上 |
| 回滚 | 停第二节点、流量回单节点；总线保留 `memory`/单节点模式 | 行为与 v0.0.7 一致 |

## 6. 验收 Gate G1–G6

| # | 验收项 | 判定标准（可执行） | 验证命令 | 本机状态 |
|---|---|---|---|---|
| G1 | **两节点互收** | 启动 A/B 两节点（tcp）；A publish 的事件 B 订阅端收到；反向同样成立 | `--filter=broadcast` + 双进程脚本 | ✅ 代码级（4 passed，tcp 两节点互收）；双进程复验待做 |
| G2 | **每节点最多一次** | 同一 `id` 重复 publish / 跨节点回环，订阅端每节点只触发一次；重复计数可见 | `--filter=broadcast` | ✅ 代码级（回环去重） |
| G3 | **同源保序** | 同 origin 连续 publish `1..N`，订阅端按序收到 | `--filter=broadcast` | ✅ 代码级（同源保序） |
| G4 | **close 后 publish 不抛** | `close()` 后 `publish` 返回 `{ok:false, code:'BUS_CLOSED'}`，业务调用方不异常 | `--filter=broadcast` | ✅ 代码级（close 后不抛） |
| G5 | **SSE 跨节点收到 decide** | 两节点部署；在 A 调用审批决定 → 连在 B `/api/events` 的客户端收到 `decide` 事件 | 双节点 + `curl -N /api/events` | ✅ 代码级（跨节点 SSE）；双进程复验待做 |
| G6 | **64KB 超限丢弃且计数** | 超过 64KB 的 payload 不投递、不截断；`stats.dropped` 递增；无订阅者事件丢弃也计数 | `--filter=broadcast` | ✅ 代码级（超大消息丢弃计数） |

**Gate 规则**：G1–G6 全过才允许说“支持多节点 SSE 扇出”；⚠ 必须在**两台机器/两个进程**上验证（单进程模拟不算 G1/G5）。

**反例（看起来通过的三处）**：

1. **「两节点互收」**：同一个 bus 实例不算——必须两个独立实例、走真实 TCP（双进程/双机更佳）。
2. **「去重」**：只测同 id 连发不算——必须测**跨节点回环**（A→B→A）。
3. **「SSE 跨节点」**：只测总线收到不算——必须从 **B 节点 `/api/events`** 的 HTTP 流里看到 `decide`。

### 6.1 双进程验证脚本骨架（发布前必跑）

```bash
# 进程 1（节点 A）
BUS_KIND=tcp BUS_NODE_ID=node-a BUS_PORT=7901 PORT=8081 node apps/im2agent/server.mjs
# 进程 2（节点 B，peers 指向 A）
BUS_KIND=tcp BUS_NODE_ID=node-b BUS_PORT=7902 BUS_PEERS=127.0.0.1:7901 PORT=8082 node apps/im2agent/server.mjs
# 观察 B 的 SSE，同时在 A 触发一次 decide
curl -N http://127.0.0.1:8082/api/events
```

**记录**：两个进程的 `stats()`、SSE 事件、是否重复、是否有 `PEER_FAILED`。

## 7. 到生产 Redis Pub/Sub 的迁移清单

| 项 | 迁移时确认 |
|---|---|
| 接口 | 保持 `publish/subscribe/stats` 不变；实现映射到 Redis `PUBLISH/SUBSCRIBE`（模式订阅按需） |
| 序列化 | 沿用同一 JSON 信封 `{topic,payload,id,origin}`；Redis 只做字节传递，**不要引入第二套格式** |
| 频道命名 | 统一前缀，如 `im2a:sse:<topic>`；禁止裸 topic 进 Redis（防与其他应用冲突） |
| 鉴权 | Redis 密码/TLS/ACL；总线端口不再对内网裸奔 |
| 去重 | 每节点保留 id 去重（Redis 不替你去重）；回环仍由 `origin/nodeId` 识别 |
| 持久化 | **不开启** Redis 持久化来“补消息”；语义仍是广播，不是队列 |
| 监控 | 发布数、接收数、去重数、丢弃数、peer/连接失败、重连次数、发布→接收延迟（**阈值待压测**） |
| 故障 | Redis 不可用 → publish 失败但不阻塞业务（同 `BUS_CLOSED`/失败语义）；本地 SSE 仍服务本节点 |
| 回滚 | 保留 `tcp/memory` 实现，配置可切回（单实例回滚无障碍） |

### 7.1 接 Redis 前先做的三件事

1. **语义回归**：用同一套 broadcast 测试（或等价用例）跑 Redis 实现，确认 G1–G6 语义不变；
2. **频道命名定稿**：`im2a:sse:<topic>` 写进配置与监控，禁止裸 topic；
3. **故障演练**：Redis 不可用时 publish 不阻塞业务、本地 SSE 仍可用（与 `BUS_CLOSED` 同语义）。

## 9. 一页速查（运维：怎么判断「扇出坏了」）

### 9.1 三步定位

1. **看两节点直连**：`stats()` 是否有 `PEER_FAILED`；节点间端口/`peers` 是否正确（最常见故障）。
2. **看总线收发**：A publish 后 B 的 `received` 是否增加；不增加 → 看网络/peer，不要先改业务。
3. **看 SSE**：B 的 `/api/events` 客户端是否收到事件；总线收到但 SSE 没到 → 桥接/本地订阅问题。

### 9.2 常见症状与原因

| 症状 | 最可能原因 | 处理 |
|---|---|---|
| 单节点正常，另一节点永远收不到 | 端口/安全组/peers/nodeId 配错（`PEER_FAILED`） | 先查网络与配置，不查业务 |
| 事件重复出现 | 去重缺失/回环未识别 | 检查 `id` 与 `origin` 去重逻辑 |
| 事件顺序乱 | 不同 origin 混排（正常）或同源多连接 | 同源应单连接；不要跨 origin 假设顺序 |
| 发布后业务 500 | 把总线异常抛给了业务 | `publish` 失败不得影响主流程（G4） |
| 内存上涨 | 慢消费者/peer 队列无界 | 有界队列 + 丢弃计数 |

### 9.3 三条红线

1. **总线不持久化**：别拿它当 Kafka；账本/审计必须走持久链路。
2. **总线失败不阻塞业务**：`publish` 不抛、失败可计数，审批/扣费照常。
3. **端口不对公网**：总线只在内网/安全组；生产换 Redis（TLS/ACL）。

### 9.4 v0.0.8 不是什么

- 不是「分布式共识/分区容错」；不是「跨节点事件不丢」；不是「消息队列」；不是「生产 Redis 已接入」。
