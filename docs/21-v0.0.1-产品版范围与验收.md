## 1. 版本定义

### 1.1 是什么 / 不是什么

| 维度 | v0.0.1（产品版，内测） | 不是什么 |
|---|---|---|
| 目标 | 20 人熟人圈可完成「注册 → 实名 → 余额 → 付费消息 → 审批 → 退款/结算」 | 不是公开注册、不是应用商店版本 |
| 实名 | `idNumber` 只存 hash + 尾号掩码；核验走 **mock 提供方**（可替换真实三要素） | 不是真实三要素上线（真实服务资质/流水号见 §6.1） |
| 支付 | **余额制**：手动充值（`topUp`，幂等）+ 按次扣减 + 仅未回复可退 | 不是真实支付渠道（支付宝/微信支付 Out）；不做「先扣后退」 |
| 合规 | 审核链前置（发送前 `EgressGuard`）+ 签名审计 + 隐私政策草案 | 不是合规终态（等保/ICP/备案等由法务推进，本文不下结论） |
| 底座 | Phase0–1：IM PaaS + §31 适配层（v7 决策） | 不是自托管内核（Phase2 评估）；不是 A2A；不含硬件 |
| 交付形态 | 本机可复现的 Node 实现 + 部署配置（Linux/vercel 类目标机另测） | 不是生产 Go/Flutter 全栈（QA ⚠ 项） |

### 1.2 与 `im2agent` 的 `v0.0.1-demo` **同名不同义**（最容易混）

| 名称 | 归属 | 含义 | 证据 |
|---|---|---|---|
| **`v0.0.1-demo`** | 技术 tag（`apps/im2agent` 的 CHANGELOG/QA 序列） | 单进程 demo：验证「链路能跑通」；**无实名、无钱包、无真实付费准入** | `apps/im2agent/README.md`、`QA.md` 的 23 项 |

## 2. 范围：In / Out

### 2.1 In（本版必须做，且可验收）

| # | 子项 | 做什么（最小） | 明确边界 | 契约落点 | 状态 |
|---|---|---|---|---|---|
| 1 | **登录（手机 OTP）** | `requestOtp → register/login`；OTP 单次、TTL、尝试次数上限 | 不发真实短信：dev 只回 `devCodeOnlyInDev`；生产短信通道另接 | §36 `ACCOUNT_CODE`（`OTP_INVALID/OTP_EXPIRED/OTP_ATTEMPTS_EXCEEDED`） | ✅ 已代码化（15 passed） |
| 2 | **实名（hash + 尾号）** | `verifyRealName` 走 **mock 提供方**；只存 `idNumberHash` + `maskedTail` | mock 只用于内测；真实三要素的流水号/失败原因码见 §6.1 | §36 不变量①（绝不存明文） | ✅ 已代码化（15 passed） |
| 3 | **余额与充值** | `topUp`（幂等键）、`balance`（available/frozen） | **手动/体验额度**；不接真实支付渠道（Out） | §37 `WALLET_CODE` | ✅ 已代码化（14 passed） |
| 4 | **扣费幂等** | `chargeForMessage` 用 `pay:<messageId>`；同消息只扣一次 | 与 §8 账本同源，不得另存「影子余额」为事实源 | §37 不变量② | ✅ 已代码化（14 passed） |
| 5 | **退款仅未回复** | `refund` 仅当注入的 `messageState` 为未回复；否则 `REFUND_WINDOW_CLOSED` | 已回复走**人工争议**（§6.2），不做自动退 | §37 不变量①（禁止先扣后退） | ✅ 已代码化（14 passed） |
| 6 | **日发送上限** | 按自然日累计，超限 `DAILY_CAP_EXCEEDED`（`dailySendCapCents` 默认 50000，⚠ 内测可调） | 与既有 `dailySendCap` 的口径对齐，不出现两套计数 | §37 不变量③ | ✅ 已代码化（14 passed） |
| 7 | **审核链前置** | 发送前过 `EgressGuard`；审核记录（规则版本/命中/人审/申诉）写审计 | 机审 API 未接（⚠）；规则层必须前置，**不得先发送后审核** | §7 + §16 | ✅ 规则层 / ⚠ 机审 |

### 2.2 Out（本版不做，写清理由）

| # | Out 项 | 为什么本版不做 | 什么时候做 |
|---|---|---|---|
| 1 | **真实支付渠道**（支付宝/微信支付） | 涉及商户资质、二清边界与对账；内测用余额/体验额度即可验证闭环 | 内测通过 + 法务确认后（⚠ 支付牌照/二清需法务） |
| 2 | **OAuth（微信/Apple 登录）** | 手机 OTP 已能覆盖内测；OAuth 只取 unionid/openid，不取关系链 | Phase1 |
| 3 | **分账** | 分账涉及二清（需牌照或持牌机构合作） | 不做（见 ROADMAP「不做二级清算/资金池」） |
| 4 | **多租户** | 内测是熟人圈单租户；组织角色不得映射个人信任档 | 企业版（Phase3） |
| 5 | 硬件/端侧、A2A、WS 横向扩展、生产 Go/PG/Flutter | 版本级排除：不是生产版本 | 各自 Phase（见 [19 §五](./19-IM2A-完整落地执行方案.md)） |

### 2.3 为什么这样切（最小可内测闭环）

1. **没有实名，付费就没有可追责主体**（ROADMAP §一）；先补 `account`，再谈钱。
2. **没有钱包，账本只是记账、钱不流动**（ROADMAP §三）；余额制是最小可验证形态，且天然避免「先扣后退」。
3. **没有审核前置，付费会变成绕过过滤的漏洞**（[15 §2.2](./15-四层技术栈映射与自研边界.md) 的陌生人付费铁律）；因此审核链放在 In 而不是 Out。
4. **真实渠道/分账/OAuth 都可以后接**：它们改变的是「钱怎么进来」，不改变「谁可以收、能退多少」的治理语义。

### 2.4 依赖与阻塞关系（排期用）

| 依赖 | 被谁阻塞 | 说明 |
|---|---|---|
| `wallet` 依赖 `account` | 未实名 → 不能开钱包/付费 | 钱包操作前必须 `canUsePaidMessaging` |
| `wallet` 依赖 `messageState` | 退款判定依赖消息状态接线 | 状态没接 → A6 无法验收 |
| `account` 依赖 OTP 通道 | dev 固定码 / 生产短信 | 内测先 dev 模式 |
| 审核前置依赖 `EgressGuard` | 机审 API 未接 | 规则层先上，机审 ⚠ |
| 内测发布依赖 §5 三张前置清单 | 运维/法务/客服 | 任一未闭环 → 不公网内测 |

## 3. 验收清单（8 条硬 Gate）

> 判定标准写「可执行断言」，验证命令写「本机能跑什么」；本机状态用 ✅/⚠/⛔。**⚠ 不等于通过**，必须有目标机/接线后的补测记录。

| # | 验收项 | 判定标准（可执行） | 验证命令 | 本机状态 |
|---|---|---|---|---|
| A1 | **未实名不能收发付费消息** | `canUsePaidMessaging` 返回 `{ok:false, code:'REALNAME_REQUIRED'}`；发送/接收付费消息均被阻断 | `node scripts/test.mjs --filter=account`；im2agent 端到端 | ✅ 已代码化（account 15 passed） |
| A2 | **明文不落库** | 任何存储/日志/审计中不出现 `idNumber` 明文；只有 `idNumberHash`（sha256(salt+idNumber)）与 `maskedTail` | `--filter=account` + 检索测试 | ✅ 已代码化（account 15 passed） |
| A3 | **OTP 单次有效** | 同一 OTP 第二次使用 → `OTP_INVALID`；过期 → `OTP_EXPIRED`；超次数 → `OTP_ATTEMPTS_EXCEEDED` | `--filter=account` | ✅ 已代码化（account 15 passed） |
| A4 | **余额不为负** | 并发/重试扣费不会出现负余额；不足 → `INSUFFICIENT_FUNDS` | `--filter=wallet` | ✅ 已代码化（wallet 14 passed） |
| A5 | **同消息只扣一次** | 连点/重放 10 次，账本只有 1 条 `CHARGE`；`pay:<messageId>` 幂等 | `--filter=wallet`；`node tests/im2agent.test.mjs` | ✅ 已代码化（wallet 14 passed + 账本幂等） |
| A6 | **已回复不可退** | `messageState` 为已回复时 `refund` → `REFUND_WINDOW_CLOSED`；未回复可退 | `--filter=wallet` | ✅ 已代码化（wallet 14 passed） |
| A7 | **日上限生效** | 同一自然日累计超 `dailySendCapCents` → `DAILY_CAP_EXCEEDED`；次日恢复 | `--filter=wallet` | ✅ 已代码化（wallet 14 passed） |
| A8 | **SUSPENDED 阻断** | 被封禁账号：登录以外的写操作被阻断；付费消息/钱包返回 `SUSPENDED` | `--filter=account` / `--filter=wallet` | ✅ 已代码化（account 15 / wallet 14） |

**A1–A3 的已核实测试名（account）**：*未实名：canUsePaidMessaging => REALNAME_REQUIRED*、*不变量①：idNumber 明文永不落库（序列化/快照只含 hash + 掩码）*、*OTP 单次有效：注册用过的 code 再用于登录 => OTP_INVALID*、*OTP 错误码 5 次 => OTP_ATTEMPTS_EXCEEDED*、*OTP 过期 => OTP_EXPIRED*、*实名核验：只返回 hash+尾号掩码*。

**A4–A8 的已核实测试名（wallet）**：*不允许负余额：扣 60 元 → INSUFFICIENT_FUNDS 且余额不变*、*幂等：同 messageId 重复扣费只 1 笔 ledger CHARGE*、*未回复可退…已回复不可退（REPLIED/SETTLED → REFUND_WINDOW_CLOSED）*、*日发送上限 → DAILY_CAP_EXCEEDED；次日 clock 推进后恢复*、*SUSPENDED：账号被暂停后充值/扣费/退款全部阻断*。

**Gate 规则**：A1–A8 全过 → 允许 20 人内测；任一 ⛔ → 不发布；任一 ⚠ → 必须有「本机替代验证 + 目标机补测计划」并写进内测公告（不能默认通过）。

### 3.1 看起来像通过、实际没通过的三处（评审重点）

1. **「未实名也能进付费流程」**：前端把按钮置灰不算通过——必须在**服务端** `canUsePaidMessaging` 处拒绝（界面只是展示，不是门控）。
2. **「退款成功」**：mock `messageState` 永远返回「未回复」时，退款会全通过——必须用**已回复**的夹具反向验证 `REFUND_WINDOW_CLOSED`。
3. **「余额充足」**：只测单笔不测并发——同一 `messageId` 并发 2 次扣费必须只有 1 条 `CHARGE`（A5 的并发版）。

### 3.2 验收夹具（不得使用真实个人信息）

| 夹具 | 内容 | 约束 |
|---|---|---|
| 手机号 | 内测白名单号码段（假号） | 不用真实用户号码 |
| 身份证号 | 构造的测试号（校验位合法但非真人） | **不得**使用员工/家属真实证件 |
| OTP | dev 固定码或 `devCodeOnlyInDev` | 生产必须关闭 dev 回显 |
| `messageState` | 未回复 / 已回复 两种夹具 | A6 正反都要测 |
| 余额 | 0 / 不足 / 充足 / 并发 四种 | A4/A5/A7 覆盖 |
| 账号状态 | UNVERIFIED / VERIFIED / REJECTED / SUSPENDED | A1/A8 覆盖 |

## 4. 数据与合规

### 4.1 `idNumber` 的存储口径（硬要求）

| 项 | 口径 | 禁止 |
|---|---|---|
| 存储 | `idNumberHash = sha256(salt + idNumber)` + `maskedTail`（尾号掩码） | 不存明文；不存可逆加密 |
| 展示 | 只展示 `maskedTail`（如尾号 4 位） | 不在 API/日志/审计 detail 里回传明文 |
| salt/密钥 | 由 KMS/环境注入，轮换需重算策略 | 不写进代码/仓库/日志 |
| 删除与导出 | 实名信息可删除、可导出（ROADMAP §一验收） | 不与审计留存冲突（审计留存按法务结论） |

### 4.2 审计事件（全部走 §16 签名链）

| 事件域 | 至少要记 | 用途 |
|---|---|---|
| 账户 | 注册、OTP 请求/失败、实名通过/驳回、登录、封禁 | 可追责主体与争议举证 |
| 钱包 | 充值、扣费、退款（含失败原因） | 对账与退款争议 |
| 付费消息 | 预审结论、扣费、查看、回复、结算 | 「谁审的、何时、谁批的」可追溯 |

> 审计只写 hash/掩码/引用，不写明文敏感信息；`messageId`/`ticketId` 必须可反查（[16](./16-三层技术栈与平台接入边界.md) 与 §16 的口径不变）。

### 4.3 隐私政策必须写明的三件事

1. **收集什么、干什么**：手机号（登录/验证码）、身份证号（仅用于实名核验，存 hash + 尾号）、余额与流水（计费与对账）、设备与日志（安全与风控）。
2. **与谁共享**：短信服务商、实名核验服务商（当前 mock，切换真实后需更新）、支付渠道（未来接入时）、法定调取情形。
3. **保留多久、怎么删**：账户/实名/余额流水的保留期；删除权如何行使；审计与账本因法定义务保留的例外（⚠ 具体年限由法务定）。

### 4.4 未成年人处理建议

- 建议：**未满 18 岁不开放付费消息与陌生人触达**；已实名但未成年 → 仅熟人免费功能 + 监护人可见（产品建议，非法律结论）。
- 不做：不靠「用户勾选已满 18」当唯一判断；不在本版做完整未成年人模式（Phase1）。
- ⚠ 具体年龄门槛、监护人同意方式由法务/合规确认，本文不下条款结论。

### 4.5 数据保留与删除（内测简化口径）

| 数据 | 内测期保留 | 删除权 | 备注 |
|---|---|---|---|
| 手机号 | 账号存续期 | 可删除（注销） | 注销后去标识化 |
| 实名 hash/尾号 | 账号存续期 + 审计期 | 可删除/导出（ROADMAP 验收） | 审计留存与删除冲突处由法务定 |

| 日志 | 30 天（建议） | 到期清理 | 不写敏感明文 |

## 6. 风险与处置

### 6.1 mock 与真实三要素的差异（最容易被忽略）

| 差异 | mock（本版） | 真实三要素 | 风险 |
|---|---|---|---|
| 核验结果 | 固定通过/固定规则 | 姓名+号码匹配、可能返回失败原因码 | 上线后失败率突增，用户被卡在实名 |
| 流水号 | 可能没有 | 每次核验有渠道流水号 | 没有流水号 → 争议时无法向供应商追证 |
| 计费 | 无 | 按次计费 | 内测免费，上线后成本突现 |
| 数据边界 | 本地 | 供应商留存/跨境条款 | 需数据处理协议（§5 法务①） |

**处置**：`AccountService` 的 `realName` 注入接口保持与真实提供方同形（请求/响应/失败原因码），mock 只替换实现；上线前用真实沙箱跑一遍并记录流水号。

### 6.2 退款争议人工通道

- 规则：**未回复可自动退；已回复只能人工争议**（`REFUND_WINDOW_CLOSED`）。
- 风险：内测用户会问「为什么已读不能退」——必须在付费前展示规则（两档计费说明），否则争议量集中在客服。
- 处置：客服工单 + 审计证据（`messageId → CHARGE → VIEWED → REPLIED` 时间线）+ 人工判定标准（⚠ 由运营/法务共同定）。

### 6.3 支付渠道未接：余额从哪来？

- 本版**只支持手动充值/体验额度**（`topUp`，`channel='manual'`）；**不得对外宣称「充值真实到账」**。
- 内测公告必须写明：额度是体验额度，不可提现、不可转让；退款退的是体验额度。
- 风险：用户把体验额度当真实余额 → 提现预期与客诉。处置：文案 + 后台标注 `channel` + 客服口径统一。

### 6.4 其他（内测期）

| 风险 | 处置 |
|---|---|
| OTP 短信通道未接 | dev 只回 `devCodeOnlyInDev`；内测用白名单号码 + 固定码（⚠ 仅内测） |
| 并发扣费 | 钱包与账本共用幂等键；压测 10 并发同 `messageId` 只 1 条 `CHARGE` |
| 审计留存不足 | 先落 §16 签名链；保留期按法务结论（§5 法务③） |
| 账号被盗/多设备 | access token TTL + `SESSION_EXPIRED`；多设备撤销在 Phase1 |

### 6.5 内测准入与退出机制

| 项 | 规则 |
|---|---|
| 准入 | 邀请制白名单（20 人），实名通过 + 接受隐私政策 + 知晓「体验额度」 |
| 额度 | 每人固定体验额度；不可提现/转让；客服可手动调整（留审计） |
| 退出 | 用户可注销；运营可封禁（`SUSPENDED`）；封禁需记录原因与操作人 |
| 数据处置 | 注销 → 去标识化 + 账本/审计按 §4.5 保留；被封 → 保留证据链 |
| 事故 | 出现资金/隐私类问题 → 立即停止新用户准入，保留现场（不删库） |

## 8. 一页速查

### 8.1 给内测用户的三句话

1. **现在只能熟人圈内测**：需要手机号登录 + 实名（我们只保存加密摘要与尾号，不存明文）。
2. **余额是体验额度**：不是真实充值、不可提现；付费消息「看到且回复才扣费」，**已回复不退**，未回复可退。
3. **Agent 会先预审再收费**：付费买的是「已被预审过的有效触点」，不是「绕过过滤的通行证」。

### 8.2 给团队的发布检查（Go / No-Go）

| 检查 | 通过条件 |
|---|---|
| 契约 | §36/§37 枚举与错误码与实现逐字一致（`scripts/verify.mjs`） |
| 验收 | A1–A8 全过；⚠ 项有目标机补测计划 |
| 合规 | 隐私政策草案 + 实名/支付法务意见（⚠ 未闭环不公网） |
| 运维 | HTTPS + 备份 + 审计告警 |
| 客服 | 退款争议/封禁申诉通道 + FAQ |
| 诚实 | 内测公告写明「体验额度、实名范围、退款规则」，不宣称生产可用 |

### 8.3 v0.0.1 不是什么（对外口径）

- **不是生产版本**：真实支付、OAuth、分账、多租户、硬件、A2A 均未包含。
- **不是 `v0.0.1-demo`**：技术 tag 证明能跑；产品版要求能对真实的人收钱且能退。
- **不是最终合规态**：等保/备案/支付资质由法务推进，本文不下结论。
