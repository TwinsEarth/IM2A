## 0. 一页结论（TL;DR）

| 项 | 结论 |
|---|---|
| 用户结论坐实 | **没有一个开源项目同时处理「熟人信任档位」与「陌生人付费消息」**：通信层只解决「消息到得了」，编排层只解决「任务拆得开」，平台层只解决「入口连得上」——三者都不判定「谁可以做什么、凭什么、收多少钱」 |
| 三层策略 | ①协议与通信层：**只借范式**（寻址/Thread/隔离/流式/邮箱）；②编排框架：**只借范式 + 本轮新增委托**（§30），协调器不照搬；③平台边界：**只做入口，不做治理闭环** |
| 脚手架 vs 治理 | 脚手架（消息、流式、群聊、邮箱）可借；**治理（信任/审批/账本/审计）与经济（付费消息）必须自研**——这正是 [15 §2](./15-四层技术栈映射与自研边界.md) 五件套 |
| 结论落点 | **脚手架可借、治理与经济层自研**；平台只做边界（L2 上限），不做治理闭环 |
| 本轮两机制 | §29 **持久邮箱**（修补 v4 `TurnInbox` 重启丢 pending 的已知缺陷）；§30 **带衰减委托**（防总 Agent 一授权就把全部权限复制给子 Agent） |
| 平台矩阵 | 覆盖 **6 个平台**：微信、飞书、钉钉、企业微信、WhatsApp、X |
| 平台接入深度 | 全部平台最多 **L2（卡片 + 回调输入）**；L3 平台内完整闭环**不采纳**（§2.4） |
| 两机制一句话 | 邮箱防丢（重启/离线可恢复、重复不重入队）；委托防扩散（scope 子集 / 时限不超父 / 跳数受限 / 级联撤销） |
| 铁律 | **熟人关系链与付费账本永不放第三方平台**（平台只做入口/通知/卡片投影，决策与账本回自有平台） |
| 状态快照（2026-10-21） | 契约 R9 已冻结（§29–§30）；v6 实现/集成进行中；契约 §32 验证命令尚未补 v6 过滤键（建议 Lead 补 `--filter=agent-mailbox / delegation`） |
| 最需拍板的平台接入取舍 | **Phase1 飞书试点：允许「卡片点击回调」还是只允许「只读通知」？** 见 §7.4 |

## 1. 三层拆解

**1.0 三层与既有契约的对应（先看边界，再看项目）**

| 层 | 我们已有的对应能力 | 该层**不负责**的事 | 越界后果 |
|---|---|---|---|
| ① 协议与通信 | §11 身份/寻址、§12 网关、§14 频道、§26 信封 | 信任档判定、收费 | 通道层各自判定 → 口径分裂 |
| ② 编排框架 | §18 讨论、§4 审批、§3 门控、§30 委托 | 关系链数据、账本 | 编排层接管权限 → 越权面扩大 |
| ③ 平台边界 | 生产 Go 网关 Channel 适配（本机不实现） | 熟人关系、付费、审计 | 平台身份直通内部 → 铁律失守 |

### 1.1 第①层：Agent 原生的 IM 协议与通信层

> 该层解决：Agent 之间「怎么找到对方、怎么说话、怎么观察、怎么不丢」。**它不解决信任档位与收费**——这两件事开源项目里没有。

| 候选项目（⚠ 只引机制） | 借鉴机制 | 我们取哪一条 / 落点 | 复用策略 | 明确避坑 |
|---|---|---|---|---|
| **Sigil** | Agent Registry：Agent 可被寻址、可被发现 | 只取「可寻址的 Agent 注册表」语义 → 契约 §11 `agent_cards` + `agent_identities`（v2 已实现） | **只借范式** | 完全 P2P/去中心化不采纳（见 §5）：信任档与付费账本需要中心化强一致 |
| **Agent-IM / LinklyAI** | Thread + MCP 原生、人类在环 | 取「Thread 作为人类在环的会话容器 + 工具在环」→ 契约 §14 `TASK/GROUP` 频道 + §12 `PROTOCOL.MCP_TOOLS` | **只借范式** | 不引入其独立消息协议（见 §5）：复用 MCP + 轻量 HTTP，避免第二套线格式 |
| **im-for-agents** | Subagent Mode 的**上下文隔离** + **SSE 观察窗** | 隔离 → §6/§17 的 `MEMORY_ISOLATED` 与摘要投影；观察窗 → §13 可见域 `project()` + §15 SSE 传输 | **只借范式** | 不借其 Subagent 调度实现（与我们既有编排重复） |
| **WKongAI** | 二进制帧 + `ag-ui` 类流式事件 | 取「流式 UI/增量事件」语义 → §25 `TurnInbox` 的 `MID_TURN` 注入 + §15 `transport.send` | **只借范式** | 现在不用它替换 PaaS/消息内核（见 §5）：Phase0–1 先验证审批态频次 |
| **Greft** | **持久邮箱**：会话历史归属 Agent 身份，离线暂存、重启可恢复 | 取「按 Agent 落盘的 append-only 邮箱」→ 契约 **§29** `services/messaging/src/agent-mailbox.mjs` | **改造复用**（借语义重写，零依赖落盘） | 不接其服务端实现；我们只要 jsonl/游标/去重三件事 |

### 1.2 第②层：IM-native 的 Agent 编排框架

> 该层解决：多个 Agent 怎么分工、怎么开会、怎么把权限传下去。**它不解决「人是否信任这些 Agent」**——那是 §1 信任矩阵与 §4 审批的事。

| 候选项目（⚠ 只引机制） | 借鉴机制 | 我们取哪一条 / 落点 | 复用策略 | 明确避坑 |
|---|---|---|---|---|
| **AgentHub** | 协调器拆解任务 + 多 Agent 群聊 | 只取「群聊作为协作面」→ §14 `GROUP/TASK` 频道 + §18 `DiscussionEngine`（v3 已实现） | **只借范式** | 协调器**不作为核心**（见 §5）：与我们既有 orchestrator/讨论引擎重复，且会引入第二套调度事实源 |
| **AGORA** | 策略链 + `delegate`/`expose` 原语 | 取「委托必须收窄」→ 契约 **§30** `services/gateway/src/delegation.mjs` | **改造复用**（借治理原语，重写实现） | 不接其完整框架；委托只做「token 链 + 衰减 + 级联撤销」 |
| **我方既有** `DiscussionEngine` + `ApprovalEngine` + `CapabilityGate` | 三模式讨论 / 九态审批 / 七步门控 | 契约 §18 / §4 / §3（v1–v3 已实现） | **自研（已有）** | 不再引入第二套编排/审批状态机 |

### 1.3 第③层：主流平台的可接入边界

> 该层解决：用户已经在微信/飞书/钉钉里，我们怎么「够得着」。**它不解决个人信任档位与付费**——平台身份是组织/账号身份，不是社会关系信任（详见 §2）。

| 平台 | 可接入能力（⚠ 需复核，政策时效性强） | 不能承载的产品语义 | 我们的策略 |
|---|---|---|---|
| **微信** | 个人号无官方 Bot API（用户输入：2026-06 微信 AI 生态指引 ⚠ 待复核）；小程序分享/落地页可作为入口 | 熟人五档、Agent 独立身份、付费账本、签名审计的可自证链路 | 只做**入口/分享/落地页**；不做消息通道；公域获客与私域承接分离（Phase3） |
| **飞书** | Channel SDK / CLI / MCP 可接入（⚠ 需复核）；适合 Phase1 内部/种子客户快速验证 | 个人熟人关系链（组织身份 ≠ 个人信任档）、C 端付费账本 | **Phase1 可选试点**：只验证「审批态使用频次」；卡片点击回调只能作为**输入源**，决策仍在自有审批引擎 |
| **钉钉** | 机器人能力标准化（⚠ 需复核） | 个人信任档位、陌生人付费、跨组织个人关系 | 企业版/组织场景的**通知通道**（Phase3）；不做关系链 |
| **企业微信** | 客户联系/机器人能力存在但限制多（⚠ 需复核） | C 端陌生人付费、个人 Agent 身份 | 企业客服/通知备选（Phase3）；不承载账本 |
| **WhatsApp** | Business Tools / MCP 类能力以通知为主（⚠ 需复核，海外政策） | 信任档位、付费消息、审计取证 | 海外**通知通道**备选；不碰关系链与账本 |
| **X** | 2026-02 起自动化限制（用户输入 ⚠ 待复核） | 任何 B 端/C 端消息与信任语义 | 仅**公域内容获客/品牌**；不做接入 |

> 平台层的共同结论：**平台能给你「触达」，给不了「信任」与「账本」**。所有平台的适配都放在生产 Go 网关的 Channel 适配器里（[02 §15](./02-技术选型与框架.md) 映射），**本机不实现任何渠道适配器**（无网络、零依赖）。

### 1.4 三层之间的边界规则（一句话版）

| 规则 | 内容 | 违反的典型信号 |
|---|---|---|
| 协议层不判权 | 消息到没到 ≠ 能不能发；判定在 §12/§3 | 通道适配器里出现 `trustLevel` 判断 |
| 编排层不持关系 | 编排只能消费 §1 的信任档，不能自己存一份 | 出现第二份「好友/成员」关系表 |
| 平台层不碰账 | 平台只做展示/回调输入，扣费在 §8/§9 | 平台侧出现「已支付」状态 |
| 委托必须收窄 | 任何「代持权限」都要过 §30 衰减规则 | 子 token 的 scope 大于父 |

### 1.5 照抄开源的三种翻车方式（评审反例）

| 翻车方式 | 具体表现 | 根因 | 我们的替代 |
|---|---|---|---|
| 把「寻址」当「身份」 | 有 Agent 注册表，就以为对方是可信 Agent | 注册表只证明「存在」，不证明「是谁、有何权限」 | §11 身份 + §12 网关 token |
| 把「群聊」当「协作」 | 多 Agent 拉一个群，谁都能说话 | 群聊没有角色/轮次/异议约束 | §18 讨论引擎（模式/轮次/异议保留） |
| 把「回调」当「审批」 | 平台点一下就扣费 | 平台回调只是输入，不是状态机决策 | §4 审批引擎 + §28 确认层 |

## 2. 「平台能给你什么、不能给你什么」矩阵

### 2.1 六平台矩阵

| 平台 | 能给你（⚠ 需复核） | 不能给你（产品语义） | 风险点 | 我们的用法 |
|---|---|---|---|---|
| 微信 | 用户触达、分享/落地页、小程序承载 | `TRUST_LEVELS` 五档、Agent 独立身份、付费消息状态机、签名审计自证 | 个人号无稳定官方通道，灰产/封号风险；政策变动 | **只做入口**；治理数据留自有平台 |
| 飞书 | 团队消息、卡片、MCP/CLI、审批流挂载 | 个人熟人档位、C 端付费、跨组织 Agent 身份 | 组织身份与我们五档不对齐；管理员可读 | **Phase1 验证通道**（可选）；回调只作输入 |
| 钉钉 | 企业机器人、组织内通知 | 个人信任、陌生人付费、跨组织个人关系 | 组织权限模型强绑定；数据驻留 | 企业版通知（Phase3） |
| 企业微信 | 外部联系人/客服能力（受限） | C 端陌生人付费、个人 Agent 身份 | 客户联系能力边界与合规审核 | 客服/通知备选（Phase3） |
| WhatsApp | 海外通知/模板消息 | 信任档位、付费消息、审计取证 | 海外政策与模板审核；内容不可自证 | 通知备选；不碰账本 |
| X | 公域曝光与获客 | 任何私域消息/信任/付费 | 自动化限制与账号风险 | 仅内容获客（Phase3） |

### 2.2 铁律与原因

> **铁律：熟人关系链与付费账本永不放第三方平台。**
>
> 三条原因（不是偏好）：
> 1. **身份不对齐**：平台身份是「账号/组织成员」，我们的五档是「社会关系信任」。把 `TRUST_LEVELS` 映射成平台角色，`STRANGER(4)` 默认值、过期即撤销、逐目标不同档全部丢失——这正是 [15 §2.1](./15-四层技术栈映射与自研边界.md) 的结论。
> 2. **账本不可托管**：付费消息要求「先预审、后付费、恰好一次、可退款、可对账」。平台计费是通道计量，不是业务账本；托管后 `idempotencyKey`、退款、渠道对账、合规自证都不在自己手里。
> 3. **审计不可外证**：平台后台的日志/截图不是可验证签名链；监管与争议解决要的是**我们能自证的证据链**（§16），不是第三方后台。

**三条具体翻车故事（评审用）**：

- **故事 1（信任档被平台角色顶替）**：把飞书「部门管理员」映射成 `TRUSTED(2)`，部门调整后一个陌生人拿到 `TRUSTED` 档，Agent 直接代用户读日程。根因：组织角色 ≠ 社会关系信任。
- **故事 2（账本被平台计费口径绑架）**：用平台支付做付费消息，平台按「消息发送」计费，而产品语义是「看到且回复才结算」；对账差异无法解释，退款只能走平台工单。根因：平台计费是通道计量，不是业务账本。
- **故事 3（审计只剩截图）**：争议时只能导出平台后台截图，无法证明「这条消息确由该 Agent 发出、未被篡改」。根因：平台日志不是签名链（§16）。

### 2.3 平台接入决策树（先问四问，再谈接入）

1. 这一步是否触碰**关系链/信任档**？是 → 不接，回自有客户端。
2. 是否触碰**钱**（定价/扣费/退款/对账）？是 → 不接，回 §8/§9 账本。
3. 是否需要**签名审计可自证**？是 → 平台只做展示，证据写自有链条（§16）。
4. 以上皆否，且只是「触达/通知/卡片展示」→ 可以做**只读通道或输入源**；任何回调必须换回自有 `ticketId`+`principalUserId`，不得让平台身份直通内部身份。

### 2.4 平台接入的深度分级（决定「接多深」）

| 级别 | 形态 | 能承载 | 不能承载 | 我们的结论 |
|---|---|---|---|---|
| **L0 无接入** | 只在自有客户端 | 全部治理 | — | 默认 |
| **L1 只读通知** | 平台推送状态/摘要 | 触达 | 决策/身份/账本 | 微信/WhatsApp/X 可用 |
| **L2 卡片 + 回调输入** | 平台展示审批卡，点击回调回自有引擎 | 交互入口 | 身份/账本/状态机 | **飞书 Phase1 试点上限** |
| **L3 完整闭环** | 平台内完成审批/扣费/审计 | 平台生态内闭环 | 我方信任档/账本/自证 | **不采纳**（违反铁律） |

### 2.5 平台接入的验收口径

| 指标 | 阈值（试点期） | 测量 |
|---|---|---|
| 回调身份映射覆盖率 | 100%（每个回调都能落到 `principalUserId`） | 回调日志抽查 |
| 平台身份 → 信任档映射 | **0 处**（禁止） | 代码评审 + 配置扫描 |
| 平台侧扣费/账本 | **0 处**（禁止） | 架构评审 |
| 审批态频次对比（飞书 vs 自有客户端） | 不低于自有基线（否则试点无价值） | 埋点 |

## 3. 本轮两机制「没有它会怎样」

### 3.1 持久邮箱（§29）—— 没有它，离线/重启丢消息，陌生人来意石沉大海

**失败场景**：A 的 Agent 向 B 的 Agent 发来意信封时，B 的进程刚好重启（或 B 离线）。v4 的 `TurnInbox` 是单进程内存态，pending 随进程消失；A 侧以为「已投递」，B 侧永远收不到。陌生人经济里，这条来意既没有到达、也没有拒绝、也没有超时上抛——用户的体感是「发了没人理」，而 A 的付费/预审计数已经发生。

**失败链**：内存态丢消息 → 来意丢失 → 协商无法开始（或重复发送造成重复计费风险）→ 陌生人对平台的信任下降；运维侧也无法解释「为什么这条没到」。

**可观测信号**：重启后 `status.pending` 归零而审计里存在投递记录；同一 `message.id` 被重复发送（应为 `duplicate:true`）；`CURSOR_INVALID` 出现在消费者重启后。

**落点**：§29。每个 Agent 一个 append-only 文件（`<dir>/<agentId>.jsonl`）；同 `id` 重复投递返回 `duplicate:true` 不重复入队；`cursor` 单调（乱序/回退 `CURSOR_INVALID`）；容量超限 `CAPACITY_EXCEEDED`（不静默丢）；新实例读同一目录必须恢复同样 pending。**这修补的正是 v4 自己登记过的缺陷**（内存 `TurnInbox` 重启丢 pending）。

### 3.2 带衰减的委托（§30）—— 没有它，总 Agent 一授权就等于把全部权限复制给子 Agent

**失败场景**：总 Agent（butler）为了省事，把自己的 token 整个传给子 Agent（或让子 Agent 复用同一 token）。子 Agent 因此获得了 butler 的全部 `domains + trustCeiling + 有效期`；它原本只该「读日程」，现在能「读记忆/发消息/调付费」。一旦子 Agent 被注入或跑偏，权限扩散不可回收——父级撤销时子级还在用旧 token。

**失败链**：委托=复制 → 权限扩散 → 越权面随子 Agent 数量指数增长 → 审计无法回答「这次调用是哪个层级的授权」→ 一次 prompt injection 就能借子 Agent 拿到父级全部能力。

**可观测信号**：子 token 的 `domains` 不是父集子集（`SCOPE_ESCALATION`）；`expiresAt` 晚于父（`EXPIRY_EXCEEDED`）；`hopLimit` 不减（`HOP_LIMIT`）；父撤销后子仍可用（应为 `PARENT_REVOKED`）；`TOKEN_INVALID` 出现在跨 principal 复用。

**落点**：§30。`delegate` 产出冻结 token（含 `parentId`、`hopLimit`）；`verify` 返回 `effectiveScope` 与 `chain`；四条衰减规则冻结：`domains ⊆` 父、`trustCeiling <=` 父、`expiresAt <=` 父、`hopLimit` 每层 -1（0 → `HOP_LIMIT`）；`revoke({cascade:true})` 级联，子级验签即 `PARENT_REVOKED`。

### 3.3 两机制与既有模块的边界（防重复）

| 新机制 | 容易和谁混 | 边界一句话 | 错误码 |
|---|---|---|---|
| §29 持久邮箱 | §25 `TurnInbox` | `TurnInbox` 管「当前轮次内注入」，邮箱管「离线/重启后的持久暂存」；邮箱是慢路径，不替代轮次内 | 独立 `MAILBOX_CODE` |
| §30 带衰减委托 | §12 `issueToken` | `issueToken` 是平台给 Agent 签 token；委托是 Agent 之间**再授权**，只能在父 token 内收窄 | 独立 `DELEGATION_CODE` |
| §30 带衰减委托 | §19 `ToolPolicy` | 工具策略判「审批形态」，委托判「这层 Agent 有没有资格持有这个 scope」 | 先委托验签，再工具策略 |

## 5. 明确不采纳清单

| 不采纳项 | 为什么 | 我们做什么 | 何时重评 |
|---|---|---|---|
| **Sigil 完全 P2P / 去中心化** | 信任档位需要**中心化强一致**的判定源（默认 `STRANGER(4)`、过期即撤销、逐目标不同档）；P2P 下每个节点各自判定，无法给出唯一结论。付费账本需要 exactly-once 与对账，链上/去中心化支付不可退款、不可冻结、不可自证 | 只借「可寻址注册表」语义（§11）；身份自持但**判定与账本中心化** | 不重评（治理事实源不分散） |
| **Agent-IM 的独立消息协议** | 第二套线格式 = 第二套鉴权/审计/限流；我们已有 §12 归一化 + §26 信封，MCP + 轻量 HTTP 足够 | 复用 MCP（§12 `MCP_TOOLS`）+ 轻量 HTTP；不引入其协议栈 | 出现必须跨生态互操作的硬需求 → 只做边界适配（同 A2A 模式） |
| **AgentHub 协调器作为核心** | 与我们既有 orchestrator/`DiscussionEngine` 重复，会形成第二套调度事实源；其多 Agent 群聊机制我们已用 §14+§18 覆盖 | 只借「群聊即协作面」范式；调度仍在自有编排层 | 不重评（调度权自持） |
| **WKongAI 现在替换 PaaS/消息内核** | Phase0–1 的首要任务是验证「审批态使用频次」与治理闭环，不是换通道；换内核的窗口在 Phase1 灰度前（v2 已给迁移步骤），现在换属于提前优化 | 先跑通审批态与付费闭环；内核替换按 [11 §6.3](./11-AI原生IM架构-v2.md) 的 M0–M4 排期 | Phase1 灰度前按 [02 §18](./02-技术选型与框架.md) 的迁移步骤重评 |
| **openvela 端侧跑完整 Agent Loop** | 端侧只承担唤醒/VAD/粗分类/敏感过滤/审批缓存；完整 Loop 在云端的治理下才能保证门控与审计；端侧跑全 Loop 会绕开门控且功耗/内存不可控 | 端侧守门（[04](./04-SDK与端侧设计.md)/[06](./06-产品形态与硬件.md)）；原始音频不出端侧、物理灯/静音不变 | 硬件立项后，仅评估「端侧受限子集」而非完整 Loop |
| **平台 L3 完整闭环（平台内审批/扣费/审计）** | 平台内闭环意味着身份、账本、审计三件事都在外部；用户点一下平台按钮就能完成扣费，无法区分「平台回调」与「用户真实决策」，也无法自证 | 所有平台最多到 L2（卡片+回调输入）；决策回 §4、扣费回 §8/§9、证据回 §16 | 不重评（铁律） |

**不采纳的统一判据**：① 它是否持有事实源（关系/身份/消息/账本/审计）？是 → 不采纳；② 它是否要求「网络位置/平台角色 = 信任」？是 → 不采纳；③ 它的实现是否绑定其运行时/协议/OS？是 → 只借范式；④ 以上皆否且语义可映射 → 才进入「改造复用」候选。

### 7.4 最需评审会拍板的 1 个平台接入取舍

**Phase1 飞书试点：允许「卡片点击回调」进入审批，还是只允许「只读通知」？**

- **选项 A（建议）**：允许卡片展示 + 点击回调，但回调**只作为输入源**：飞书 `open_id` 必须映射到自有 `principalUserId`，点击只生成/推进自有 `ticketId` 的动作请求，**决策与状态机仍在 §4 审批引擎**；飞书组织角色不得映射为 `TRUST_LEVELS`。
- **选项 B（保守）**：只读通知，用户必须回自有客户端操作——最安全，但 Phase1 的「审批态频次」验证会被入口摩擦污染（测到的是跳转成本，不是审批意愿）。
- **选项 C（危险，不建议）**：把飞书审批流当作审批引擎，组织角色直接当信任档——会丢失五档、过期撤销、签名审计与账本归属，直接违反 §2.2 铁律。
- **建议**：选 A，并在试点报告中明确「飞书只贡献入口与回调，不贡献身份与账本」；若 A 的映射实现超过 2 人周，退回 B。
- **为什么必须现在拍板**：A 与 B 的选择决定试点要写多少身份映射代码、以及 Phase1 的验收指标怎么设计；拖到试点中途再改，会把「审批态频次」测成「跳转成本」。C 永远不选（违反铁律）。
